# 함수 호출과 도구 사용의 모델-실행 경계

> [!note] 학습 안내
> **난이도:** 중급<br>
> **선수 지식:** [[concept.대규모-언어-모델|대규모 언어 모델]], [[concept.사고-연쇄-프롬프팅|사고 연쇄 프롬프팅]]<br>
> **읽고 나면:** 2023년 6월 함수 호출, 같은 해 11월 병렬 호출·JSON mode, 2024년 엄격한 구조화 출력을 구분하고, 모델의 호출 제안과 애플리케이션의 검증·권한 부여·실행이 왜 별도 단계인지 설명할 수 있다.

## 1단계 — 먼저 잡을 핵심

### 핵심 문장

**함수 호출(function calling)**은 언어 모델이 외부 함수를 직접 실행하는 능력이 아니라, 개발자가 제시한 함수 설명을 보고 **호출할 함수와 인수를 구조화된 데이터로 제안하는 인터페이스**다. 실제 API·database·code·device에 접근하는 주체는 모델 밖의 애플리케이션이다.

2023년 6월 OpenAI가 공개한 `gpt-4-0613`·`gpt-4-32k-0613`과 `gpt-3.5-turbo-0613`의 핵심 흐름은 다음과 같다.

1. 개발자가 `functions`에 함수 이름·설명·JSON Schema parameter를 넣는다.
2. 모델이 일반 text 또는 한 함수의 이름과 JSON argument를 출력한다.
3. 애플리케이션이 argument를 parse·validate하고 사용자·service의 권한을 확인한다.
4. 애플리케이션이 함수를 실행하고 결과를 대화에 돌려준다.
5. 모델이 결과를 읽어 최종 답을 생성하거나 다음 호출을 제안한다.

따라서 **호출 객체는 행동이 아니라 행동 후보를 담은 데이터**다. Schema는 입력 모양을 설명하지만 권한, 업무 규칙, 부작용 허용, tool 결과의 신뢰성과 최종 답의 사실성을 보장하지 않는다.

### 세 시점을 한 기능으로 합치지 않는다

| 시점 | 확인되는 기능 | 아직 함께 있었다고 말할 수 없는 것 |
| --- | --- | --- |
| 2023-06-13 | `functions`·`function_call`, 함수 선택과 JSON argument 제안 | 한 message의 parallel calls, exact schema guarantee |
| 2023-11-06 | 한 message의 복수 함수 호출, 별도 JSON mode, `-1106` model | JSON mode의 exact schema guarantee |
| 2024-08-06 | `strict: true` Structured Outputs와 constrained decoding | 올바른 value·올바른 tool 선택·실행 성공·안전한 권한의 보장 |

원 웹글은 이 세 층을 모두 2023년 최초 기능의 속성처럼 서술한다. 역사적 API snapshot과 후대 확장을 분리해야 무엇이 실제 혁신이었고 어디에 검증 코드가 여전히 필요한지 보인다.

## 2단계 — 작동 원리

### 함수 목록은 capability catalog다

함수 설명은 보통 이름, 자연어 설명, parameter type·required field·enum 같은 schema로 구성된다. 이 catalog는 모델에 가능한 행동의 **어휘와 인수 형식**을 알려 준다. 함수가 server에 실제로 존재하는지, 현재 사용자가 호출할 권한이 있는지, 호출이 결제를 일으키는지는 schema만으로 알 수 없다.

설명 품질은 선택 성능에 영향을 준다. 이름이 겹치거나 경계가 모호한 도구가 많으면 잘못된 선택이 늘 수 있다. 그러나 좋은 설명은 보안 경계의 대체물이 아니다. 애플리케이션은 모델이 고른 이름을 allowlist와 대조하고, 모든 인수를 신뢰하지 않은 입력으로 다뤄야 한다.

### 모델은 실행 요청을 생성한다

2023년 6월 인터페이스에서 모델은 상황에 따라 일반 assistant text를 내거나 함수 이름과 argument 문자열을 출력했다. 개발자는 `function_call`로 선택을 모델에 맡기거나 특정 함수를 요구할 수 있었다. 여기서 모델이 수행하는 계산은 다음 token 또는 구조화된 field의 생성이다.

이를 개념적으로 쓰면 다음과 같다.

$$
(f, a) \sim p_\theta(f,a \mid x,\mathcal{F}),
$$

여기서 $x$는 대화, $\mathcal{F}$는 함수 catalog, $f$는 선택한 함수, $a$는 생성한 argument다. 이 식에는 외부 함수 $f(a)$의 실제 실행이 들어 있지 않다. 실행은 별도의 runtime이 담당한다.

### 애플리케이션이 신뢰 경계를 만든다

호출을 받은 orchestrator는 최소한 다음 검사를 분리해야 한다.

| 검사 | 묻는 질문 |
| --- | --- |
| 구문 | JSON으로 parse되는가? |
| Schema | field·type·enum·required 조건을 만족하는가? |
| 의미 | 존재하는 account·날짜·단위이며 업무 규칙에 맞는가? |
| 인증 | 요청을 보낸 주체는 누구인가? |
| 권한 | 그 주체가 이 resource와 action을 사용할 수 있는가? |
| 부작용 승인 | 결제·발송·삭제처럼 되돌리기 어려운 행동을 사용자가 확인했는가? |
| 실행 | timeout·중복 호출·부분 실패를 어떻게 처리하는가? |

Schema validation을 통과한 `{"amount": 1000000}`도 허가된 송금이라는 뜻은 아니다. 반대로 권한이 있어도 존재하지 않는 주문 ID나 잘못된 시간대가 들어갈 수 있다. 형식과 의미, 권한은 각각 다른 실패 표면이다.

### 결과는 다시 모델 입력이 된다

도구 결과는 관찰(observation)로 대화에 들어간다. 모델은 이 결과를 요약하거나 다음 도구를 제안한다. 최신 날씨·계정 상태가 답에 들어갈 수 있는 이유는 모델의 학습 cutoff가 사라져서가 아니라 **외부 system의 현재 값이 새 context로 제공됐기 때문**이다.

이 경로는 prompt injection의 새 입구이기도 하다. 2023년 OpenAI 발표도 신뢰하지 않은 tool output이 모델에 의도하지 않은 행동을 지시하는 proof-of-concept를 언급했다. Tool 결과를 높은 권한의 instruction으로 취급하지 않고, data와 instruction의 출처를 구분하며 실제 영향이 있는 행동에는 사용자 확인을 두어야 한다.

## 3단계 — 기술과 근거

### 2023년 6월: 표준화된 호출 제안

OpenAI의 2023년 6월 13일 발표는 Chat Completions API의 `functions`와 `function_call`을 소개했다. 함수는 JSON Schema로 설명하고 모델은 `gpt-4-0613` 또는 `gpt-3.5-turbo-0613`에서 호출할 argument가 든 JSON 객체를 출력했다. `gpt-4-32k-0613`도 같은 function-calling 개선과 긴 context를 포함했다. 발표의 예시는 외부 도구 연결, 자연어를 API·database query로 변환, text에서 구조화된 data 추출이었다.

이 기능은 자유 형식 text를 정규식으로 해석하는 것보다 함수 선택과 argument를 별도 channel로 분리했다는 점에서 중요한 interface 개선이었다. 하지만 최초 발표도 “개선할 사례를 eval로 보내 달라”고 했고, 실제 실행은 개발자 code의 몫이었다. `model output = executable action`으로 붙이는 것은 발표 내용보다 강한 해석이다.

### 2023년 11월: 병렬 호출과 JSON mode

OpenAI의 2023년 11월 6일 DevDay 발표는 `gpt-4-1106-preview`에서 한 message에서 여러 함수를 호출하는 기능을 별도 개선으로 소개했다. `gpt-3.5-turbo-1106`에도 parallel function calling이 포함됐다. 따라서 원 웹글의 “2023년 6월 구현이 여러 함수를 동시에 처리했다”는 설명은 최초 release와 후대 release를 섞는다.

같은 발표의 JSON mode는 출력이 **문법적으로 유효한 JSON object**가 되도록 하는 기능이었다. 어떤 JSON Schema와 정확히 일치하는지는 별도 문제다. 병렬 호출, JSON validity와 schema conformity는 이름이 비슷해도 같은 보장이 아니다.

### 2024년 8월: 엄격한 schema 일치

2024년 8월 Structured Outputs 발표에서 OpenAI는 이전 JSON mode가 특정 schema 준수를 보장하지 않았다고 명시했다. `strict: true`는 function definition과 함께 constrained decoding을 사용해 지원되는 JSON Schema에 출력을 맞추는 후대 기능이다. OpenAI 자체의 복잡한 schema eval에서 `gpt-4-0613`은 40% 미만, `gpt-4o-2024-08-06`의 strict 조건은 100%로 보고됐다.

이 100%는 그 회사의 schema-following eval 결과다. 발표의 제한 절도 model이 JSON 안의 value를 잘못 만들 수 있고, refusal·token 중단이 별도 처리 경로이며, parallel function call과 strict schema를 함께 쓰면 schema를 벗어날 수 있다고 적었다. **정확한 모양은 정확한 내용이 아니다.**

같은 발표는 function definition의 `strict: true`뿐 아니라 일반 응답의 `response_format`에 `json_schema`를 지정하는 경로도 제공했다. [[099_구조화 출력의 스키마 준수와 의미 정확성 경계|구조화 출력]]은 외부 action 없이 추출·분류·변환 결과를 schema object로 돌려주는 더 넓은 interface다. Function calling은 그 object가 실행 후보가 된다는 점에서 권한·부작용·tool result 관문을 추가한다.

### 도구 사용은 2023년 6월에 처음 생기지 않았다

ReAct는 2022년 공개되고 ICLR 2023에 실린 연구로, reasoning trace와 task-specific action, environment observation을 교대로 생성했다. Wikipedia API를 쓰는 질의응답과 interactive task를 통해 model–environment loop를 실험했다. Toolformer도 2023년 2월 공개된 연구에서 GPT-J 6.7B가 calculator·QA·search·translation·calendar API를 언제 어떤 argument로 호출하고 결과를 다음 token prediction에 어떻게 넣을지 self-supervised하게 학습했다.

두 연구는 OpenAI Chat Completions의 함수 schema API와 같은 제품 interface가 아니다. 하지만 “도구를 고르고 결과를 다시 문맥에 넣는 언어 모델”이라는 연구 문제와 구현은 6월 release보다 앞선다. 확인되는 변화는 도구 사용의 발명보다 **상용 API에서 호출 제안을 표준 field로 제공한 것**이다.

## 검증과 한계

### 원 웹글의 검증 정정

- **함수 호출이 모델을 세계와 직접 상호작용하는 능동 agent로 바꿨다:** 모델은 호출 데이터를 출력한다. Network·database·filesystem 접근과 부작용은 애플리케이션 runtime이 수행한다.
- **2023년 이전 model은 database·code·API를 사용할 수 없었다:** ReAct·Toolformer 등 prompt·학습 기반 tool-use 연구와 custom orchestration이 선행했다. 2023년 OpenAI API는 중요한 표준 interface이지 최초의 tool use 전체가 아니다.
- **최초 format은 deterministic·schema-validated여서 description과 정확히 일치했다:** 2024년 공식 발표는 `gpt-4-0613`의 복잡한 schema 일치가 40% 미만이었다고 보고하고 `strict: true`를 새 기능으로 소개했다.
- **여러 함수를 동시에 호출했다:** 한 message의 복수·parallel function calling은 2023년 11월 `-1106` 발표에서 별도 개선으로 확인된다.
- **함수 호출이 실시간 정보 한계를 해결했다:** 최신 data는 tool이 제공한다. 모델의 pretrained knowledge cutoff와 올바른 tool·query를 고르는 문제는 남는다.
- **호출 request는 실행 가능하고 신뢰할 수 있다:** JSON·schema·의미·권한·실행 성공·최종 답 grounding은 별도 검사다.
- **고객 서비스·개발·분석·전자상거래를 혁신했다:** 원 웹글은 각 분야의 adoption 규모, 통제 비교, 실패율이나 경제 효과를 제시하지 않는다. 가능한 use case와 실증된 산업 효과를 구분한다.
- **함수 호출이 현대 agent framework의 단일 토대다:** ReAct·Toolformer와 더 오래된 planning·API integration·workflow engine도 서로 다른 계보를 이룬다. LangChain 등 특정 framework의 확산은 별도 version·usage evidence가 필요하다.

### 형식 신뢰성과 행동 신뢰성

함수 호출 system의 성공률은 한 숫자가 아니다. 적어도 tool-selection accuracy, argument schema validity, semantic argument accuracy, authorization decision, execution success, tool-result grounding과 final-task success를 따로 측정해야 한다. Retry가 schema 오류를 줄여도 잘못된 주문을 여러 번 실행하면 더 위험해질 수 있으므로 side-effecting operation에는 idempotency key와 confirmation state가 필요하다.

도구를 많이 등록할수록 능력의 범위는 넓어지지만 선택 혼동, context 비용과 attack surface도 커질 수 있다. 최소 권한, task별 allowlist, 입력·출력 크기 제한, timeout, audit log, sandbox, 사람 승인과 compensating action을 model prompt 밖의 control로 둔다.

### Agent와 function call은 동의어가 아니다

함수 호출 한 번은 action proposal interface다. 장기 목표를 유지하고 여러 단계를 계획하며 실패에서 복구하는 agent system에는 state management, loop termination, scheduling, memory, evaluation과 권한 policy가 더 필요하다. 반대로 text에서 구조화된 field 하나를 추출하는 function call은 agent loop가 아닐 수 있다.

따라서 function calling이 agent를 가능하게 하는 중요한 구성 요소라는 설명은 타당하지만, 그것만으로 자율성·안전성·production readiness가 완성됐다고 결론 내리지 않는다.
