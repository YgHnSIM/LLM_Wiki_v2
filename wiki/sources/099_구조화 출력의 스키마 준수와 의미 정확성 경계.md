# 구조화 출력의 스키마 준수와 의미 정확성 경계

> [!note] 학습 안내
> **난이도:** 중급<br>
> **선수 지식:** [[concept.자기회귀-생성|자기회귀 생성]], [[concept.파싱|파싱]]<br>
> **읽고 나면:** 2023년 함수 호출·JSON mode와 2024년 엄격한 Structured Outputs를 구분하고, JSON 구문·schema·의미·권한의 보장 범위를 설명하며, 생성 제약과 사후 검증을 나눌 수 있다.

## 1단계 — 먼저 잡을 핵심

### 핵심 문장

**구조화 출력**(structured output)은 언어 모델 응답이 기계 판독 가능한 형식이나 선언된 schema를 따르도록 만드는 interface다. 2024년 OpenAI의 `strict: true` Structured Outputs는 지원되는 JSON Schema와 정상 완료 경로에서 **출력 구조**를 강하게 보장했다. 그러나 schema에 맞는 문자열·숫자가 입력과 현실에 맞는지는 별도 문제다.

다음 네 질문을 한 단어 ‘검증’으로 합치지 않는다.

| 관문 | 묻는 질문 | 통과해도 남는 문제 |
| --- | --- | --- |
| JSON 구문 | 표준 parser가 읽을 수 있는가? | 원하는 field·type과 다를 수 있다. |
| Schema | `required`·`type`·`enum`·중첩 구조가 맞는가? | 값이 사실과 다를 수 있다. |
| 의미 | 입력·database·업무 규칙에 맞는 값인가? | 요청 주체의 권한은 별도다. |
| 시스템 | 인증·인가·승인·실행 조건을 만족하는가? | 외부 service와 후속 설명도 실패할 수 있다. |

원 웹글은 구조화 출력이 취약한 자연어 parsing을 줄이고 추출·분류·workflow 연결을 쉽게 했다는 큰 흐름을 설명한다. 이 방향은 유용하지만 JSON mode, 엄격한 schema, Pydantic, XML DTD와 여러 provider를 같은 보장으로 묶는 대목은 공식 자료의 범위보다 넓다.

### 2025년에 쓴 2024년 회고

원 웹글은 2025년 9월 17일 공개됐지만 장의 중심 사건을 2024년으로 배치한다. 따라서 2024년에 쓰인 동시대 1차 기록이 아니라, 2023–2024년 API 변화를 후대에 정리한 설명으로 읽는다. 기능의 날짜·보장·구현은 각 시점의 공식 발표로 다시 확인한다.

| 날짜 | 확인되는 기능 | 확인되지 않는 확대 |
| --- | --- | --- |
| 2023-06-13 | 함수 설명과 JSON Schema parameter, 모델의 함수 이름·JSON argument 제안 | 모델의 외부 함수 직접 실행, exact schema guarantee |
| 2023-11-06 | `response_format` 기반 JSON mode와 문법적으로 유효한 JSON object | 특정 schema 일치 |
| 2024-02-26 | LangChain의 beta `with_structured_output` RFC | Pydantic 자체의 보편적 token-level 제약 |
| 2024-08-06 | Function definition의 `strict: true`, response format의 `json_schema`, 지원 schema 제약 | 값의 사실성·완전성·업무 타당성 |

## 2단계 — 작동 원리

### 자유 형식 출력에서 생기는 실패

같은 email 주소도 모델은 문장, bullet, Markdown link, code fence나 설명을 섞어 표현할 수 있다. 사람이 읽기에는 모두 충분해도 고정 문자열이나 정규식에 의존하는 parser는 작은 표현 차이에서 깨진다. 프롬프트로 JSON을 요청하는 방식은 성공률을 높일 수 있지만 생성 가능한 token을 제한하지 않으므로 보장이 아니다.

JSON mode는 이 가운데 **구문 관문**을 강화했다. OpenAI의 2023년 11월 발표는 JSON mode가 valid JSON object를 보장한다고 설명했다. `{ "name": 7 }`은 유효한 JSON이어도 application이 `name`을 문자열로 요구한다면 schema에는 맞지 않는다.

### Schema를 생성 제약으로 바꾼다

OpenAI가 2024년에 공개한 구현은 JSON Schema를 문맥자유문법(CFG)으로 변환한다. 첫 요청에서 schema를 전처리해 artifact를 만들고 cache한 뒤, 생성한 접두사와 문법 상태에 따라 다음에 허용되는 token을 매 단계 계산한다.

자기회귀 확률을 개념적으로 쓰면 다음과 같다.

$$
p'(t_i \mid t_{<i},x)
\propto
p_\theta(t_i \mid t_{<i},x)\,\mathbf{1}[t_i \in A_G(t_{<i})]
$$

$A_G(t_{<i})$는 schema에서 얻은 문법 $G$가 현재 접두사 다음에 허용하는 token 집합이다. 허용되지 않는 token은 단순히 덜 선호되는 것이 아니라 확률이 0으로 masking된다. 닫히지 않은 중괄호나 허용되지 않은 key처럼 문법상 불가능한 경로는 막히지만, 허용된 문자열 자리에 틀린 이름을 쓰는 일은 막지 못한다.

### Provider와 SDK의 역할을 나눈다

2024년 OpenAI 발표는 두 interface를 제시했다.

1. Function definition에 `strict: true`를 지정해 tool argument를 schema에 맞춘다.
2. 일반 응답의 `response_format`에 `json_schema`를 지정해 외부 실행 없이 추출·분류 결과를 받는다.

Native SDK는 Pydantic·Zod object를 지원되는 JSON Schema로 바꾸고 응답을 typed object로 역직렬화할 수 있다. Pydantic은 schema 표현과 validation을 담당하는 library이지 그 자체가 언어 모델의 token 분포를 제한하는 decoding engine은 아니다. LangChain의 2024년 RFC도 `with_structured_output`을 function calling 또는 provider별 steering과 output parsing을 결합하는 beta interface로 설명했다. 실제 보장은 선택된 provider·model·strategy와 strict 설정을 확인해야 한다.

## 3단계 — 기술과 근거

### 내부 schema 평가가 측정한 것

OpenAI의 2024년 발표는 복잡한 JSON Schema 내부 평가에서 `gpt-4-0613`이 40% 미만, `gpt-4o-2024-08-06`의 Structured Outputs가 100%를 기록했다고 보고했다. Under the hood 절은 새 모델의 학습만으로는 93%였고 deterministic constrained decoding을 결합해 100%에 도달했다고 설명한다.

이 수치는 OpenAI가 구성한 **schema-following 평가**다. 추출 precision·recall, field value의 사실성, 함수 선택, 권한, 외부 실행 성공이나 최종 답의 정확도를 100%로 만들었다는 뜻이 아니다. Vendor 내부 평가와 task·schema 분포가 다른 application에 같은 수치를 그대로 대입하지 않는다.

### 정상 결과와 예외 경로

Schema 일치는 모든 응답에 무조건 적용되는 단일 반환 경로가 아니다.

- Safety policy 때문에 모델이 거부하면 schema object 대신 별도 `refusal` 문자열을 반환할 수 있다.
- 최대 token이나 다른 중단 조건으로 generation이 일찍 끝나면 완전한 schema 결과를 전제할 수 없다.
- 2024년 발표 당시 strict schema 준수가 필요하면 parallel function calls를 끄도록 안내했다.
- API는 JSON Schema 전체가 아니라 지원되는 부분집합을 처리했다.
- 새 schema의 첫 요청에는 문법 전처리·cache 때문에 추가 latency가 생길 수 있었다.

Application은 `refusal`, incomplete result, parse/schema success와 semantic failure를 다른 상태로 기록해야 한다. 자동 retry나 structured error response는 constrained decoding 자체의 보장이라기보다 application 또는 framework가 설계할 동작이다.

### Schema는 모호함을 없애지 않는다

입력에 해당 정보가 없는데 모든 field를 채우도록 요구하면 모델은 schema에 맞는 값을 추측할 수 있다. `unknown`, `null`, 빈 배열, 복수 후보와 근거 span처럼 불확실성을 표현할 경로를 schema에 넣어야 한다. 이 설계도 환각을 자동 제거하지 않지만, model이 모양을 맞추기 위해 임의의 하나를 고르도록 강제하는 일을 줄인다.

Extraction에서는 다음 지표를 분리한다.

- JSON parse 성공률
- Schema 통과율
- Field별 precision·recall·exact match
- 원문 근거 span과 값의 일치
- 누락·추가·잘못된 normalization 비율
- Refusal·incomplete·retry 비율과 latency·cost

### 적용 범위를 좁힌 응용

구조화 출력은 entity·relation 추출, closed-set classification, intent와 parameter 분리, document field 정규화, agent state 기록에 유용하다. 다만 전통 NER pipeline보다 항상 정확하거나 저렴하다는 비교 결과는 원 웹글에 없다. 한 schema와 한 provider의 format reliability를 task quality 전체로 확대하지 않는다.

## 검증과 한계

### 원문에서 바로잡을 주장

- **JSON mode가 schema를 보장했다:** JSON mode는 valid JSON을 보장하지만 exact schema는 보장하지 않는다.
- **JSON·XML·XML DTD가 같은 보장을 받았다:** 여기서 확인된 Structured Outputs의 직접 범위는 지원되는 JSON Schema다.
- **Pydantic이 token 수준 제약을 강제한다:** Pydantic은 schema·validation 계층이고 generation 제약은 provider strategy에 달려 있다.
- **유효 token을 선호한다:** OpenAI 구현 설명은 문법상 무효한 token의 확률을 0으로 masking한다.
- **형식에 맞지 않으면 모델이 일반적인 실패 신호를 낸다:** 명시된 별도 경로는 safety refusal이다. 부적합한 입력에서 schema를 억지로 채울 수 있다.
- **Conditional field를 자유롭게 쓸 수 있다:** 지원되는 JSON Schema는 부분집합이며 복잡한 조건 규칙에는 제약이 있다.
- **오류를 자동으로 retry한다:** Retry는 application·framework의 정책이지 strict decoding의 핵심 보장이 아니다.
- **항상 token과 API cost가 늘어난다:** 공식 발표가 직접 밝힌 overhead는 새 schema 전처리 latency다. Token·재시도 절감까지 포함한 비용은 과제별 측정이 필요하다.
- **Provider 전반의 표준 interface다:** Provider별 native 기능·schema subset과 exception path는 다르다. Framework의 공통 API가 같은 보장을 뜻하지 않는다.
- **프로덕션 준비를 완성했다:** Format failure를 줄인 중요한 interface 개선이지만 factuality·권한·실행·monitoring은 남는다.

### Raw artifact와 사실 근거

번역·해설 raw는 원 웹글의 전체 흐름과 이번 검토의 출발점을 보존한다. Raw에 번역된 “schema-validated”, “validated data”, “production-ready”는 원문의 표현 강도를 보여 주지만 사실에 관한 근거 자체는 아니다. 이 공개 문서는 공식 발표에서 확인되는 기능·날짜·제한과 편집적 평가를 분리한다.

### 확인된 한계

OpenAI의 공개 설명은 자사 API 구현과 내부 평가를 다룬다. 모든 provider, open-source decoder, grammar engine, schema language의 동등성을 입증하지 않는다. LangChain RFC는 framework interface의 의도를 보여 주지만 provider별 실제 보장을 대신하지 않는다. 또한 이 문서는 schema-conforming extraction의 형식 경계를 다루며, domain별 정확도·privacy·fairness와 인간 검수 비용에는 별도 자료가 필요하다.
