# LLM 에이전트의 추론-행동 루프와 자율성 경계

> [!note] 학습 안내
> **난이도:** 중급<br>
> **선수 지식:** [[대규모 언어 모델]], [[사고 연쇄 프롬프팅]], [[함수 호출과 도구 사용]]<br>
> **읽고 나면:** LLM 에이전트를 모델 하나가 아니라 model·orchestrator·tool·state·policy의 결합으로 설명하고, 2024년 기원설과 자율성·학습·안전·응용 성과에 관한 과장을 1차 연구의 범위로 교정할 수 있다.

## 1단계 — 먼저 잡을 핵심

### 2024년은 기원이 아니라 평가가 확장된 시점이다

원 웹글은 에이전트형 AI 시스템이 2024년에 등장해 수동적인 언어 모델을 자율적 행위자로 바꿨다고 서술한다. 그러나 reasoning trace와 environment action을 교대시킨 ReAct는 2022년에 공개돼 ICLR 2023에 실렸고, Toolformer·Reflexion·Generative Agents도 2023년에 발표됐다. 2024년에는 WebArena·SWE-bench·OSWorld처럼 장기·상호작용 과제를 실제 website·repository·computer 환경에서 측정하는 benchmark가 두드러졌다.

따라서 2024년을 단일한 발명 시점으로 쓰기보다, 앞선 tool-use·memory·reflection 연구가 더 복잡한 환경과 end-to-end 평가로 이동한 시점으로 보는 편이 정확하다. 원 웹글에서 재사용할 핵심은 **언어 모델의 출력이 외부 상태를 읽고 바꾸는 반복 loop 안에 놓일 때 어떤 구성 요소와 검증 관문이 필요한가**라는 질문이다.

### 핵심 문장

- **LLM 에이전트**는 목표와 현재 state를 바탕으로 다음 action을 제안하는 model을 orchestrator·tool·memory·policy·evaluator가 둘러싼 system이다.
- 사고 연쇄 text는 다음 행동을 유도할 수 있지만, 실행 가능한 plan·원인 설명·정답 보증과 같지 않다.
- 함수 호출 객체는 action proposal이다. Application이 인증·권한·semantic validity를 확인하고 실행하기 전에는 외부 행동이 아니다.
- 대화 기록·vector store·episodic memory·skill library는 외부 state다. 이를 읽고 retry하는 것과 model weight를 online learning으로 갱신하는 것은 다르다.
- 자율성은 이분법적 속성이 아니라 위임된 goal·tool·권한·step budget·시간·부작용·사람 승인 범위의 조합이다.
- 가능해 보이는 시연과 반복 가능한 end-to-end 성공, 안전한 production deployment는 서로 다른 근거를 요구한다.

### 한 장으로 보는 시스템 경계

| 층 | 맡는 일 | 그 자체로 보장하지 않는 것 |
| --- | --- | --- |
| Model | Context에서 text·plan·tool call 후보 생성 | 호출 실행, 계획 충실성, 권한 |
| Orchestrator | State·loop·retry·종료·budget 관리 | Model 판단의 정확성 |
| Tool adapter | Schema 변환과 외부 service 연결 | 사용자 authorization, 업무 타당성 |
| State·memory | 대화·관찰·artifact·checkpoint 보존 | Weight 학습, 사실의 정확성 |
| Policy·identity | 인증·최소 권한·승인 결정 | 외부 service 성공 |
| Executor·environment | 읽기·쓰기·code·browser 행동 수행 | Goal 정당성, 최종 답 grounding |
| Evaluator·monitor | 결과·postcondition·cost·위험 관측 | 모든 숨은 실패의 탐지 |

## 2단계 — 작동 원리

### 추론–행동–관찰 loop

한 step의 입력은 사용자 목표 $g$, 현재 state $s_t$, 허용된 tool catalog $\mathcal T_t$다. Model과 orchestrator가 다음 action 후보를 만들고, runtime이 policy를 통과한 action만 실행한다.

$$
\hat a_t \sim p_\theta(a\mid g,s_t,\mathcal T_t),
\qquad
a_t = \Pi(\hat a_t, i_t, P_t),
$$

$$
o_{t+1}=E(a_t),
\qquad
s_{t+1}=U(s_t,a_t,o_{t+1}).
$$

$\Pi$는 identity $i_t$와 policy $P_t$에 따른 허용·거절·승인 요구를, $E$는 실제 environment 실행을, $U$는 observation을 state에 반영하는 update를 뜻한다. Model은 보통 $\hat a_t$를 생성한다. $a_t$의 허가와 $E(a_t)$의 부작용은 application이 책임진다.

ReAct는 thought–action–observation을 prompt 안에서 교대해 이 loop를 선명하게 보여 줬다. 하지만 연구용 action space와 production 권한 체계는 같지 않다. Wikipedia 검색을 고르는 것과 계좌 이체를 승인하는 것은 동일한 token-generation 문제로 환원되지 않는다.

### 추론 text와 plan을 세 층으로 나눈다

원 웹글은 chain-of-thought가 복잡한 목표를 정확한 단계로 분해하는 planning mechanism이 됐다고 설명한다. 실제로 사고 연쇄 prompting은 일부 산술·상식·기호 과제에서 정답률을 높였고 ReAct는 reasoning trace를 action 선택과 연결했다. 그러나 출력된 설명이 model 내부 계산을 충실하게 보고한다거나 실행 가능한 plan이라는 보장은 없다.

다음 세 층을 구분한다.

1. **추론 text:** Model이 생성한 자연어 중간 산출물이다.
2. **실행 plan:** Dependency·precondition·resource·승인·종료 조건이 명시된 action 구조다.
3. **실행 trace:** 실제로 허가·실행된 call, observation, error와 state change 기록이다.

그럴듯한 1번이 2번의 모순과 누락을 숨길 수 있고, 올바른 2번도 환경 변화 때문에 3번에서 실패할 수 있다. Plan 품질은 문장 설득력만이 아니라 precondition·postcondition과 실제 trace로 확인해야 한다.

### Memory와 learning을 섞지 않는다

Agent memory는 보통 context window, 요약, key–value store, vector database, event log, file이나 code library에 상태를 저장하고 다음 요청 때 다시 넣는 방식이다. Generative Agents는 observation을 memory stream에 쌓고 reflection과 plan에 사용했다. Reflexion은 scalar·natural-language feedback을 episodic memory에 저장해 다음 attempt의 prompt에 넣었다.

Reflexion의 핵심은 **weight를 갱신하지 않는 verbal reinforcement**다. 실패를 기억하고 다음 trial의 출력이 바뀌었다고 해서 optimizer가 model parameter를 학습한 것은 아니다. 반대로 online fine-tuning이나 reinforcement learning은 data selection, objective, update schedule, regression·drift 평가가 필요한 별도 학습 system이다.

### 자율성은 위임 범위다

같은 model과 tool도 실행 설정에 따라 보조 도구 또는 agent가 된다. 한 번의 read-only query 뒤 답을 돌려주면 위임 범위가 작다. 여러 시간 동안 외부 event를 감시하고 write tool을 호출하며 실패에서 복구하도록 허용하면 범위가 커진다.

자율성을 기술할 때는 최소한 다음을 적는다.

- Goal을 누가 설정·변경하는가?
- 어떤 resource와 tool을 읽고 쓸 수 있는가?
- Step·token·시간·비용 budget은 얼마인가?
- 어떤 action에 사용자 확인이 필요한가?
- Error 뒤 retry·대체 경로·중단을 누가 결정하는가?
- 상태 변화는 log·rollback·compensating action으로 추적 가능한가?

“사람 개입 없이 수행했다”는 말은 이 조건과 benchmark episode 안에서만 해석할 수 있다.

## 3단계 — 기술과 근거

### 2022–2024년의 확인 가능한 연표

| 공개·게재 시점 | 연구 | 직접 확인되는 범위 |
| ---: | --- | --- |
| 2022 공개·2023 게재 | ReAct | Reasoning trace와 action·observation을 교대하고 QA·interactive benchmark에서 평가 |
| 2023 | Toolformer | GPT-J 6.7B가 다섯 종류 API call을 self-supervised하게 선택·삽입하도록 학습 |
| 2023 | Reflexion | Weight update 없이 verbal feedback을 episodic memory에 넣어 retry하는 language-agent loop |
| 2023 | Generative Agents | 25개 agent의 sandbox에서 memory·reflection·planning architecture와 행동의 believability 평가 |
| 2023-06 | OpenAI Function Calling | Model이 함수 이름·JSON argument를 제안하고 application이 검증·실행하는 product interface |
| 2024 | WebArena | 네 실제형 website domain의 장기 task를 end-to-end success로 평가 |
| 2024 | SWE-bench | 12개 Python repository의 2,294개 real issue에 대한 patch test 기반 평가 |
| 2024 | OSWorld | Web·desktop application의 369개 실제 computer task를 screenshot·accessibility 기반 agent에 평가 |
| 2024 | ToolEmu | 36개 고위험 toolkit의 144개 case를 LM-emulated sandbox와 safety evaluator로 시험 |

이 연표는 모든 agent 계보를 포괄하지 않는다. 고전 AI의 symbolic agent·planning, reinforcement-learning agent, robotics와 multi-agent system은 LLM 이전부터 존재했다. 여기서 검증하는 범위는 LLM을 reasoning·action proposal component로 쓰는 2022–2024년 연구다.

### Tool use는 model 능력과 runtime 능력의 합성이다

Toolformer는 training sequence에 API call과 결과를 삽입해 model이 언제 tool을 쓸지 학습했다. ReAct는 prompt와 환경 wrapper가 action을 해석해 observation을 되돌렸다. OpenAI의 Function Calling은 함수 설명과 argument를 구조화된 field로 제공했다. 세 방식은 tool 선택과 결과 이용을 다루지만 training 방식·interface·실행 주체가 다르다.

원 웹글은 2024년 framework가 authentication·security를 처리해 다양한 tool을 안전하고 신뢰성 있게 사용하게 했다고 서술한다. 그러나 tool adapter가 OAuth token을 전달하는 것과 요청 주체가 특정 resource를 수정할 권한이 있는지를 판정하는 것은 다르다. Schema 준수, semantic validation, identity, authorization, confirmation, transaction, timeout, idempotency와 audit를 각각 application 경계에 둬야 한다.

### Benchmark는 ‘자율성 성공’보다 실패 위치를 보여 준다

WebArena는 shopping·social forum·collaborative development·content management의 실제형 website에서 812개 장기 task를 구성했다. 원 논문의 최고 GPT-4 기반 agent success rate는 14.41%, 인간은 78.24%였다. OSWorld의 369개 실제 computer task에서도 인간 72.36%에 비해 최고 model은 12.24%였다. 이 수치는 2024년에 장기 digital work가 보편적으로 해결됐다는 주장보다 model perception·planning·interaction·recovery의 큰 격차를 보여 준다.

SWE-bench는 12개 Python repository의 2,294개 issue와 test를 엮어 patch가 실제 문제를 해결했는지 평가했다. 최초 논문의 최고 결과는 Claude 2의 1.96%였다. 이 benchmark의 원 protocol은 repository context에서 patch를 생성·test하는 능력을 측정했으며, 오늘날의 IDE·terminal·browser를 반복 사용하는 coding agent 전체와 같지 않다. 그래도 “복잡한 software feature를 최소 개입으로 완수했다”는 일반론을 확인하려면 issue-level test success가 필요한 이유를 보여 준다.

ToolEmu는 실제 고위험 API 대신 언어 모델이 tool execution을 모사하는 sandbox와 별도 자동 evaluator를 사용했다. 논문은 시험한 가장 안전한 agent에도 evaluator 기준 23.9%의 failure rate가 남았다고 보고했다. 이는 실제 배포 실패율이 아니라 emulator·test case·evaluator가 정한 연구 결과다. 동시에 sandbox가 blast radius를 줄일 수 있어도 목표의 정당성·권한·민감 정보·간접 prompt injection을 자동 해결하지 않는다는 반례다.

### Eval은 결과·과정·부작용을 함께 기록한다

Agent task success 하나만 보면 우연히 맞은 경로와 위험한 side effect를 구분하기 어렵다. 반대로 step별 tool accuracy만 보면 긴 직렬 loop에서 실패가 누적되는 효과를 숨긴다. [[자동 평가 지표는 무엇을 보상하는가]]의 component·end-to-end 장부를 agent에 확장하면 다음 축이 필요하다.

| 평가 축 | 묻는 질문 |
| --- | --- |
| Goal success | Episode 끝에 요구한 postcondition이 충족됐는가? |
| Plan·trajectory | 불필요한 step·loop·모순·권한 우회가 있었는가? |
| Tool component | 선택·argument·schema·semantic value·result grounding이 맞았는가? |
| Side effect | 허용되지 않은 write·전송·노출·중복 실행이 있었는가? |
| Cost·latency | Token·tool call·wall time·금전 비용이 budget 안인가? |
| Recovery | Timeout·잘못된 observation·환경 변화 뒤 안전하게 복구·중단하는가? |
| Security | Indirect instruction·credential·권한 상승을 차단하는가? |
| Reproducibility | Model·tool·environment version과 seed·trace를 재현할 수 있는가? |

## 검증과 한계

### 원 웹글의 주요 정정

- **에이전트형 AI는 2024년에 등장했다:** ReAct는 2022년 공개, Toolformer·Reflexion·Generative Agents는 2023년 연구다. 고전 agent 연구는 더 오래됐다.
- **GPT-4·Claude 같은 model은 본질적으로 외부 system과 상호작용할 수 없었다:** Model 자체에는 외부 권한이 없지만, ReAct·Toolformer와 custom orchestrator는 2023년 이전부터 tool interaction을 구성했다. Capability는 model과 runtime을 함께 봐야 한다.
- **Chain-of-thought가 robust planning을 제공했다:** 중간 reasoning text가 일부 과제 성능을 높인 것과 plan의 정확성·충실성·실행 가능성은 다르다.
- **Tool module이 인증·보안을 처리해 안전한 실행을 보장했다:** Adapter·schema와 identity·authorization·confirmation·sandbox·transaction은 별도 runtime control이다.
- **Feedback loop와 reinforcement learning으로 agent가 계속 학습했다:** Reflexion처럼 fixed model에 feedback text를 다시 넣는 방식도 있다. Memory·retry와 parameter update를 구분해야 한다.
- **Persistent memory가 agent의 지식을 자동으로 축적했다:** 외부 store는 저장·검색·provenance·삭제 정책을 가진 system state이며, 잘못된 기억도 지속시킬 수 있다.
- **Coding·research·travel·healthcare·education workflow가 이미 자율적으로 완성됐다:** 원 웹글은 application별 protocol, baseline, success rate, 사람 개입과 안전 결과를 제시하지 않는다. 이는 가능 사례이지 입증된 보편 성과가 아니다.
- **논문 검색부터 제출까지 전체 연구 workflow를 수행했다:** 제출 권한·저자 책임·근거 품질까지 확인한 연구가 제시되지 않았다. 생성 가능한 단계 목록을 실제 학술 성과와 동일시하지 않는다.
- **2024년 system이 표준 architecture와 안전 framework를 확립했다:** 여러 연구가 memory·planning·tool loop를 공유해도 구현·평가·보안 보장은 서로 다르다.
- **Robotics·autonomous vehicle·smart home에 같은 원리가 성공적으로 적용됐다:** LLM agent 연구의 digital benchmark를 물리적 safety-critical control의 성과로 일반화할 근거가 없다.

### 연구 결과의 적용 범위

ReAct·Toolformer·Reflexion·Generative Agents는 서로 다른 model, prompt·training 방법, action space와 metric을 사용했다. HumanEval retry, Sims-like sandbox의 believability와 WebArena task success를 같은 ‘agent intelligence’ 점수로 합칠 수 없다.

WebArena·OSWorld의 낮은 baseline은 특정 2023–2024 model과 harness의 결과다. 후대 model·scaffolding의 성능을 그대로 나타내지 않지만, model 이름만으로 end-to-end reliability를 추정할 수 없다는 점은 남는다. SWE-bench 최초 설정도 modern coding agent leaderboard의 후대 variant와 섞지 않는다.

ToolEmu는 언어 모델이 API를 모사하고 또 다른 evaluator가 safety를 판정하므로 emulator fidelity와 evaluator error라는 추가 proxy가 있다. 해당 수치를 실제 고위험 service의 사고율로 바꾸지 않는다. 반대로 실제 API를 바로 연결한 성공 demo도 공격·오류를 충분히 표집한 safety 평가가 아니다.

### 남는 질문

장기 agent가 목표를 스스로 재해석할 수 있는 범위, 충돌하는 memory를 교정하는 방법, 여러 agent와 사람이 공유하는 권한·책임, 동적으로 변하는 website와 API에서 regression을 재현하는 방법은 여전히 열린 문제다. 더 큰 action space와 더 긴 horizon은 능력을 늘리면서 오류 전파와 attack surface도 함께 늘린다.

Agent의 가치는 ‘자율적’이라는 label이 아니라 **어떤 목표를 어느 권한과 비용으로, 몇 번의 검증 관문을 통과해, 어떤 side effect 없이 달성했는가**로 판단해야 한다.
