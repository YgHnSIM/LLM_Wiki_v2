# 학습 데이터 생애주기와 출처 추적

> [!note] 학습 안내
> **난이도:** 입문–중급<br>
> **선수 지식:** [[말뭉치 기반 학습]] — 자료를 모아 정제·분할·학습·평가한다는 흐름을 알고 시작한다.<br>
> **읽고 나면:** 학습 자료의 snapshot, 수집·변환·혼합·공개 버전·학습 run을 한 계보로 기록하는 이유와, 출처 기록·권리·동의·재현 가능성이 서로 다른 질문인 이유를 설명할 수 있다.

## 1단계 — 먼저 잡을 핵심

### 데이터는 파일 하나가 아니라 변환 이력이다

학습 데이터는 보통 “웹 자료 1조 token”처럼 하나의 양으로 소개된다. 하지만 모델이 실제로 읽은 것은 처음 발견한 자료가 아니라, 특정 시점의 **snapshot**에 수집·선별·주석·번역·정제·중복 제거·혼합·표본추출을 차례로 적용한 결과다. 같은 이름의 데이터셋도 수집 시점, filter, 중복 제거 규칙, mixture 비율, release version이 다르면 다른 입력이다.

그래서 이 문서는 다음 경로를 한 줄의 **데이터 계보(lineage)** 로 기록한다.

> 원천 snapshot → 수집·선별 → 주석·번역 → 정제·중복 제거 → mixture·sampling → 공개 version → 학습 run → 정정·철회 상태

각 화살표에는 적어도 “무엇을 넣었는가, 무엇을 만들었는가, 어떤 규칙·시점·책임자가 적용했는가”가 붙어야 한다. W3C PROV-O의 entity·activity·agent 모델은 이러한 관계를 표현하는 어휘를 제공한다. 다만 어휘가 있다고 과거의 모든 변환이나 권리가 자동으로 증명되는 것은 아니다.

### 기록은 권리 판단이 아니다

출처 URL, 데이터셋 카드, component 목록, hash와 version은 매우 중요하다. 그렇지만 아래의 등식은 성립하지 않는다.

| 확인한 사실 | 아직 확인하지 못한 사실 |
| --- | --- |
| 출처 URL이나 collection method를 기록했다 | 이용 허락·계약 조건·동의가 유효하다는 법적 판단 |
| 공개 접근 가능한 자료였다 | 학습·재배포·상업 이용이 허용된다는 결론 |
| 변환과 version을 문서화했다 | 특정 item이 특정 training run에 실제로 선택됐다는 증명 |
| correction 또는 withdrawal 요청을 받았다 | 이미 배포된 checkpoint의 영향을 자동으로 제거했다는 증명 |

따라서 이 문서는 법률 자문이나 허가 판정표가 아니다. 어떤 근거가 있고, 어느 칸이 **unknown**인지 숨기지 않아 책임 있는 검토와 재현을 가능하게 하는 기록 구조다.

## 2단계 — 작동 원리

### 일곱 경계 장부로 계보를 끊기지 않게 적는다

| 경계 | 기록할 최소 내용 | 흔한 오해 |
| --- | --- | --- |
| 입력·대상 | 원천 이름·URL, snapshot 시각, 범위, item 또는 component 식별자 | “웹”이라는 한 단어가 동일한 자료를 뜻한다 |
| 변환 경로 | 수집·선별·주석·번역·filter·dedup·sampling의 입력·출력·설정 | 전처리는 학습 분포와 무관한 청소 작업이다 |
| 시간·상태·자원 | 실행 시각, 코드·config·hash, 담당 agent, 보존 위치, version | 최신 파일명만 있으면 과거 run도 재현된다 |
| 결과 계약 | 공개 dataset release, model training run, benchmark split의 정확한 산출물 | 공개 데이터셋과 실제 학습 입력은 항상 같다 |
| 지표·평가 기준 | item·document·token·epoch의 분모, coverage·중복·오염 검사 조건 | 큰 token 수 하나로 대표성·품질을 알 수 있다 |
| 실패·복구 경계 | 제거 실패, 누락 metadata, correction·withdrawal 요청, unknown 처리 규칙 | 결손 기록은 0 또는 없음과 같다 |
| 권한·책임·출처 추적 | publisher·collector·transformer·release manager, license/terms/consent의 원문 위치와 확인 상태 | 출처를 적었으므로 권리도 확인됐다 |

이 장부는 모든 조직에 같은 법적 절차를 요구하는 checklist가 아니다. “무엇을 안다”, “무엇을 추정한다”, “무엇을 아직 모른다”를 분리하는 방법이다.

### version은 파일명보다 넓은 계약이다

다음 세 레코드를 구분하면 많은 혼동이 줄어든다.

| 레코드 | 반드시 연결할 것 | 그 자체로 보장하지 않는 것 |
| --- | --- | --- |
| 원천 snapshot | source, 수집 시각, 범위, fingerprint 또는 hash | 원천의 license·terms·consent가 학습 사용을 허용함 |
| 처리된 release | transform config, code revision, version, 제외·중복 제거 규칙 | 그 release의 모든 item이 같은 비율로 training에 노출됨 |
| training run | mixture, sampling seed 또는 policy, run ID, checkpoint | correction·withdrawal이 checkpoint에서 완전히 제거됨 |

예를 들어 C4는 특정 Common Crawl snapshot과 품질 filter의 결과이고, 그 filter가 언어·지리·사회집단에 서로 다른 배제 효과를 낼 수 있음을 문서화한 사례다. The Pile도 component, effective size, deduplication 범위를 따로 기록한다. 이런 기록은 자료가 “좋다”는 도장이 아니라, 나중에 다른 사람이 어떤 입력과 변환이 결과를 만들었는지 질문할 출발점이다.

### sampling은 계보의 마지막이 아니라 학습 입력을 결정하는 변환이다

공개 release에 100개의 component가 있어도 training run이 모두를 한 번씩 읽는 것은 아니다. Epoch 가중치, up/down-sampling, shuffle, tokenization, sequence packing과 seed가 실제 노출 분포를 바꾼다. T5의 C4 처리와 The Pile의 component별 epoch 가중치는 데이터셋 설명과 training distribution을 분리해 기록해야 하는 이유를 보여 준다.

그러므로 “이 모델은 데이터셋 X로 학습됐다”라는 문장에는 최소한 release version과 mixture·sampling 규칙이 붙어야 한다. 세부 정보가 없으면 빈칸을 그럴듯한 추정으로 채우지 않고 `unknown`으로 남긴다.

## 3단계 — 기술과 근거

### 데이터 문서화는 질문을 남기는 기술이다

Gebru 외의 datasheet는 dataset의 motivation, composition, collection, preprocessing·cleaning·labeling, use, distribution, maintenance를 질문으로 남긴다. Bender와 Friedman의 data statement는 NLP에서 언어 variety, 화자, annotator, curation rationale을 기록해야 과학적 비교와 편향 검토가 가능하다고 설명한다. 둘 다 “모든 데이터셋이 안전하거나 적법하다”는 보증서를 제시하지 않는다.

따라서 release 문서에서 다음을 분리해 적는다.

- **관찰된 사실:** snapshot 날짜, component 목록, 공개된 transform, 공개된 license 또는 terms 링크.
- **운영 선택:** 어떤 filter·dedup·sampling을 했고 누구의 config·code revision인지.
- **검토 상태:** 권리·동의·개인정보·withdrawal에 대해 확인한 원문과 담당자, 또는 `unknown`.
- **추론 금지:** 공개 URL, dataset card, weight release 하나만으로 training 재현·허가·영향 제거를 결론 내리지 않는다.

### 계보 그래프는 책임을 분산시키지 않는다

PROV-O에서는 **entity**(snapshot·release·checkpoint), **activity**(crawl·filter·training), **agent**(개인·조직·software)를 연결할 수 있다. 예를 들어 “release R은 filter activity F가 생성했고, F는 snapshot S를 사용했으며, team T가 연결됐다”라고 적을 수 있다. 이는 책임과 재검토의 위치를 드러내는 최소 표현이다.

하지만 provenance graph가 있다고 해서 item 단위의 저작권 상태, 모든 동의, 모든 downstream checkpoint의 영향이 자동으로 해결되지는 않는다. 그래프는 증거의 **위치**를 가리키며, 법적·윤리적·기술적 판단을 대체하지 않는다.

### 소비 문서에는 현재 자료의 의미만 남긴다

[[말뭉치 기반 학습]]은 자료의 대표성·주석·분할·희소성·영역 이동을 설명한다. 그 문서에서 필요한 것은 현재 말뭉치가 고정 파일이 아니라 변환 이력이 있는 입력이라는 사실이다. snapshot–release–run 전체의 반복 설명과 rights/provenance의 한계는 여기서 한 번만 완결한다.

[[The Pile]]은 공개된 22개 component와 datasheet의 실제 기록을 검토한다. [[데이터 품질과 분포 다양성은 같은 축인가]]는 mixture·filter·quality proxy가 성능과 어떤 관계를 갖는지 비교한다. 이 owner는 어느 문서가 어떤 질문을 맡는지 정리할 뿐, 이들 자료의 권리 상태를 새로 판정하지 않는다.

## 검증과 한계

- **직접 영향:** C4, T5, The Pile과 Pile datasheet는 각자가 공개한 snapshot·filter·mixture·component·문서화 범위를 설명한다. 그 기록을 다른 비공개 training run의 사실로 옮겨 쓰지 않는다.
- **가능 조건:** source identifier, 시간, transformation config, version, 담당자와 가능한 fingerprint가 있어야 lineage를 재구성할 수 있다. 기록이 없는 과거 단계는 소급해 추측하지 않는다.
- **병행 맥락:** datasheet, data statement, PROV-O는 dataset documentation과 provenance 모델링의 방법을 제공한다. 이들이 특정 LLM training corpus나 policy를 직접 낳았다고 주장하지 않는다.
- **후대 유추:** 출처 추적은 감사·재현·정정 논의를 가능하게 하지만, 좋은 모델·공정한 데이터·유효한 권리·완전한 unlearning을 자동 보장하지 않는다.

특히 correction 또는 withdrawal은 request의 시점·범위·검증 방법, dataset release와 downstream run의 연결, checkpoint 재학습·편집·배포 정책을 따로 확인해야 한다. “삭제했다”와 “모델 영향이 없다”를 같은 말로 쓰지 않는다.

## 학습 확인

1. 원천 snapshot, 처리된 release, training run을 각각 하나씩 기록해야 하는 이유는 무엇인가?
2. source URL과 dataset card가 있어도 학습 이용 권한이나 item의 실제 training 노출을 바로 결론 낼 수 없는 이유는 무엇인가?
3. dataset의 correction 또는 withdrawal 요청이 있을 때, 어떤 기록이 있어야 후속 checkpoint와의 관계를 검토할 수 있는가?

다음 배치에서는 규모·다양성·품질의 수치가 권리·책임·영향의 결론으로 자동 변환되지 않는 이유를 비교한다.
