# 언어 모델 추론 서빙

> [!note] 학습 안내
> **난이도:** 중급<br>
> **선수 지식:** [[자기회귀 생성]], [[계산 복잡도와 비용 모델]] — 다음 token을 한 번씩 고른다는 사실과 FLOPs·memory·wall-clock의 차이를 알고 시작한다.<br>
> **읽고 나면:** prefill과 decode, KV cache와 batching을 한 요청의 생애 주기로 설명하고, throughput·TTFT·token 간 지연·tail latency·가용성·에너지를 분리해 실제 LLM 서비스의 능력을 평가할 수 있다.

## 1단계 — 먼저 잡을 핵심

### 모델 실행과 서비스는 경계가 다르다

학습된 언어 모델은 입력 token에서 다음 token 확률을 계산한다. **추론 서빙(inference serving)**은 여기에 동시 요청 접수, 대기열, batch 구성, GPU memory 할당, 출력 전송, 시간 초과와 실패 복구를 더해 사용자가 실제 응답을 받게 하는 시스템이다.

좋은 benchmark 점수를 가진 model도 요청이 몰릴 때 memory 부족으로 거절되거나 첫 token이 늦으면 좋은 서비스가 아니다. 반대로 높은 tokens/s를 내는 server도 일부 요청의 p99 지연이 매우 길거나 출력 품질을 낮춘 조건에서만 빠르다면 목표를 달성했다고 할 수 없다.

한 요청은 보통 다음 생애 주기를 지난다.

1. **도착·대기:** 요청이 queue에 들어가 scheduler 선택을 기다린다.
2. **Prefill:** Prompt token 전체를 처리해 첫 출력 분포와 각 layer의 key·value 상태를 만든다.
3. **Decode:** 직전까지의 출력에 조건부로 새 token 하나를 고르고 그 token의 key·value를 cache에 더한다.
4. **종료·회수:** 종료 token이나 길이 제한에 도달하면 memory를 해제하고 결과를 확정한다.

서비스 최적화는 이 네 구간 중 무엇을 바꾸는지 밝혀야 한다.

### 빠르다는 말은 최소 여섯 질문으로 나뉜다

| 지표 | 묻는 질문 | 놓치기 쉬운 조건 |
| --- | --- | --- |
| 처리량(throughput) | 초당 몇 요청 또는 몇 token을 끝내는가? | 입력·출력 길이, 품질, 동시 요청 수 |
| 첫 token 시간(TTFT) | 도착부터 첫 출력까지 얼마나 기다리는가? | Queue와 prefill이 함께 들어가는지 |
| token 간 지연(TPOT·ITL) | 첫 token 뒤 새 token이 어느 간격으로 오는가? | 평균인지 p95·p99인지 |
| 종단 지연 | 요청 전체가 언제 끝나는가? | 출력 token 수와 streaming 여부 |
| 가용성 | 정한 시간과 품질 안에 성공한 요청 비율은 얼마인가? | 오류·거절·timeout·재시도 처리 |
| 자원 효율 | 유효 요청당 GPU 시간·memory·energy·비용은 얼마인가? | Idle 전력과 복제·여유 용량 |

이 지표들은 서로 영향을 주지만 서로의 대리값이 아니다. 더 큰 batch는 처리량을 높이는 대신 queue와 token 지연을 늘릴 수 있다.

## 2단계 — 작동 원리

### Prefill은 넓게 계산하고 decode는 반복한다

길이 $P$인 prompt $x_{1:P}$와 최대 $O$개의 출력 token을 생각하자. Prefill에서는 prompt가 이미 모두 알려져 있으므로 causal mask를 지키면서 여러 위치를 병렬 계산할 수 있다. Decode에서는

$$
p(x_{P+t}\mid x_{1:P+t-1})
$$

에서 실제 $x_{P+t}$를 정한 뒤에야 다음 단계의 조건이 완성된다. 그래서 표준 자기회귀 생성에는 최대 $O$번의 순차 round가 남는다.

Streaming 응답에서 종단 시간을 거칠게 나누면

$$
T_{\mathrm{end}}\approx T_{\mathrm{TTFT}}+(O-1)T_{\mathrm{TPOT}}
$$

로 볼 수 있다. 여기서 $T_{\mathrm{TTFT}}$는 queue·prefill·첫 token 전송을 포함할 수 있고, $T_{\mathrm{TPOT}}$는 후속 token 간 평균 시간이다. 실제 요청마다 길이와 경합이 달라지므로 이 식은 측정 정의를 돕는 근사이지 p99를 예측하는 보편식이 아니다.

### KV cache는 재계산을 memory로 바꾼다

Decode할 때 과거 모든 token의 key와 value를 다시 만들면 prefix 계산이 반복된다. **KV cache**는 각 layer에서 이미 계산한 key·value를 저장해 새 query가 이를 재사용하게 한다.

Layer 수를 $L$, cache에 든 token 수를 $T$, key·value head 수를 $h_{\mathrm{kv}}$, head 차원을 $d_h$, 원소당 byte를 $b$라고 하면 한 요청의 기본 cache 크기는 대략

$$
M_{\mathrm{KV}}=2LTh_{\mathrm{kv}}d_hb
$$

이다. 앞의 2는 key와 value 두 묶음이다. Batch가 같은 길이 $T$인 요청 $B$개라면 $B$배가 되고, 실제 continuous batch에서는 요청별 길이를 합산해야 한다.

예를 들어 $L=32$, $T=2048$, $h_{\mathrm{kv}}=8$, $d_h=128$, $b=2$ byte이면

$$
M_{\mathrm{KV}}
=2\cdot32\cdot2048\cdot8\cdot128\cdot2
=268{,}435{,}456\text{ bytes}
=256\text{ MiB}
$$

이다. 이는 요청 하나의 기본 K·V tensor만 센 값이다. Allocator block, metadata, temporary buffer, model weight와 activation은 포함하지 않는다. Multi-Query·Grouped-Query Attention, sliding window, cache quantization은 $h_{\mathrm{kv}}$, $T$, $b$를 바꾸지만 품질·kernel·호환 조건을 별도로 확인해야 한다.

### 반복 단위 scheduling은 batch의 빈자리를 다시 쓴다

고정 request-level batch는 길이가 다른 요청을 한 묶음으로 넣고 모두 끝날 때까지 구성을 바꾸지 않을 수 있다. 짧은 요청이 먼저 끝나면 slot이 놀고, 새 요청은 긴 요청이 끝날 때까지 기다린다.

Orca의 **iteration-level scheduling**은 다음 token iteration마다 실행할 요청 집합을 다시 고른다. 흔히 continuous batching이라고 부르는 계열의 핵심은 끝난 요청을 빼고 새 요청을 넣어 batch를 계속 채우는 것이다. 다만 매 iteration의 재구성이 공짜는 아니다. Scheduler overhead, 서로 다른 sequence 길이, prefill과 decode의 계산 성격, memory 여유와 공정성이 함께 작용한다.

| 방식 | Batch를 바꾸는 경계 | 장점 | 대표 위험 |
| --- | --- | --- | --- |
| 정적 batch | 묶음 전체가 끝난 뒤 | 구현과 shape가 단순함 | 긴 요청이 짧은 요청 반환을 지연 |
| 동적 request batch | 짧은 대기 창 뒤 요청 단위 | 도착을 묶어 GPU 이용률 개선 | Batch 대기와 길이 편차 |
| iteration-level batch | 생성 iteration 사이 | 완료 slot 회수와 새 요청 합류 | Scheduling·memory 관리 복잡성 |

### PagedAttention은 연속 sequence와 연속 물리 memory를 분리한다

요청의 최대 출력 길이만큼 연속 memory를 미리 예약하면 실제 길이가 짧을 때 내부 낭비가 생긴다. 길어지는 cache를 매번 더 큰 연속 공간으로 옮기는 것도 비싸다.

PagedAttention은 논리적인 token 순서를 고정 크기 KV block으로 나누고, block table을 통해 떨어진 물리 block에 연결한다. 새 token이 생길 때 필요한 block만 할당하며 요청이 끝나면 반환한다. 같은 prompt를 공유하는 여러 sample이나 beam은 물리 block을 공유하고 쓰기가 갈라질 때 copy-on-write를 사용할 수 있다.

이 방식은 KV cache의 **할당·공유·fragmentation**을 개선한다. Model의 attention 수학, token별 생성 의존성, weight memory나 모든 latency 원인을 없애지는 않는다. Block이 너무 작으면 table 접근과 kernel overhead가 커지고, 너무 크면 마지막 block의 내부 낭비가 커지는 설계 선택도 남는다.

### Speculative decoding은 작은 제안을 큰 모델이 검증한다

Speculative decoding은 작은 draft model $q$가 여러 token을 먼저 제안하고 target model $p$가 그 위치들의 확률을 병렬로 계산해 받아들일지를 정한다. Draft token $x$는 대표적으로

$$
a(x)=\min\left(1,\frac{p(x)}{q(x)}\right)
$$

의 확률로 받아들인다. 처음 거절한 위치에서는 $\max(0,p-q)$를 정규화한 수정 분포에서 다시 뽑는다. 이 절차와 논문의 가정 아래 최종 sample 분포는 target $p$를 유지한다.

두 token $A,B$에서 $q=(0.6,0.4)$, $p=(0.3,0.7)$라 하자. Draft가 $A$이면 $0.3/0.6=0.5$ 확률로 받아들이고, 거절하면 수정 분포에서 $B$를 고른다. Draft가 $B$이면 $p(B)/q(B)>1$이라 항상 받아들인다. 최종 확률은

$$
\Pr(A)=0.6\cdot0.5=0.3,\qquad
\Pr(B)=0.4+0.6\cdot0.5=0.7
$$

가 되어 target과 같다. 실제 가속은 draft가 target을 얼마나 잘 맞히는지, draft 비용, 검증 batch와 hardware 이용률에 달렸다. Acceptance가 낮으면 버린 draft 계산과 두 model의 overhead 때문에 이득이 작거나 음수가 될 수 있다.

## 3단계 — 기술과 근거

### 세 serving 기법의 측정 장부

| 기법 | 작업 | 결과 계약 | 시스템 경계 | 핵심 지표 |
| --- | --- | --- | --- | --- |
| Orca | 여러 길이의 자기회귀 요청 | 같은 model 출력 절차 | 분산 worker, iteration scheduler와 selective batching | Throughput, latency, batch 이용률 |
| vLLM·PagedAttention | 동적 KV cache를 가진 동시 요청 | Model accuracy를 바꾸지 않음 | Scheduler, block manager와 custom attention kernel | Request rate, latency, memory waste |
| Speculative decoding | Draft가 제안하고 target이 검증 | 논문 조건에서 target 분포 유지 | Draft+target의 end-to-end decode | Acceptance, wall-clock, 출력 분포 |

Orca 논문은 GPT-3 175B 조건에서 같은 latency 수준의 FasterTransformer보다 36.9배 throughput을 보고했다. 이 값은 특정 model·cluster·baseline·요청 분포의 시스템 결과다. 모든 continuous batching 구현의 보편 상수가 아니다.

vLLM 논문은 여러 model과 workload에서 기존 시스템보다 같은 latency 수준의 throughput을 2–4배 높였다고 요약한다. 기존 방식은 실험에서 실제 token state 저장에 KV cache memory의 20.4–38.2%만 사용한 경우가 있었고, PagedAttention의 더 나은 할당이 더 많은 요청을 batch에 넣게 했다. 반면 custom attention kernel 자체는 최적화된 FasterTransformer보다 20–26% 느린 microbenchmark도 보고했다. 느린 부분 kernel을 허용해 전체 memory 이용률과 end-to-end 처리량을 높인 사례다.

Speculative decoding 논문은 T5-XXL에서 표준 T5X 대비 2–3배 가속과 동일한 출력 분포를 보고했다. 이를 다른 model·sampling 설정·draft 품질·traffic에 그대로 적용하지 않는다.

### Tail latency는 평균의 나머지가 아니다

$N$개의 지연 시간을 정렬했을 때 p99는 관측값의 약 99%가 그 이하에 끝나는 경계다. 평균이 같아도 p99는 매우 다를 수 있다. 특히 요청이 여러 shard·tool·retriever에 fan-out하고 모두의 결과를 기다리면 드문 구성요소 지연이 종단 요청에서 자주 보일 수 있다.

LLM serving에도 queue burst, 긴 prompt·출력, memory preemption, 다른 tenant와의 경합, expert imbalance, network와 외부 도구가 꼬리를 만든다. 처리량을 한계까지 올리면 queue가 급격히 길어질 수 있으므로 load별 p50·p95·p99와 timeout·거절률을 함께 그려야 한다.

### 실제 비교를 위한 최소 실험 기록

1. Model·revision, tokenizer, quantization과 runtime version
2. GPU 종류·수, memory, interconnect와 replica·parallelism
3. Prompt·output 길이 분포, 도착률·burst와 요청 유형
4. Scheduler·batch·KV cache·prefix sharing·speculation 설정
5. TTFT·TPOT·종단 지연의 p50·p95·p99와 처리량
6. Timeout·오류·거절·재시도, 출력 품질과 안전 정책
7. Warmup·측정 기간, GPU·host·network energy와 비용 경계

Tokens/s만 있고 입력 길이·품질·tail·실패가 없으면 사용자에게 제공된 능력을 재현할 수 없다.

### CS_WIKI와 함께 읽기

[CS_WIKI의 「평균 성능은 왜 서비스의 컴퓨팅 능력을 설명하지 못하는가」](https://yghnsim.github.io/CS_Wiki/analyses/%ED%8F%89%EA%B7%A0-%EC%84%B1%EB%8A%A5%EC%9D%80-%EC%99%9C-%EC%84%9C%EB%B9%84%EC%8A%A4%EC%9D%98-%EC%BB%B4%ED%93%A8%ED%8C%85-%EB%8A%A5%EB%A0%A5%EC%9D%84-%EC%84%A4%EB%AA%85%ED%95%98%EC%A7%80-%EB%AA%BB%ED%95%98%EB%8A%94%EA%B0%80/)는 구성요소 속도에서 사용자 요청의 기한·품질·분포로 측정 경계를 넓힌다. 현재 문서는 그 틀을 prefill·decode·KV cache·batching이라는 LLM 고유 생애 주기에 적용한다.

## 검증과 한계

- **직접 영향:** Orca는 iteration-level scheduling을 Transformer 생성 serving에 구현했고, vLLM은 이를 비교 기준으로 삼아 PagedAttention과 block memory manager를 결합했다.
- **가능 조건:** GPU matrix 성능, 충분한 HBM·bandwidth, 적합한 kernel과 scheduler는 높은 처리량을 실현하는 조건이다. 어느 하나만으로 서비스 목표를 보장하지 않는다.
- **병행 맥락:** *The Tail at Scale*은 LLM 이전 대규모 서비스의 tail latency 원리를 제공한다. 이 논문이 PagedAttention을 직접 낳았다고 주장하지 않는다.
- **후대 유추:** 운영체제 paging과 PagedAttention은 논리·물리 주소 분리라는 유추를 공유하지만, CPU page fault의 모든 기법이 GPU KV cache에 그대로 적용되는 것은 아니다.

여기서 다룬 식은 decoder-only Transformer의 대표 cache 장부다. Encoder–decoder, cross-attention, MLA, recurrent state, offloading과 분산 cache는 다른 항을 가질 수 있다. Speculative decoding의 target 분포 보존은 올바른 acceptance·수정 sampling 구현에 대한 명제이며, floating-point bitwise 동일성이나 항상 낮은 latency를 뜻하지 않는다.

가용성은 p99가 짧다는 사실과도 다르다. 장애·배포 오류·공통 원인, 탐지·복구 시간, 안전 filter와 데이터 보호는 별도 운영 근거가 필요하다. 에너지도 latency×정격 전력으로 자동 계산하지 말고 GPU·host·network·idle과 replica 경계를 실제로 측정해야 한다.

## 학습 확인

1. $L=24$, $T=1024$, $h_{\mathrm{kv}}=4$, $d_h=128$, $b=2$인 요청 하나의 기본 KV cache byte를 계산하고, 식에 포함되지 않은 memory를 두 가지 적어라.
2. 처리량이 높아졌는데 p99 TTFT가 나빠질 수 있는 이유를 queue, batch와 이용률로 설명하라.
3. PagedAttention과 speculative decoding은 각각 무엇을 바꾸며, 자기회귀 token 의존성·출력 분포·memory 가운데 무엇을 유지하는가?
