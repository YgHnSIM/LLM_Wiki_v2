# 계산 복잡도와 비용 모델

> [!note] 학습 안내
> **난이도:** 중급<br>
> **선수 지식:** 없음 — 곱셈 횟수, 저장할 수의 개수와 장치 간 이동을 이 문서에서 구분한다.<br>
> **읽고 나면:** $O(\cdot)$, FLOPs, peak memory, HBM 대역폭, 통신, wall-clock을 같은 “비용”으로 합치지 않고, dense attention·FlashAttention·희소 MoE의 주장을 조건과 함께 비교할 수 있다.

## 1단계 — 먼저 잡을 핵심

### 비용은 하나의 숫자가 아니다

모델이 “싸다”는 문장은 적어도 다음 축 중 무엇을 말하는지 밝혀야 한다.

| 축 | 묻는 질문 | 다른 축으로 대신할 수 없는 이유 |
| --- | --- | --- |
| 점근 산술량 | 길이·차원이 커질 때 필요한 연산 수가 어떻게 자라는가? | 상수, 하드웨어와 메모리 이동을 숨긴다. |
| FLOPs | 특정 shape에서 부동소수점 연산을 얼마나 하는가? | 같은 FLOPs도 kernel 이용률에 따라 시간이 다르다. |
| memory capacity | 어느 순간에 weight·activation·중간값을 얼마나 저장해야 하는가? | 저장할 수 있어도 읽고 쓰는 속도는 별도다. |
| memory bandwidth·I/O | HBM·SRAM 등 계층 사이에 데이터를 얼마나 이동하는가? | 연산량이 작아도 이동이 병목일 수 있다. |
| communication | 여러 장치가 token·gradient·expert를 얼마나 주고받는가? | 단일 GPU의 FLOPs에는 보이지 않는다. |
| wall-clock | 실제 한 step·token이 얼마나 걸리는가? | batch, kernel, 병렬화, 네트워크와 hardware에 의존한다. |

따라서 parameter 수, FLOPs, latency를 서로의 대리값으로 자동 치환하지 않는다.

### $O(\cdot)$는 성장률의 언어다

$f(n)=O(g(n))$는 충분히 큰 $n$에서 $f(n)$이 어떤 상수배의 $g(n)$보다 빠르게 커지지 않는다는 상한 표기다. 예를 들어 dense attention의 score·value 곱은 sequence 길이 $n$, head 차원 $d$에 대해 $O(n^2d)$다. 이는 입력이 두 배가 되면 항상 실행 시간이 정확히 네 배라는 예측도, GPU 메모리가 충분하다는 보장도 아니다.

## 2단계 — 작동 원리

### 가장 작은 dense attention 비용 장부

한 head에서 $Q,K,V\in\mathbb R^{n\times d}$이고 $n=4$, $d=2$라고 하자. score 행렬은

$$
S=QK^{\mathsf T}\in\mathbb R^{4\times4}
$$

이다. 각 score 원소는 길이 2 내적이므로 $4\cdot4\cdot2=32$번의 곱셈이 든다. softmax 뒤의 $PV$도 같은 shape의 곱이라 32번의 곱셈이 든다. 따라서 이 두 행렬곱만 세면 64번의 곱셈이며, score 또는 probability 행렬 하나는 $4\cdot4=16$개 실수를 저장한다.

일반 $n,d$로 올리면 $QK^{\mathsf T}$와 $PV$는 각각 대략 $n^2d$ 곱셈을 요구한다. projection, softmax, mask, backward와 batch·head 수는 이 간단한 장부 밖의 비용이다. 이 예는 왜 sequence 길이 축에서 $n^2$가 나타나는지 보일 뿐 전체 Transformer step의 정확한 FLOP 수가 아니다.

### 같은 수학식, 다른 실행 비용

[[FlashAttention]]은 dense softmax attention의 수학적 결과를 근사하지 않으면서 score·probability 전체를 HBM에 물질화하지 않는다. 그래서 attention 중간 **추가 메모리**는 선형으로 줄일 수 있지만, $QK^{\mathsf T}$와 $PV$의 $O(n^2d)$ 산술량은 그대로 남는다. Backward에서 일부 값을 다시 계산해 FLOPs가 늘어도 HBM 읽기·쓰기가 줄면 wall-clock이 짧아질 수 있다.

즉 “메모리 효율적”과 “계산량 선형”은 다른 주장이다. 비용 모델은 어떤 값을 저장하는지, 어느 메모리 계층을 오가는지, 어떤 dtype과 kernel을 쓰는지까지 적어야 실제 실행으로 이어진다.

## 3단계 — 기술과 근거

### Transformer의 대표 항을 분리한다

| 항 | 대략적 산술량 | 주로 커지는 축 | 빠뜨리기 쉬운 조건 |
| --- | --- | --- | --- |
| attention score·value 곱 | $O(n^2d)$ | sequence 길이 $n$ | head 수·batch·mask·backward |
| Q/K/V·output projection | $O(nd^2)$ | hidden 차원 $d$ | FFN 폭과 layer 수는 별도 |
| position-wise FFN | 대략 $O(ndd_{\mathrm{ff}})$ | $d,d_{\mathrm{ff}}$ | activation·gated 변형·backward |
| KV cache 추론 저장 | 대략 sequence에 선형 | 이미 생성한 길이 | layer·head·dtype·batch |

Transformer의 self-attention은 긴 $n$에서 pairwise score 때문에 이차 항이 눈에 띄지만, 실제 model 비용은 FFN 폭·layer 수·backward·parallelization을 빼고 단일 항으로 결론 내릴 수 없다.

### 희소 MoE의 네 장부

[[전문가 혼합]]에서는 expert 수 $E$와 token당 선택 수 $k$를 분리한다. $k\ll E$라면 한 token이 실행하는 expert FFN FLOPs는 모든 expert를 실행할 때보다 적을 수 있다. 그러나 선택되지 않은 expert도 weight·optimizer state·checkpoint에 저장되고, token dispatch와 gather가 장치 간 통신을 만든다.

| 비교값 | 무엇을 세는가 | sparse MoE에서의 해석 |
| --- | --- | --- |
| total parameters | 모든 expert와 공유 weight | $E$와 함께 크게 늘 수 있다. |
| active FLOPs | token이 실제 통과한 $k$개 expert | $k$를 고정하면 total보다 느리게 늘 수 있다. |
| peak memory | weight·activation·optimizer state | inactive expert도 학습·저장되어야 한다. |
| wall-clock | end-to-end 처리 시간 | routing 불균형·all-to-all 통신·batch가 좌우한다. |

### 비교 가능한 보고의 최소 조건

한 성능 또는 비용 수치를 비교할 때 다음을 함께 적는다.

1. model·sequence·batch·precision·training 또는 inference 단계
2. 세는 값(FLOPs, peak memory, HBM bytes, communication bytes, throughput, latency)
3. hardware, device 수, parallelism과 kernel·compiler 조건
4. quality 측정과 허용한 근사 또는 exact 여부

이 조건이 다르면 “두 배 빠르다”와 “같은 FLOPs다”가 모순일 필요는 없다. 전자는 특정 실행 측정이고 후자는 보통 계산 그래프의 다른 장부이기 때문이다.

### 필연적인 부분과 설계 선택

| 구분 | 현재 문맥에서의 의미 |
| --- | --- |
| 수학적 귀결 | naive dense $n\times n$ score 계산은 $n^2$개의 위치쌍을 고려한다. |
| 모델 선택 | layer 수, $d$, FFN 폭, expert 수, context 길이, attention pattern을 정한다. |
| 시스템 선택 | tiling, recomputation, sharding, communication overlap, dtype와 kernel을 정한다. |
| 측정 선택 | peak 또는 평균, per-token 또는 per-batch, warmup 포함 여부를 정한다. |
| 해결하지 않는 것 | 낮은 FLOPs·memory 하나만으로 낮은 비용, 접근성, 에너지 사용이나 높은 품질을 보장하지 않는다. |

## 검증과 한계

- Big-O는 충분히 큰 입력에서의 성장률이다. 작은 batch·짧은 문맥에서의 상수항과 kernel launch overhead를 예측하지 않는다.
- FLOPs는 보통 실수 연산 수를 세는 추정치라, memory-bound kernel·통신·cache miss·load imbalance의 시간을 직접 말하지 않는다.
- peak memory는 weight만이 아니라 activation, optimizer state, KV cache와 temporary buffer를 포함할지에 따라 달라진다.
- 서로 다른 품질·정확도·sequence length에서 얻은 throughput을 같은 효율 주장으로 묶어서는 안 된다.

## 학습 확인

### 확인 질문과 답

1. $n=4,d=2$에서 $QK^{\mathsf T}$의 곱셈 수는 왜 32인가?

   **답:** $4\times4$개의 score마다 길이 2 내적을 계산하므로 $4\cdot4\cdot2=32$다.

2. FlashAttention이 attention 중간 메모리를 선형화해도 $O(n^2d)$ 산술량이 남는 이유는 무엇인가?

   **답:** 모든 query-key 쌍의 score와 value 가중합은 여전히 계산하며, 달라진 것은 중간 행렬의 저장·I/O 순서이기 때문이다.

3. MoE의 total parameter와 active FLOPs를 분리해야 하는 이유는 무엇인가?

   **답:** token은 일부 expert만 실행하지만 모든 expert weight·optimizer state는 저장되고, dispatch 통신도 별도 비용이기 때문이다.
