# 문자 인코딩과 정규화

> [!note] 학습 안내
> **난이도:** 입문<br>
> **선수 지식:** 없음 — 이 문서 안에서 byte, UTF-8, Unicode code point, grapheme cluster, 정규화와 token을 차례로 정의한다.<br>
> **읽고 나면:** 같은 글자처럼 보이는 두 입력이 왜 다른 byte·code point·token 열이 될 수 있는지, 어떤 정규화와 tokenizer 설정을 기록해야 재현 가능한 입력 계약이 되는지 설명할 수 있다.

## 1단계 — 먼저 잡을 핵심

### 같은 글자처럼 보여도 같은 데이터라고 단정할 수 없다

사람이 읽는 **문자**와 컴퓨터가 보관·전달·처리하는 단위는 하나가 아니다. 네 단위를 먼저 분리하면 “한 글자”, “한 byte”, “한 token”을 같은 말처럼 쓰는 오류를 피할 수 있다.

- **byte**는 여기서 8비트 저장·전송 단위다. UTF-8 표준 문서는 이를 *octet*이라고 부른다. byte 열은 아직 어떤 글자인지 말해 주지 않는다.
- **Unicode code point**는 Unicode가 부여한 숫자 위치다. `가`는 `U+AC00`이고, UTF-8은 Unicode scalar value를 1–4개 octet으로 부호화한다. UTF-16의 surrogate 범위 `U+D800`–`U+DFFF`는 UTF-8 문자로 직접 부호화하지 않는다.
- **grapheme cluster**는 사용자가 보통 한 글자처럼 선택·삭제·표시하길 기대하는 text 단위의 기본 근사다. 하나의 code point일 수도, 여러 code point의 결합일 수도 있다. 언어·문자 체계별 요구에 따라 규칙을 tailor할 수도 있으므로, glyph·키 입력·보편적인 사람 글자 수와 같은 말은 아니다.
- **token**은 특정 모델의 tokenizer가 vocabulary와 규칙으로 만든 입력 ID 단위다. byte, code point, grapheme cluster와 일대일로 대응한다는 보장은 없다.

한국어 한 음절만으로도 차이가 보인다. 아래 두 문자열은 올바르게 표시하면 모두 `가`이고 UAX #15에서는 canonical equivalent다. UAX #29의 기본 규칙에서도 각각 하나의 grapheme cluster로 다룰 수 있다. 하지만 code point 열과 UTF-8 byte 열은 다르다.

```text
NFC 형태: 가
code point: U+AC00                         (1개)
UTF-8:     EA B0 80                       (3 bytes)

NFD 형태: 가
code point: U+1100 U+1161                 (2개)
UTF-8:     E1 84 80 E1 85 A1              (6 bytes)
```

따라서 화면에서 같은 `가`가 보인다는 사실만으로 byte가 같거나, code point 수가 같거나, tokenizer가 같은 ID 열을 만들었다고 결론 내릴 수 없다. 반대로 byte가 유효한 UTF-8이라는 사실도 단어 경계·의미·권한을 판정해 주지는 않는다.

### 이 문서가 맡는 경계

이 owner는 **외부 text가 모델 입력 ID가 되기 전의 표현 계약**을 완결한다. 즉, input byte를 어떤 encoding으로 decode했는지, Unicode 문자열에 어떤 normalization을 적용했는지, 어떤 tokenizer artifact가 token ID를 만들었는지를 기록하는 방법을 다룬다.

[[서브워드 토큰화]]는 유한 vocabulary로 문자열을 조각내는 이유와 trade-off를, [[Byte Pair Encoding]]은 빈번한 symbol pair를 병합하는 한 알고리즘을 맡는다. 이 문서는 BPE merge가 시작하기 전에 무엇이 symbol 열로 들어오는지와, 같은 text가 왜 다른 input contract가 될 수 있는지를 맡는다.

## 2단계 — 작동 원리

### byte에서 token ID까지의 세 변환

외부에서 byte 열 $b$를 받는 text interface를 다음처럼 적을 수 있다.

$$
b \xrightarrow{\operatorname{decode}_{E}} s
\xrightarrow{\operatorname{normalize}_{F}} s'
\xrightarrow{\operatorname{tokenize}_{T}} [t_1,\ldots,t_n]
$$

- $b$는 $0$부터 $255$까지의 byte 열이다.
- $E$는 `UTF-8` 같은 선언된 decoding 규칙이다. 유효하지 않은 byte 열이면 문자열 대신 error를 반환하거나 replacement character를 넣을 수 있다. 어느 쪽인지는 interface 계약이다.
- $s$는 decode된 Unicode scalar value의 열, 곧 Unicode 문자열이다.
- $F$는 `NFC`, `NFD`, `NFKC`, `NFKD` 또는 identity처럼 명시한 **실제 normalization 정책**이다. 외부 normalizer가 적용할 수도, tokenizer 내부 normalizer가 적용할 수도 있다. 후자의 경우 식은 논리적 순서를 나타낼 뿐이며, 실제 적용 위치·순서와 외부 단계가 `identity`인지 함께 기록한다.
- $T$는 tokenizer model·vocabulary·merge rule·normalizer·special-token mapping·options·version과 deterministic/sampling encode mode(후자면 seed)를 포함한 artifact다. 출력 $[t_1,\ldots,t_n]$은 vocabulary 안의 token ID 열이며, $n$은 그 열의 길이, $t_i$는 $i$번째 token의 ID다.

이 식은 모든 제품이 다섯 단계를 별도 함수로 구현한다는 뜻은 아니다. API가 이미 programming-language string을 받을 수 있고, tokenizer 내부에 normalizer가 들어 있을 수도 있다. 중요한 것은 **어느 단계가 어디서 일어났는지와 실패 시 무엇을 보존하는지**를 숨기지 않는 것이다.

`가` 예를 다시 보면, UTF-8 byte `EA B0 80`은 `U+AC00`으로 decode된다. `E1 84 80 E1 85 A1`은 `U+1100 U+1161`으로 decode된다. 두 번째 입력에 NFC를 적용하면 첫 번째 code point 열로 바뀐다. 그 뒤 같은 deterministic encoding configuration을 적용할 때에만 같은 token ID 열을 기대할 근거가 생긴다. sampling을 쓰는 tokenizer라면 mode·옵션·seed도 그 configuration에 포함한다. normalization을 생략하거나 tokenizer의 normalizer가 다르면, 눈에 보이는 글자는 같아도 tokenizer가 받는 symbol 열이 달라질 수 있다.

### 정규화는 하나의 "깨끗하게 만들기"가 아니다

Unicode normalization은 문자열을 정해진 form으로 바꿔 binary comparison으로 equivalence를 검사할 수 있게 하는 규칙이다. 네 form의 차이는 두 축으로 읽으면 된다.

| form | 먼저 하는 일 | 결과의 성격 |
| --- | --- | --- |
| NFD | canonical decomposition 뒤 canonical ordering | canonical equivalent를 분해된 열로 맞춘다 |
| NFC | canonical decomposition과 canonical ordering 뒤 canonical composition | canonical equivalent를 가능한 composed 열로 맞춘다 |
| NFKD | compatibility decomposition 뒤 canonical ordering | compatibility distinction도 분해한다 |
| NFKC | compatibility decomposition과 canonical ordering 뒤 canonical composition | compatibility distinction도 접어 composed 열로 맞춘다 |

NFC와 NFD는 `가`와 `가`처럼 canonical equivalent인 표현을 정렬하는 데 쓰인다. 반면 NFKC와 NFKD는 더 강한 변환이다. 예를 들어 `①`은 NFKC에서 `1`이 된다. 이는 어떤 검색·비교 업무에는 유용할 수 있지만, 표면상의 구별이 수학 표기·식별자·원문 보존에서 중요할 수도 있다는 뜻이다. 따라서 “정규화했으니 의미가 같다”가 아니라, **어느 form을 어떤 field에 왜 적용했는가**를 말해야 한다.

또한 정규화된 문자열 $x$, $y$를 단순히 이어 붙인 $xy$가 같은 form으로 계속 정규화돼 있다는 보장은 없다. 스트리밍 입력과 chunk 단위 처리에서는 결합 경계 주변을 다시 정규화할지, 전체 문자열이 도착한 뒤 처리할지를 계약에 넣어야 한다.

### tokenizer는 Unicode 표준의 마지막 단계가 아니다

Tokenizer는 text를 model vocabulary의 ID 열로 바꾸는 **모델별** 변환이다. SentencePiece는 normalizer, trainer, encoder, decoder를 하나의 pipeline으로 설명한다. normalization이 입력을 실제로 바꾼 경우, encode한 뒤 decode하는 계약은 원본 byte 열이 아니라 normalization된 text를 복원한다. identity 규칙이거나 입력이 이미 그 form이면 두 text가 같을 수 있다. 따라서 tokenizer의 normalization rule과 version은 model checkpoint만큼 input 재현에 중요할 수 있다.

Byte Pair Encoding도 입력 단위를 하나로 고정하지 않는다. Gage의 원형은 byte pair 압축이고, Sennrich·Haddow·Birch의 NMT 설정은 문자·문자열 pair에서 시작한다. 현대의 byte-level BPE는 byte 표현을 초기 symbol로 쓸 수 있다. 어느 경우든 BPE의 merge 규칙은 **어떤 byte를 유효한 UTF-8로 decode할지**, **NFC를 적용할지**, **사용자에게 한 글자로 보이는 단위를 어디서 끊을지**를 스스로 결정하지 않는다.

그래서 `token 수`를 문자 수나 언어 난이도의 대용으로 바로 쓰지 않는다. 같은 문장도 tokenizer의 vocabulary·fallback·normalization에 따라 다른 길이가 되고, 언어별 token 길이 차이는 context window·비용·평가 조건과 연결될 수 있다. 그것이 곧 의미 보존이나 언어 형평성을 보장하는 것은 아니다.

## 3단계 — 기술과 근거

### 일곱 경계 장부

| 변환 경로 | UTF-8 validation·decode, 외부/내부 normalization form과 순서, tokenizer normalizer·pre-tokenizer·vocabulary·merge 규칙·special-token mapping·options, deterministic/sampling mode와 seed |

| 결과 계약 | valid input을 어느 form의 text와 어느 tokenizer ID 열로 바꾸는지, decode·round trip이 원문인지 normalized text인지 |
| 지표·평가 기준 | invalid/replacement 비율, normalization 뒤 동일 열로 접히는 입력 비율, coverage·fallback, sample당 byte·code point·token 길이 |
| 실패·복구 경계 | malformed UTF-8, replacement에 의한 정보 손실, train/inference normalizer 불일치, tokenizer revision 변경, stream 결합 뒤 미정규화 |

이 장부의 `normalization 뒤 동일 열로 접히는 입력 비율`은 일반적인 품질 점수가 아니다. 선택한 form이 실제 자료에서 얼마나 많은 표면 구별을 합치는지 점검하는 관찰값이다. NFKC에서 값이 높다는 사실은 오류도 개선도 아니라, 그 form의 영향이 크므로 목적·field·복구 정책을 더 분명히 써야 한다는 신호다.

### 재현 가능한 text test set을 만든다

모델의 tokenizer를 평가하거나 text interface를 교체할 때 평범한 ASCII 문장만 비교하면 중요한 실패가 가려진다. 다음처럼 경계 사례를 함께 넣는다.

1. 정상 UTF-8과 malformed UTF-8 byte 열: reject, replacement, logging 중 실제 오류 정책을 확인한다.
2. canonical pair: `가`와 `가`, 또는 base letter와 combining mark를 NFC·NFD 전후에 비교한다.
3. grapheme 사례: combining mark, ZWJ emoji, Hangul jamo처럼 code point 수와 사용자 선택 단위가 다른 입력을 넣는다.
4. compatibility 사례: `①`, 전각·반각, 위첨자처럼 NFKC/NFKD가 접을 수 있는 구별을 field별 정책과 함께 넣는다.
5. 여러 문자 체계와 희귀 문자: coverage·byte fallback·unknown 처리와 token 길이를 같은 model revision에서 기록한다.

측정하는 분모도 분리한다. `invalid input 비율`은 transport·decode의 실패를, `replacement 비율`은 이미 잃어버린 정보를, `tokens/sample`은 특정 tokenizer의 비용·context 사용량을 말한다. 어느 하나도 언어 이해·안전성·권한 판단의 정확도를 대신하지 않는다.

### 소비 문서에서의 국소 질문

[[Byte Pair Encoding]]은 “어떤 인접 symbol pair를 병합해 vocabulary를 만드는가”에 집중한다. 그 문서의 symbol은 byte, 문자, 문자열 중 어느 초기 단위를 쓰는지에 따라 달라질 수 있다. 이 owner는 그 앞단의 encoding·normalization 계약을 한 곳에 모아 BPE 문서가 Unicode 전체를 다시 설명하지 않게 한다.

[[구조화 출력]]과 [[함수 호출과 도구 사용]]으로 갈수록 text는 JSON·schema·의미 검사·authorization 관문을 지난다. 이 문서가 보장하는 것은 그 첫 관문에서 byte와 text 표현을 명시하는 일뿐이다. UTF-8 validation이나 NFC가 JSON 구문·schema 준수·의미 정확성·실행 권한을 보장한다고 확장하지 않는다.

## 검증과 한계

- UTF-8은 encoding form이지 언어 판별기·의미 판별기·안전 정책이 아니다. 유효한 UTF-8 text도 혼동 가능한 문자열, 잘못된 이름, 악성 instruction일 수 있다.
- grapheme cluster는 사용자 인식 문자에 대한 default programmatic approximation이다. 글꼴의 glyph 수, cursor 동작, 언어별 맞춤 편집 규칙과 정확히 같다는 보장은 없으며 tailoring을 문서화해야 한다.
- NFC/NFD는 canonical equivalence를 다루고, NFKC/NFKD는 compatibility distinction을 없앨 수 있다. compatibility form을 원문 보존, 식별자, 수식, 보안-sensitive field에 적용할지는 별도의 domain policy가 필요하다.
- auto-detection만으로 모든 byte 열의 encoding을 신뢰성 있게 알아낼 수 있는 보편 규칙은 없다. producer가 charset을 선언하지 않으면 guess·reject·사용자 확인 중 어느 정책을 썼는지 남긴다.
- byte fallback 또는 unknown token 처리는 해당 tokenizer의 구성 기능이다. 임의 입력을 ID 열로 만들 수 있어도 원문 의미 보존, 언어별 동등한 token 비용, 모델의 올바른 해석을 보장하지 않는다.
- 이 owner는 text representation까지만 다룬다. JSON parsing, schema validation, semantic validation, authentication·authorization, 외부 실행과 그 복구 계약은 다음 `문자에서 실행 권한까지` 연결과 도구 사용 문서가 맡는다.
