# 실시간 멀티모달 상호작용

> [!note] 학습 안내
> **난이도:** 중급<br>
> **선수 지식:** [[concept.멀티모달-대규모-언어-모델|멀티모달 대규모 언어 모델]]<br>
> **읽고 나면:** 끊임없이 도착하는 음성·영상·text를 다룰 때 media clock, frame·chunk·packet·token·turn, buffer·backpressure, interrupt·cancel, A/V sync와 복구가 왜 서로 다른 계약인지 설명하고 측정 장부를 만들 수 있다.

## 1단계 — 먼저 잡을 핵심

### 실시간은 model 이름이 아니라 시간 있는 실행 계약이다

**실시간 멀티모달 상호작용**은 시간표가 붙은 음성·영상·text·센서 입력이 계속 도착하는 동안, system이 현재 대화 상태를 보존하고 점진적 출력을 재생·표시하며 사용자의 새 입력과 중단을 처리하는 **runtime 계약**이다. 여기서 필요한 것은 빠른 model 하나만이 아니다. 무엇을 언제 받았는지, 어느 출력이 어느 입력 turn에 속하는지, 늦은 data를 어떻게 다루는지, 사용자가 끼어들면 어디까지 멈출 수 있는지를 함께 정해야 한다.

그래서 [[멀티모달 대규모 언어 모델]]의 encoder·bridge·shared core·training modality와 이 개념을 분리한다. Audio 또는 video를 입력받는 model은 있을 수 있지만, 그것만으로 capture clock, buffer, A/V presentation, turn policy, reconnect, cancel의 약속이 생기지는 않는다. 반대로 여러 model·codec·renderer를 쓰는 system도 이 runtime 계약을 잘 지킬 수 있다.

### 다섯 단위는 같은 ‘조각’이 아니다

| 단위 | 무엇을 뜻하는가 | 보통 누가 정하는가 | 자동으로 같지 않은 것 |
| --- | --- | --- | --- |
| media frame | 일정 sample 구간의 audio 또는 한 장의 video처럼 capture·presentation에 쓰는 media 단위 | capture device·codec·renderer | transport packet, model token |
| encoded chunk | codec이 압축해 만든 연속 data 조각 | codec·muxer | 원본 frame 하나, network packet 하나 |
| transport packet | network로 보내는 순서·timestamp·주소가 붙은 전달 단위 | transport protocol·network stack | codec chunk, 대화 turn |
| model input/output chunk 또는 token | model이 한 번에 소비·생성하는 text/embedding/audio 표현 단위 | model·runtime | media 시간 또는 사용자의 발화권 |
| conversation turn | 누가 말할 차례인지, 어느 입력까지를 하나의 의도로 볼지 정한 대화 상태 단위 | turn policy·application | 침묵 한 구간, VAD flag |

한 audio frame을 여러 packet으로 나눌 수도 있고, packet 하나가 여러 sample을 실을 수도 있다. Model은 여러 frame을 모아 한 번에 추론하거나, text token을 먼저 내고 audio를 나중에 합성할 수 있다. 따라서 `packet = frame = token = turn`이라고 가정하면 늦은 packet, 쪼개진 출력, 끼어들기에서 소속을 잃는다.

### 가장 작은 시간 예

48 kHz mono PCM을 20 ms씩 capture하면 한 media frame에는 $48{,}000\times0.020=960$ sample이 있다. 30 fps video라면 한 frame 간격은 약 33.3 ms다. 이 숫자는 설명용 설정일 뿐, 모든 product의 고정 chunk 크기나 지연 목표가 아니다.

어떤 audio frame이 media time 120 ms를 가리켜도 network arrival time은 155 ms일 수 있다. 다음 frame이 먼저 도착할 수도 있다. 화면에 이미 출력한 model token의 순서도 이 두 시간과 다를 수 있다. 실시간 system은 이 서로 다른 순서를 하나의 정렬 기준처럼 쓰지 않고, 각각의 이름과 mapping을 보존한다.

## 2단계 — 작동 원리

### 시간축과 상태축을 따로 둔다

| 축 | 답하는 질문 | 잘못 섞으면 생기는 오류 |
| --- | --- | --- |
| media clock | 소리·영상이 capture 또는 presentation에서 언제여야 하는가? | 늦게 도착한 정상 frame을 새 입력으로 오해한다. |
| reference 또는 wall clock | 서로 다른 track·device·log를 어느 공통 기준에 대응시킬 수 있는가? | A/V 차이를 arrival time만으로 판단한다. |
| arrival·order | packet 또는 event가 이 process에 언제·어떤 순서로 들어왔는가? | network 지연을 media 시간 변화로 읽는다. |
| model·dialogue state | 어느 session·turn·output epoch·생성 revision에 속하는가? | 이전 turn의 늦은 출력이 현재 답처럼 재생된다. |

RTP는 sequence number와 timestamp로 source timing을 재구성하도록 하고, audio·video가 별도 RTP session이어도 RTCP timing information으로 synchronized playback을 할 수 있다고 설명한다. RFC 7273은 media clock과 reference clock signalling을 더 명시적으로 다룬다. 이것은 RTP 계열의 설계 범위이지 모든 LLM product가 RTP를 써야 한다는 명령은 아니다. 핵심은 **도착 순서만으로 presentation 시간을 정하지 말라**는 분리다.

### 입력과 출력은 서로 다른 두 흐름이다

한 가능한 흐름을 다음처럼 읽을 수 있다.

```text
capture → timestamp/frame → encode/chunk → transport → receive/jitter buffer
        → decode → VAD → turn policy → model context/inference

model delta → text/audio/video render preparation → playout buffer → presentation
```

입력 쪽 buffer는 network jitter와 decode의 변동을 흡수한다. 출력 쪽 buffer는 model delta가 들쭉날쭉해도 speaker·screen이 끊기지 않게 돕는다. 어느 buffer든 무한정 늘리면 delay와 메모리가 늘고, 너무 줄이면 late frame·underflow·끊김이 늘 수 있다. RFC 3611은 packet loss·discard, end-system delay와 jitter-buffer의 nominal·maximum delay·parameter를 따로 보고할 수 있게 한다. Underflow·overflow는 application이 자체적으로 기록할 수 있는 운영 지표다. 즉, “buffer가 있다”는 말만으로 좋은 지연이나 좋은 품질을 뜻하지 않는다.

### VAD는 말소리 탐지이고 turn detection은 대화 결정이다

[[음성 활동 감지]]는 audio 구간에 음성이 있는지의 신호를 만든다. RFC 6464의 V bit도 audio level과 함께 voice activity의 힌트를 실을 뿐, 사용자가 발화를 끝냈는지 또는 system이 발화권을 넘겨야 하는지를 정하지 않는다.

**turn detection**은 그 힌트에 partial transcript, 문장·질문 완결성, 상대의 현재 출력, 사용자의 barge-in policy, silence window를 더해 “지금 model에 응답을 시작시킬까, 기다릴까, backchannel만 낼까”를 결정한다. Chiba와 Higashinaka의 incremental processing·voice activity projection 비교도 partial ASR 처리와 turn 판단이 구별되는 층임을 보여 준다. 어느 한 detector가 모든 언어·소음·사용 습관에 최선이라는 뜻은 아니다.

### Backpressure는 늦어졌다는 관측을 행동으로 바꾸는 계약이다

capture, encode, network, inference, synthesis, rendering 중 하나가 느려지면 queue가 쌓인다. WHATWG Streams의 backpressure는 consumer의 capacity가 producer에 전달되어 producer가 high-water mark를 넘지 않게 조절하는 추상화다. media system에서는 그 신호 뒤에 **무엇을 버리거나 늦출지**를 명시해야 한다.

| 선택 | 무엇을 보존하는가 | 무엇을 잃을 수 있는가 | 기록할 상태 |
| --- | --- | --- | --- |
| throttle | 모든 data를 유지하려는 시도 | 최신성·응답성 | queue depth, target rate |
| drop stale media | 현재성 | 빠진 audio/video 구간 | dropped frame range와 이유 |
| coalesce | 최근 상태·요약 | 중간 delta의 세부 | merged input/output IDs |
| lower quality | 흐름의 연속성 | 해상도·bitrate·음질 | 적용한 profile·시각 |
| cancel | 새 요청 또는 사용자의 새 발화 | 아직 끝나지 않은 generation | cancel request·acknowledgement·잔여 buffer |

WebRTC의 `bufferedAmount`와 jitter-buffer target 같은 API도 queue를 관측하거나 target을 정하는 browser 범위의 도구다. OS, network, renderer와 model queue 전체를 자동으로 측정하거나 최적화하지는 않는다.

### Interrupt와 cancel은 한 개의 완료 event가 아니다

사용자가 system이 말하는 중에 새로 말하기 시작했다고 하자. `cancel`은 적어도 다음 사실을 분리해 기록해야 한다.

| 질문 | 가능한 상태 | 왜 분리하는가 |
| --- | --- | --- |
| future generation을 멈추라는 요청을 보냈는가? | `cancel_requested` | 요청 송신은 model이 멈췄다는 증거가 아니다. |
| model 또는 synthesizer가 더 만들지 않기로 했는가? | `generation_stopped` 또는 `cancel_acknowledged` | 이미 만든 delta와 새 delta를 구분한다. |
| 아직 재생하지 않은 local/remote output buffer를 비웠는가? | `queued_media_discarded` | 생성 중단만으로 queued audio가 사라지지 않을 수 있다. |
| 사용자가 이미 들었거나 화면에 본 output을 되돌릴 수 있는가? | 보통 불가능 | presentation은 외부 세계에 발생한 뒤 rollback되지 않는다. |

OpenAI Realtime API의 `response.cancel`, `conversation.item.truncate`, `output_audio_buffer.clear`는 이 층들을 나누어 다루는 한 product-level event contract의 예다. 다른 API가 같은 event 이름·순서·보장을 가진다는 뜻은 아니다. 취소가 tool call의 외부 효과를 되돌리는 것도 아니다. 이미 실행된 write의 committed·failed·unknown과 compensation은 [[함수 호출과 도구 사용]]의 owner가 맡는다.

### Full-duplex는 동시 전송과 동시 대화 능력을 구분해야 한다

WebRTC 같은 interface에서 양방향 media를 보내는 `sendrecv` 상태는 **양방향 전송 상태**다. Model이 사용자 음성을 계속 조건으로 읽으면서 자연스러운 backchannel·overlap·interruption을 처리하는 것은 **대화적 full-duplex**다. Moshi는 병렬 user·system speech stream을 model에 두는 한 구현 방향을 제시하지만, pipeline VAD/ASR/TTS의 중단·겹침 한계와 모든 배포 환경의 해법을 확정하지 않는다.

따라서 UI가 microphone input과 speaker output을 동시에 켠다고 해도 model execution이 무제한으로 동시 실행되거나, 어떤 overlap도 안전하게 이해한다는 뜻은 아니다. session별 concurrency, output epoch, GPU·codec resource, 우선순위와 interruption policy를 별도로 정한다.

### 일곱 경계 장부

| 지표·평가 기준 | capture-to-first presentation, steady cadence, p50/p95/p99, jitter·late discard·under/overflow, A/V offset, interruption·recovery 성공률을 같은 분모와 window로 기록한다. |
| 실패·복구 경계 | packet loss·reorder, decoder failure, VAD/turn 오류, queue saturation, stale output, cancellation race, reconnect를 어느 ID·epoch·authority로 정리하는지 적는다. |
| 권한·책임·출처 추적 | capture permission·track origin·session·model/prompt/codec/policy revision·cancel actor·event trace를 남기고, data의 장기 보관·동의·재사용은 [[학습 데이터 생애주기와 출처 추적]]의 더 넓은 owner와 연결한다. |

이 장부는 하나의 framework를 강제하지 않는다. 다만 “빠른 음성 AI”라는 결과를 재현하려면 input, clock, policy, output, failure boundary를 빠뜨리지 않게 한다.

### 지연과 동기는 출발·도착점을 명시해야 한다

예를 들어 first output latency를 다음처럼 쓸 수 있다.

$$
L_{\mathrm{capture\rightarrow first}}
=t_{\mathrm{first\_presented}}-t_{\mathrm{capture\_reference}}
$$

$L_{\mathrm{capture\rightarrow first}}$는 정한 capture 기준점에서 처음 presentation까지의 지연이다. 두 $t$는 같은 reference clock 또는 공개한 clock mapping 위에서 재야 한다. $t_{\mathrm{capture\_reference}}$는 첫 음성 sample 시각인지, turn detector가 발화 종료로 판단한 시각인지, button을 누른 시각인지 먼저 정해야 한다. $t_{\mathrm{first\_presented}}$도 server가 `delta`를 보낸 시각이 아니라 사용자의 speaker·screen에 처음 **presentation**된 시각으로 정할지 명시한다. 같은 이름의 “latency”라도 이 두 기준이 바뀌면 수치가 달라진다.

A/V presentation offset은 공통 reference에 mapping한 뒤 다음처럼 기록할 수 있다.

$$
\Delta_{AV}=t_{\mathrm{audio\_presented}}-t_{\mathrm{video\_presented}}
$$

$\Delta_{AV}>0$이면 이 정의에서는 audio가 video보다 나중에 presentation됐다는 뜻이다. $\Delta_{AV}=0$에 가까운지가 항상 최선이라는 뜻도, 모든 application에 같은 허용 오차가 있다는 뜻도 아니다. content·device·accessibility·measurement path에 맞는 target과 측정 방법을 공개해야 한다. RFC 3550·7273은 RTP 시간 mapping의 근거를 제공하지만 UX의 보편 SLO를 정하지 않는다.

| 평가 층 | 함께 볼 측정값 | 단독으로 놓치기 쉬운 것 |
| --- | --- | --- |
| capture·transport | frame loss, packet reorder, jitter, late discard, input buffer depth | 사용자가 실제로 답을 들었는가 |
| inference·generation | turn-decision latency, first delta, delta cadence, cancellation acknowledgement | renderer의 playout queue와 A/V alignment |
| presentation | first perceptible output, playout underflow, A/V offset, stale output rate | model이 실제 요청 내용을 이해했는가 |
| dialogue | barge-in 처리율, false/late turn transfer, overlap·backchannel quality | network·codec 특정 원인 |
| recovery | reconnect time, state revalidation rate, duplicate/stale event rejection | 이전 session이 자동 복구됐다는 가정 |

Full-Duplex-Bench는 pause·backchannel·turn-taking·interruption을 분리한 평가축의 한 예다. Benchmark score는 실제 사용자의 만족, 대역폭·device 다양성, privacy, 외부 effect의 안전성을 모두 대변하지 않는다.

### 하나의 interrupt trace를 끝까지 적어 본다

설명용 session `s-17`에서 assistant output `turn=51, epoch=4`가 speaker queue에 있다고 하자. 사용자가 새로 말하면 microphone track `mic-2`의 frame은 media timestamp와 sequence를 붙여 들어온다. VAD가 음성을 알린 뒤 turn policy가 그것을 barge-in으로 판정할 수 있다. 그때 controller는 `cancel_requested(s-17, turn=51, epoch=4)`를 기록한다.

그 다음에는 (1) model/synthesizer가 `epoch=4`의 새 delta를 중단했는지, (2) 아직 재생되지 않은 `epoch=4` media가 queue에서 제거됐는지, (3) 이미 speaker에 나온 부분이 얼마인지, (4) 새 user input이 `turn=52`로 확정됐는지를 따로 event로 남긴다. 늦게 도착한 `epoch=4` packet은 새 `turn=52`의 output으로 재생하지 않는다. reconnect 뒤에도 이전 turn·permission·track·sequence가 그대로 유효하다고 추정하지 않고, authority가 정한 resume 또는 fresh-session 절차로 다시 확인한다.

이 trace는 product의 유일한 event 이름이나 implementation 순서가 아니다. 핵심은 **취소 요청, 생성 중단, queue 정리, 이미 지각된 결과, 새 turn 확정**을 한 성공/실패 bit로 접지 않는 것이다.

### 다른 owner와의 책임 경계

- [[멀티모달 대규모 언어 모델]]은 encoder·bridge·fusion·training modality와 model I/O를 맡는다. 이 문서는 그 model을 어떤 clock·buffer·turn policy로 운용하는지를 맡는다.
- [[언어 모델 추론 서빙]]은 text token의 prefill·decode·KV cache·batching·tail을 맡는다. Audio/video packet과 presentation clock 전체를 그 문서의 token latency로 환원하지 않는다.
- [[음성 활동 감지]]와 [[자동 음성 인식]]은 signal 구분과 speech-to-text 경로를 맡는다. 이 문서는 VAD/ASR 결과가 turn policy와 incremental interaction 안에서 어떤 상태가 되는지 다룬다.
- [[음성을 텍스트로 옮기는 경계에서 무엇이 사라지는가 — 인식·합성·네이티브 오디오]]는 ASR→text model→TTS와 native audio model의 표현·평가 경계를 비교한다. 이 owner는 그 어느 경로든 실시간으로 실행할 때의 clock·buffer·cancel 계약을 맡는다.
- [[함수 호출과 도구 사용]]은 외부 side effect의 authorization·confirmation·commit·unknown reconciliation을 맡는다. Audio output cancel은 이미 실행된 외부 action의 rollback이 아니다.

## 검증과 한계

### 자주 생기는 범주 오류

- **Model이 audio/video를 받으니 실시간 system이다:** model I/O는 capture·network·render·interrupt의 시간 계약을 정하지 않는다.
- **도착 순서가 media 순서다:** packet arrival은 network 상황을 반영하며 source timestamp·presentation mapping과 다르다.
- **VAD가 false가 되면 turn이 끝났다:** VAD는 음성 활동 신호이고, turn transfer는 context와 policy를 포함한 대화 결정이다.
- **Full-duplex transport면 model도 자연스럽게 동시 대화한다:** 양방향 전송, 동시 model execution, overlap 이해는 서로 다른 능력이다.
- **`cancelled` event면 사용자가 아무것도 듣지 못했다:** future generation, queued media, 이미 presentation된 결과는 다른 상태다.
- **A/V sync에는 보편적인 고정 ms 기준이 있다:** clock source·content·device·measurement point를 정하지 않으면 같은 수치를 비교할 수 없다.
- **Reconnect가 성공하면 이전 대화 상태도 복구됐다:** transport 연결, authentication, track permission, turn context, output epoch의 복구는 각각 확인해야 한다.

### 근거의 적용 범위

RTP·RTCP RFC는 media timestamp, packet, clock mapping과 보고 형식을 제공하지만 LLM turn policy·model chunk size·사용자 경험의 SLO를 정하지 않는다. WHATWG Streams와 WebRTC API는 browser/웹 runtime의 추상화 또는 interface다. OpenAI Realtime API reference는 특정 product의 rolling event contract이며 2026-07-25에 확인한 예시이지 보편 protocol이 아니다.

Moshi와 Full-Duplex-Bench의 결과도 특정 model·dataset·benchmark 설정에 묶여 있다. 이 문서는 약 200 ms 같은 연구 수치를 모든 service의 필수 목표로 삼지 않는다. 실시간 서비스의 지연·동기·privacy·accessibility·안전 목표는 product, network, device와 사용자 과업에 맞춰 별도 계약으로 정해야 한다.
