# 긴 문맥 언어 모델

> [!note] 학습 안내
> **난이도:** 심화<br>
> **선수 지식:** [[Transformer]], [[검색 증강 생성]]<br>
> **읽고 나면:** 긴 문맥 언어 모델의 입력 한도·계산 경로·위치 처리·정보 접근·추론 품질을 분리하고, 같은 최대 길이를 가진 모델도 유효 활용 능력이 다른 이유를 설명할 수 있다.

## 1단계 — 먼저 잡을 핵심

### 한 문장 정의

**긴 문맥 언어 모델(long-context language model)**은 일반적인 짧은 입력보다 훨씬 긴 token sequence를 한 요청이나 연속 상태 안에서 처리하도록 설계·학습·배포된 언어 모델이다. `긴 문맥`은 단일 architecture 이름이 아니라 입력 용량과 장거리 정보 활용을 다루는 모델·runtime·평가의 묶음이다.

### 길이 숫자 하나를 여섯 축으로 나눈다

| 축 | 묻는 질문 | 대표 측정 |
|---|---|---|
| 명목 입력 한도 | API·configuration이 몇 token을 허용하는가? | 최대 input·input+output token, truncation 규칙 |
| 학습·평가 길이 | Model이 어느 길이의 자료를 실제로 학습·시험했는가? | Training curriculum, position scaling, 평가 구간 |
| 연결 범위 | 한 위치가 다른 위치에 어떤 경로로 접근하는가? | Dense·sparse attention, recurrence, external retrieval |
| 계산·memory | 긴 입력을 어느 비용으로 prefill·저장하는가? | FLOPs, HBM I/O, device 수, latency, KV cache |
| 정보 접근 | 필요한 항목을 위치·개수별로 찾는가? | Single/multi-needle recall, multi-hop tracing, aggregation |
| 답변 품질 | 찾은 증거를 정확히 결합하고 인용하는가? | QA·reasoning·summarization·citation 정확도 |

‘1M context’는 첫 축의 사양일 수 있다. 나머지 다섯 축을 측정하지 않으면 100만 토큰 전체를 이해한다는 결론을 낼 수 없다.

### 왜 중요한가

긴 창은 여러 장·여러 파일·긴 대화를 한 입력에 함께 둘 수 있어 구간 분할 전에 사라지던 관계를 보존할 가능성을 높인다. 그러나 입력이 길수록 비용·잡음·위치 편향·정보 접근 실패와 데이터 노출 범위도 커진다. 그래서 이 개념의 핵심은 ‘더 많이 넣는다’가 아니라 **더 긴 입력에서 어떤 정보가 어떤 비용과 정확도로 실제 답에 도달하는지** 추적하는 데 있다.

## 2단계 — 작동 원리

### 입력에서 출력까지의 다섯 단계

1. **입력 구성:** 원문·검색 결과·대화 기록을 token sequence로 만들고 최대 길이·출력 예약 공간에 맞춘다.
2. **Prefill:** 모델이 입력 전체를 통과하며 attention과 layer state를 계산하고 생성용 KV cache를 만든다.
3. **장거리 접근:** Dense·sparse attention, recurrent memory 또는 외부 retrieval 경로로 관련 위치에 도달한다.
4. **선택과 결합:** 질문에 필요한 여러 항목을 구분·집계하고 관계와 모순을 해석한다.
5. **생성과 근거화:** 답을 순차 생성하면서 원자료의 주장·위치와 일치하는지 유지한다.

각 단계는 독립적인 실패 지점을 만든다. 입력이 잘리지 않았어도 attention이 필요한 위치를 충분히 활용하지 못할 수 있고, 관련 구간을 찾았어도 여러 사실을 잘못 결합할 수 있다. 정확한 답이 나와도 citation이 실제 근거 위치와 맞지 않을 수 있다.

### 계산 경로는 하나가 아니다

표준 dense self-attention은 모든 token pair의 score를 계산해 길이 $N$에 대해 대체로 $O(N^2d)$ 산술량을 갖는다. 구현에 따라 중간 memory와 I/O는 달라진다. [[FlashAttention]]은 exact dense operator를 타일링해 큰 attention matrix의 물질화와 HBM 왕복을 줄이지만 pairwise 산술량은 남는다.

다른 경로는 다른 trade-off를 만든다.

- **분산 exact attention:** RingAttention처럼 각 장치가 query block을 유지하고 key·value block을 링으로 순환시키며, 장치별 activation memory를 block size에 묶은 채 장치 수에 비례해 전체 처리 sequence를 늘린다.
- **Sparse/local attention:** 일부 연결만 계산해 비용을 줄이지만 먼 위치 사이의 직접 경로를 제한한다.
- **Recurrent memory:** [[Transformer-XL]]처럼 과거 segment의 유한 상태를 재사용해 한 번의 거대한 창과 다른 방식으로 의존 범위를 늘린다.
- **외부 retrieval:** [[검색 증강 생성|RAG]]처럼 모델 밖에서 관련 passage를 먼저 골라 내부 입력을 줄인다.
- **압축 memory:** 과거 정보를 고정 크기 또는 요약 표현으로 누적해 세부 보존과 장기 범위를 교환한다.

### 위치와 학습 길이를 함께 맞춘다

Model이 위치 1K까지 학습됐다고 해서 position encoding만 바꾸면 임의의 길이에 안정적으로 일반화하는 것은 아니다. 위치 간 phase·bias, attention logit 분포, 장거리 자료와 최적화가 함께 달라진다. LWM은 Llama 2 7B의 RoPE scaling과 장문 자료, 32K→128K→256K→512K→1M 단계를 결합했다.

이 때문에 학습 길이, 실제 evaluation 길이와 product limit을 따로 기록한다. 10M에서 합성 retrieval을 시험했다는 사실은 10M product 창이나 모든 실제 과제의 10M 이해를 뜻하지 않는다.

## 3단계 — 기술과 근거

### 2024년 100만 토큰 사례가 보여 준 차이

LWM은 공개 7B model에서 RingAttention·FlashAttention·RoPE scaling과 점진적 context extension을 문서화했다. RingAttention은 sequence와 activation을 장치에 분산하고 key·value 전송을 block 계산과 겹치며, local FlashAttention은 attention matrix materialization과 HBM I/O를 줄인다. Llama 2 7B(4K)에서 초기화한 뒤 32K→128K→256K→512K→1M의 다섯 stage를 거쳤고, single needle에는 강했지만 multi-needle 수와 난도가 커지면 성능이 낮아졌다.

Gemini 1.5 Pro는 2024년 2월 표준 128K와 제한 고객용 1M private preview로 발표됐다. Technical report는 sparse MoE Transformer와 architecture·data·optimization·systems 전반의 변경을 밝혔지만 구체적인 long-context attention·position·memory recipe는 공개하지 않았다. 같은 1M 숫자만으로 LWM의 구현을 Gemini에 귀속할 수 없다.

### 명목 창과 유효 창의 평가 사다리

평가를 쉬운 순서에서 어려운 순서로 놓으면 다음과 같다.

1. **Truncation 확인:** 입력 끝의 marker가 실제 model input에 들어갔는가?
2. **Single retrieval:** 한 개의 눈에 띄는 key–value나 문장을 위치별로 찾는가?
3. **Multiple retrieval:** 여러 항목을 빠짐없이 구분해 회수하는가?
4. **Aggregation·tracing:** 여러 위치의 값과 단계를 집계하거나 따라가는가?
5. **문서 과제:** 긴 QA·요약·code 분석에서 내용과 관계를 보존하는가?
6. **Grounding:** 답의 각 주장을 정확한 source span에 연결하는가?

Gemini 1.5 v1은 single needle에서 1M까지 99.7%를 넘었다. 100개의 needle을 한 번에 회수할 때는 128K까지 약 70%, 1M까지 60%를 넘는 recall을 유지했다. RULER의 17-model main evaluation에서는 거의 모든 모델이 길이 증가에 따라 저하했고, 별도의 Yi-34B 분석에서는 task complexity 증가에도 큰 저하가 나타났다. 이 사다리에서 어느 단계까지 통과했는지 말해야 ‘유효하다’는 표현의 의미가 분명해진다.

### 위치 편향은 별도 평가 축이다

*Lost in the Middle*은 multi-document QA와 key–value retrieval에서 관련 정보의 위치를 바꿨다. 대표 결과는 시작과 끝에서 높고 가운데에서 낮은 U자형 성능이었다. Long-context를 표방한 model도 문맥 전 위치를 균일하게 사용하지 못할 수 있음을 보여 준다.

이는 모든 새 모델이 반드시 같은 모양을 보인다는 뜻이 아니다. Model·task·prompt·정보 수에 따라 달라질 수 있으므로 시작·중간·끝과 여러 길이를 교차해 평가해야 한다.

### 긴 문맥과 RAG는 경쟁하면서 보완한다

| 경로 | 먼저 줄이는 것 | 대표 실패 | 유리한 조건 |
|---|---|---|---|
| 긴 문맥 | 분할·검색 전에 버리는 원자료 | Prefill 비용, 내부 retrieval·reasoning 실패, 잡음 | 자료가 한정돼 있고 여러 구간의 관계를 함께 읽어야 할 때 |
| RAG | Model 내부에 넣는 후보 수 | Retriever 누락, 잘못된 ranking, passage 경계 손실 | Corpus가 크고 자주 바뀌며 source·권한 filtering이 필요할 때 |
| 결합 | Retrieval로 후보를 줄인 뒤 긴 창으로 함께 읽음 | 두 단계의 오류가 연쇄될 수 있음 | 여러 회수 문서의 비교·종합과 비용 통제가 모두 필요할 때 |

Gemini 1.5의 *Les Misérables* 실험은 Gemini 1.0 Ultra로 100문항을 생성한 뒤 cycle consistency와 사람 검토로 걸렀다. 같은 Gemini 1.5 Pro의 710K 전체 문맥과 4K TF-IDF 검색 문맥은 AutoAIS 91.4 대 84.8, human AIS $80.0\pm1.0$ 대 $78.2\pm1.4$였다. 사람 평가 차이는 작고 한 권·100문항이라는 조건을 가지므로, 특정 전체 문맥 실험의 수치 우위를 모든 RAG architecture의 불필요성으로 일반화하지 않는다.

## 검증과 한계

### 흔한 오해

| 오해 | 더 정확한 설명 |
|---|---|
| 최대 창이 1M이면 1M 전체를 이해한다. | 최대 입력 허용과 정보 접근·추론·근거화는 별도 능력이다. |
| 긴 문맥 모델은 모두 효율적 attention·계층 memory·재귀 retrieval을 쓴다. | Model별 공개 stack이 다르고 일부 상용 구현은 구체 recipe를 공개하지 않는다. |
| FlashAttention이 attention FLOPs를 선형으로 만들었다. | Exact dense attention의 추가 저장과 HBM I/O를 줄이지만 $O(N^2d)$ 산술량은 남는다. |
| RoPE나 ALiBi면 학습 없이 임의 길이로 외삽한다. | Position 조정, 실제 장문 학습과 목표 길이별 평가가 함께 필요하다. |
| Single needle 99%면 전체 책을 이해한다. | 여러 정보 회수·집계·추론·citation은 더 강한 별도 과제다. |
| 긴 창은 RAG·chunking·요약을 없앤다. | 비용·최신성·권한·provenance와 검색 누락의 trade-off 때문에 결합할 수 있다. |

### 적용 한계

유효 문맥 길이는 model의 영구 속성 하나가 아니라 model version·task·prompt·정보 위치·needle 수·output format·runtime 조건의 함수다. Benchmark 길이를 API 배포 상태로, product limit을 실제 업무 정확도로, 한 model의 구현을 model군 전체의 architecture로 옮기지 않는다.

긴 입력은 input pricing, time-to-first-token, memory와 KV cache를 늘리고 민감 정보·prompt injection에 노출되는 표면도 넓힌다. 법률·의료·금융·전체 codebase 같은 응용은 별도의 domain dataset, 오류 비용, access control, citation과 human review 기준으로 검증해야 한다.
