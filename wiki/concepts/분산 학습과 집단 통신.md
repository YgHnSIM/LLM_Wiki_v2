# 분산 학습과 집단 통신

> [!note] 학습 안내
> **난이도:** 중급<br>
> **선수 지식:** [[concept.accelerator-matrix-compute|가속기와 행렬 계산]], [[concept.memory-hierarchy-data-movement|메모리 계층과 데이터 이동]]<br>
> **읽고 나면:** data·tensor·pipeline·expert parallelism과 state sharding을 “GPU를 많이 쓴다”로 합치지 않고, 각 방식이 무엇을 복제·분할하며 어떤 collective communication과 품질·memory 조건을 남기는지 설명할 수 있다.

## 1단계 — 먼저 잡을 핵심

### 장치를 늘리면 계산과 함께 통신도 늘어난다

모델이 한 accelerator의 memory에 들어가지 않거나 원하는 시간 안에 학습이 끝나지 않으면 계산과 상태를 여러 장치에 나눈다. 그러나 장치 수 $p$를 두 배로 늘린다고 시간이 자동으로 절반이 되지는 않는다. 각 장치가 맡은 계산이 줄어드는 동안 weight·activation·gradient를 교환하고 동기화하는 시간이 생기며, 가장 느린 장치를 기다릴 수도 있다.

분산 학습의 첫 질문은 “몇 개 GPU인가?”가 아니라 다음 세 가지다.

1. **무엇을 나누는가:** batch, tensor 차원, layer, expert, optimizer state
2. **언제 무엇을 교환하는가:** forward, backward, optimizer step의 어느 지점에서 어떤 tensor를 보내는가
3. **무엇을 같게 유지하는가:** global batch, model 수학, precision, optimizer와 품질 목표

같은 384개 GPU도 384개의 완전한 model replica를 쓰는지, 한 model을 여러 GPU에 쪼개는지에 따라 memory와 network 장부가 다르다.

### 집단 통신은 여러 장치의 공동 연산이다

**Collective communication**은 참여 장치 집합이 tensor를 함께 교환·결합하는 연산이다.

| Collective | 입력과 출력의 직관 | 대표 용도 |
| --- | --- | --- |
| broadcast | 한 장치의 값을 모두에게 보낸다. | 초기 parameter·설정 배포 |
| AllReduce | 각 장치 값을 합·평균해 모두가 결과를 받는다. | data-parallel gradient 동기화 |
| AllGather | 각자 가진 shard를 모아 모두가 전체를 얻는다. | sharded parameter·activation 재구성 |
| ReduceScatter | 합친 결과를 shard로 나눠 각자 받는다. | gradient 합산과 분산 저장 결합 |
| AllToAll | 각 장치가 목적지별 조각을 서로 보낸다. | MoE token을 expert 장치로 dispatch |

Collective 이름만으로 비용이 정해지지는 않는다. Tensor byte, 장치 수, topology, link bandwidth·latency, overlap과 구현이 함께 필요하다.

## 2단계 — 작동 원리

### Data parallelism은 batch를 나눈다

두 장치가 같은 parameter $\theta$를 복제하고 서로 다른 mini-batch $B_1,B_2$를 처리한다고 하자. 각 장치는 local gradient

$$
g_1=\nabla_\theta L(B_1;\theta),\qquad
g_2=\nabla_\theta L(B_2;\theta)
$$

를 계산한다. Global batch 평균 gradient는

$$
g=\frac{|B_1|g_1+|B_2|g_2}{|B_1|+|B_2|}
$$

이며, batch 크기가 같으면 $(g_1+g_2)/2$다. AllReduce로 같은 $g$를 얻은 뒤 모든 replica가 같은 update를 적용한다.

이 방식은 한 장치당 activation 계산을 줄이지만 각 장치에 model weight를 복제한다. Model 자체가 한 장치 memory에 들어가지 않으면 data parallelism만으로 해결되지 않는다. Global batch를 장치 수와 함께 늘리면 optimization dynamics가 바뀔 수 있으므로 learning-rate·warmup과 품질을 다시 확인해야 한다.

### Tensor parallelism은 한 layer 안의 행렬을 나눈다

Megatron-LM은 Transformer MLP와 attention의 행렬곱을 열 또는 행 차원으로 나누는 intra-layer model parallelism을 제시했다. 예를 들어 $Y=XW$에서 $W$의 열을 두 장치가 나누면

$$
W=[W_1\;W_2],\qquad
Y=[XW_1\;XW_2]
$$

처럼 각 장치가 출력 feature 일부를 계산할 수 있다. 다음 연산이 전체 $Y$를 필요로 하면 AllGather가 필요하고, 행 분할의 부분합은 AllReduce가 필요할 수 있다.

한 장치의 weight·activation 부담은 줄지만 layer마다 collective가 반복된다. 작은 tensor나 느린 link에서는 통신 latency가 계산 이득을 삼킬 수 있다. 논문의 8.3B GPT-like model과 512-GPU 결과는 특정 V100 cluster·model·parallel 구성의 측정이며 모든 규모의 효율을 보장하지 않는다.

### Pipeline parallelism은 layer 구간을 나눈다

Layer 1–10은 장치 A, 11–20은 장치 B처럼 연속 구간을 나누고 activation을 다음 stage로 보낸다. 한 batch 전체를 기다리면 B가 놀기 때문에 mini-batch를 microbatch로 쪼개 여러 batch의 forward·backward를 겹친다.

Pipeline에는 stage가 일을 받기 전이나 backward를 기다리는 **bubble**이 생긴다. Stage별 계산량이 다르면 가장 느린 stage가 전체 속도를 제한한다. Microbatch를 늘리면 bubble 비중은 줄 수 있지만 activation memory와 global batch·optimizer 조건이 달라질 수 있다.

### ZeRO와 FSDP는 복제 상태를 shard한다

Data-parallel 학습은 각 replica가 parameter뿐 아니라 gradient와 optimizer state도 모두 저장할 수 있다. Adam 계열에서는 parameter 외에 gradient와 여러 state가 붙어 model weight보다 훨씬 많은 memory를 요구한다.

ZeRO는 단계적으로 optimizer state, gradient, parameter를 data-parallel rank에 분할한다. 필요한 계산 시점에 AllGather로 parameter shard를 모으고, ReduceScatter로 gradient를 합치며 다시 분할할 수 있다. 계산 수학을 바꾸지 않고 중복 memory를 줄이지만, parameter를 필요할 때 주고받는 통신과 schedule 복잡성이 늘어난다.

### 여러 축을 조합한다

BLOOM은 Megatron-DeepSpeed를 사용해 data·tensor·pipeline parallelism과 ZeRO를 조합했다. PaLM은 각 TPU v4 Pod 안에서 12-way model parallelism과 256-way fully sharded data parallelism을 쓰고, 두 Pod 사이를 2-way data parallel로 연결했다. “3D parallelism”이나 “FSDP”라는 이름보다 실제로 batch·layer·tensor·state 중 무엇을 어느 장치 집합에 나눴는지 확인해야 한다.

## 3단계 — 기술과 근거

### BLOOM 176B의 측정 장부

| 항목 | 기록 |
| --- | --- |
| 작업 | 176B decoder-only Transformer 사전학습 |
| 규모 | 366B 누적 token, 384개 A100 80GB, 48개 node |
| 결과 계약 | 논문의 language-model objective와 checkpoint·평가 |
| 시스템 경계 | Jean Zay cluster의 전체 분산 학습 |
| 고정 조건 | Megatron-DeepSpeed, data·tensor·pipeline parallelism과 ZeRO |
| 지표 | 약 3.5개월, 1,082,990 GPU-hours, 학습 loss·평가 |

GPU-hour는 장치 수와 시간을 곱한 자원량이지 end-to-end wall-clock과 같은 단위가 아니다. 384개 장치를 약 3.5개월 사용한 run에서 maintenance·중단·재시작과 실제 utilization을 단순 나눗셈 하나로 복원할 수 없다.

### PaLM 540B의 측정 장부

| 항목 | 기록 |
| --- | --- |
| 작업 | 540.35B dense decoder-only Transformer 사전학습 |
| 규모 | 780B token, TPU v4 6,144개와 host 1,536개 |
| 결과 계약 | causal LM objective와 논문별 downstream 평가 |
| 시스템 경계 | 두 TPU v4 Pod를 연결한 전체 학습 |
| 고정 조건 | Pod 내 12-way model parallel·256-way FSDP, Pod 간 2-way data parallel |
| 지표 | batch 2,048에서 238.3k token/s, model FLOPs utilization 46.2% |

PaLM은 pipeline parallelism을 사용하지 않았다. BLOOM의 3D parallel 구성을 PaLM에 복사하거나, TPU의 utilization과 A100 GPU-hour를 하나의 효율 순위로 나누지 않는다.

### 확장 효율을 읽는 최소 구분

$T_1$이 장치 하나의 시간, $T_p$가 $p$개 장치의 시간이라면 고정 문제에서 speedup과 parallel efficiency를

$$
S_p=\frac{T_1}{T_p},\qquad
E_p=\frac{S_p}{p}
$$

로 정의할 수 있다. 하지만 540B model처럼 장치 하나에 들어가지 않는 작업은 실제 $T_1$을 측정할 수 없다. 작은 model의 단일 장치 기준선에서 얻은 $E_p$와 큰 model의 weak scaling을 섞지 않는다.

Throughput이 늘어도 global batch와 총 token이 함께 늘었다면 같은 문제를 빨리 푼 것인지, 같은 시간에 더 큰 문제를 푼 것인지 구분해야 한다. 학습에서는 더 큰 batch가 같은 loss·downstream quality에 도달했는지도 결과 계약에 포함한다.

### 병렬 방식별 비용 장부

| 방식 | 주로 줄이는 것 | 새 통신·제약 |
| --- | --- | --- |
| Data parallel | 장치당 sample 계산 시간 | gradient AllReduce, model·state 복제, global batch |
| Tensor parallel | 장치당 layer weight·계산 | layer 내부 AllReduce·AllGather, 낮은 latency link 요구 |
| Pipeline parallel | 장치당 layer·weight | activation 전송, bubble, stage 균형 |
| State sharding | optimizer·gradient·parameter 중복 memory | 필요 시 AllGather·ReduceScatter와 schedule |
| Expert parallel | 장치당 활성 expert 계산·저장 배치 | token AllToAll, routing 불균형·capacity |

### CS_WIKI와 함께 읽기

[CS_WIKI의 「병렬 확장성」](https://yghnsim.github.io/CS_Wiki/concepts/%EB%B3%91%EB%A0%AC-%ED%99%95%EC%9E%A5%EC%84%B1/)은 고정 문제와 고정 시간의 확장을 구분한다. 현재 문서는 그 구분을 model·batch·state와 collective 통신에 적용한다. CS_WIKI 링크는 맥락 독서이며, BLOOM·PaLM 구성은 각 LLM 원 논문을 근거로 한다.

## 검증과 한계

- **직접 영향:** Megatron-LM은 Transformer layer를 나누는 tensor parallel 방식을 제시했고, ZeRO는 data-parallel state 복제를 분할하는 memory 최적화를 제시했다.
- **가능 조건:** BLOOM과 PaLM은 여러 병렬 축과 cluster를 실제 사용해 단일 장치에 들어가지 않는 model을 훈련했다. 장치 수가 model 품질을 직접 만들었다는 뜻은 아니다.
- **병행 맥락:** 일반 병렬 컴퓨팅의 speedup·efficiency 언어는 분산 학습을 해석하는 배경이지만, 모든 HPC 기법이 두 LLM 설계에 직접 영향을 주었다고 주장하지 않는다.
- **후대 유추:** 오늘날의 FSDP 구현 세부를 2020년 ZeRO나 2022년 PaLM 구성에 소급하지 않는다. 논문이 밝힌 state와 collective 범위만 사용한다.

동기식 학습은 느린 장치, network 장애와 재시작의 영향을 받는다. 이 문서는 fault tolerance·checkpoint storage·scheduler 전체를 설명하지 않으며, 통신 byte만으로 비용·전력·탄소를 자동 계산하지 않는다. 보안·프라이버시 때문에 data를 중앙에 모을 수 없는 federated learning도 별도 문제다.

## 학습 확인

1. Data parallelism과 tensor parallelism은 각각 batch와 weight의 어느 축을 나누며, 왜 model이 한 GPU에 들어가지 않을 때 전자만으로 부족한가?
2. ZeRO가 memory를 줄이면서 communication을 늘릴 수 있는 이유를 parameter·gradient·optimizer state와 AllGather·ReduceScatter로 설명하라.
3. 512개 GPU의 “76% scaling efficiency”와 6,144개 TPU의 “46.2% model FLOPs utilization”을 직접 비교할 수 없는 시스템 경계와 기준선을 적어라.
