# 구조화 출력

> [!note] 학습 안내
> **난이도:** 중급<br>
> **선수 지식:** [[자기회귀 생성]], [[파싱]]<br>
> **읽고 나면:** 자유 형식 생성·JSON mode·strict schema 출력을 구분하고, 제약 decoding과 사후 validation의 역할 및 schema에 맞는 오답이 생기는 이유를 설명할 수 있다.

## 1단계 — 먼저 잡을 핵심

### 정의

**구조화 출력(structured output)**은 언어 모델의 응답을 JSON 같은 기계 판독 형식 또는 선언된 schema에 맞춰 application data로 전달하는 interface다. 넓게는 prompt와 parser를 이용한 구조화도 포함할 수 있고, 좁게는 생성 단계에서 허용되는 token을 제한해 schema 준수를 보장하는 기능을 가리킨다. 어떤 의미로 쓰였는지 provider·model·option과 validation 경로를 함께 적는다.

구조화 출력이 강화하는 것은 **형식 계약**이다. 이 계약이 다음 관문을 합치지는 않는다.

```text
자유 형식 text
  → JSON 구문 유효성
  → schema 준수
  → field value의 의미·사실 검증
  → 인증·인가·승인
  → 외부 실행·결과 grounding
```

일반 데이터 추출은 대개 schema와 의미 검증까지 필요하다. [[함수 호출과 도구 사용|함수 호출]]은 여기에 외부 실행과 부작용 통제를 더한다.

### 세 가지 출력 방식을 구분한다

| 방식 | 생성 제약 | 보장 범위 | 대표 실패 |
| --- | --- | --- | --- |
| Prompt로 JSON 요청 | 보장 없음 | 잘 따를 가능성을 높임 | 설명 text·code fence·invalid JSON |
| JSON mode | JSON 구문 | 정상 완료 시 valid JSON object | field·type·required가 예상과 다름 |
| Strict schema output | 지원 schema 기반 constrained decoding | 정상 완료 시 지원되는 schema 구조 | schema-valid한 틀린 값·누락된 근거 |

2023년 11월 JSON mode와 2024년 8월 Structured Outputs는 연속된 형식 개선이지만 같은 보장이 아니다. Exact schema가 필요한 application에서 두 이름을 교환해 쓰지 않는다.

## 2단계 — 작동 원리

### 1. 출력 계약을 설계한다

Schema는 단순히 field 이름을 나열하는 문서가 아니다. 자료형, 필수 여부, 허용 enum, 배열과 중첩 object를 정하고 모호함과 결손을 표현하는 방법도 포함한다.

- 입력에 값이 없을 수 있으면 `null`, 빈 배열이나 명시적인 `unknown` 상태를 설계한다.
- 분류 범주가 겹치면 복수 후보·근거 span·불확실성 field가 필요한지 결정한다.
- 금액·날짜·단위처럼 cross-field rule이 있으면 JSON Schema 뒤의 domain validator를 둔다.
- Schema version과 consumer code의 호환성을 관리한다.

지나치게 느슨한 schema는 downstream code에 모호함을 넘기고, 지나치게 엄격한 schema는 model이 없는 정보를 억지로 채우게 할 수 있다.

### 2. 생성 가능한 token을 제한한다

OpenAI가 2024년에 설명한 구현은 JSON Schema를 [[문맥자유문법]]으로 전처리하고 cache한다. [[자기회귀 생성]]의 각 단계에서 현재까지의 접두사와 문법 상태로 다음에 허용되는 token을 계산한 뒤, 허용되지 않는 token의 확률을 0으로 만든다.

예를 들어 schema가 `color` field의 값을 `"red" | "green"`으로 제한하면 다른 enum 문자열을 완성하는 token 경로를 차단할 수 있다. 그러나 입력 사물이 실제로 빨간지 초록인지는 문법이 판단하지 않는다.

CFG는 재귀적인 중첩 JSON 구조를 표현할 수 있다. 이것은 OpenAI가 공개한 특정 implementation 설명이며 모든 structured-output provider가 같은 grammar engine을 쓴다는 증거는 아니다.

### 3. 반환 경로를 분기한다

Application은 schema object 하나만 기다려서는 안 된다.

| 상태 | 처리 |
| --- | --- |
| 정상 schema 결과 | Typed object로 decode한 뒤 semantic validation |
| Safety refusal | 별도 refusal UI·policy 경로 |
| Token limit·중단 | Incomplete로 기록하고 retry 가능성 판단 |
| Network·service error | Model semantic failure와 분리 |
| Schema는 통과했으나 의미 오류 | Domain rule·database·원문 근거로 reject |

Retry가 필요한 경우에도 같은 prompt의 무한 반복보다 오류 종류, retry budget, idempotency와 사람 검토 기준을 명시한다.

## 3단계 — 기술과 근거

### Function calling과 일반 응답

Structured Outputs는 외부 tool argument와 일반 응답 모두에 쓸 수 있다.

| 목적 | 출력 object의 의미 | 다음 단계 |
| --- | --- | --- |
| 일반 `json_schema` 응답 | 추출·분류·변환 결과 | 검증 뒤 application data로 사용 |
| Function definition의 `strict: true` | 어떤 function을 어떤 argument로 호출하자는 제안 | 권한·부작용·argument 의미를 확인한 뒤 application이 실행 |

Model은 schema object를 생성한다. 실제 database write, 결제, email 전송은 runtime이 수행한다. 따라서 tool argument의 exact shape가 action의 정당성이나 성공을 보장하지 않는다.

### SDK·Pydantic·Framework

Pydantic과 Zod는 개발 언어의 type model을 schema로 표현하고 반환값을 역직렬화·검증하는 데 유용하다. OpenAI native SDK는 이 표현을 지원되는 JSON Schema로 변환해 provider-native constrained decoding과 연결할 수 있다.

Framework abstraction은 다른 경로도 가질 수 있다. LangChain의 2024년 `with_structured_output` RFC는 function calling 또는 provider별 steering과 output parsing을 결합하는 interface를 제안했다. Pydantic object가 보인다는 사실만으로 생성 중 token masking, provider-native strict mode, 사후 parser·retry 중 어느 방식인지 알 수 없다.

### 평가 장부

Format reliability와 task quality는 다른 분모로 측정한다.

| 지표 | 측정 대상 |
| --- | --- |
| Parse success | JSON decoder가 읽은 응답 비율 |
| Schema pass | 정상 완료 응답 중 schema를 통과한 비율 |
| Field precision·recall | 추출한 값의 추가·누락 |
| Semantic exactness | 원문·database·업무 규칙과 맞는 값 |
| Refusal·incomplete rate | 별도 반환 경로의 빈도 |
| End-to-end success | Consumer가 결과를 안전하게 사용한 전체 요청 비율 |

OpenAI는 complex-schema 내부 평가에서 `gpt-4o-2024-08-06` Structured Outputs의 100%를 보고했다. 같은 발표의 Under the hood 설명에서는 model training만으로 93%, constrained decoding 결합으로 100%에 도달했다고 했다. 이는 해당 schema-conformance 평가이며 의미 정확성 100%가 아니다.

### Parser가 사라진 것이 아니다

취약한 자연어 정규식과 code-fence 제거 로직은 줄어든다. 그러나 JSON decoding, schema validation, domain validation과 error handling은 남는다. ‘Parsing 제거’보다 **ad-hoc text parsing을 typed validation으로 교체했다**고 설명하는 편이 정확하다.

## 검증과 한계

### 흔한 오해

- **Valid JSON이면 schema도 맞는다:** `{ "x": 1 }`은 유효한 JSON이지만 `x`가 문자열이어야 하는 schema에는 맞지 않는다.
- **Schema가 맞으면 내용도 맞는다:** 허용된 string field에 환각한 이름을 넣어도 schema는 통과한다.
- **Strict output은 결정론이다:** 같은 schema를 지켜도 sampling과 입력에 따라 value는 달라질 수 있다.
- **Pydantic이 model을 제약한다:** Pydantic은 schema·validation library다. 생성 제약은 연결한 provider strategy가 담당한다.
- **모든 JSON Schema를 쓸 수 있다:** Provider는 지원되는 부분집합과 model을 명시한다.
- **모든 응답이 schema object다:** Refusal과 불완전 종료는 별도 경로다.
- **모든 provider가 같은 보장을 준다:** 같은 이름의 abstraction도 native feature·tool strategy·post-processing이 다를 수 있다.
- **구조화 출력은 hallucination을 없앤다:** 형식 오류와 사실 오류는 다른 failure class다.

### Failure condition

- User input이 schema와 무관하지만 output field를 반드시 채워야 하는 경우
- 서로 양립할 수 없는 field 사이의 업무 규칙을 schema가 표현하지 못한 경우
- 새 schema 전처리 latency가 짧은 request budget을 넘는 경우
- 최대 token·stop·network error로 generation이 완료되지 않은 경우
- Parallel tool call과 strict schema 조합이 provider 제한과 충돌하는 경우
- Consumer가 schema-valid object를 authorization 없이 실행하는 경우
- Schema version은 바뀌었지만 downstream code가 이전 계약을 기대하는 경우

### 적용 범위

이 문서의 강한 보장은 OpenAI가 2024년에 공개한 호환 model·지원 JSON Schema·정상 완료 경로를 중심으로 설명한다. XML DTD, 모든 grammar decoder, 모든 vendor API가 같은 방식과 보장을 쓴다고 일반화하지 않는다. Format reliability가 entity extraction·classification·data normalization의 정확도와 비용을 기존 방법보다 항상 높인다는 비교도 별도 evaluation이 필요하다.
