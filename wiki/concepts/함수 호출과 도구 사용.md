# 함수 호출과 도구 사용

> [!note] 학습 안내
> **난이도:** 중급<br>
> **선수 지식:** [[대규모 언어 모델]], [[사고 연쇄 프롬프팅]]<br>
> **읽고 나면:** 함수 호출을 모델의 구조화된 출력 interface와 외부 runtime의 실행 protocol로 나누고, schema 준수·argument 정확성·권한·실행·결과 grounding을 각각 검사할 수 있다.

## 1단계 — 먼저 잡을 핵심

### 한 문장 정의

**함수 호출과 도구 사용**은 언어 모델이 사용 가능한 operation의 설명을 읽고 함수 이름과 argument를 제안하며, 외부 application이 이를 검증·실행한 뒤 결과를 다시 모델에 제공하는 model–runtime protocol이다.

핵심은 다음 등식이 성립하지 않는다는 점이다.

$$
\text{model이 call을 생성함}
\ne
\text{tool이 실행됨}
\ne
\text{의도한 task가 안전하게 성공함}.
$$

모델 출력은 **제안**, schema validator는 **형식 검사**, authorization layer는 **허용 결정**, executor는 **외부 상태 변화**, model의 마지막 response는 **결과 설명**을 맡는다. 이 역할을 한 주체의 ‘행동’으로 뭉치면 실패 원인과 책임 경계를 찾을 수 없다.

### 다섯 단계 protocol

| 단계 | 입력 | 출력 | 대표 실패 |
| --- | --- | --- | --- |
| 1. Tool 기술 | 이름·설명·schema | capability catalog | 모호한 경계, 과도한 권한 |
| 2. Call 제안 | user context·catalog | 함수 이름·argument | wrong tool, invalid value |
| 3. 검증·승인 | call·identity·policy | 실행 허가 또는 거절 | 인증·권한 누락 |
| 4. 실행 | 승인된 call | result·error·state change | timeout, 중복, 부분 실패 |
| 5. 결과 통합 | tool result·대화 | 답 또는 다음 call | result 왜곡, injection, 무한 loop |

## 2단계 — 작동 원리

### Schema는 언어와 runtime의 접점이다

JSON Schema 같은 기술은 함수의 이름, parameter 자료형, required field와 enum을 모델과 parser가 공유하게 한다. 이는 자유 형식 text에서 call을 추출하는 것보다 구문 경계를 선명하게 만든다.

그러나 schema가 표현하는 것은 **자료 구조의 허용 범위**다. “이 사용자가 이 계좌에서 송금할 수 있는가”, “이 날짜는 업무상 허용되는가”, “이 API 응답은 공격자가 심은 instruction인가” 같은 판단은 schema 밖의 policy와 data validation이 담당한다.

### 제어 흐름은 model 밖에 있다

간단한 runtime loop는 다음 상태를 가진다.

1. `model_request`: 대화와 tool catalog를 보낸다.
2. `assistant_text` 또는 `tool_call`: model output 유형을 판별한다.
3. `validate_authorize`: 이름·argument·identity·policy를 검사한다.
4. `execute`: timeout·idempotency·sandbox 조건에서 tool을 실행한다.
5. `tool_result`: 결과와 error를 model context에 넣는다.
6. `continue_or_stop`: 다음 call을 허용할지, 답을 반환할지 결정한다.

Model은 2번과 5번 이후의 token generation을 담당하지만 maximum step, retry budget, 승인 상태와 종료 조건은 orchestrator가 유지한다. 함수 호출 API 자체가 장기 plan이나 memory를 자동으로 제공하지 않는다.

### 관찰은 외부 지식을 문맥으로 옮긴다

Tool은 search, calculator, database, code runtime, device controller처럼 서로 다른 기능을 제공한다. 실행 결과는 model의 parameter를 갱신하지 않고 새 input context가 된다. 따라서 최신 정보나 정확한 계산의 이점은 **외부 source의 result가 조건으로 추가되는 것**이지 model 내부 지식이 실시간으로 바뀌는 것이 아니다.

ReAct는 thought–action–observation을 교대로 prompt에 놓았고 Toolformer는 API call을 training sequence 안에 삽입해 tool 선택과 결과 통합을 학습했다. 2023년 상용 function calling은 이 넓은 문제를 표준 response field와 schema catalog로 product API에 노출한 한 방식이다.

### 읽기와 쓰기 tool의 위험은 다르다

날씨 조회처럼 외부 상태를 읽는 call과 결제·발송·삭제처럼 상태를 바꾸는 call은 같은 schema 형식이어도 위험이 다르다. Side effect가 있는 tool에는 다음 control이 특히 중요하다.

- 최소 권한과 resource 단위 authorization
- preview와 사용자 confirmation
- idempotency key와 중복 실행 방지
- transaction·rollback 또는 compensating action
- timeout·rate limit·step budget
- 입력·출력 audit log와 민감 정보 redaction

이 control은 prompt에 “조심하라”고 적는 것보다 강한 runtime 제약이어야 한다.

## 3단계 — 기술과 근거

### 보장 장부를 분리한다

| 보장 | 대표 방법 | 보장하지 않는 것 |
| --- | --- | --- |
| Valid JSON | JSON mode·parser | 특정 schema 일치 |
| Schema conformity | Validator·strict constrained decoding | value의 사실성·업무 타당성 |
| Tool selection | Model training·description·eval | argument 정확성·권한 |
| Semantic validation | Domain rule·database lookup | 사용자 승인 |
| Authorization | Identity·policy engine | 외부 service 성공 |
| Execution reliability | Retry·idempotency·transaction | model의 최종 요약 정확성 |
| Result grounding | Citation·trace·postcondition check | 부작용의 정당성 전체 |

2024년 `strict: true` Structured Outputs는 위 표의 schema conformity를 강화했다. OpenAI의 발표는 복잡한 schema eval에서 strict 조건의 100%를 보고했지만, 동시에 JSON value의 model error, refusal·generation 중단과 parallel call 제한을 명시했다. 한 열의 개선을 전체 system reliability로 바꾸지 않는다.

### 순차 호출과 병렬 호출

순차 호출은 앞선 결과를 보고 다음 tool과 argument를 정할 수 있다. 병렬 호출은 서로 독립적인 여러 읽기 작업의 round trip을 줄일 수 있지만, dependency가 있거나 side effect가 충돌하면 부적절하다.

2023년 6월 `-0613` release의 여러 함수 설명 중 선택과 2023년 11월 `-1106` release의 한 message 복수 호출을 구분한다. “여러 tool을 사용할 수 있다”와 “여러 call을 한 turn에 병렬로 반환한다”는 다른 기능이다. Strict Structured Outputs의 2024년 발표도 parallel calls와 함께 쓰면 schema 일치를 벗어날 수 있다고 경고했다.

### Eval은 end-to-end와 component를 함께 본다

Agent task가 성공했는지만 보면 어떤 component가 실패했는지 알기 어렵다. 다음 지표를 함께 기록한다.

- Call 필요 여부 판정과 tool 선택 정확도
- Argument parse·schema 통과율과 field별 semantic accuracy
- 불허 요청을 거절한 비율과 허용 요청의 false rejection
- Execution success, latency, timeout·retry·duplicate rate
- Tool result에서 final answer로의 factual grounding
- 전체 task success, cost, step count와 irreversible side effect

Offline fixture에서는 tool 결과와 error를 고정해 model regression을 비교하고, staging에서는 sandboxed executor로 postcondition을 검사한다. Production audit는 실제 권한과 상태 변화까지 추적하되 민감 data를 최소화한다.

## 검증과 한계

### 흔한 오해

- **모델이 함수를 호출한다:** API 용어는 function call이지만 model은 call data를 생성하고 application이 실행한다.
- **Schema가 있으면 argument가 정확하다:** Type이 맞아도 잘못된 ID·날짜·금액일 수 있다.
- **Strict output은 결정론이다:** 지원 schema 형태를 constrained decoding으로 맞추는 것과 같은 입력에서 항상 같은 의미·value를 내는 것은 다르다.
- **도구가 있으면 hallucination이 사라진다:** 모델이 tool을 부르지 않거나 잘못 조회하고, 결과를 잘못 읽거나 무시할 수 있다.
- **최신 정보를 호출하면 cutoff가 사라진다:** 최신 정보는 그 turn의 tool result에만 들어오며 model parameter는 그대로다.
- **Tool description이 권한 policy다:** 설명은 선택을 돕지만 인증·인가를 시행하지 않는다.
- **병렬 호출은 항상 빠르고 좋다:** Dependency·rate limit·side effect·strict schema와 충돌할 수 있다.
- **Function calling이면 agent다:** 단일 extraction call은 장기 목표·계획·memory·복구 loop가 없을 수 있다.

### Prompt injection과 confused deputy

Web page·email·database field 같은 tool output에는 model을 향한 악성 instruction이 섞일 수 있다. Model이 이를 developer instruction처럼 따르면 공격자가 model을 통해 더 높은 권한의 tool을 움직이는 confused-deputy 문제가 생긴다.

Data provenance label, instruction hierarchy, untrusted-content 격리, tool별 allowlist와 사용자 confirmation을 함께 사용한다. 특히 외부 text를 읽은 직후 결제·삭제·전송 tool을 자동 실행하는 경로는 trust-domain 전환을 명시적으로 차단하거나 승인 단계로 넘긴다.

### 자율성은 interface 밖에서 정해진다

같은 function call model도 application이 한 번만 호출을 허용하면 보조 parser이고, 여러 step과 memory·goal state를 허용하면 agent loop의 일부가 된다. 자율성은 model 이름보다 사용할 수 있는 tool, 권한, step budget, 종료 조건, 인간 승인과 rollback 가능성의 조합으로 기술해야 한다.
