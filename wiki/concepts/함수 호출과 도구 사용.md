# 함수 호출과 도구 사용

> [!note] 학습 안내
> **난이도:** 중급<br>
> **선수 지식:** [[concept.대규모-언어-모델|대규모 언어 모델]], [[concept.사고-연쇄-프롬프팅|사고 연쇄 프롬프팅]]<br>
> **읽고 나면:** 함수 호출을 모델의 구조화된 출력 interface와 외부 runtime의 실행 protocol로 나누고, proposal·실행 시도·외부 효과·관측 결과, schema·권한·확인·복구·결과 grounding을 각각 검사할 수 있다.

## 1단계 — 먼저 잡을 핵심

### 한 문장 정의

**함수 호출과 도구 사용**은 언어 모델이 사용 가능한 operation의 설명을 읽고 함수 이름과 argument를 제안하며, 외부 application이 이를 검증·실행한 뒤 결과를 다시 모델에 제공하는 model–runtime protocol이다.

핵심은 다음 등식이 성립하지 않는다는 점이다.

$$
\text{model이 call을 생성함}
\ne
\text{tool이 실행됨}
\ne
\text{의도한 task가 안전하게 성공함}
$$

모델 출력은 **제안**, schema validator는 **형식 검사**, authorization layer는 **허용 결정**, executor는 **외부 상태 변화**, model의 마지막 response는 **결과 설명**을 맡는다. 이 역할을 한 주체의 ‘행동’으로 뭉치면 실패 원인과 책임 경계를 찾을 수 없다.

### 다섯 단계 protocol

| 단계 | 입력 | 출력 | 대표 실패 |
| --- | --- | --- | --- |
| 1. Tool 기술 | 이름·설명·schema | capability catalog | 모호한 경계, 과도한 권한 |
| 2. Call 제안 | user context·catalog | 함수 이름·argument | wrong tool, invalid value |
| 3. 검증·인가 | call·identity·policy | 형식·의미 검사와 허가 또는 알려진 거절 | 잘못된 대상, 인증·권한 누락 |
| 4. 확인·실행 시도 | 허가된 call·필요한 confirmation | action ID를 단 executor 요청 | 만료된 확인, timeout, 중복 |
| 5. 조정·결과 통합 | 응답·상태 조회·감사 record | committed·failed·unknown과 답 또는 다음 call | 응답 유실, 부분 효과, result 왜곡 |

### 제안·시도·효과·관측은 서로 다르다

설명을 위해 모델이 아래 **설명용 예**의 공유 후보를 냈다고 하자.

| field | value |
| --- | --- |
| action_id | act-20260725-001 |
| idempotency_key | idem-share-d17-partner7-v1 |
| action | share_document |
| document_id | D-17 |
| principal·role | partner-7 · viewer |

이 후보만으로도 네 가지 서로 다른 사실이 생긴다.

| 말 | 이 예에서 실제로 확인해야 할 것 |
| --- | --- |
| **proposal(제안)** | 모델이 위 action과 argument를 만들었다. 아직 외부 요청은 보내지 않았다. |
| **execution attempt(실행 시도)** | runtime이 정해진 endpoint에 이 action ID를 붙여 요청을 보냈다. 응답을 받지 못할 수도 있다. |
| **external effect(외부 효과)** | 권위 있는 문서 서비스가 partner-7에게 D-17의 viewer 권한을 실제로 만들었거나 바꾸었다. |
| **observed·recorded outcome(관측·기록 결과)** | runtime이 응답·상태 조회·감사 기록으로 효과를 확인하거나, 아직 확인하지 못했다고 남겼다. |

따라서 timeout, 모델의 “공유했습니다”라는 문장, HTTP 성공 응답은 서로 바꿔 쓸 수 없다. 특히 관측이 없다는 것은 효과가 없었다는 증명이 아니다.

## 2단계 — 작동 원리

### Schema는 언어와 runtime의 접점이다

JSON Schema 같은 기술은 함수의 이름, parameter 자료형, required field와 enum을 모델과 parser가 공유하게 한다. 이는 자유 형식 text에서 call을 추출하는 것보다 구문 경계를 선명하게 만든다.

그러나 schema가 표현하는 것은 **자료 구조의 허용 범위**다. “이 사용자가 이 계좌에서 송금할 수 있는가”, “이 날짜는 업무상 허용되는가”, “이 API 응답은 공격자가 심은 instruction인가” 같은 판단은 schema 밖의 policy와 data validation이 담당한다.

### 제어 흐름은 model 밖에 있다

간단한 runtime loop는 다음 상태를 가진다.

1. `model_request`: 대화와 tool catalog를 보낸다.
2. `assistant_text` 또는 `tool_call`: model output 유형을 판별한다.
3. `validate_authorize_confirm`: 형식·의미·identity·policy를 검사하고, 필요하면 정확한 대상과 parameter에 confirmation을 묶으며, 불필요하면 면제 결정과 근거를 기록한다.
4. `execute_attempt`: action ID와 해당 interface의 idempotency contract를 붙여 executor에 요청한다.
5. `reconcile`: 응답·상태 조회·event를 대조해 committed·failed·unknown을 판정하고, partial effect는 failed 또는 unknown의 증거·잔여 효과로 기록한다.
6. `result_integration`: committed·failed의 확인된 사실과 `unknown`이라는 미확정 상태를 구분해 model context에 넣고, action ID·관측 근거·다음 reconciliation을 durable trace에 남긴다.
7. `continue_or_stop`: 재시도·다음 call·사람 escalation·답 반환·중단을 policy와 budget에 따라 결정한다.

Model은 2번과 5번 이후의 token generation을 담당하지만 maximum step, retry budget, 승인 상태와 종료 조건은 orchestrator가 유지한다. 함수 호출 API 자체가 장기 plan이나 memory를 자동으로 제공하지 않는다.

호출 후보가 runtime에 도착하기 전에도 text 표현·parser·schema·업무 의미·identity·policy가 서로 다른 계약을 이룬다. JSON argument가 유효하더라도 어떤 resource를 가리키는지, 요청 주체가 누구인지, 그 action을 허용할지는 아직 별도 검사 대상이다. [[문자에서 실행 권한까지]]는 이 앞단 관문을 한 trace로 연결하고, 이 문서는 그 뒤 runtime이 후보를 검증·실행·결과 통합하는 protocol을 계속 맡는다.

### 허가된 후보에서 확정 결과까지

write action의 상태는 다음처럼 기록한다.

**proposed** → **structurally validated** → **semantically validated** → **authorized** → **confirmed** → **[execution attempt]** → **committed / failed / unknown**

형식·의미·인가·확인 관문은 dispatch 전에 알려진 거절로 끝날 수 있으며, 이때는 **failed (known no effect)** 로 기록한다. confirmed 상태(confirmation이 불필요하면 policy에 기록된 waiver를 포함) 뒤에만 executor가 실제 요청을 보낸다. 위 화살표는 모든 product의 물리적 wire 순서가 아니라, 각 상태가 무엇을 증명했는지 남기는 감사·결과 계약 순서다.

1. **proposed**: 모델이 action 후보를 냈다. action ID를 만들고, model·prompt·tool version을 붙인다.
2. **structurally validated**: parser와 schema가 형식·자료형·필수 field를 통과시켰다. 이것만으로 대상이나 의도는 맞지 않는다.
3. **semantically validated**: D-17의 존재·현재 version·공유 규칙·수신자·업무 precondition을 확인했다. 이 확인은 시간이 지나면 낡을 수 있다.
4. **authorized**: 현재 identity·resource·action·policy에서 허용 결정을 받았다. authorization은 사용자 확인이나 executor 성공이 아니다.
5. **confirmed**: policy가 confirmation을 요구했다면 preview와 확인이 정확한 action ID·payload·resource version·만료 시각에 묶여 충족됐다. confirmation이 불필요한 risk tier라면 그 면제 결정과 근거를 policy record에 남긴다. payload나 대상이 바뀌면 이전 confirmation 또는 면제 결정을 재평가한다.
6. **committed**: 권위 있는 외부 상태 조회 또는 동등한 postcondition이 의도한 결과를 확인했고, runtime이 그 결과를 durable record에 남겼다. 이는 database의 ACID commit이라는 일반 명칭도, 수신자가 이메일을 읽었다는 보장도 아니다.
7. **failed**: 실행하지 않았음 또는 의도한 postcondition이 성립하지 않았음과 남은 효과를 신뢰할 만하게 확인했다. 일부 효과가 남았다면 그 사실과 후속 조치를 함께 기록한다.
8. **unknown**: 요청·응답 유실, timeout 또는 불완전한 관측 때문에 효과 발생 여부를 아직 분류할 수 없다. 실패의 완곡어법이 아니라 지식의 공백이다.

unknown인 write action은 새 action ID나 새 payload로 자동 재시도하지 않는다. 먼저 같은 logical operation ID·idempotency record·권위 있는 상태 조회로 **reconciliation(조정)** 한다. 계약이 같은 key의 재시도를 허용할 때만 같은 key를 사용하며, key 보존 기간·payload 동일성·응답 재현 범위도 interface가 명시해야 한다. 이 문서가 권장하는 interface contract에서는 같은 key에 다른 payload를 붙이는 요청을 충돌로 거절한다.

### 실패 창마다 다음 행동이 다르다

1. **executor에 도달하지 않았음이 확인됨:** dispatch 전 validation 거절이나 executor가 수신하지 않았다는 positive record처럼 효과가 없음을 확인했을 때만 failed로 기록한다. 연결·응답 failure만으로는 수신 여부를 알 수 없으므로 unknown으로 남긴다. policy는 시간이 지난 precondition·authorization·필요한 confirmation 또는 waiver 결정을 다시 검사한 뒤에만 재시도를 허용한다.
2. **요청은 도달했을 수 있으나 응답이 없음:** unknown으로 멈춘다. action ID로 downstream 상태와 idempotency record를 조회해 committed 또는 failed를 판정하고, 증거가 부족하면 사람에게 escalation한다.
3. **여러 효과 중 일부만 관측됨:** 예를 들어 계약된 action이 문서 공유와 알림 기록을 함께 요구하는데 공유만 되었다면, 원래 action은 postcondition을 만족하지 못한 failed 또는 아직 판정 중인 unknown이다. 이미 일어난 공유를 숨기지 않고 residual effect를 기록한다.

**precondition**은 실행 전 참이어야 하는 사실, **postcondition**은 실행 뒤 관측 가능한 목표 사실, **invariant**는 어느 상태에서도 깨지면 안 되는 규칙이다. 예를 들어 “소유자가 아닌 사람에게 D-17을 공유하지 않는다”는 invariant다. **idempotency(멱등성)** 는 선언한 동일 요청 계약 안에서 반복해도 의도한 효과가 한 번과 같다는 뜻이지 보편적인 exactly-once 보장이 아니다. **rollback**은 같은 atomic 경계 안의 되돌림이고, **compensation(보상)** 은 이미 분산된 효과를 완화하는 새 action이다. 보상도 자체 authorization·필요한 confirmation·idempotency·실패 기록을 가져야 하며, 외부 수신자가 복사한 파일처럼 되돌릴 수 없는 효과까지 지우지 못할 수 있다.

### 관찰은 외부 지식을 문맥으로 옮긴다

Tool은 search, calculator, database, code runtime, device controller처럼 서로 다른 기능을 제공한다. 실행 결과는 model의 parameter를 갱신하지 않고 새 input context가 된다. 따라서 최신 정보나 정확한 계산의 이점은 **외부 source의 result가 조건으로 추가되는 것**이지 model 내부 지식이 실시간으로 바뀌는 것이 아니다.

ReAct는 thought–action–observation을 교대로 prompt에 놓았고 Toolformer는 API call을 training sequence 안에 삽입해 tool 선택과 결과 통합을 학습했다. 2023년 상용 function calling은 이 넓은 문제를 표준 response field와 schema catalog로 product API에 노출한 한 방식이다.

### 읽기와 쓰기 tool의 위험은 다르다

날씨 조회처럼 외부 상태를 읽는 call과 결제·발송·삭제처럼 상태를 바꾸는 call은 같은 schema 형식이어도 위험이 다르다. Side effect가 있는 tool에는 다음 control이 특히 중요하다.

- 최소 권한과 resource 단위 authorization
- preview와 policy가 요구할 때의 사용자 confirmation, 또는 기록된 waiver
- idempotency key와 중복 실행 방지
- transaction·rollback 또는 compensating action
- timeout·rate limit·step budget
- 입력·출력 audit log와 민감 정보 redaction

이 control은 prompt에 “조심하라”고 적는 것보다 강한 runtime 제약이어야 한다.

## 3단계 — 기술과 근거

### 보장 장부를 분리한다

| 보장 | 대표 방법 | 보장하지 않는 것 |
| --- | --- | --- |
| Valid JSON | JSON mode·parser | 특정 schema 일치 |
| Schema conformity | Validator·strict constrained decoding | value의 사실성·업무 타당성 |
| Tool selection | Model training·description·eval | argument 정확성·권한 |
| Semantic validation | Domain rule·database lookup | 사용자 승인 |
| Authorization | Identity·policy engine | 외부 service 성공 |
| Execution reliability | Retry·idempotency·transaction | model의 최종 요약 정확성 |
| Result grounding | Citation·trace·postcondition check | 부작용의 정당성 전체 |

2024년 `strict: true` Structured Outputs는 위 표의 schema conformity를 강화했다. OpenAI의 발표는 복잡한 schema eval에서 strict 조건의 100%를 보고했지만, 동시에 JSON value의 model error, refusal·generation 중단과 parallel call 제한을 명시했다. 한 열의 개선을 전체 system reliability로 바꾸지 않는다.

Structured Outputs는 function argument뿐 아니라 일반 응답의 `json_schema`에도 적용됐다. [[구조화 출력]]은 extraction·classification·transformation object의 형식 계약을 다루고, function calling은 그 object가 외부 action 제안으로 이어진다는 점에서 authorization·side effect·execution 관문을 더한다. 두 interface가 같은 schema를 쓰더라도 system boundary는 다르다.

### 한 action의 일곱 칸 장부

| 항목 | 이 문서가 기록하는 계약 |
| --- | --- |
| 입력·대상 | action ID, idempotency key, caller identity, tool·schema·policy version, resource·parameter와 payload digest를 묶어 같은 논리적 의도를 식별한다. |
| 변환 경로 | proposal → 형식 검사 → 의미 검사 → authorization → 필요한 confirmation → 실행 시도 → reconciliation·결과 통합으로 간다. |
| 시간·상태·자원 | resource snapshot·version, credential·approval expiry, retry·time·cost budget, downstream operation·idempotency record의 보존 기간을 남긴다. |
| 결과 계약 | committed는 postcondition이 확인된 결과, failed는 알려진 미완료·잔여 효과, unknown은 아직 판정할 수 없는 결과다. HTTP-level accepted 응답(예: 202)이나 tool text만으로 이 셋을 정하지 않는다. |
| 지표·평가 기준 | 전체 action을 분모로 schema·semantic·authorization·confirmation 통과율, unauthorized write 수, duplicate-effect rate, unknown→resolved 시간, postcondition 확인률, compensation 뒤 residual-effect rate를 함께 본다. |
| 실패·복구 경계 | timeout·response loss는 blind retry가 아니라 reconciliation으로 보낸다. partial effect는 기록·보상 또는 사람 escalation의 입력이며, 보상 성공이 원래 상태 복원을 자동 증명하지 않는다. |
| 권한·책임·출처 추적 | 모델은 proposal, orchestrator는 상태 전이와 retry, policy owner는 허용·확인 규칙, executor·외부 service는 효과와 상태 조회를 맡는다. action·trace ID, principal, version, 승인 근거, 시각, outcome을 감사하되 민감 payload·credential은 최소화·redaction한다. |

### 순차 호출과 병렬 호출

순차 호출은 앞선 결과를 보고 다음 tool과 argument를 정할 수 있다. 병렬 호출은 서로 독립적인 여러 읽기 작업의 round trip을 줄일 수 있지만, dependency가 있거나 side effect가 충돌하면 부적절하다.

2023년 6월 `-0613` release의 여러 함수 설명 중 선택과 2023년 11월 `-1106` release의 한 message 복수 호출을 구분한다. “여러 tool을 사용할 수 있다”와 “여러 call을 한 turn에 병렬로 반환한다”는 다른 기능이다. Strict Structured Outputs의 2024년 발표도 parallel calls와 함께 쓰면 schema 일치를 벗어날 수 있다고 경고했다.

### Eval은 end-to-end와 component를 함께 본다

Agent task가 성공했는지만 보면 어떤 component가 실패했는지 알기 어렵다. 다음 지표를 함께 기록한다.

- Call 필요 여부 판정과 tool 선택 정확도
- Argument parse·schema 통과율과 field별 semantic accuracy
- 불허 요청을 거절한 비율과 허용 요청의 false rejection
- Execution success, latency, timeout·retry·duplicate rate와 전체 action 대비 committed·failed·unknown 비율
- unknown outcome을 reconciliation으로 판정하는 시간, postcondition 확인률, compensation 뒤 남은 효과와 승인 없는 write 수
- Tool result에서 final answer로의 factual grounding
- 전체 task success, cost, step count와 irreversible side effect

Offline fixture에서는 tool 결과와 error를 고정해 model regression을 비교하고, staging에서는 sandboxed executor로 postcondition을 검사한다. Production audit는 실제 권한과 상태 변화까지 추적하되 민감 data를 최소화한다.

[[LLM 에이전트]]처럼 같은 관문을 여러 step 반복하는 system에서는 앞선 observation 오류가 다음 tool 선택과 argument 분포를 바꾼다. 따라서 call별 정확도만 평균내지 않고 전체 goal의 postcondition, trajectory, retry·중복 side effect, cost·latency와 안전한 중단·복구를 함께 기록한다. WebArena의 낮은 당시 end-to-end baseline과 ToolEmu의 고위험 실패 실험은 구조화된 호출 interface가 장기 신뢰성이나 안전성을 자동 완성하지 않는다는 점을 보여 준다.

## 검증과 한계

### 흔한 오해

- **모델이 함수를 호출한다:** API 용어는 function call이지만 model은 call data를 생성하고 application이 실행한다.
- **Schema가 있으면 argument가 정확하다:** Type이 맞아도 잘못된 ID·날짜·금액일 수 있다.
- **Strict output은 결정론이다:** 지원 schema 형태를 constrained decoding으로 맞추는 것과 같은 입력에서 항상 같은 의미·value를 내는 것은 다르다.
- **도구가 있으면 hallucination이 사라진다:** 모델이 tool을 부르지 않거나 잘못 조회하고, 결과를 잘못 읽거나 무시할 수 있다.
- **최신 정보를 호출하면 cutoff가 사라진다:** 최신 정보는 그 turn의 tool result에만 들어오며 model parameter는 그대로다.
- **Tool description이 권한 policy다:** 설명은 선택을 돕지만 인증·인가를 시행하지 않는다.
- **Timeout은 효과가 없었다는 뜻이다:** 응답만 잃었을 수 있으므로 unknown을 먼저 기록하고 reconciliation한다.
- **Idempotency key가 exactly-once를 보장한다:** key scope·payload 동일성·보존 기간·downstream 계약이 없으면 중복과 늦은 요청의 의미를 정할 수 없다.
- **Rollback은 모든 외부 효과를 지운다:** 이미 다른 service·사람·물리 세계에 퍼진 효과에는 domain별 compensation과 잔여 효과 기록이 필요하다.
- **성공 응답이 postcondition이다:** 수신한 status와 권위 있는 상태·업무 결과는 다를 수 있다.
- **병렬 호출은 항상 빠르고 좋다:** Dependency·rate limit·side effect·strict schema와 충돌할 수 있다.
- **Function calling이면 agent다:** 단일 extraction call은 장기 목표·계획·memory·복구 loop가 없을 수 있다.

### Prompt injection과 confused deputy

Web page·email·database field 같은 tool output에는 model을 향한 악성 instruction이 섞일 수 있다. Model이 이를 developer instruction처럼 따르면 공격자가 model을 통해 더 높은 권한의 tool을 움직이는 confused-deputy 문제가 생긴다.

Data provenance label, instruction hierarchy, untrusted-content 격리, tool별 allowlist와 사용자 confirmation을 함께 사용한다. 특히 외부 text를 읽은 직후 결제·삭제·전송 tool을 자동 실행하는 경로는 trust-domain 전환을 명시적으로 차단하거나 승인 단계로 넘긴다.

### 자율성은 interface 밖에서 정해진다

같은 function call model도 application이 한 번만 호출을 허용하면 보조 parser이고, 여러 step과 memory·goal state를 허용하면 agent loop의 일부가 된다. 자율성은 model 이름보다 사용할 수 있는 tool, 권한, step budget, 종료 조건, 인간 승인과 rollback 가능성의 조합으로 기술해야 한다.
