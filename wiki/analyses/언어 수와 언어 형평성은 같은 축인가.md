# 언어 수와 언어 형평성은 같은 축인가

> [!note] 학습 안내
> **난이도:** 심화<br>
> **선수 지식:** [[concept.저자원-언어|저자원 언어]], [[concept.서브워드-토큰화|서브워드 토큰화]]<br>
> **읽고 나면:** 모델의 지원 언어 수와 언어 공동체가 얻는 성능·비용·안전·권한을 일곱 관문으로 분리하고, 서로 다른 다국어 연구의 숫자를 같은 순위표로 읽을 수 없는 이유를 설명할 수 있다.

## 1단계 — 먼저 잡을 핵심

### 비교 질문

[[062_XLM과 교차 언어 사전 학습|XLM]]의 XNLI 결과에는 15개 언어가 놓이고, [[082_BLOOM과 공개 접근 다국어 LLM|BLOOM]]은 46개 자연어를 학습 범위에 넣었다. NLLB는 200개 번역 언어, MaLA-500은 534개 language-script 단위, Aya는 101개 instruction-tuning 언어를 말한다. 숫자만 보면 15에서 534까지 확대된 한 줄 진보처럼 보인다.

그러나 이 숫자들의 분모는 서로 다르다. 어떤 수는 **평가표의 언어 열**, 어떤 수는 **사전 학습 말뭉치에 포함된 언어**, 어떤 수는 **기계번역이 다루는 언어**, 어떤 수는 **instruction-tuning 자료가 있는 언어**다. 같은 이름의 언어가 목록에 있어도 자료량, 분절 비용, 과제 성능, 이용 비용과 공동체의 결정권은 같지 않다.

### 잠정 결론

**지원 언어 수(language coverage)는 모델이나 자료가 어느 언어 표지·문자열·과제를 다룬다고 선언했는지 세는 범위 지표다. 언어 형평성(language equity)은 각 언어 공동체가 필요한 과제에서 어떤 성능·오류·비용·안전·권한과 실제 결과를 얻는지 묻는 분배 질문이다. 둘은 관련되지만 같은 축이 아니다.**

지원 언어 수는 선언된 언어 집합에 들어 있는 항목의 개수로 셀 수 있다.

이 단순한 집계는 첫 문을 몇 개 만들었는지 보여 준다. 반면 형평성을 판단하려면 언어, 과제와 사용자 집단마다 효용과 부담이 어떻게 분포하는지 봐야 한다. 평균 정확도 하나나 선언 목록의 원소 수 하나로는 그 분포를 복원할 수 없다.

### 숫자의 분모를 먼저 읽는다

| 연구·시스템 | 자주 인용되는 언어 수 | 실제로 센 것 | 바로 비교할 수 없는 이유 |
| --- | ---: | --- | --- |
| XLM | 15 | XNLI 평가에 놓인 영어 포함 15개 언어 | 범용 지원 목록이나 unseen-language 성능 수가 아님 |
| BLOOM | 46 | ROOTS와 BLOOM이 구분한 자연어 46개 | 별도의 프로그래밍 언어 13개가 있고, 언어별 token 비중이 다름 |
| NLLB | 200 | 기계번역 대상 언어 약 200개와 40,000개 초과 방향 | 범용 생성·QA·교육·의료 능력이 아니라 MT 범위 |
| MaLA-500 | 534 | ISO 639-3 코드와 script를 결합한 534개 language-script 단위 | 평가별 교집합은 534·370·177·351개로 달라짐 |
| Aya | 101 | instruction fine-tuning에 사용한 101개 언어 | 본문 평가는 99개 언어이며 모든 과제·언어의 동일 성능을 뜻하지 않음 |
| Alhanai 등 | 8 / 11 | 새로 인간 번역한 8개 언어 / 기존 3개를 합친 평가 11개 언어 | 번역된 WinoGrande·MMLU 일부·Belebele의 선택형 평가 |
| Nagar 등 | 1개 언어쌍 | Hindi–English 합성 code-switch 실험 | 질문만 섞고 answer choice는 영어인 CommonSenseQA 한 과제 |
| MMLU-ProX v1 | 13 | 영어 포함 같은 11,829문항을 번역한 평가 언어 13개 | 모델 학습 언어 수가 아니라 multilingual reasoning benchmark의 열 수 |

따라서 “534가 200보다 더 형평하다”거나 “46개 언어 모델이 15개 언어 모델보다 네 배 포용적이다”라는 계산은 성립하지 않는다. 먼저 무엇을 셌는지 맞추고, 그 다음 각 언어에서 어떤 문을 실제로 통과했는지 확인해야 한다.

## 2단계 — 작동 원리

### 형평성의 일곱 관문

[[저자원 언어]]의 일곱 자원 장부는 무엇이 부족한지 진단한다. 이 분석은 같은 장부를 언어 목록에서 실제 분배 결과로 이동하는 관문으로 재배열한다. 언어가 모델 설명서에 한 번 등장한 뒤 실제로 유용한 결과를 얻기까지는 최소 일곱 관문이 있다. 이 관문은 점수를 더해 하나의 순위를 만드는 체크리스트가 아니라, 어느 단계에서 주장이 끊기는지 찾는 감사 구조다.

| 관문 | 확인 질문 | 통과의 일부 증거 | 목록 수만 셀 때 빠지는 것 |
| --- | --- | --- | --- |
| 1. 목록·입력 | 언어·방언·문자 체계가 명시되고 입력 문자열을 안정적으로 처리하는가? | 언어·script 정의, normalization, 입출력 시험 | label 하나가 모든 방언·문자 변이를 대표한다고 가정 |
| 2. 데이터 | 자연·병렬·주석 자료가 얼마나 있고 어느 장르·시기·출처·권리를 가지는가? | 언어별 고유 token, 장르, sampling, 번역자, snapshot/version, provenance·license/terms 확인 상태 | 언어가 corpus에 한 줄 등장하면 충분한 학습 질량과 이용 권한이 있다고 봄 |
| 3. 토크나이저 | 같은 내용을 몇 token으로 나누며 문자·형태론을 얼마나 효율적으로 표현하는가? | fertility, unknown/fallback, sequence length, vocabulary coverage | 문자열을 잃지 않는다는 사실을 같은 계산비·성능과 같다고 봄 |
| 4. 용량·전이 | 공유 parameter와 sampling이 유익한 전이를 만들며 negative transfer를 억제하는가? | 언어별 ablation, target data 조건, 평균·최악 성능, forgetting | 다국어 공유 자체가 작은 언어에 공평하게 capacity를 배분한다고 봄 |
| 5. 평가 | 필요한 과제를 native 또는 검증된 자료로 측정하고 언어별 오류 분포를 공개하는가? | native/translated 구분, answer language, prompt·shot, metric, 인간 평가 | 평균·최고 설정 한 점을 모든 언어 능력으로 확대 |
| 6. 접근·비용·안전 | 공동체가 checkpoint/API와 compute를 실제로 이용하며 비용·latency·위험을 감당할 수 있는가? | 접근 조건, hardware·가격, 배치·현장 시험, domain별 안전성 | 공개 URL이나 API 존재를 실제 이용 가능성과 같다고 봄 |
| 7. 공동체 권한·결과 | 당사자가 언어·방언·자료·평가·배포·수정·중단을 결정하고 원하는 결과를 얻는가? | 참여 역할, 의사 결정권, 소유·이의 제기·유지 보수, adoption·교육·의료 outcome | 화자 수나 benchmark 향상을 권한과 삶의 개선으로 대체 |

첫 관문은 필요하지만 충분하지 않다. Tokenizer가 모든 Unicode 문자열을 표현해도 어떤 언어는 같은 문장을 훨씬 긴 sequence로 처리할 수 있다. 높은 benchmark accuracy를 얻어도 API 가격과 지연이 현지 서비스에 맞지 않을 수 있다. 현지 평가자가 참여해도 자료 포함과 모델 배포를 결정할 권한이 없을 수 있다.

### 자료 계보는 언어 수의 다른 분모다

언어별 token 수와 출처 목록은 계보를 추적하는 출발점이지만, 그 수치나 URL 하나가 이용 허락·동의·책임 주체를 판정하지는 않는다. 언어별 자료도 snapshot → 변환·mixture → release → training run의 어느 단계인지, 어느 조건이 확인됐고 무엇이 `unknown`인지 남겨야 한다. 이 기록 구조는 [[학습 데이터 생애주기와 출처 추적]]에서, 규모 수치와 권리·책임을 같은 지표로 환산할 수 없는 이유는 [[데이터의 양에서 권리와 책임까지]]에서 다룬다.

### 관문은 순차적이지만 한 번에 끝나지 않는다

일곱 관문은 `목록 → data → tokenizer → capacity/transfer → 평가 → 접근·안전 → 권한·outcome`으로 읽을 수 있다. 다만 실제 개발에서는 평가가 data 오류를 발견하고, 공동체 결정이 언어 경계와 과제를 바꾸며, 배포 비용이 모델·tokenizer 선택을 되돌리는 순환이 생긴다.

그래서 “지원한다”는 문장은 다음처럼 단계가 드러나야 한다.

1. 어느 언어·script 변형을 입력받는지 정한다.
2. 어느 시점의 어떤 data가 어떤 변환·mixture를 거쳐 run에 들어갔는지와 권리·동의 확인 상태를 기록한다.
3. Tokenizer와 normalization이 언어별 분절 길이·계산량에 미친 영향을 잰다.
4. Shared capacity·sampling·transfer가 언어별 이득과 부정적 전이를 어떻게 배분했는지 확인한다.
5. 실제 사용 과제와 맞는 native·translated benchmark를 구분해 평가한다.
6. Checkpoint·API·hardware·안전 조건 아래 실제 이용 비용을 측정한다.
7. 공동체가 무엇을 결정했고 어떤 장기 결과가 나타났는지 별도로 추적한다.

이 가운데 다섯째 관문까지 검증한 연구는 중요한 성능 근거를 제공한다. 여섯째·일곱째 관문을 측정하지 않았다는 이유로 그 성능 개선을 무효화해서는 안 된다. 반대로 성능 개선을 곧바로 디지털 격차 해소로 부를 수도 없다.

### 형평성 보고서의 최소 단위

언어별 결과를 보고할 때는 최소한 `언어·script/방언 × task/domain × data 조건 × tokenizer × model/transfer recipe × prompt/metric × 비용·접근 조건 × 공동체 역할`을 한 기록으로 묶어야 한다. 평균을 제시하더라도 표본 수, 분산, 최악 언어와 실패 유형을 함께 남긴다.

이 구조는 모든 언어에 똑같은 점수를 강제하자는 뜻이 아니다. 공동체마다 필요한 과제와 허용 가능한 위험이 다르므로, 형평성의 목표도 당사자와 함께 정의해야 한다. 중요한 것은 서로 다른 목표와 부담을 언어 수 한 개로 숨기지 않는 것이다.

## 3단계 — 기술과 근거

### 격차의 분모는 화자 수가 아니라 기술 효용이다

Joshi 등은 7,000개가 넘는 언어를 NLP 자원 수준으로 분류하면서 화자 수와 연구·자료·도구의 풍부함이 같은 척도가 아님을 보였다. 사용자가 많은 언어도 특정 과제의 병렬·주석 자료와 평가 도구가 부족할 수 있고, 논문과 자원이 일부 언어에 집중된 상태에서 모델을 “language-agnostic”이라고 부르면 그 분포가 가려진다.

Blasi 등은 약 6,500개 언어를 세계적 분모로 놓고, 과제별로 가용한 성능 자료와 수요 가정을 결합해 MT·NLU·QA·TTS·parsing·morphology의 기술 효용 격차를 추정했다. 이 두 연구가 여기서 제안한 일곱 관문을 직접 정의한 것은 아니다. 다만 언어가 목록에 존재하는지보다 어느 과제의 자료·도구·성능을 실제로 얻는지를 따로 측정해야 한다는 출발 근거를 제공한다.

### XLM: 평가 언어 수와 전이 조건을 함께 읽는다

XLM은 언어별 corpus에서 CLM과 MLM을 각각 검토하고 shared BPE와 Transformer parameter를 공유했다. 작은 corpus 언어가 학습에서 완전히 사라지지 않도록 언어 sampling 분포를 평탄화했으며, 병렬 문장이 있는 조건에서는 TLM으로 두 언어 문맥을 함께 마스킹했다. XNLI에서는 영어 task label로 fine-tune한 모델을 15개 언어 열에서 비교했다.

여기서 15는 **평가 언어의 분모**다. XLM 전이는 target-language label 없이 가능했지만 target 언어의 unlabeled text나 병렬 문장 조건까지 모두 없었던 것은 아니다. Shared BPE가 vocabulary를 함께 쓴다는 사실도 언어별 subword 길이와 downstream 성능이 같음을 보장하지 않는다. 따라서 XLM은 목록 관문보다 data·tokenizer·transfer·평가 관문을 어떻게 연결하는지 보여 주는 선행 사례다.

Rust 등의 9개 언어·5개 과제 통제 연구는 이 구분을 더 선명하게 했다. Pretraining data size와 별도로 언어에 맞는 tokenizer가 downstream 성능에 중요했고, multilingual model의 tokenizer를 monolingual tokenizer로 바꾸자 거의 모든 언어·과제에서 개선됐다. 이 결과는 모든 LLM에 동일한 배수의 불이익이 생긴다는 법칙은 아니지만, 문자 표현 가능성과 분절 효율을 분리해야 한다는 직접 근거다.

### BLOOM: 포함, 노출 질량, 공개 접근은 서로 다르다

BLOOM은 46개 자연어와 13개 프로그래밍 언어를 포함한 ROOTS를 사용했다. 자연어 46과 전체 언어 범주 59를 상황에 따라 섞으면 이미 분모가 달라진다. 더 중요한 점은 언어가 ROOTS에 포함됐다는 사실과 실제 byte·token·sampling 비중이 같지 않다는 것이다. ROOTS는 498개 구성 자료와 약 1.6TB 규모를 문서화했지만 언어·출처별 분포는 불균등했다.

Byte-level BPE는 다양한 문자열을 표현할 수 있는 넓은 fallback을 제공한다. 그러나 같은 의미를 몇 token으로 표현하는지, 긴 sequence 때문에 context·latency 비용이 얼마나 늘어나는지는 별도 측정이다. BLOOM의 공개 weight와 code도 검사·변형·독립 평가의 통로를 열었지만, 최종 학습에 A100 80GB GPU 384개와 1,082,990 compute hours가 사용됐다는 장부는 artifact 접근과 계산 자원 접근이 다름을 보여 준다.

ROOTS는 native-speaker 참여와 data governance를 corpus 구축의 일부로 다뤘다. 이는 단순한 언어 목록보다 넓은 시도다. 다만 참여 규모만으로 언어 공동체의 최종 결정권·보상·배포 통제가 균등했는지, BLOOM 사용이 실제 outcome을 개선했는지는 알 수 없다.

### NLLB: 200은 번역 범위이고, 40,000은 방향의 수다

NLLB 기술보고서는 약 200개 언어와 40,000개가 넘는 번역 방향을 평가했다. FLORES-200의 인간 번역 benchmark, human evaluation과 모든 FLORES-200 언어를 포괄하는 toxicity benchmark를 함께 사용했고, 이전 SOTA 대비 44% 상대 BLEU 개선을 보고했다. Data mining, sparsely gated MoE와 과적합 완화도 저자원 번역을 확장하는 핵심 수단이었다.

이 수치는 MT에서 이룬 중요한 범위와 성능이다. 하지만 200개 언어에 대한 자유 생성·추론·교육 튜터·의료 상담 능력이나 그 서비스의 안전을 측정한 것은 아니다. 번역 방향 수는 언어쌍의 조합을 세므로 언어 수와도 다른 분모다. NLLB는 data·capacity·MT 평가와 번역 안전 관문에 강한 근거를 제공하지만, 그 자체로 접근 비용이나 공동체 권한·사회적 결과를 닫지는 않는다.

### MaLA-500과 Aya: 넓은 모델 범위도 평가 분모가 다시 갈라진다

MaLA-500은 Llama 2에 Glot500-c의 534개 language-script 단위를 사용해 vocabulary를 260,164개로 확장하고 continued pretraining을 수행했다. 논문은 언어를 ISO 639-3 코드와 script의 결합으로 정의했다. 따라서 같은 구어 언어의 서로 다른 script가 별도 단위가 될 수 있으며, 534를 다른 논문의 단순 언어명 수와 바로 비교하면 안 된다.

평가 분모도 하나가 아니다. Intrinsic Glot500-c 평가는 534개 단위, Parallel Bible Corpus는 370개, SIB-200은 교집합 177개, Taxi1500은 351개를 사용했다. 평균 결과는 MaLA-500이 비교 모델을 앞섰지만 일부 언어에서는 Llama 2보다 하락했다. 이는 넓은 vocabulary와 continued pretraining의 가치를 보여 주는 동시에 “534개 언어가 같은 수준에 도달했다”는 해석을 막는다.

Aya는 101개 언어로 instruction fine-tuning한 13B 모델이며, 99개 언어에 걸쳐 판별·생성 과제, human evaluation과 simulated win rate를 포함한 평가를 제시했다. 101은 학습 범위이고 99는 평가 범위다. Mixture 구성, data pruning, toxicity·bias·safety 분석을 함께 수행한 점은 단순 count보다 넓지만, 모든 언어가 같은 data·과제·성능·공동체 권한을 얻었다는 결과는 아니다.

### Alhanai와 MMLU-ProX: 평가 언어를 늘리면 격차가 보인다

Alhanai 등은 WinoGrande와 MMLU 세 분야를 8개 아프리카 언어로 새로 인간 번역했다. 기존 Afrikaans·Zulu·Xhosa를 합쳐 11개 언어에서 여러 모델을 비교했고, 약 100만 번역 단어와 400개가 넘는 Llama-3-70B fine-tuning 결과를 분석했다. GPT-4o의 영어와 11개 언어 평균 격차는 과제에 따라 12.0–19.9 percentage points였다.

단일언어 fine-tuning은 평균 +5.6 points, 교차언어 전이는 평균 +2.9 points, 고품질 자료는 저품질 자료보다 평균 +5.4 points 향상됐다. 동일 문항 분할에서 영어의 적합–부적합 상승폭으로 보정한 문화 적합성 상승폭은 11개 언어 평균 +3.0 points였다. 이 비교들은 서로 다른 개입과 기준선이므로 한 번에 더해 “총 16.9 points” 같은 점수로 만들 수 없다. 문화 적합 질문에서 정확도가 높아졌다는 결과도 모델이 문화를 보존했다는 outcome은 아니다.

이 연구의 사람 번역·검증·평가 비용은 보고된 항목을 합치면 약 $40,218.78이었다. 저자원 언어 평가를 늘리는 일 자체가 전문 인력과 자원을 요구함을 보여 준다. 동시에 번역 benchmark, 선택형 과제와 11개 언어라는 범위가 실제 아프리카 사용 사례 전체를 대표하지 않는다는 한계도 남는다.

MMLU-ProX v1은 영어를 포함한 13개 언어에 같은 11,829문항을 두고 25개 모델을 5-shot CoT로 평가했으며, 그중 7개 모델에는 zero-shot 결과도 보고했다. 같은 Qwen2.5-72B의 5-shot CoT accuracy는 English 70.3%, Swahili 40.1%였다. 평가 열을 늘리자 영어 평균만으로 보이지 않던 큰 차이가 드러난 사례다.

이 분석은 수치와 번역 상태를 검증한 v1 snapshot을 판본 고정 비교 사례로 사용한다. 이는 공식 110 원문 공개 시점의 최신 MMLU-ProX 범위를 대표한다는 뜻이 아니며, 후속 29언어 확장판의 수치와 섞지 않는다. V1의 번역은 Claude 3.7 Sonnet→GPT-4o 반자동 번역 뒤 전문가 검증을 진행 중인 절차였고, 작성 당시 언어·과목 조합별 검증은 끝나지 않았다. 평가 계산 약 4,000 H100 GPU-hours를 포함한 개발 비용은 시장 가격으로 약 $60,000에 이른다고 보고했다. 같은 문항을 번역해 비교 가능성을 높였지만, native use case와 번역된 과제는 같지 않으며 benchmark 접근성도 비용과 전문성의 관문을 통과해야 한다.

### Nagar: “영어에 가까움”은 가장 좁은 조건에서 읽는다

Nagar 등은 CommonSenseQA 1,200개 질문을 Hindi–English code-switch text로 바꾸고 Llama-3-8B-Instruct를 [[QLoRA]]로 fine-tune했다. 질문만 code-switch했고 answer choice는 영어로 유지했다. 코드 혼합 지수(Code-Mixing Index, CMI) 2 조건의 평균 accuracy는 English 90.4%, Hindi 85.6%로 4.8-point 차이였다. Base의 78.0%와 54.0%보다 격차가 크게 줄었다.

이 결과는 합성 code-switch 자료가 한 조건에서 transfer를 도울 수 있다는 근거다. 그러나 Hindi–English 한 언어쌍, 다지선다 상식추론 한 과제, 영어 answer choice, 제한된 수동 검수와 non-archival work-in-progress라는 분모를 유지해야 한다. 여러 저자원 언어의 번역·자유 생성·의료·교육 능력이 영어 수준에 이르렀다는 결론으로 확대할 수 없다.

### 여덟 사례를 일곱 관문에 놓으면 보이는 것

| 사례 | Count의 분모 | 직접 통과를 시험한 관문 | 이 자료만으로 닫히지 않는 관문 |
| --- | --- | --- | --- |
| XLM | XNLI 15개 평가 언어 | data, shared tokenizer, transfer, 언어별 평가 | unseen language, 접근 비용, 공동체 권한·outcome |
| BLOOM | 46개 자연어 학습 범위 | data provenance·분포, tokenizer, 공개 artifact와 일부 governance | 언어별 동등 성능·비용, 실제 adoption·outcome |
| NLLB | 200개 MT 언어·40k+ 방향 | data mining, capacity, MT·human·toxicity 평가 | 범용 LLM 과제, 현장 배포와 공동체 outcome |
| MaLA-500 | 534개 language-script 학습 단위 | vocabulary, continued pretraining, 여러 교집합 평가 | 모든 단위의 동등 성능·접근·권한 |
| Aya | 101개 tuning·99개 평가 언어 | mixture, instruction tuning, 다면 평가·safety | 언어별 동일 data·오류·비용과 사회적 결과 |
| Alhanai 등 | 신규 번역 8개·평가 11개 | 인간 번역, fine-tuning/transfer, quality·문화 적합 평가 | 아프리카 전체 과제, 배포·유지·공동체 권한 |
| Nagar 등 | Hindi–English 한 쌍 | 합성 code-switch, QLoRA, 한 상식추론 정확도 | 다른 언어·과제·자연성·현장 접근과 outcome |

이 표에서 가장 넓은 count가 모든 열에서 가장 멀리 간 사례는 없다. 반대로 count가 작다고 연구 가치가 작은 것도 아니다. Alhanai의 8개 신규 인간 번역과 Nagar의 한 언어쌍 실험은 분모가 좁기 때문에 어떤 개입이 어느 조건에서 작동했는지를 더 구체적으로 읽을 수 있다.

실무 결론은 “언어를 적게 지원하라”가 아니다. 목록 관문을 넓히되, 새 언어마다 data·tokenizer·capacity·평가·접근·권한 장부를 함께 확장해야 한다. Count는 시작 진척도를 보여 주고, 형평성 평가는 그 뒤에 남은 불균형을 드러낸다.

## 검증과 한계

### 확인된 사실

- XLM의 15는 XNLI 평가 언어 수이고, shared BPE·target-language text·sampling·TLM 조건과 함께 보고됐다.
- BLOOM은 46개 자연어와 13개 프로그래밍 언어를 구분했고, ROOTS의 언어·출처 분포는 불균등했다. Weight·code 접근과 대규모 계산 자원은 별도 장부다.
- NLLB의 200은 MT 언어 범위이며 40,000개가 넘는 번역 방향, FLORES-200, human·toxicity 평가를 포함한다.
- MaLA-500의 534는 language-script 단위이고 평가별 언어 교집합은 534·370·177·351개로 달랐다.
- Aya는 101개 언어로 instruction fine-tuning하고 99개 언어 평가를 수행했다.
- Alhanai 등의 신규 인간 번역은 8개 언어, 총 평가는 11개 언어였다. 영어 대비 평균 격차가 남았고 fine-tuning·cross-lingual·data quality·문화 적합성은 서로 다른 비교였다.
- Nagar 등의 4.8-point English–Hindi 격차는 한 synthetic code-switch CommonSenseQA 조건에서 나온 값이다.
- MMLU-ProX v1은 13개 언어, 언어당 11,829문항과 25개 모델의 5-shot CoT 평가이며 후속 29언어 확장판이나 공식 110 공개 시점의 최신 범위를 대표하지 않는다.

### 비교를 통한 해석

여덟 사례를 함께 읽으면 language count는 목록 관문의 coverage를 나타내지만 형평성은 일곱 관문에 걸친 분포로 보아야 한다는 결론을 얻는다. 이는 각 논문이 직접 제안한 하나의 표준 지표가 아니라, 서로 다른 연구의 분모와 검증 범위를 비교해 만든 분석 틀이다. 이 때문에 문서의 `verification`은 `partial`이다. 개별 수치가 불확실해서가 아니라, 일곱 관문과 종합 결론이 근거를 가로지르는 비교 해석이기 때문이다.

이 분석은 benchmark 개선과 사회적 형평성을 분리하지만 둘을 대립시키지 않는다. 잘 설계된 언어별 benchmark는 불평등을 보이게 하고 개입 효과를 검증하는 필수 단계다. 다만 실제 형평성 결론에는 접근 비용, 안전, 당사자의 결정권과 장기 outcome이 추가로 필요하다.

### 아직 입증되지 않은 계보와 인과

이 비교는 XLM→BLOOM→NLLB→MaLA/Aya→2025 연구가 하나의 직접 계보를 이룬다고 주장하지 않는다. 문제의식·기법·평가 축이 겹치지만, 각 연구의 직접 영향에는 명시적 인용·설계 기록과 참여자 증언이 더 필요하다.

지원 언어 수를 늘린 것이 자동으로 평균 성능을 낮춘다거나 shared capacity가 필연적으로 작은 언어를 해친다는 인과도 여기서 입증되지 않는다. 그런 판단에는 같은 architecture·compute·data 조건에서 언어 수와 sampling을 바꾸는 통제 실험이 필요하다. 반대로 더 많은 언어를 목록에 넣으면 자연스럽게 공정성이 높아진다는 인과도 확인되지 않는다.

Alhanai·Nagar·MMLU-ProX의 benchmark 향상은 교육 성과, 임상 안전, 경제 참여, 언어 유지, 실제 adoption이나 공동체 권한의 개선을 측정하지 않았다. 합성 data와 번역 benchmark가 문법·문화 보존을 자동 보장한다는 인과도 없다. 이 미측정 상태를 실패의 증거로 읽지 않되, 완료된 사회적 성과로도 쓰지 않는다.

### 이 분석의 범위

선택한 자료는 주로 text model과 text benchmark다. 음성, 수어, OCR, 입력기와 보조공학의 언어 형평성은 같은 일곱 관문을 다시 정의해야 하며 이 문서가 직접 검증하지 않는다. `language`와 `dialect`의 경계도 순수한 기술 분류가 아니므로 ISO 코드 수가 공동체가 인정하는 언어 경계를 완전히 대신하지 않는다.

또한 이 여덟 사례는 저자원 언어 연구의 전부가 아니다. 일곱 관문은 누락을 찾는 비교 도구이지 보편적으로 검증된 가중 합산 지수나 인증 규격이 아니다. 실제 프로젝트에서는 해당 공동체와 사용 과제에 맞춰 관문별 기준과 우선순위를 다시 정해야 한다.
