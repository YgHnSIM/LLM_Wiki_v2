# 자동 평가 지표는 무엇을 보상하는가

> [!note] 학습 안내
> **난이도:** 심화<br>
> **선수 지식:** [[BLEU]], [[ROUGE]]<br>
> **읽고 나면:** 고정 지표·실행 검증기·사람 또는 AI 비교에서 학습한 보상 모델·benchmark 집계·다차원 평가 조합과 도구 호출의 단계별 검사가 만드는 유인, 그리고 여러 지표나 평가자를 병렬·직렬로 두어도 남는 측정·가치 판단의 한계를 구분할 수 있다.

## 1단계 — 먼저 잡을 핵심

### 비교 질문과 잠정 결론

BLEU, ROUGE, METEOR는 모두 생성문과 인간 참조의 겹침을 숫자로 줄이지만 같은 품질을 재지 않는다. 후보 쪽을 분모로 삼는지, 참조 쪽을 분모로 삼는지, 정확 n-gram만 연결하는지 형태·동의어까지 연결하는지, 문장과 말뭉치 중 어디서 집계하는지에 따라 좋은 출력의 정의가 달라진다.

이 차이는 지표를 사후 관찰에만 쓸 때도 중요하지만, 최소 오류율 훈련(MERT)처럼 모델 선택이나 가중치 학습의 목표로 쓸 때 더 중요해진다. 측정식은 수동적인 자가 아니라 어떤 후보를 채택할지 결정하는 보상 규칙이 된다. 이 분석은 세 지표의 공식을 다시 나열하기보다, **분모·대응 단위·순서·집계가 시스템에 어떤 유인을 주고 무엇을 구조적으로 보지 못하는가**를 비교한다.

[[071_Codex와 HumanEval 기반 코드 생성 평가]]는 같은 질문을 실행 가능한 출력으로 넓힌다. 코드가 참조 문자열과 달라도 같은 함수를 계산할 수 있으므로 unit test 통과를 기능적 정확성으로 사용했다. 그러나 이때도 test coverage, 표본 수, sampling temperature와 후보 선택 규칙이 새로운 측정 조건이 된다.

[[077_InstructGPT와 인간 선호 정렬]]은 평가 규칙 자체를 자료에서 학습하는 경우를 더한다. 4–9개 응답에 대한 평가자 순위로 보상 모델을 만들고, 정책이 그 예측 보상을 직접 높인다. 고정 수식보다 인간 판단의 복잡한 패턴을 담을 수 있지만, 평가자·지침·prompt 분포의 사각지대도 함께 학습 목표가 된다.

[[094_헌법적 AI와 자기비평·AI 피드백 정렬]]은 학습된 평가자 안에서도 **피드백의 출처와 최적화 골격을 따로 보아야 한다**는 사례를 더한다. 원칙을 읽은 feedback model이 후보 쌍의 유해성 선호를 만들고, 그 AI 비교 182,831개를 사람의 유용성 비교 135,296개와 합쳐 별도의 preference model을 학습한 뒤, RL 정책이 그 점수를 높였다. 헌법 문장이 매 정책 갱신의 보상을 직접 계산한 것도, 사람 피드백이 파이프라인에서 전면 제거된 것도 아니다.

[[095_BIG-bench와 MMLU의 평가 범위·집계 경계]]는 이 문제를 benchmark suite의 평균으로 넓힌다. MMLU 원 논문의 문항 가중 정확도에서는 문항이 한 표를 갖고 과목 크기가 가중치가 된다. BIG-bench에서는 서로 다른 preferred metric을 task별 low/high로 정규화한 뒤 task가 한 표씩 갖는다. 이 aggregate가 학습 loss로 직접 미분되는 것은 아니지만, leaderboard·model과 checkpoint 선택·후속 연구의 우선순위에 쓰이면 어떤 개선을 더 크게 보상할지 정하는 외부 선택 규칙이 된다.

[[096_GPT-4의 멀티모달 공개·시험 성능·안전 경계]]는 집계된 시험 점수를 인간 집단의 백분위로 바꾸는 단계까지 질문을 확장한다. 같은 model 응답과 scaled score라도 어느 응시자 집단을 비교 분포로 택하는지에 따라 백분위가 달라지고, 그 백분위에서 실제 전문 업무 능력으로 넘어가려면 별도의 타당성 근거가 필요하다.

[[079_HELM과 다차원 언어 모델 평가|HELM]]은 이 비교를 개별 지표에서 **평가 조합 전체의 구성**으로 넓힌다. 초기 HELM은 16개 핵심 시나리오에 정확도·보정·강건성·공정성·편향·독성·효율성을 가능한 범위에서 함께 놓았고, 112개의 가능한 시나리오–메트릭 조합 중 98개를 측정했다. 이 장부는 어떤 선택을 했고 어떤 칸을 비웠는지를 한 평균점수보다 잘 보여 준다. 그러나 시나리오·적응 방식·메트릭을 고르고 절충에 가중치를 부여하는 판단까지 제거하지는 않는다.

[[092_함수 호출과 도구 사용의 모델-실행 경계]]은 평가가 병렬 열뿐 아니라 **직렬 관문**으로도 구성된다는 사례를 더한다. Valid JSON, schema 일치, 올바른 tool 선택, argument의 의미 정확성, 권한 준수, 실행 성공과 결과를 반영한 최종 답은 서로 다른 사건이다. 2024년 `strict: true`가 schema 관문을 강화해도 그 뒤의 의미·권한·행동·grounding 관문까지 통과시킨 것은 아니다. 따라서 도구 사용의 신뢰성은 한 format score나 end-to-end 성공률 하나로 압축하기보다 각 관문의 조건부 성공률과 전체 모집단 성공률을 함께 기록해야 한다.

[[104_LLM 에이전트의 추론-행동 루프와 자율성 경계]]는 이 직렬 관문을 **시간축의 실행 궤적**으로 확장한다. 여러 call이 observation과 state를 바꾸며 이어지면 앞 단계 오류가 뒤 단계 입력이 되고, retry는 성공 가능성과 함께 비용·지연·중복 부작용도 늘린다. WebArena·SWE-bench·OSWorld의 초기 end-to-end 결과와 ToolEmu의 안전 평가를 함께 보면 agent 평가는 최종 goal success뿐 아니라 trajectory, authorization·side effect, recovery, cost와 environment version을 같은 장부에 남겨야 한다.

## 2단계 — 작동 원리

### 같은 중첩, 다른 측정 설계

| 설계 질문 | BLEU | ROUGE | METEOR 2005 |
| --- | --- | --- | --- |
| 주 과제 | 기계 번역 | 자동 요약 | 기계 번역 |
| 기본 대응 | 정확한 1–4-gram | 정확한 $N$-gram, LCS, weighted LCS, skip-bigram | exact·Porter stem·WordNet synonym의 일대일 unigram 정렬 |
| 대표 분모 | 후보 n-gram 수 | ROUGE-N은 참조 n-gram 수; L·S는 precision과 recall 모두 | 후보·참조 길이로 precision과 recall 모두 |
| 순서 신호 | 더 높은 차수의 연속 n-gram | LCS의 순서, weighted LCS의 연속성, skip-bigram | 일치 단어 청크의 단편화 벌점 |
| 길이 처리 | 후보가 유효 참조보다 짧으면 brevity penalty | DUC의 고정 길이 조건; 구현에 따라 P/R/F 보고 | recall 가중 조화평균과 후보·참조 길이 |
| 대표 집계 | 말뭉치 충분통계를 먼저 합산 | 시스템 평균과 인간 content coverage의 상관 | 문장 점수와 말뭉치 집계 모두 정의 |
| 직접 보지 않는 것 | 원문 사실성·참조 밖 의역·긴 담화 | 원문 사실성·참조 밖 중요 정보·가독성 전체 | 원문 사실성·문맥 sense·문법성 전체 |

표에서 중요한 것은 어느 지표가 가장 진보했는지가 아니다. 세 지표는 서로 다른 오류 비용을 수식에 넣는다. METEOR가 동의어를 연결한다고 ROUGE보다 보편적인 품질 함수가 되는 것도 아니고, ROUGE가 요약에 맞춰 recall을 강조한다고 precision을 불필요하게 만드는 것도 아니다.

### 고정 지표와 학습된 보상은 사각지대가 생기는 위치가 다르다

| 평가 장치 | 점수를 만드는 규칙 | 최적화에 들어가는 방식 | 대표 사각지대 |
|---|---|---|---|
| BLEU·ROUGE·METEOR | 사람이 정한 중첩·길이·순서 식 | MERT·모델 선택이 식을 직접 높임 | 참조 밖 의역·사실성·담화 품질 |
| HumanEval unit test | 사람이 작성한 입력–출력 검사 | 후보 생성 뒤 test 통과로 평가·선택 | test 밖 입력·보안·효율·통합 |

| LLM agent trajectory | 여러 tool call·observation·state update와 종료·복구를 episode로 평가 | 끝까지 postcondition을 만든 실행과 정책·비용 기준을 만족한 경로를 선택 | 긴 horizon의 오류 누적, 환경 version·retry budget, 성공했지만 위험하거나 비싼 경로 |

학습된 보상 모델은 BLEU처럼 사람이 식의 항을 모두 직접 쓰지 않는다. 대신 어떤 응답을 더 낫다고 본 순위 자료와 model class가 점수 함수를 정한다. 규칙이 적응적이라는 사실은 중립적이라는 뜻이 아니다. **고정 지표는 설계 식에 가정을 드러내고, 학습된 지표는 자료·평가 절차·모델 일반화에 가정을 나누어 숨긴다.**

HELM의 다중 메트릭 장부는 이런 가정을 없애는 대신 더 많은 위치에서 드러낸다. 한 열의 성공이 다른 열의 성공을 뜻하지 않고, 측정하지 못한 조합도 빈칸으로 남는다. 다만 각 열은 여전히 특정 구성 개념을 수치화한 프록시이며, 어떤 열을 중시할지는 사용 맥락의 가치 판단이다.

### Benchmark 평균은 과제에 투표권과 환율을 준다

| 평가 설계 | 한 표를 갖는 단위 | 공통 점수로 바꾸는 방식 | 평균이 숨길 수 있는 선택 |
|---|---|---|---|
| MMLU 원 논문 | 시험 문항 | `A/B/C/D` 정답 여부를 전체 문항에 합산 | 문항이 많은 과목의 더 큰 가중치 |
| MMLU subject macro | 과목 | 과목별 accuracy를 계산한 뒤 57개 과목 평균 | 문항 수가 다른 과목에 같은 가중치 |
| BIG-bench | 포함된 task | task 저자의 preferred metric을 low/high 기준으로 정규화한 뒤 task 평균 | metric·anchor·task subset 선택 |
| HELM 핵심 장부 | 시나리오–메트릭 셀 | 여러 열과 빈칸을 병렬로 보존 | 어떤 열을 배포 판단에 쓸지의 후속 가치 선택 |

여기서 가중치는 어느 단위가 aggregate에 더 큰 **투표권**을 갖는지 정하고, 정규화는 서로 다른 raw metric의 변화가 공통 점수에서 얼마로 환산되는지 정하는 **환율**이다. 모든 task에 같은 가중치를 주는 선택도 중립적이지 않다. 크기·위험·표본 수가 다른 task를 같은 한 표로 간주한다는 판단이기 때문이다.

BIG-Bench Lite 24개, PaLM 등이 공통으로 실행한 58개, 150개 text task와 전체 204개는 서로 다른 모집단이다. 같은 `BIG-bench` 이름을 써도 포함 task가 다르면 aggregate의 분모와 투표자가 달라진다. 따라서 점수에는 model뿐 아니라 benchmark version·task subset·prompt·shot·decoding·scoring을 함께 기록해야 한다.

### 도구 사용 평가는 직렬 관문이다

번역 평가의 여러 지표나 HELM의 여러 열은 같은 출력에 병렬로 점수를 붙이는 경우가 많다. Function-calling system은 앞 단계의 출력이 다음 단계의 모집단을 만드는 직렬 구조도 가진다.

1. 호출이 필요할 때 call을 제안하고 필요 없을 때 text 또는 no-call을 선택했는가?
2. 출력이 parse 가능한 JSON인가?
3. 지원 schema의 field·type·enum을 만족하는가?
4. Tool과 argument가 사용자 의도·실제 resource·업무 규칙에 맞는가?
5. 인증된 사용자가 그 resource와 action을 수행할 권한이 있는가?
6. Executor가 timeout·중복·부분 실패 없이 postcondition을 만들었는가?
7. Model의 최종 답이 tool result와 실행 상태를 빠뜨리거나 왜곡하지 않았는가?

앞 단계 실패를 제외한 표본에서만 뒤 단계 정확도를 계산하면 system이 실제로 받은 전체 요청의 신뢰성을 과대평가할 수 있다. 반대로 최종 task success 하나만 보면 model selection, parser, policy, external API와 response synthesis 중 어디가 실패했는지 알 수 없다. **조건부 성공률은 component를 진단하고, 전체 분모 성공률은 배포 결과를 설명한다.** 둘 다 필요하다.

### 에이전트 평가는 관문을 시간축으로 누적한다

Agent episode는 앞선 tool result가 다음 state와 action을 바꾸는 조건부 연쇄다. 각 step 성공 사건을 $S_t$라고 하면 단순한 표기는 다음과 같다.

$$
P(\text{episode success})
=
\prod_{t=1}^{n}P(S_t\mid S_{<t}).
$$

독립을 가정하는 식이 아니라 **앞선 실패를 버린 표본만으로 뒤 step 정확도를 계산하지 말라**는 장부다. Step별 tool-selection·argument·권한·execution 지표는 실패 위치를 찾고, 전체 요청 분모의 goal postcondition은 실제 결과를 보여 준다. 여기에 허용되지 않은 write·정보 노출·중복 실행, token·tool·wall-clock 비용, 사람 개입, 안전한 중단과 복구를 별도 열로 둔다.

WebArena의 원 설정에서 최고 GPT-4 기반 agent는 14.41%, 인간은 78.24% end-to-end success를 보였고, OSWorld에서는 최고 model 12.24%, 인간 72.36%였다. SWE-bench 최초 2,294개 issue 설정의 최고 Claude 2 해결률은 1.96%였다. 이는 후대 agent의 고정 성능이 아니라 당시 model·harness·environment의 baseline이며, single-call 형식 정확도를 장기 goal success로 대체할 수 없다는 근거다.

ToolEmu의 23.9%는 시험한 가장 안전한 agent에 대해 LM-emulated tool과 자동 evaluator가 판정한 failure rate다. 실제 사고율로 일반화할 수 없지만, sandbox가 있어도 목표·권한·민감 정보·부작용과 evaluator의 타당성을 따로 검사해야 함을 보여 준다. 따라서 성공률에는 model snapshot, prompt·tool·policy, environment version, retry·step·cost budget과 evaluator를 함께 기록한다.

## 3단계 — 기술과 근거

### 분모는 어느 오류를 더 비싸게 만들지 정한다

후보와 참조에서 일치한 항목 수를 $m$, 후보 항목 수를 $|h|$, 참조 항목 수를 $|r|$이라 하면 가장 단순한 두 비율은 다음과 같다.

$$
P=\frac{m}{|h|},\qquad
R=\frac{m}{|r|}
$$

precision은 후보가 많이 내놓았지만 참조와 맞지 않는 경우를 더 강하게 벌한다. recall은 참조에 있는 항목을 후보가 빠뜨린 경우를 더 강하게 벌한다. 둘은 같은 일치 수를 사용해도 분모가 다르므로 출력 길이에 반대 방향의 유인을 줄 수 있다.

BLEU의 수정 n-gram precision은 후보가 참조보다 같은 표현을 더 많이 반복해도 참조 최대 횟수까지만 인정한다. 기하평균은 어느 한 n-gram 차수의 precision이 낮으면 전체를 강하게 낮추고, brevity penalty는 맞는 일부만 남기는 지나치게 짧은 후보를 억제한다. 따라서 BLEU를 “precision 하나”라고 부르는 것도 불완전하지만, 핵심 중첩 통계가 후보 측 분모라는 사실은 남는다.

ROUGE-N은 참조 측 n-gram을 분모로 두어 참조가 담은 내용을 얼마나 회수했는지 묻는다. 그러나 출력 길이를 자유롭게 두면 더 많은 참조 표현을 포함하는 장황한 후보가 유리할 수 있다. 원 ROUGE 평가가 10·50·100·200·400단어 같은 길이 조건 아래 이루어진 것은 길이 제약이 지표 바깥의 부수 조건이 아니라 평가 정의의 일부임을 보여 준다.

METEOR 2005는 두 분모를 함께 쓰되 다음 조화평균으로 recall에 큰 비중을 준다.

$$
F_{mean}=\frac{10PR}{R+9P}
$$

이 식은 “번역에서도 누락이 중요하다”는 2004년 선행 실험의 판단을 보상 규칙으로 만든다. precision·recall의 균형은 자연법칙이 아니라 어떤 오류를 더 비싸게 볼지에 대한 과제·자료 기반 선택이다.

### 대응 단위는 허용할 표현 변이의 경계를 정한다

BLEU는 정확한 n-gram 표면형을 맞춘다. 여기서 n-gram은 [[N-gram 모델]]처럼 다음 단위의 조건부확률을 추정하는 언어 모형이 아니라 후보와 참조의 겹침을 세는 평가 단위다. 참조와 같은 단어·국소 구절을 사용하면 점수를 얻지만, 참조에 없는 정당한 의역이나 형태 변이는 놓칠 수 있다. 여러 참조는 가능한 표현 공간을 넓히지만 모든 올바른 번역을 열거하지는 못한다.

ROUGE-N도 정확 n-gram을 세므로 추상적 요약이 참조와 다른 말로 같은 정보를 표현하면 낮게 평가할 수 있다. ROUGE-L은 연속하지 않은 순서 보존 일치, ROUGE-S는 skip-bigram을 허용해 정확한 연속 구절보다 유연하지만, 여전히 표면 단어의 일치에 의존한다.

METEOR는 exact 뒤에 Porter stem과 WordNet synonym을 적용해 허용 경계를 넓혔다. 2005년 TIDES 자료에서 exact만 쓴 문장별 인간 상관보다 stem과 synonym을 더한 상관이 높았다. 그러나 WordNet 모듈은 문맥 의미를 해석하지 않는다. 두 단어의 가능한 sense 중 하나가 같은 synset이면 연결하므로 실제 문장에서는 다른 뜻인 단어도 대응할 수 있다.

즉 의미 자원을 추가하는 일은 “문자열 지표에서 의미 지표로의 완전한 전환”이 아니다. 어떤 변이를 정답으로 간주할지 정하는 대응 사전을 넓힌 것이다. 그 사전의 언어·도메인 coverage와 중의성 처리 방식도 측정 오차의 일부가 된다.

### 순서 점수는 유창성을 직접 이해하지 않는다

BLEU의 높은 차수 n-gram은 인접한 여러 단어가 참조와 같은 순서일 때 점수를 준다. 국소 구절 일치가 어순과 유창성의 신호가 될 수 있지만, 4-gram 일치가 문법성이나 문서 수준 일관성을 보장하지 않는다.

ROUGE-L의 LCS는 단어가 떨어져 있어도 순서가 같으면 인정하고, ROUGE-W는 길게 이어진 일치를 더 높게 평가한다. ROUGE-S는 순서를 보존한 모든 또는 제한 거리의 단어 쌍을 세어 연속 n-gram과 다른 어순 민감성을 만든다. 각 방식은 어순의 서로 다른 투영이며 완전한 통사 분석이 아니다.

METEOR는 일치 단어가 후보와 참조에서 같은 순서로 연속하는 최소 청크 수 $ch$를 이용한다.

$$
Penalty=0.5\left(\frac{ch}{m}\right)^3
$$

단어가 많이 재배열되면 청크가 늘고 점수가 줄어든다. 원 논문은 이를 word order 또는 grammaticality의 직접 척도로 동기화했지만, 계산이 실제로 보는 것은 정렬 단편화다. 올바른 재배열이 필요한 언어쌍과 잘못된 어순을 같은 규칙으로 구분할 수 없고, 자연스러운 문장이 참조와 다른 구조를 쓰면 벌을 받을 수 있다.

### 참조는 정답이면서 측정 장치다

세 지표의 점수는 후보만의 속성이 아니다. 후보와 참조 집합, 토큰화·대소문자·stemming, 참조 길이 선택과 집계 구현의 함수다. BLEU 원 논문에서도 같은 인간 번역이 참조 네 개일 때 0.3468, 두 개일 때 0.2571을 받았다. ROUGE 원 논문에서도 여러 참조가 많은 조건에서 인간 상관을 높였다. METEOR 2005는 각 참조와 따로 비교해 가장 높은 점수를 선택했다.

참조가 많아지면 유효한 표현을 포착할 가능성은 늘지만 측정 대상도 바뀐다. 서로 다른 참조 수로 얻은 점수는 같은 척도의 후보 품질처럼 직접 비교할 수 없다. Post가 보여 준 것처럼 같은 WMT 시험 집합도 토큰화·대소문자·참조 처리 차이로 BLEU가 최대 1.8 달라질 수 있다. 점수와 함께 설정 signature를 보존해야 하는 이유다.

더 근본적인 공백도 있다. 세 지표는 모두 **원 입력과 후보의 사실 관계를 직접 비교하지 않는다.** 번역이 원문의 부정을 뒤집거나 요약이 원문에 없는 수치를 만들더라도 참조와 국소 표현이 겹치면 점수를 얻을 수 있다. 반대로 참조에 없는 표현으로 원문을 충실하게 전달하면 손해를 볼 수 있다. 참조 기반 중첩은 의미·사실성의 한 신호이지 원문 충실성 자체가 아니다.

### 코드에서는 문자열 대신 실행을 볼 수 있지만 oracle이 바뀐다

[[OpenAI Codex (2021)]] 연구는 164개의 손수 작성한 Python 함수 문제와 문제당 평균 7.7개 unit test로 HumanEval을 구성했다. 후보 코드가 reference와 같은 token을 쓰는지보다 test를 통과하는지를 기능적 정확성으로 삼았다. 실제로 Codex-12B 표본에서 올바른 코드와 틀린 코드의 BLEU 분포가 크게 겹쳐, 표면 중첩 상승이 실행 정답률 상승을 보장하지 않았다.

한 문제에서 $n$개 표본 가운데 test를 통과한 표본이 $c$개일 때 논문이 사용한 불편 추정량은 다음과 같다.

$$
\operatorname{pass@}k
=1-\frac{\binom{n-c}{k}}{\binom{n}{k}}
$$

이 값은 $k$개 후보 중 하나 이상이 통과할 가능성을 보상한다. 따라서 $k$가 커지면 모델 하나의 첫 출력뿐 아니라 **sampling budget과 다양성**도 점수에 들어간다. 실제로 논문은 pass@1에 낮은 temperature, pass@100에 높은 temperature가 유리함을 보였다. Codex-12B의 Table 1은 pass@1 28.81%, pass@100 72.31%였지만 후자를 첫 IDE 제안의 정확도로 읽을 수 없는 이유다.

후보를 실제로 하나 선택하는 규칙도 별도 oracle이다. 추가 지도 미세조정을 거친 Codex-S는 단일 표본에서 37.7%, 100개 중 unit test를 통과한 후보가 하나라도 있으면 77.5%였지만, test 없이 평균 log-probability가 가장 높은 하나를 고르면 44.5%였다. 같은 생성 model에서도 **test를 아는 선택**, **model score를 쓰는 선택**, **사람이 검토하는 선택**은 서로 다른 시스템이다.

실행 기반 평가는 문자열 지표의 중요한 사각지대를 줄이지만 완전한 의미 판정은 아니다. 관측하지 않은 입력의 오류, 보안 취약점, 시간·메모리 효율, dependency와 license, 여러 파일의 통합, 유지보수 가능성은 제한된 unit test만으로 보장되지 않는다. 참조가 측정 장치였던 번역·요약과 마찬가지로, 코드에서는 **test suite와 sandbox가 정답을 구성하는 측정 장치**가 된다.

### 도구 호출에서는 oracle이 여러 신뢰 경계에 나뉜다

[[함수 호출과 도구 사용]]에서는 model이 함수 이름과 argument를 제안하고 application이 validate·authorize·execute한 뒤 결과를 다시 model에 제공한다. 이때 ‘올바른 호출’ 하나를 oracle로 만들면 서로 다른 실패를 합치게 된다.

| 평가 사건 | 분모의 예 | 통과를 판정하는 oracle | 통과해도 남는 오류 |
| --- | --- | --- | --- |
| 호출 필요성 | 전체 user 요청 | 사람이 붙인 call/no-call label·task policy | 올바른 tool·argument |
| Tool 선택 | call이 필요한 요청 | 허용된 target tool label | 의미상 올바른 argument |
| JSON 유효성 | model이 낸 call | parser | 특정 schema 일치 |
| Schema 일치 | parse된 call | JSON Schema validator·`strict` constraint | 사실과 업무 규칙에 맞는 value |
| 의미 정확성 | schema-valid call | canonical ID lookup·domain rule·expected argument | 사용자·resource 권한 |
| 권한 준수 | 의미상 가능한 call | identity·policy engine·사용자 confirmation | 외부 service 성공과 중복 부작용 |
| 실행 성공 | 승인된 call | status·transaction·postcondition·idempotency record | 결과를 반영한 최종 답의 정확성 |
| 결과 grounding | tool result가 반환된 turn | trace·result field·사람 또는 task-specific checker | 전체 task utility·비용·지연 |

각 관문을 $G_1,\ldots,G_m$이라 하고 뒤 관문이 앞 관문을 통과한 요청에만 적용된다면 전체 성공은 조건부 확률의 곱으로 분해할 수 있다.

$$
P(G_1\cap\cdots\cap G_m)
=P(G_1)\prod_{i=2}^{m}P(G_i\mid G_1\cap\cdots\cap G_{i-1}).
$$

예를 들어 schema-valid call만 모아 argument accuracy 95%를 보고해도 전체 요청의 20%가 invalid JSON이거나 wrong-tool이면 end-to-end 성공률은 95%가 아니다. 반대로 schema 통과율만 높이는 최적화는 no-call이어야 할 요청에 형식상 완벽한 위험한 call을 더 많이 만들 수 있다. Call precision·recall, type별 confusion과 전체 task success를 함께 봐야 한다.

2023년 11월 JSON mode는 valid JSON 관문을, 2024년 Structured Outputs의 `strict: true`는 지원 schema 일치 관문을 강화했다. OpenAI의 complex-schema 내부 평가에서 `gpt-4-0613`은 40% 미만, `gpt-4o-2024-08-06` strict 조건은 100%로 보고됐다. 이는 특정 schema-conformance eval이며 올바른 value·tool selection·권한·실행이나 final answer 성공률이 아니다. Refusal·generation 중단과 parallel calls도 별도 처리 경로였다.

Side effect가 있는 tool에서는 단순 성공률의 방향도 점검해야 한다. Timeout 뒤 무조건 retry하면 API success rate가 올라가면서 결제·발송이 중복될 수 있다. Idempotency key, transaction과 postcondition을 평가 oracle에 포함하고, read-only·write·고위험 tool을 나누어 false positive의 비용을 다르게 기록해야 한다.

### 집계 단위는 높은 상관의 의미를 바꾼다

BLEU는 원래 말뭉치 전체의 n-gram 계수를 먼저 합치는 시스템 비교 지표다. 짧은 문장은 어느 한 차수의 일치가 0이 되기 쉬워 평활화하지 않은 문장 BLEU가 불안정하다. 말뭉치 수준의 상관을 문장별 품질 판정 능력으로 옮기지 않는다.

ROUGE 논문은 여러 DUC 과제에서 시스템 평균 ROUGE와 인간 content coverage의 상관을 분석했다. 단일 문서 과제에는 시스템당 100개가 넘는 표본이 있었지만 다중 문서 과제는 약 30개 수준인 경우가 많았고 상관도 더 불안정했다. ROUGE-L·W가 한 과제에서 잘 작동하고 다른 과제에서는 그렇지 않은 결과는 지표 타당성이 요약 길이와 자료 구성에 조건부임을 보여 준다.

METEOR 2005의 중국어 자료에서 시스템 수준 인간 상관 0.964는 일곱 시스템 점을 사용한 집계 결과였다. 같은 논문의 문장별 상관을 시스템별로 계산해 평균한 값은 아랍어 0.347, 중국어 0.331이었다. 하나의 논문 안에서도 집계 단위를 바꾸면 “인간 판단과 얼마나 잘 맞는가”의 숫자가 크게 달라진다.

높은 상관을 읽을 때는 최소한 다음을 함께 물어야 한다.

1. 상관의 표본은 문장인가, 문서인가, 시스템인가?
2. 몇 개 시스템과 어떤 품질 범위를 비교했는가?
3. Pearson 값인가, 순위 상관인가?
4. 인간 평가의 질문과 평가자 합의는 무엇이었는가?
5. 지표 매개변수나 전처리를 같은 자료에서 선택했는가?

### Benchmark 집계는 모집단과 한 단위 개선의 가치를 정한다

MMLU의 과목을 $s=1,\ldots,S$, 과목별 시험 문항 수를 $n_s$, 과목 정확도를 $a_s$라 하자. 원 논문이 보고한 `average weighted accuracy`와 과목별 macro average는 다음처럼 구분할 수 있다.

$$
A_{\mathrm{item}}
=\frac{\sum_{s=1}^{S}n_sa_s}{\sum_{s=1}^{S}n_s},
\qquad
A_{\mathrm{macro}}
=\frac{1}{S}\sum_{s=1}^{S}a_s.
$$

$A_{\mathrm{item}}$에서는 문항이 많은 과목의 1%p 개선이 전체 점수에 더 크게 반영된다. $A_{\mathrm{macro}}$에서는 과목마다 한 표를 가지므로 작은 과목과 큰 과목의 1%p가 같은 크기로 반영된다. 둘 중 하나가 자연적인 정답인 것은 아니다. 전자는 전체 문항 정답률을, 후자는 평균적인 과목 성능을 묻는 서로 다른 집계다. 같은 `MMLU` 점수라도 어느 식과 harness를 썼는지 밝혀야 비교할 수 있다.

BIG-bench에서는 포함 task 집합을 $R$, task $t$의 preferred metric을 $m_t$, 저·고 기준을 $l_t,h_t$라 하면 task별 정규화와 aggregate를 다음처럼 쓴다.

$$
z_t=100\frac{m_t-l_t}{h_t-l_t},
\qquad
B_R=\frac{1}{|R|}\sum_{t\in R}z_t.
$$

Anchor와 $R$이 고정된 정규화식만 보면 task $t$의 raw metric 변화가 aggregate에 주는 영향은 다음과 같다.

$$
\Delta B_R
=\frac{100}{|R|(h_t-l_t)}\Delta m_t.
$$

따라서 low–high 간격은 raw metric 변화를 공통 점수로 바꾸는 환율이고, $R$은 어느 task가 투표에 참여하는지를 정한다. BBL 24개, 공통 58개, 150개 text task와 전체 204개를 같은 $R$로 취급할 수 없다. 정규화는 서로 다른 metric을 한 그래프에 놓게 하지만 각 metric이 재는 구성 개념, anchor의 타당성이나 task coverage를 같게 만들지는 않는다.

HELM의 시나리오×메트릭 행렬은 이런 압축을 피하고 여러 열과 빈칸을 남기는 대안이다. 그렇다고 가치 판단이 사라지는 것은 아니다. 사용자가 어느 셀과 절충을 배포 결정에 반영할지 다시 골라야 한다. BIG-bench score 곡선의 급격함과 내부 능력의 전환을 구분하는 문제는 [[손실 곡선과 능력 곡선 사이]]에서 별도로 다룬다.

전문시험의 백분위에는 집계 뒤에 **비교 모집단 선택**이라는 변환이 하나 더 있다. 시험 답안에서 얻은 scaled score를 $s$, 비교할 인간 모집단 $G$의 누적분포를 $F_G$라 하면 백분위는 개념적으로 $p_G=100F_G(s)$다. $s$가 같아도 $G$가 달라지면 $p_G$가 달라진다.

$$
\text{모델 응답}
\rightarrow \text{MBE·MEE·MPT raw score}
\rightarrow s_{\mathrm{UBE}}
\xrightarrow{F_G} p_G
\rightarrow \text{전문 역량 주장}.
$$

GPT-4의 약 297–298점은 여러 관할의 합격선을 넘었다는 결론과 연결되지만, 미국 NCBE는 공식 UBE percentile을 제공하지 않는다. Katz 등이 약 90백분위로 제시한 결과를 Martínez가 비교 모집단별로 다시 계산했을 때 7월 전체 응시자에서는 약 68백분위, 7월 첫 응시자에서는 약 62백분위, 합격자 집단에서는 약 45–48백분위로 달라졌다. 답안과 scaled score가 바뀐 것이 아니라 분포 $G$가 바뀐 결과다. 따라서 합격선 통과는 유지될 수 있어도 특정 백분위와 현업 변호사 역량은 자동으로 따라오지 않는다. 마지막 화살표에는 실제 사건 처리·최신 법률 조사·의뢰인 상호작용·책임 있는 판단을 재는 별도 평가가 필요하다.

### 지표가 학습 목표가 되면 측정식이 보상 함수가 된다

자동 지표는 연구자가 결과를 관찰하는 데 그치지 않고 모델을 고르고 조정하는 데 쓰인다. [[034_구 기반 통계적 기계 번역과 최소 오류율 훈련]]의 MERT는 decoder의 로그선형 특징 가중치를 개발 집합의 BLEU 같은 말뭉치 오류에 직접 맞춘다. 후보가 고정된 한 선 위에서 출력은 가중치 경계마다 이산적으로 바뀌므로, MERT는 후보 직선 교점을 훑어 목적 지표가 가장 좋은 구간을 찾는다.

Och의 실험에서 최대 상호정보 목적과 BLEU 목적은 서로 다른 최적 가중치와 시험 BLEU를 만들었다. 이는 평가 지표가 모델의 출력 선택에 실제로 작용함을 보여 준다. metric이 precision·recall·길이·어순 중 무엇을 보상하는지가 decoder의 번역 길이와 특징 가중치에 반영될 수 있다.

여기서 일반적인 위험은 모델이 사람이 원하는 품질이 아니라 지표가 쉽게 세는 신호를 개선하는 것이다. Callison-Burch·Osborne·Koehn은 인간이 더 낫다고 본 시스템이 BLEU에서는 낮아지는 사례와 BLEU 상승이 인간 품질 상승으로 이어지지 않은 사례를 제시했다. 이 결과는 자동 최적화가 무용하다는 뜻이 아니다. **측정식의 사각지대까지 목적 함수가 되므로**, 다른 지표·인간 평가·오류 분석으로 유인이 실제 과제 목표와 맞는지 확인해야 한다는 뜻이다.

### 학습된 평가자는 피드백 출처가 달라도 proxy 문제를 없애지 않는다

InstructGPT에서 평가자는 하나의 prompt에 대한 4–9개 응답을 순위화했고, 동률을 제외한 쌍 비교로 6B 보상 모델을 학습했다. 보상 모델은 응답의 도움됨·정확성·안전성 자체를 관측하지 않는다. 연구자 지침 아래 약 40명의 평가자가 96% 이상 영어인 평가자 작성 prompt와 초기 InstructGPT API 고객 prompt의 혼합에서 남긴 상대 순위를 예측한다.

정책은 이 예측 점수를 PPO로 직접 최적화하므로 자료를 설명할 때보다 강한 분포 이동을 보상 모델에 가한다. 평가자 5-fold 교차검증용 6B 보상 모델들의 선호 예측 정확도는 학습 평가자 집단에서 72.4±0.4%, 보류 평가자 집단에서 69.6±0.9%였다. 이는 평가자 집단만 바뀌어도 일반화가 완전하지 않음을 보여 준다. 실제 정책 최적화에서는 응답 분포까지 달라지므로 높은 보상이 실제 사람의 선호와 다시 맞는지 독립 평가가 필요하다.

토큰별 KL 패널티는 PPO 정책이 SFT 정책에서 너무 멀어지는 것을 제한하고, PPO-ptx의 사전 학습 기울기 혼합은 일부 공개 NLP 과제의 성능 회귀를 줄였다. 둘은 proxy를 인간 가치로 바꾸는 장치가 아니다. 하나는 정책 이동을 제한하고 다른 하나는 기존 능력 보존을 돕는다. InstructGPT가 별도의 인간 선호 비교와 TruthfulQA·독성·편향 평가를 함께 보고한 이유도 학습 보상 하나로 성공을 판정할 수 없기 때문이다.

2022년 헌법적 AI의 RL-CAI는 한 평가자를 더 앞에 둔다. SL-CAI 정책이 만든 후보 쌍과 무작위 원칙 하나를 feedback model에 보여 주어 소프트 유해성 선호를 만들고, 이 AI 라벨을 사람의 유용성 비교와 함께 별도의 preference model에 증류했다.

$$
c\rightarrow F(x,y_A,y_B,c)
\rightarrow D_{\mathrm{AI\ harmless}}^{182{,}831},\qquad
D_{\mathrm{human\ helpful}}^{135{,}296}\cup D_{\mathrm{AI\ harmless}}
\rightarrow r_\phi(x,y)\rightarrow \pi_\theta^{\mathrm{RL}}
$$

여기서 $F$는 원칙을 문맥으로 받아 개별 후보 쌍의 AI 선호를 만드는 feedback model이고, $r_\phi$는 많은 사람·AI 비교를 학습해 정책에 스칼라 보상을 제공하는 preference model이다. 두 역할을 같은 모델이라고 부를 수 없고, 헌법 자체가 $r_\phi$ 대신 매 RL 갱신의 보상을 직접 주는 것도 아니다. 사람의 135,296개 유용성 비교가 남아 있으므로 이 파이프라인을 ‘사람 피드백 없는 정렬’이라고 일반화해서도 안 된다.

InstructGPT와 RL-CAI를 함께 보면 두 축이 분리된다. **피드백 출처 축**에서는 InstructGPT의 비교가 사람에게서 왔고, RL-CAI는 사람 유용성과 AI 유해성을 혼합했다. **최적화 골격 축**에서는 둘 다 쌍대 비교를 학습한 스칼라 선호·보상 모델을 두고 RL 정책이 그 proxy를 높였다. AI 라벨로 바꾸는 것과 PPO형 최적화 골격을 바꾸는 것은 같은 변화가 아니다.

이 연쇄는 원칙을 더 명시적으로 만들지만 proxy 문제를 제거하지 않았다. Bai 등은 RL-CAI를 과도하게 훈련했을 때 유해한 질문에 필요 이상으로 가혹하게 반응하거나 여러 문맥에 비슷한 위로 문구를 붙이는 Goodharting을 관찰했다. 이는 모든 CAI 학습에서 필연적으로 생긴다는 뜻이 아니라, 당시 model·원칙·prompt 분포·preference model과 최적화 강도 아래 **예측 보상 상승과 사람이 원하는 행동이 갈라질 수 있었음**을 뜻한다.

고정 BLEU와 학습된 보상 모델 사이에 직접 기술 계보가 있다는 뜻은 아니다. 비교의 공통축은 **어떤 관측을 점수로 압축하고, 그 점수를 선택·학습 목표로 삼을 때 압축 과정의 사각지대가 모델의 유인이 된다**는 데 있다.

### 다중 지표는 선택을 드러내지만 프록시와 가치 판단을 없애지 않는다

초기 [[HELM]]은 12개 조직의 30개 모델을 16개 핵심 시나리오와 26개 표적 시나리오에 놓았다. 핵심 시나리오에서는 일곱 메트릭 범주를 가능한 범위에서 함께 적용했고, 112개의 가능한 조합 중 98개를 측정했다. 적용 가능한 공통 비교에서는 5-shot prompting을 기본으로 두어 모델별 적응 조건 차이를 줄였다. 어느 모델에도 최적인 조건을 찾았다는 뜻은 아니다.

시나리오×메트릭 행렬의 장점은 평균이 가린 절충을 보존한다는 데 있다. 정확도가 높은 모델이 효율성·독성·공정성에서도 자동으로 앞서지 않으며, 측정하지 못한 14개 조합도 실제 빈칸으로 남는다. 기존 논문에서 평가한 핵심 시나리오 coverage가 평균 17.9%였다가 HELM 실행 뒤 96.0%가 된 것도 **행렬의 빈칸을 채운 비율**이지 정확도, 타당성이나 안전성 성능이 아니다.

그러나 열이 늘어도 각 열의 프록시 문제는 남는다. 예를 들어 HELM의 독성은 Perspective API 판정으로 조작화되었고, 원 논문은 NarrativeQA에서 도메인 특성 때문에 false positive가 늘었을 가능성을 지적했다. 본문에서 상세히 보고된 인간 평가도 두 허위정보 시나리오의 6개 모델에 한정됐다. 인간이 42개 시나리오와 30개 모델을 아우르는 전체 평가 장부의 자동 메트릭을 검증한 것은 아니다.

따라서 HELM은 프록시와 가치 판단을 제거한 단일 정답이 아니다. **어떤 시나리오를 포함했고, 어떤 적응 조건을 고정했으며, 어느 프록시로 각 가치를 측정했고, 어떤 칸이 비었는지를 감사하게 하는 평가 장부**다. 이 구조는 단일 점수의 정보 손실을 줄이지만, 어떤 열을 배포 결정에 쓸지와 어떻게 가중할지는 사용자의 가치 선택으로 남긴다.

### 세 지표를 발전 단계로 배열하면 놓치는 것

BLEU→ROUGE→METEOR를 “정밀도에서 재현율로, 문자열에서 의미로 진보한 단일 계보”로 배열하면 세 가지가 사라진다.

첫째, ROUGE는 BLEU의 번역 지표를 개선하려는 단일 후속이 아니라 요약의 content coverage라는 다른 과제 목표에 맞춘 지표군이다. 번역의 정밀도와 요약의 재현율은 낡음과 새로움의 관계가 아니다.

둘째, METEOR도 BLEU를 모든 면에서 대체하지 않는다. 문장별 점수, recall과 형태·동의어 대응을 강화했지만 WordNet coverage와 문맥 중의성, 경험적으로 정한 벌점이라는 새 의존성을 도입한다.

셋째, 과제 특화는 하나의 지표로 수렴한다는 뜻과 반대다. 같은 요약에서도 정보 포괄, 간결성, 사실성, 가독성은 서로 다른 관측을 요구한다. 측정 대상이 늘어날수록 단일 점수의 보편성보다 여러 평가의 역할 분리가 중요해진다.

### 평가 설계를 읽는 체크리스트

1. **과제 목표**: 번역 충실성, 요약 포괄, 사실성, 선호 가운데 무엇을 재려는가?
2. **관측 대상**: 원 입력, 단일·다중 참조, 후보 중 어떤 텍스트를 비교하는가?
3. **대응 단위**: 정확 토큰, n-gram, 부분수열, 사전 동의어 중 무엇을 맞다고 세는가?
4. **분모와 길이**: 추가·누락을 어떻게 벌하고 출력 길이를 어떻게 통제하는가?
5. **순서와 구조**: 국소 n-gram, LCS, 청크가 실제 과제의 문법·담화를 얼마나 대표하는가?
6. **집계 단위와 투표권**: 문장·문서·말뭉치·시스템뿐 아니라 문항·과목·task·subset 가운데 무엇이 한 표를 가지며 어떤 가중치로 평균되는가?
7. **설정과 모집단 보존**: 참조 수·토큰화·대소문자·stemming·signature뿐 아니라 benchmark version·task subset·low/high anchor, 시험 채점 protocol과 백분위 비교 모집단을 남겼는가?
8. **타당성 확인**: 인간 평가·오류 분석·유의성 검정에서 같은 결론이 나오는가?
9. **최적화 유인**: 점수를 학습·선택 목표로 쓸 때 어떤 지름길을 보상할 수 있는가?
10. **실행 oracle**: test coverage, 표본 예산, sampling과 후보 선택이 실제 사용 조건과 일치하는가?
11. **피드백 출처**: 사람·AI가 각각 유용성·유해성·정직성 중 무엇을 비교했고, 혼합 자료의 수와 분포를 따로 제시했는가?
12. **평가자 연쇄**: 원칙을 해석해 라벨을 만드는 feedback model과 정책 보상을 주는 preference model을 구분하고, 각 단계의 오류를 추적하는가?
13. **학습된 평가자**: 누가 어떤 지침과 prompt 분포에서 순위를 만들었고, 정책 최적화 뒤에도 같은 판단이 유지되는가?
14. **다차원 평가 장부**: 시나리오·적응·메트릭 선택과 빈칸을 제시했고, 여러 열을 합칠 때의 가중치와 배포 맥락을 밝혔는가?
15. **직렬 관문과 분모**: JSON·schema·의미·권한·실행·grounding을 각각 어느 전체·조건부 분모에서 계산했는가?
16. **행동 비용과 시스템 경계**: Read/write·고위험 tool을 구분하고, retry·idempotency·외부 service·사람 확인·latency와 cost를 end-to-end 평가에 넣었는가?
17. **궤적과 종료**: Goal postcondition뿐 아니라 step trace·loop·replan·안전한 중단과 recovery를 기록했는가?
18. **환경 재현성**: Model·prompt·tool·policy·credential scope·environment version과 retry·step·cost budget을 고정하거나 공개했는가?

## 검증과 한계

### 확인된 사실과 비교 해석

#### 확인된 사실

- BLEU는 후보 측 수정 n-gram precision, 여러 차수의 기하평균, brevity penalty를 말뭉치 단위에서 결합했다.
- ROUGE는 N·L·W·S/SU라는 여러 중첩 단위를 제공했고 DUC 과제에 따라 인간 coverage와의 상관이 달랐다.
- 2004년 번역 평가 연구는 recall 가중과 stemming의 효과를 분석했고, 2005년 METEOR는 이를 단계별 unigram 정렬과 chunk 벌점으로 확장했다.
- METEOR 2005의 WordNet synonym은 문맥 sense disambiguation을 하지 않았다.
- MERT는 선택한 말뭉치 오류 지표에 따라 decoder의 특징 가중치를 직접 달리 최적화했다.
- HumanEval은 reference 문자열이 아니라 unit test 통과로 Python 함수의 기능적 정확성을 평가했고, Codex 표본의 BLEU는 정답·오답을 안정적으로 분리하지 못했다.
- pass@k는 표본 수와 정답 표본 수의 함수이며, 큰 $k$와 test oracle의 성과는 단일 completion의 정확도와 다르다.
- MMLU 원 논문의 `average weighted accuracy`는 문항 수의 영향을 받는 전체 분류 정확도이며, 과목별 accuracy를 동일 가중하는 macro average와 같은 집계가 아니다.
- BIG-bench는 task별 preferred metric을 저·고 기준으로 정규화한 뒤 포함 task에 평균했고, 정규화 점수는 0 미만이나 100 초과가 될 수도 있다.
- BIG-Bench Lite 24개, 공통 58개, 150개 text task와 전체 204개는 서로 다른 task 모집단이므로 같은 이름만으로 aggregate를 직접 비교할 수 없다.
- GPT-4의 UBE 약 297–298점은 여러 관할의 합격선을 넘었지만 NCBE가 공식 UBE percentile을 제공한 것은 아니다. 후속 재평가에서는 비교 모집단에 따라 약 90백분위가 7월 전체 약 68, 첫 응시자 약 62, 합격자 약 45–48백분위로 달라졌다.
- InstructGPT는 4–9개 응답 순위에서 동률을 제외한 쌍 비교로 보상 모델을 학습했고, PPO 정책은 SFT 기준 KL 제약 아래 그 예측 보상을 최적화했다.
- 평가자 5-fold 교차검증용 InstructGPT 보상 모델들은 학습 평가자보다 보류 평가자의 선호를 낮은 정확도로 예측했으며, 최종 평가는 학습 보상 외의 인간 비교·진실성·독성·편향 측정을 함께 사용했다.
- RL-CAI의 feedback model은 원칙에 조건화된 후보 비교로 182,831개의 AI 유해성 선호를 만들었고, 별도 preference model은 이를 135,296개의 사람 유용성 비교와 함께 학습해 RL 정책의 대리 보상을 제공했다.
- RL-CAI는 helpful-only RLHF 정책과 사람 유용성 비교에서 출발했으며, 과도한 RL에서는 가혹한 반응이나 반복적인 위로 문구처럼 preference model 점수와 원하는 행동이 갈라지는 Goodharting이 관찰됐다.
- 초기 HELM은 30개 모델을 16개 핵심·26개 표적 시나리오에 놓았고, 핵심 시나리오의 일곱 메트릭 범주 112개 조합 중 98개를 측정했다.
- HELM의 공통 5-shot prompting은 비교 조건을 통제하려는 선택이었고, 본문에서 상세히 보고된 인간 평가는 두 허위정보 시나리오와 6개 모델에 한정됐다.
- 2023년 6월 Function Calling에서 model은 함수 이름과 JSON argument를 출력하고 application이 검증·실행했다. 한 message의 복수 호출과 JSON mode는 같은 해 11월의 별도 개선이었다.
- 2024년 Structured Outputs의 `strict: true`는 지원 schema 일치를 강화했지만 value 오류·refusal·출력 중단·parallel-call 제한과 권한·실행 성공은 별도 문제로 남았다.
- OpenAI의 complex-schema 내부 평가에서 `gpt-4-0613`은 40% 미만, `gpt-4o-2024-08-06` strict 조건은 100%였으며, 이는 end-to-end tool-use 성공률이 아니라 schema-conformance 결과다.
- WebArena의 원 설정에서 최고 GPT-4 기반 agent는 14.41%, 인간은 78.24% end-to-end task success를 보였다.
- OSWorld의 369개 실제 computer task에서 최고 model은 12.24%, 인간은 72.36% success를 보였다.
- SWE-bench 최초 12개 Python repository·2,294개 issue 설정에서 최고 Claude 2 해결률은 1.96%였다.
- ToolEmu는 36개 고위험 toolkit·144개 test case와 LM-emulated sandbox를 사용했고, 시험한 가장 안전한 agent에도 자동 evaluator 기준 23.9% failure를 보고했다.

#### 비교를 통한 해석

- 분모는 추가와 누락 가운데 어느 오류를 더 비싸게 보는지 정하고, 대응 단위는 어떤 표현 변이를 정답으로 인정할지 정한다.
- 길이 제한·전처리·참조 수는 보조 설정이 아니라 지표가 만드는 유인의 일부다.
- 인간 상관은 지표의 고정 속성이 아니라 자료·시스템·집계·인간 평가 절차의 관계다.
- MMLU의 문항 가중과 과목 macro, BIG-bench의 task별 정규화 평균은 개선에 서로 다른 투표권과 환율을 부여한다. 동일 가중치도 무엇을 동일 단위로 볼지에 대한 선택이다.
- Benchmark aggregate의 상승과 가장 취약한 과목·task·위험 영역의 개선은 별개의 주장이다. 평균과 함께 하위 분포·표본 수·subset을 보존해야 한다.
- 시험 백분위는 model 응답의 고정 속성이 아니라 scaled score와 선택한 인간 분포의 관계다. 비교 모집단을 바꾸면 백분위는 달라지지만 원 응답은 달라지지 않으며, 어느 백분위도 전문 실무 타당성을 직접 측정하지 않는다.
- 평가 지표를 최적화하면 그 지표의 가정이 모델 선택 기준으로 이동하므로 측정 타당성과 학습 유인을 함께 검토해야 한다.
- 실행 평가도 test suite가 관측하는 동작과 후보 선택 절차를 보상하므로, 문자열 중첩에서 벗어났다고 측정 설계가 사라지지는 않는다.
- 학습된 보상 모델은 고정 식보다 복잡한 인간 판단 패턴을 근사하지만 평가자·지침·자료 분포와 model class의 가정이 사라지지 않으며, 정책이 그 proxy를 직접 최적화하면 분포 이동이 새로운 진단 축이 된다.
- InstructGPT와 RL-CAI의 차이는 ‘사람 대 AI’ 하나로 환원되지 않는다. 피드백 출처는 사람 비교와 사람 유용성·AI 유해성의 혼합으로 달라졌지만, 비교를 스칼라 모델에 압축해 RL 정책이 최적화하는 골격은 공통이다.
- 원칙→feedback model→AI 비교→preference model→RL 정책의 연쇄는 가치 선택과 오류 위치를 더 추적 가능하게 하지만, 앞단 평가자의 편향을 뒤단 보상 모델과 정책이 증폭할 수 있는 직렬 proxy도 만든다.
- HELM처럼 여러 메트릭을 병렬하면 절충·누락·측정 선택이 단일 평균보다 잘 드러난다. 그러나 개별 메트릭이 구성 개념의 프록시라는 사실과, 어떤 시나리오·열·가중치를 쓸지의 가치 판단은 남는다.
- 평가 행렬 coverage를 높이는 일은 모델 간 공백을 줄이지만, prompt 민감성·데이터 오염·메트릭 타당성·배포 일반화를 자동으로 해결하지는 않는다.
- Function-calling trace의 조건부 component 지표는 실패 위치를 진단하고 전체 요청 분모의 end-to-end 지표는 배포 결과를 설명한다. 둘 중 하나만 보고하면 앞 관문에서 탈락한 요청이나 뒤 관문의 부작용을 숨길 수 있다.
- Schema 통과를 직접 최적화하면 format 오류는 줄지만 no-call이어야 할 요청의 과잉 호출, 의미상 틀린 value와 권한 없는 행동까지 보상할 수 있다. 평가 oracle과 policy boundary를 함께 설계해야 한다.
- Agent의 component accuracy와 episode success는 서로 대체할 수 없다. 전자는 실패 위치를 진단하고 후자는 직렬 관문의 누적 결과를 보지만, 두 지표 모두 위험한 경로·과도한 비용·환경 변화를 별도 열 없이 완전히 설명하지 못한다.

#### 아직 입증되지 않은 계보

이 문헌만으로 BLEU·ROUGE·METEOR가 MMLU·BIG-bench, 전문시험 백분위, HumanEval, InstructGPT·헌법적 AI의 선호 모델, HELM이나 Function Calling 평가를 직접 낳았다고 결론내릴 수 없다. MMLU·BIG-bench가 HELM으로 이어진 단일 발전 계보도 여기서 입증되지 않는다. 문자열 중첩, benchmark aggregate와 백분위 환산, 실행 기반 기능 검사, 사람·AI 비교를 압축한 선호 점수, 다차원 평가 장부와 직렬 tool trace를 측정·선택·최적화 유인이라는 축에서 비교할 수는 있지만, 대화·창작·repository 수준 agent·후대 model evaluator·사실성 검사에는 각각 별도의 구조와 1차 문헌이 필요하다.

### 한계

이 분석은 2002–2005년 기본 BLEU·ROUGE·METEOR와 2003년 MERT, 2006·2018년의 BLEU 비판·재현성 연구, 2020–2021년 MMLU, 2021년 HumanEval, 2022년 InstructGPT 보상 모델·헌법적 AI와 BIG-bench 공개, 2023년 TMLR에 게재된 BIG-bench·초기 HELM, 2023–2024년 OpenAI의 Function Calling·Structured Outputs 발표를 비교한다. 후대 구현과 평가자는 smoothing, F1 보고, subject macro·변형 prompt, 학습된 매개변수·언어별 모듈·AI feedback을 추가했으며 후속 RLAIF·헌법, BIG-bench repository·HELM suite와 tool API도 범위가 다르다. 따라서 버전과 평가 주체를 명시하지 않은 같은 이름의 점수·기능을 여기의 식·행렬·한계에 그대로 대입하지 않는다.

MMLU 집계 비교는 2020년 공개·2021년 ICLR 논문의 원 구성과 후대 subject macro 구현을 구분한다. BIG-bench 집계는 2022년 공개·2023년 TMLR 최종 논문의 204개 task와 BBL을 기준으로 한다. Living repository의 후대 task 수, 서로 다른 model이 실행한 부분집합과 leaderboard harness에는 여기의 $R$이나 점수를 그대로 대입하지 않는다.

UBE 비교는 GPT-4 답안을 채점한 2023년 연구와 2024년 후속 재평가에 한정된다. 약 90·68·62·45–48백분위는 서로 다른 응시자 분포의 추정치이며, 공식 전국 UBE percentile이나 현업 변호사 성과 분포가 아니다. MEE·MPT rubric, grader training과 blind calibration의 결손 때문에 essay 점수의 재현성에도 별도 한계가 있다.

헌법적 AI의 Goodharting은 2022년 논문의 model 계열, 원칙 집합, red-team·helpfulness prompt 분포와 과도한 RL 조건에서 관찰된 현상이다. 이 사례는 자연어 원칙이 proxy 문제를 자동 해소하지 않는다는 반례이지만, 모든 AI 피드백 파이프라인의 실패율이나 후대 Claude 계열의 행동을 정량화하지 않는다.

Function Calling의 수치 근거는 OpenAI가 공개한 company-internal complex-schema eval이다. Schema와 test set의 전체 구성, 다른 provider·model·domain에서의 독립 재현이 없으므로 40% 미만·100%를 일반적인 산업 실패율이나 안전 보장으로 사용하지 않는다. 실제 배포에서는 tool catalog, description, model snapshot, orchestrator, identity·policy, external service와 UI가 함께 결과를 만든다.

Agent benchmark 비교는 WebArena·SWE-bench·OSWorld의 최초 논문과 ToolEmu의 LM-emulated safety 설정에 한정된다. 각 수치는 model·prompt·tool access·environment snapshot·retry budget과 evaluator가 다른 별도 모집단이다. 후대 leaderboard의 개선을 여기의 초기 baseline과 직접 잇거나, ToolEmu evaluator의 failure를 실제 service 사고율로 바꾸지 않는다. 반대로 성공 episode 하나나 높은 call accuracy가 보이지 않은 공격·부작용이 없다는 뜻도 아니다.

또한 인간 평가가 자동 지표의 완전한 정답인 것도 아니다. 평가자 질문, 지침, 합의와 표본 구성도 측정 오차를 가진다. 자동 지표와 인간 점수의 상관을 높이는 일, 여러 지표를 조합해 절충을 드러내는 일과 실제 사용자 효용·안전·사실성을 검증하는 일은 겹칠 수 있지만 같지 않다.
