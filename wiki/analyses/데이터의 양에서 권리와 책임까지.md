# 데이터의 양에서 권리와 책임까지

> [!note] 학습 안내
> **난이도:** 중급<br>
> **선수 지식:** [[학습 데이터 생애주기와 출처 추적]], [[말뭉치 기반 학습]] — snapshot·변환·mixture·release·training run이 서로 다른 기록이라는 사실을 알고 시작한다.<br>
> **읽고 나면:** raw bytes·문서·token·반복 노출·언어 수 같은 규모 지표가 무엇을 말하는지와, 그것만으로 권리·동의·대표성·재현성·downstream 책임을 결론 낼 수 없는 이유를 구분할 수 있다.

## 1단계 — 먼저 잡을 핵심

### 큰 수치는 학습 노출의 장부이지 권리 판정표가 아니다

언어 모델 논문은 수백억·수천억 token, 수백 개 component, 수십 개 언어를 말한다. 이 수치는 필요한 정보다. 예를 들어 GPT-3는 다섯 자료원의 sampling weight와 epoch를 붙인 300B-token mixture를, Chinchilla는 $D$를 누적 training token으로 두고 1.4T-token 학습 조건을 기록한다. 이런 수치는 **얼마나 많은 계산 입력이 어떤 비율로 노출됐는가**를 비교하게 한다.

그러나 큰 수치 하나가 다음 질문까지 답하지는 않는다.

| 수치 또는 기록 | 직접 알 수 있는 것 | 그 자체로 알 수 없는 것 |
| --- | --- | --- |
| raw bytes·문서 수 | 공개한 수집물의 대략적 물리 규모 | 원천별 권리·동의·개인정보 상태 |
| unique token·component 수 | 처리된 자료의 구성과 측정 분모 | 같은 자료가 실제 run에 같은 비율로 쓰였는지 |
| 누적 training token $D$ | model이 처리한 token 노출량과 compute 조건 | 고유 문서 수, 품질, 이용 허락, 공동체 대표성 |
| sampling weight·epoch | component별 노출 분포를 정한 설계 선택 | 그 선택이 공정하거나 적법하다는 결론 |
| dataset card·source URL | 재검토할 출발점과 공개된 문서화 범위 | 모든 원천의 권리·terms·consent가 검증됐다는 증명 |

따라서 “더 많이 학습했다”는 문장은 **규모·노출** 주장으로, “책임 있게 만들었다”는 문장은 **문서화·권리·의사 결정·정정 체계** 주장으로 따로 읽어야 한다. 둘은 서로 관련될 수 있지만 하나의 점수로 환산되지 않는다.

### 책임은 데이터 양의 반대말이 아니다

책임을 “작은 데이터만 쓰기”라고 부르면 문제를 잘못 줄인다. 작은 corpus에도 출처·동의·개인정보·이의 제기 문제가 남고, 큰 corpus도 source별 기록·검토·release 조건을 더 잘 남길 수 있다. 중요한 질문은 크기 자체가 아니라 **어떤 artifact의 어떤 version을 누가 어떤 근거와 규칙으로 포함·변환·배포·수정했는가**다.

이 문서는 법률 자문이나 특정 자료의 허가 판정이 아니다. 관할·시점·원문 license·terms·consent와 실제 이용 방식이 없으면 `permitted`나 `not permitted`로 채우지 않고, 확인된 기록과 `unknown`을 나눈다.

## 2단계 — 작동 원리

### 여섯 주장은 같은 데이터에 관해 서로 다른 증거를 요구한다

| 주장 | 물어야 할 질문 | 필요한 근거의 예 | 다른 주장으로 대신할 수 없는 이유 |
| --- | --- | --- | --- |
| 규모 | 얼마나 많은 byte·문서·token·노출을 셌는가? | 집계 규칙, tokenizer, epoch, sampling weight | token 수는 원천 권리나 품질을 측정하지 않는다 |
| 품질·분포 | 어떤 장르·언어·출처가 어떤 비율로 들어갔는가? | filter·dedup·mixture·평가 조건 | 높은 성능이나 넓은 분포가 이용 허락을 증명하지 않는다 |
| 문서화·추적 | snapshot에서 run까지 어떤 변환이 기록됐는가? | version, hash, config, data card, 책임 주체 | 잘 기록됐다는 사실은 내용의 권리·동의를 판정하지 않는다 |
| 권리·동의 | 원천별로 어떤 조건과 범위가 확인됐는가? | 원문 license·terms·consent·관할·시점 기록 | 공개 접근·project license·URL은 이를 자동으로 대신하지 않는다 |
| 재현 | 같은 release·mixture·code·환경·compute를 다시 맞출 수 있는가? | snapshot, sampling, seed, system config, run log | 권리 확인이나 dataset card만으로 exact retraining은 끝나지 않는다 |
| 책임·구제 | 누가 포함·제외·배포·수정·이의 처리·후속 사용 규칙을 결정하는가? | policy, maintainer, escalation, correction·withdrawal 기록 | dataset 규모나 contributor 수가 결정권·구제 효과를 보장하지 않는다 |

이 표의 목적은 빈칸을 모두 즉시 채우는 것이 아니다. 논문이 token 수를 보고할 때 그 수가 답하는 질문을 존중하되, 답하지 않는 칸을 성과나 허가의 결론으로 몰래 바꾸지 않는 데 있다.

### 규모 장부는 snapshot·release·run을 건너뛰면 끊어진다

GPT-3의 curated filter·fuzzy deduplication·다섯 자료원 가중치는 “300B token”이 원자료의 단순 길이가 아니라 변환·혼합·반복 노출의 결과임을 보여 준다. Chinchilla의 $D$도 unique document 수가 아니라 training 중 누적 처리한 token이다. 반면 The Pile은 22개 component의 raw size와 epoch 가중 effective size를 구분하고, Pile datasheet는 component의 provenance·processing·배포·저작권·PII·동의에 관해 무엇을 알고 무엇을 모르는지 질문한다.

이 서로 다른 장부를 연결하려면 [[학습 데이터 생애주기와 출처 추적]]의 세 레코드가 필요하다.

1. **원천 snapshot:** 언제 어떤 범위의 자료를 보았는지와 출처·조건의 확인 상태.
2. **처리된 release:** 어떤 filter·dedup·annotation·translation·version을 적용했는지.
3. **training run:** 어떤 mixture·sampling·epoch·seed·code·환경으로 실제 model에 노출했는지.

셋 중 하나가 빠졌다고 해당 연구가 무가치해지는 것은 아니다. 다만 빠진 단계는 다른 단계의 수치로 추정해 채우지 않는다.

### 경계 장부는 책임의 위치를 찾는다

이 분석은 새 lifecycle template을 만들지 않는다. 대신 규모 주장이 권리·책임 주장으로 넘어갈 때 어느 경계에서 추가 근거가 필요한지 표시한다.

| 경계 | 규모에서 확인하는 것 | 권리·책임으로 넘어가려면 더 필요한 것 |
| --- | --- | --- |
| 입력·대상 | 자료량, component, 언어·도메인 분모 | 원천별 조건, 영향 받는 사람과 자료 경계 |
| 변환 경로 | filter·dedup·mixture·sampling | 누가 규칙을 정했고 제외·손상이 어떻게 검토되는지 |
| 시간·상태·자원 | snapshot 시점, epoch, compute·storage | version 변경, 업데이트·중단과 책임자의 기록 |
| 결과 계약 | loss·benchmark·coverage·노출량 | 누구에게 어떤 위해·이익·수정 가능성을 약속하는지 |
| 지표·평가 기준 | token·문서·언어 수, 품질 proxy | 권리·동의·대표성·구제를 하나의 metric으로 가장하지 않는지 |
| 실패·복구 경계 | 오염·중복·누락 metadata·training failure | correction·withdrawal·incident의 접수·검토·downstream 알림 규칙 |
| 권한·책임·출처 추적 | data card와 공개 artifact | 포함·release·재배포·접근·정정 결정을 누가 하는지와 근거 |

이 장부는 “큰 model은 모두 위험하다”라는 결론도, “잘 문서화하면 모든 문제가 해결된다”라는 결론도 내리지 않는다. 비교할 주장의 경계를 더 정직하게 만드는 도구다.

## 3단계 — 기술과 근거

### The Pile: project-level 공개와 원천별 상태는 다른 층이다

The Pile은 22개 component, raw·effective size, 일부 deduplication과 분할 조건을 문서화해 mixture를 비교하기 좋은 사례다. Datasheet는 project 배포의 MIT 표기와 함께 underlying text의 저작권, host terms, PII, 저자 동의가 component마다 다르며 대규모 자료를 전수 확인할 수 없다는 한계를 기록한다.

이 사례에서 확인할 수 있는 것은 “project가 어떤 corpus artifact를 어떤 설명과 함께 배포했는가”다. **project-level license가 모든 원천 저작물의 권리를 새로 통일한다**거나, component 목록이 특정 item이 특정 run에 반드시 들어갔음을 보인다고 결론 내리면 안 된다. 규모·문서화·권리·실제 노출은 각각 더 좁은 증거를 요구한다.

### ROOTS와 BLOOM: governance는 파일 접근보다 넓다

ROOTS는 498개 구성 자료와 약 1.6TB의 다국어 corpus를 기술하고, 큰 초기 subset의 gated release, source-specific license·release 전략, data governance와 representation 한계를 함께 다룬다. BLOOM의 RAIL은 Model, Data, Complementary Material을 구분하고 model·파생물의 이용 제한과 재배포 고지를 적는다.

이는 공개·접근·책임을 한 단어로 줄이지 않는 실천적 사례다. Gate나 license가 있다고 원 저자 동의·공동체 대표성·downstream 피해가 자동 해결되는 것은 아니며, 반대로 제한적 release가 있어도 구성·조건·검토 과정을 공개해 감사 가능성을 높일 수 있다. 질문은 “열렸는가” 하나가 아니라 **어떤 artifact를 누가 어떤 조건으로 받고, 누가 포함·배포·수정 규칙을 정하며, 이의가 생기면 어디로 가는가**다.

### 규모의 이익과 책임의 비용은 함께 있지만 같은 인과가 아니다

파운데이션 모델 보고서는 넓은 사전 학습이 여러 downstream task에 재사용될 기회를 주는 동시에 model access, adaptation data, compute와 전문성이 집중될 수 있음을 지적한다. 여기서 규모는 새로운 capability와 재사용의 가능 조건이다. 그러나 규모가 커졌기 때문에 어떤 권리 체계가 더 낫다거나, 공개·gate·문서화가 실제 피해를 얼마나 줄였다는 효과까지 직접 입증하지는 않는다.

같은 이유로 **성능 개선**을 rights/compliance의 증거로, **문서화**를 fairness의 증거로, **license**를 exact reproducibility의 증거로 쓰지 않는다. 이 분석은 각 선택이 무의미하다고 말하는 것이 아니라, 좋은 결과를 주장할 때 필요한 증거의 종류를 추가하자는 것이다.

### 기존 문서의 책임을 겹치지 않게 둔다

[[데이터 품질과 분포 다양성은 같은 축인가]]는 filter·mixture·sampling·반복 노출과 성능의 관계를 맡는다. [[공개 가중치와 재현 가능성은 같은 축인가]]는 weight·code·data·license·compute·governance의 공개 벡터를 맡는다. 이 문서는 그 두 비교를 반복하지 않고, 규모 숫자가 rights/responsibility 결론으로 넘어갈 때 필요한 snapshot·조건·결정·구제 기록을 연결한다.

[[언어 수와 언어 형평성은 같은 축인가]]에서는 언어 count와 언어별 token 비중을 읽되, 언어 이름이나 token 수가 공동체의 허가·결정권·실제 outcome을 증명하지 않는다는 국소 규칙만 사용한다. lifecycle owner의 세부 변환 장부도 새 owner에 남긴다.

## 검증과 한계

### 확인된 사실

- GPT-3와 Chinchilla는 token 수를 각각 mixture·epoch·누적 노출과 결합해 보고했다. 이 수치는 training 조건의 측정값이지 고유 자료량·권리·동의의 단일 대리변수가 아니다.
- The Pile 논문과 datasheet는 component, processing, distribution과 project-level 배포 정보를 기록하면서 underlying text의 저작권·terms·PII·동의가 균일하지 않거나 전수 확인하기 어렵다는 범위를 함께 적었다.
- ROOTS는 source별 release 전략·gated subset·governance와 representation 한계를 기록했고, BLOOM RAIL은 Model·Data·Complementary Material의 적용 범위를 구분한다.
- Datasheets for Datasets는 motivation부터 maintenance까지 질문을 남기는 문서화 방법을 제시한다. 이 방법은 권리 판정이나 피해 감소의 자동 보증서가 아니다.

### 비교를 통한 해석

이 자료들을 함께 읽으면 규모, 품질·분포, 문서화, 권리·동의, 재현, 책임·구제는 **서로 의존할 수 있지만 대체할 수 없는 장부**라는 해석이 가능하다. 더 많은 token은 더 많은 training exposure를, 더 자세한 dataset card는 더 많은 재검토 가능성을 제공할 수 있다. 어느 경우에도 그것만으로 permission, consent, representation, exact retraining, downstream remedy를 증명하지는 않는다.

### 아직 입증되지 않은 인과와 범위

이 분석은 특정 filter·gate·license·datasheet가 실제 침해·편향·오용을 어느 정도 줄였는지 추정하지 않는다. 그러한 효과에는 비교 가능한 incident, 사용자·권리자 경험, enforcement, update·withdrawal 처리와 deployment 결과가 필요하다. The Pile, ROOTS, GPT-3, Chinchilla와 파운데이션 모델 보고서 사이에 단일한 직접 계보도 주장하지 않는다.

법적 허가·침해·공정성은 관할·시점·원문 조건·사용 행위와 사실관계에 따라 달라진다. 이 문서는 법률 자문이 아니며, 공개성·문서화·규모만으로 개별 자료의 권리 상태를 판정하지 않는다.

## 학습 확인

1. 누적 training token $D$, 고유 문서 수, source URL, dataset release version은 각각 어떤 질문에 답하며 어떤 질문에는 답하지 않는가?
2. The Pile의 project-level 배포 조건과 underlying text의 권리·terms·동의를 같은 것으로 읽으면 어떤 종류의 오류가 생기는가?
3. ROOTS의 gated release와 BLOOM RAIL을 함께 보더라도, 왜 실제 downstream 책임·구제 효과를 자동으로 결론 낼 수 없는가?

다음 연결에서는 물리 메모리와 문맥·검색·에이전트 상태를 위치, 수명, 갱신과 복구 보장으로 비교한다.
