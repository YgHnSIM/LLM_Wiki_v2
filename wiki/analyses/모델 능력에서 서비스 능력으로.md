# 모델 능력에서 서비스 능력으로

> [!note] 학습 안내
> **난이도:** 중급 → 심화<br>
> **선수 지식:** [[언어 모델 추론 서빙]], [[수치 형식·혼합 정밀도·양자화]] — prefill·decode·KV cache와 weight storage·compute dtype을 먼저 구분한다.<br>
> **읽고 나면:** model benchmark, 공개 weight, fine-tuning memory와 실제 서비스의 throughput·지연·energy·가용성·접근성을 같은 “능력”으로 합치지 않고, model–runtime–hardware–traffic–운영 정책과 외부 write 결과 계약의 공동 결과로 평가할 수 있다.

## 1단계 — 먼저 잡을 핵심

### 비교 질문과 결론

언어 모델의 능력은 보통 정답률, loss, 선호 평가와 생성 품질로 측정한다. 사용자가 경험하는 능력은 거기에 **실제로 실행할 수 있는가**, **요청이 몰려도 제시간에 응답하는가**, **오류와 장애 중에도 정한 품질을 유지하는가**, **감당할 자원으로 반복 제공할 수 있는가**가 더해진다.

따라서 이 장의 결론은 다음과 같다.

> Model capability는 서비스 능력의 필수 입력일 수 있지만 충분조건은 아니다. 서비스 능력은 model, runtime, hardware, workload와 운영 결과 계약이 함께 만든다.

2023년 공개 가중치 확산, QLoRA와 Mixtral은 접근 가능한 선택지를 넓혔다. 그러나 weight를 내려받을 수 있음, single-GPU fine-tuning이 가능함, active parameter가 적음, vLLM 배포 경로가 있음은 각각 다른 단계의 근거다. 어느 것도 특정 traffic에서 낮은 p99 TTFT·높은 가용성·낮은 energy/request를 단독으로 입증하지 않는다.

### 능력을 네 경계로 나눈다

| 경계 | 대표 질문 | 증거 |
| --- | --- | --- |
| Model | 어떤 입력에서 어떤 품질의 확률·출력을 만드는가? | Loss, benchmark, 사람 평가, 안전 평가 |
| 실행 | 어느 hardware·precision·runtime에서 한 번 돌릴 수 있는가? | Peak memory, kernel 지원, 단일 요청 latency |
| 서비스 | 동시 traffic에서 기한 안에 얼마나 많은 유효 요청을 끝내는가? | Throughput, TTFT·TPOT·p99, timeout·거절 |
| 운영·접근 | 누가 어떤 조건으로 반복 실행·수정·복구할 수 있는가? | License, artifact, 비용, 권한, SLO·복구 기록 |

이 경계는 서열이 아니라 측정 범위다. 높은 model 품질을 희생해 latency만 낮추거나, 빠른 정상 상태를 보이며 장애 복구를 생략하는 것도 완전한 개선이 아니다.

## 2단계 — 작동 원리

### 학습된 가중치에서 사용자 응답까지

한 서비스 요청의 경로를 펼치면 다음과 같다.

1. **Artifact 선택:** Model revision, tokenizer, adapter와 quantization을 고정한다.
2. **Runtime 변환:** Weight loading, kernel, tensor·pipeline·expert parallelism을 정한다.
3. **Admission·queue:** 요청을 받을지, 기다리게 할지, 어느 replica로 보낼지 결정한다.
4. **Prefill·decode:** Prompt를 처리하고 KV cache를 만들며 token을 순차 생성한다.
5. **후처리와 외부 action:** 안전 정책, tool·retrieval 호출, format 검증과 streaming을 수행한다. write action은 proposal만으로 완료되지 않고, authorization·필요한 confirmation·action ID·executor 경계를 지난다.
6. **종료·복구:** 결과를 반환하고 cache를 회수하며 timeout·오류·retry를 기록한다. 외부 write는 응답 코드 하나가 아니라 committed·failed·unknown outcome, reconciliation과 postcondition으로 종료 상태를 판정한다.

Model benchmark는 주로 1·4의 출력 품질 일부를 본다. Serving system은 2–6을 포함한다. RAG나 tool use가 들어가면 외부 저장소·network·다른 서비스의 지연과 실패도 종단 결과에 합성된다. 특히 응답 유실 뒤 effect가 unknown인 요청을 단순 성공·실패 어느 쪽에도 넣지 않으면 유효 성공률·tail latency·retry 비용을 잘못 읽게 된다.

### 세 종류의 “더 많은 사용자”

접근성도 하나의 말이 아니다.

- **Artifact 접근:** Weight·code·tokenizer를 얻을 수 있는가?
- **실행 접근:** 가진 hardware·runtime으로 memory와 kernel 조건을 만족하는가?
- **서비스 접근:** 비용·queue·지역·권한·가용성 조건 아래 실제 요청을 지속해서 보낼 수 있는가?

[[090_공개 가중치 LLM 파동과 서로 다른 공개 범위]]의 weight 공개는 첫째와 둘째의 선택지를 넓힌다. [[091_QLoRA와 4비트 양자화 미세조정]]은 특정 fine-tuning memory 장벽을 낮춘다. [[097_Mixtral의 생산 배포 효율 주장과 증거 경계]]의 공개 vLLM·SkyPilot 경로는 실행 가능성을 강화한다. 그러나 요청별 가격, p99, outage와 안전·privacy를 측정하지 않으면 셋째를 완전히 설명하지 못한다.

### 같은 model도 traffic에 따라 다른 시스템이 된다

길이 32인 prompt 100개와 길이 32K인 prompt 100개는 같은 request count여도 prefill FLOPs·KV cache·TTFT가 다르다. 출력 길이 분포가 넓으면 고정 batch에서 짧은 요청이 긴 요청을 기다릴 수 있다. 도착이 평균 10 requests/s여도 한꺼번에 몰리면 queue가 길어진다.

그래서 workload는 평균 하나가 아니라 적어도 다음 분포를 가져야 한다.

- 입력·출력 token 길이
- 도착 간격과 burst
- streaming·non-streaming 비율
- sampling·beam·parallel sample과 shared prefix
- tenant·priority와 deadline
- tool·retrieval·safety pipeline 사용 여부

Runtime 비교에서 이 분포를 고정하지 않으면 더 높은 throughput이 scheduler 개선인지 더 짧은 요청 때문인지 알 수 없다.

### 처리량과 지연은 load 곡선으로 읽는다

낮은 부하에서는 GPU가 놀아 작은 batch로도 지연이 짧을 수 있다. 요청률을 올리면 batch 효율과 throughput이 증가한다. Capacity 근처에서는 queue가 쌓여 TTFT와 tail latency가 급격히 커지고, memory 부족은 preemption·거절·timeout을 만든다.

따라서 단일 “최대 tokens/s”보다 다음 곡선을 비교한다.

| 부하 점 | 처리량 | p50·p99 TTFT | p50·p99 TPOT | 오류·거절 | 품질 |
| --- | --- | --- | --- | --- | --- |
| 낮음 | Idle이 많은 기준 | 짧을 가능성 | 작은 batch 조건 | 거의 없음 | 기준 |
| 목표 | SLO를 만족하는 운영점 | 기한 이내 | 기한 이내 | 허용치 이내 | 기준 유지 |
| 포화 | Queue가 빠르게 증가 | 급증 가능 | 경합 증가 | preemption·거절 증가 | timeout 포함 확인 |

**유효 처리량**은 정한 품질과 기한 안에 성공한 요청만 세어야 한다. 늦거나 실패한 요청을 분모·분자에서 어떻게 처리했는지 밝힌다.

## 3단계 — 기술과 근거

### 이 본편의 측정 장부

| 항목 | 기록 |
| --- | --- |
| 작업 | 동시 사용자의 prompt prefill과 자기회귀 decode를 streaming 서비스로 완료하기 |
| 규모 | Model·device·replica 수, prompt·output 길이 분포, 도착률·burst와 동시 요청 수 |
| 결과 계약 | 같은 model 품질·sampling 조건과 정한 deadline 안에 성공한 유효 응답, 그리고 외부 write가 있다면 postcondition으로 판정한 committed·failed·unknown outcome |
| 시스템 경계 | Model weight에서 runtime·accelerator·scheduler·KV cache·network·후처리·복구까지 |
| 고정 조건 | Model revision, quantization, hardware, runtime, parallelism, traffic와 안전 정책 |
| 지표 | TTFT·TPOT·종단 지연의 p50·p95·p99, 유효 처리량, peak memory, energy/request, 성공·거절·timeout·duplicate, unknown 해소 시간과 postcondition 확인률 |

이 장부가 다른 두 실험의 “빠르다”를 비교할 공통 계약이다. 한 열이 달라졌다면 같은 model 이름이나 requests/s만으로 우열을 정하지 않는다.

### 역사적 경계가 칩에서 서비스로 넓어졌다

2017년 1세대 TPU 평가는 최고 TOPS만 제시하지 않았다. 실제 data-center inference workload와 99백분위 응답 시간 제약, 성능/W를 함께 보았다. 이는 accelerator의 능력을 사용 중인 서비스 조건에서 측정한 사례다.

2022년 Orca는 자기회귀 생성이 여러 iteration으로 구성돼 request-level batch에 빈 slot과 대기가 생긴다는 문제를 다뤘다. Scheduler가 iteration마다 batch를 다시 구성하고 선택된 연산을 batching하는 방식으로 model graph 밖의 시간 사용을 바꿨다.

2023년 vLLM은 KV cache가 요청 길이에 따라 동적으로 자라며 contiguous reservation·fragmentation·중복 복사가 batch 수를 제한한다는 문제를 다뤘다. PagedAttention은 cache의 논리 순서와 물리 block을 분리해 필요한 만큼 할당·공유하고, 더 많은 동시 요청을 memory에 넣었다.

같은 해 speculative decoding은 별도 draft model이 여러 token을 제안하고 target이 병렬 검증하는 방법으로 token별 순차 round의 비용을 줄였다. 정확한 sampling 절차 아래 target 분포를 유지하지만 acceptance와 두 model 비용이 wall-clock을 좌우한다.

이 흐름은 model architecture의 품질 향상만으로 설명되지 않는다. **특화 hardware → 반복 workload용 scheduler → 동적 model state memory manager → 생성 절차의 검증형 병렬화**가 실행과 서비스의 별도 연구 대상이 된 과정이다.

### 공개·양자화·희소성이 바꾸는 서로 다른 장부

| 변화 | 직접 넓히는 능력 | 남는 서비스 질문 |
| --- | --- | --- |
| 공개 weight·code | Local inspection·수정·배포 선택지 | Hardware·운영 인력·license·보안과 SLO |
| QLoRA | Frozen quantized base의 fine-tuning memory 절감 | Inference kernel·KV cache·batch·latency |
| Mixtral top-2 | Token당 active expert FLOPs와 model quality trade-off | Total weight memory·expert dispatch·tail |
| Weight·cache quantization | 저장·전송 byte 감소 가능 | Dequantization·quality·hardware kernel |
| PagedAttention | KV cache fragmentation·sharing 개선 | Model weight, decode 순차성, queue·장애 |
| Speculative decoding | Accepted token당 target round 감소 가능 | Draft cost·acceptance·traffic별 이득 |

이 표에서 “효율”은 공통 형용사일 뿐 같은 숫자가 아니다. Training peak memory, active FLOPs, KV cache byte, throughput과 p99는 각각 다른 열이다.

### vLLM 결과를 올바른 크기로 읽기

vLLM 논문은 여러 model·dataset에서 FasterTransformer와 Orca보다 높은 request rate를 비슷한 latency로 유지했고, 요약 수치로 2–4배 throughput을 제시했다. ShareGPT·Alpaca의 sequence 길이, OPT model 규모와 GPU 구성, sampling 방식에 따라 차이가 달랐다. OPT-175B·짧은 Alpaca sequence처럼 KV cache 공간이 넉넉하면 비교 시스템도 큰 batch를 만들 수 있어 vLLM 이점이 줄었다.

더 중요한 반례는 kernel과 종단 결과가 반대 방향일 수 있다는 점이다. PagedAttention kernel은 block table·branch·가변 길이 처리 때문에 비교 attention kernel보다 20–26% 높은 latency를 보였지만, memory 낭비를 줄여 전체 service throughput은 높아졌다. Kernel microbenchmark 하나를 서비스 능력으로 자동 승격할 수 없다.

### 품질·지연·에너지·가용성의 공동 계약

서비스 개선 $A$와 기준 $B$를 비교하려면 최소한 같은 model output 계약과 workload에서 다음을 기록한다.

| 항목 | 필요한 기록 |
| --- | --- |
| 품질 | 같은 checkpoint·sampling인지, quantization·draft·timeout이 출력 분포를 바꾸는지 |
| 지연 | Queue 포함 TTFT·TPOT·종단의 p50·p95·p99 |
| 처리량 | Requests/s와 input·output tokens/s, SLO 안의 유효 처리량 |
| Memory | Weight·KV cache·temporary·fragmentation과 peak·steady state |
| 에너지 | GPU·CPU·memory·network의 측정 경계, idle·replica와 요청당 joule |
| 가용성 | 성공·timeout·OOM·거절, committed·failed·unknown outcome, retry·reconciliation과 장애 탐지·복구 시간 |
| 접근성 | Artifact·license, 필요한 hardware와 지역·가격·권한 |

Latency가 절반이어도 전력이 두 배이고 같은 수의 replica를 유지하면 energy/request가 자동으로 절반이 아니다. Quantization으로 한 GPU에 model이 들어가도 드문 OOM이나 품질 저하로 요청을 재시도하면 유효 비용이 달라진다. 빠른 정상 상태와 장애 중 가용성도 별도 결과다.

여기서 [[LLM 추론 에너지 지표]]는 GPU·node·service 경계와 J의 분자·분모를, [[전력에서 서비스 결과 계약까지 무엇을 세어야 하나]]는 그 수치를 quality·deadline·traffic·retry가 포함된 유효 결과 계약에 묶는 일을 맡는다. [[함수 호출과 도구 사용]]은 action ID·reconciliation·postcondition·compensation의 한 action protocol을 맡는다. 이 본편은 어느 쪽의 회계식을 반복하지 않고, 선택한 runtime·hardware·workload에서 그 계약이 실제 서비스 능력으로 어떻게 드러나는지만 기록한다.

외부 write가 있는 service에서 “응답 성공률”은 충분한 분모가 아니다. timeout 뒤에 effect가 unknown이면 새로운 요청처럼 세지 말고 같은 logical action의 해결까지 추적해야 한다. unknown을 reconciliation하는 조회·대기·사람 escalation은 latency와 cost를 늘릴 수 있고, 같은 key의 안전한 재시도 계약이 없으면 duplicate effect 위험도 남는다. 따라서 서비스의 좋은 결과는 model이 응답을 냈다는 사실이 아니라, 정한 deadline·품질·권한 조건 아래 postcondition을 확인한 action까지 포함해 세어야 한다.

### CS_WIKI와 함께 읽기

[CS_WIKI의 「평균 성능은 왜 서비스의 컴퓨팅 능력을 설명하지 못하는가」](https://yghnsim.github.io/CS_Wiki/analyses/%ED%8F%89%EA%B7%A0-%EC%84%B1%EB%8A%A5%EC%9D%80-%EC%99%9C-%EC%84%9C%EB%B9%84%EC%8A%A4%EC%9D%98-%EC%BB%B4%ED%93%A8%ED%8C%85-%EB%8A%A5%EB%A0%A5%EC%9D%84-%EC%84%A4%EB%AA%85%ED%95%98%EC%A7%80-%EB%AA%BB%ED%95%98%EB%8A%94%EA%B0%80/)는 평균·fan-out·tail·유효 처리량을 분리한다. [「빠른 서비스는 왜 가용한 서비스를 보장하지 않는가」](https://yghnsim.github.io/CS_Wiki/analyses/%EB%B9%A0%EB%A5%B8-%EC%84%9C%EB%B9%84%EC%8A%A4%EB%8A%94-%EC%99%9C-%EA%B0%80%EC%9A%A9%ED%95%9C-%EC%84%9C%EB%B9%84%EC%8A%A4%EB%A5%BC-%EB%B3%B4%EC%9E%A5%ED%95%98%EC%A7%80-%EC%95%8A%EB%8A%94%EA%B0%80/)는 정상 상태의 빠른 응답과 실패 탐지·복구를 분리한다. 이 장은 두 경계를 LLM의 model 품질, KV cache와 token streaming에 연결한다.

## 검증과 한계

### 네 인과 관계를 분리한다

- **직접 영향:** Orca의 iteration-level scheduling은 vLLM이 비교·채택한 serving 선행선이며, vLLM은 paging에서 영감을 받은 KV block 관리를 명시했다.
- **가능 조건:** GPU·TPU, 낮은 정밀도 kernel, 충분한 HBM·network와 공개 runtime은 큰 model을 반복 실행할 수 있게 하지만 어떤 model 품질이나 SLO가 나온다는 직접 원인은 아니다.
- **병행 맥락:** *The Tail at Scale*의 평균·tail·fan-out 분석은 LLM service를 평가하는 시스템 원리를 제공한다. LLM architecture의 직접 계보로 주장하지 않는다.
- **후대 유추:** 공개 weight를 과거의 범용 컴퓨터처럼 “누구나 같은 능력을 가짐”으로 읽는 것은 후대 유추다. 실제 hardware·비용·license·운영 역량의 비대칭이 남는다.

### 확인된 사실, 비교 해석, 미입증 계보

확인된 사실은 공개 weight·QLoRA·Mixtral이 서로 다른 artifact·fine-tuning·active compute 경계를 넓혔고, Orca·vLLM·speculative decoding이 scheduler·cache·decode 절차의 별도 병목을 다뤘다는 것이다. TPU와 vLLM 자료는 peak·kernel 수치가 service-level latency·throughput과 같지 않음을 구체적으로 보인다.

비교를 통한 해석은 LLM 시대의 컴퓨팅 능력이 model parameter 안에만 있지 않고 **사용자가 기한 안에 유효한 결과를 받는 전체 경로**에 있다는 것이다. 이 해석은 여러 자료의 측정 경계를 합성한 것이지 어느 한 논문의 직접 문장이 아니다.

아직 입증되지 않은 계보는 memory wall·operating-system paging·tail-tolerant service가 특정 LLM architecture나 vLLM을 필연적으로 낳았다는 주장이다. vLLM은 paging의 영감을 직접 밝히지만, 더 넓은 컴퓨터사 흐름을 단일 발명 계보로 만들지 않는다.

이 문서는 특정 상용 API의 현재 가격·uptime·모델 정책을 평가하지 않는다. Security, privacy, content moderation, multi-region failover와 전력망·carbon accounting도 별도 운영 자료가 필요하다. 논문 속 speedup은 당시 hardware·software·baseline 결과이며 최신 runtime 순위를 뜻하지 않는다.

이 문서는 idempotency key, transaction, compensation이나 postcondition의 구현 owner가 아니다. HTTP의 제한된 method 의미, request ID와 long-running operation 지침은 service interface가 명시한 계약에서만 해석한다. 한 action의 proposed·confirmed·committed·failed·unknown 상태와 reconciliation·감사 경계는 [[함수 호출과 도구 사용]]에서 완결한다.

## 학습 확인

1. MMLU 점수가 높고 weight가 공개된 model이 특정 사용자에게 “가용한 서비스”가 되기까지 확인할 네 경계를 적어라.
2. PagedAttention kernel 자체가 느려도 end-to-end throughput이 높아질 수 있는 이유를 KV cache memory와 batch 수로 설명하라.
3. 같은 model·workload에서 runtime 두 개를 비교하는 실험표를 설계하라. 품질·TTFT·TPOT·p99·유효 처리량·memory·energy·실패를 모두 포함해야 한다.

다음에는 [[공개 가중치와 재현 가능성은 같은 축인가]]에서 artifact 접근과 학습·실행 재현의 차이를 더 자세히 보고, [[훈련 병렬성과 생성 순차성은 다른 축이다]]에서 service가 물려받은 token별 의존성을 복습한다.
