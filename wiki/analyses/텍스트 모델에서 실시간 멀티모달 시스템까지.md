# 텍스트 모델에서 실시간 멀티모달 시스템까지

> [!note] 학습 안내
> **난이도:** 중급<br>
> **선수 지식:** [[언어 모델 추론 서빙]]의 prefill·decode, [[음성을 텍스트로 옮기는 경계에서 무엇이 사라지는가 — 인식·합성·네이티브 오디오]]의 ASR·TTS·native audio 비교. clock·buffer·turn은 필요한 만큼 여기서 다시 구분한다.<br>
> **읽고 나면:** 빠른 text token 생성, 음성 표현을 바꾸는 model, 사용자가 실제로 듣고 끼어드는 실시간 대화 system이 왜 서로 다른 결과 계약인지 구분하고, 각각에 맞는 지표와 event trace를 설계할 수 있다.

## 1단계 — 먼저 잡을 핵심

### 비교 질문과 짧은 답

텍스트 답변이 빨리 나오면 음성 대화도 빠르다고 말할 수 있을까? native audio를 받는 model이면 자동으로 실시간 대화가 될까? 둘 다 충분하지 않다.

**text token 생성**은 보통 주어진 request와 문맥에서 다음 출력 조각을 언제 만들었는지를 다룬다. **음성 표현 경로**는 audio를 text로 바꾸거나, text를 audio로 합성하거나, audio를 직접 model 입출력으로 다룰 때 무엇이 model의 조건이 되는지를 다룬다. **실시간 멀티모달 상호작용**은 capture된 media가 어느 turn에 속하는지, 언제 재생됐는지, 사용자가 끼어들면 어느 출력을 멈췄는지까지 다룬다.

| 흔한 말 | 그 말이 직접 확인하는 것 | 아직 확인하지 않는 것 |
| --- | --- | --- |
| “첫 token이 빨리 나왔다” | request·queue·model decode 관점의 초기 출력 | microphone capture, 발화 종료 판단, audio 합성·재생, 사용자의 청취 시점 |
| “native audio model이다” | 공표된 model 입력·출력 또는 학습 범위 | 내부 tokenizer·codec·clock·buffer 구조, 모든 환경의 지연·안전 |
| “실시간 음성 대화다” | 별도로 공개한 session·turn·presentation 계약이 있을 때에만 그 범위 | model 자체가 모든 overlap·재연결·외부 효과를 자동으로 해결한다는 보장 |

따라서 세 표현은 서로를 포함하는 등급표가 아니다. 하나의 product 안에 함께 있을 수 있지만, 각각 다른 질문에 답한다.

### 같은 요청도 두 장부를 지난다

설명용으로 두 경로를 나란히 놓아 보자.

    audio → ASR → text → 언어 모델 → text → TTS → audio
    audio input → audio를 다루는 것으로 공표된 model → audio output

첫 줄에서는 ASR이 만든 text가 언어 모델의 직접 조건이 되고, TTS가 그 text를 다시 들을 수 있는 audio로 바꾼다. 둘째 줄은 model이 audio를 포함해 입출력한다고 공표된 경우의 높은 수준 표현이다. 둘째 줄만 보고 내부 encoder·codec·decoder를 추정할 수는 없다.

두 줄 모두 실제 대화에서는 다음의 실행 경로 안에 놓인다.

    capture → timestamp·buffer → turn 결정 → inference → playout → 사용자 presentation

이 아래 줄은 model architecture의 세부가 아니라 runtime의 약속이다. 첫 줄의 모듈식 pipeline도, 둘째 줄의 native audio model도 이 약속 없이 사용자가 무엇을 언제 들었는지 설명할 수 없다.

## 2단계 — 작동 원리

### text request의 완료와 media turn의 완료는 다르다

[[언어 모델 추론 서빙]]에서 보는 전형적 text request는 비교적 분명한 입력 경계를 가진다. prompt가 queue에 들어가고, prefill이 문맥을 처리한 뒤, 이전 출력에 조건부인 decode가 token을 이어 만든다. Orca와 vLLM은 이 반복적 생성 workload에서 request·iteration scheduling과 KV cache 관리가 왜 중요한지를 보인다.

이때 “첫 token”은 유용한 관측점이다. 하지만 그 token이 아직 socket, UI, speech synthesizer, speaker를 지나지 않았다면 사용자가 답을 들었다고 말할 수 없다. 반대로 speaker에서 첫 소리가 나와도 그 소리가 현재 요청에 속하는지, 이미 취소된 output의 잔여분인지까지는 token index 하나로 판정하지 못한다.

연속 media 대화에는 request ID에 더해 session, track, input epoch, turn, output epoch 같은 소속 정보가 필요할 수 있다. 이 이름들은 모든 product의 고정 schema가 아니다. 핵심은 하나의 긴 audio stream과 그 위에서 여러 번 바뀌는 대화 상태를 단일 request로 접지 않는 것이다.

### 음성 경로는 표현을 바꾸지만 실행 계약을 대신하지 않는다

ASR→text→언어 모델→TTS 경로에서 ASR은 audio를 text로 변환하고, 중앙 언어 모델은 그 text를 조건으로 답을 만든다. Whisper는 30초 log-Mel 입력에서 text token과 특수 token을 생성하는 형식을, WaveNet은 언어·음성 조건에서 파형 표본을 생성하는 형식을 제시했다. 이 경로는 WER, 내용 품질, MOS처럼 단계별 오류를 나누어 관찰하기 좋다.

OpenAI는 GPT-4o를 text·vision·audio를 한 신경망에서 end-to-end로 학습한 model이라고 공표했다. 이 사실은 text만을 model의 유일한 중간 표현으로 놓지 않는 입출력·학습 범위를 뒷받침한다. 그러나 공표가 capture timestamp, network queue, playout buffer, turn policy 또는 취소 순서를 규정하지는 않는다. native audio는 표현 경계를 바꿀 수 있지만, 실시간 실행 계약을 없애지는 않는다.

[[음성을 텍스트로 옮기는 경계에서 무엇이 사라지는가 — 인식·합성·네이티브 오디오]]는 바로 이 표현·평가 경계를 맡는다. 이 문서는 그 두 표현 경로가 실제 대화에 들어갈 때 추가로 생기는 시간·상태·presentation 책임을 연결한다.

### media 시간과 model 출력 순서를 하나로 접지 않는다

audio frame의 capture 시각, RTP packet의 도착 순서, model delta의 생성 순서, speaker의 presentation 시각은 서로 다른 관측값이다. RTP/RTCP는 media timestamp·sequence number와 NTP–RTP 시간 mapping의 범위를 제공하며, RFC 7273은 media clock과 reference clock signalling을 구분한다. 이것은 모든 LLM product가 RTP를 써야 한다는 뜻이 아니라, **도착 순서만으로 사용자 경험의 시간을 재지 말라**는 설계 교훈을 준다.

또한 VAD가 내는 음성 활동 신호와 “사용자가 말을 끝냈으니 system이 답할 차례”라는 turn 결정도 다르다. RFC 6464의 voice activity bit는 turn-taking policy를 규정하지 않는다. Chiba와 Higashinaka의 비교처럼 partial ASR과 voice activity projection은 turn 판단에 들어갈 수 있는 신호이지, 그 자체로 대화 책임 이전을 보장하지 않는다.

여기서 필요한 상세 clock·buffer·backpressure·cancel·복구 계약은 [[실시간 멀티모달 상호작용]]이 소유한다. 이 분석은 그 메커니즘을 다시 정의하지 않고, text와 audio의 어느 측정값이 그 계약의 어느 지점에서 끝나는지를 구분한다.

### delta, cancel, presentation은 서로 다른 결과 상태다

model이 output delta를 만들었다는 event는 render가 준비됐다는 event와 다르고, render 준비는 사용자가 speaker나 screen에서 실제로 지각했다는 event와도 다르다. 사용자의 새 발화에 반응해 cancel을 보냈다는 사실도 generation 중단, 아직 재생하지 않은 media의 폐기, 이미 재생한 output의 회수와 같지 않다.

한 product의 API는 이 상태들을 별도 event로 노출할 수 있다. 예를 들어 OpenAI Realtime API reference에는 turn detection, response delta·cancel, conversation item truncate, output audio buffer 관련 event가 있다. 이는 특정 API의 rolling contract 예시일 뿐 보편 protocol은 아니다. tool write처럼 이미 외부 세계에 남은 효과의 commit·unknown·보상은 [[함수 호출과 도구 사용]]의 별도 책임이다.

## 3단계 — 기술과 근거

### 한 문장을 세 개의 측정 장부로 쓴다

다음 표는 같은 “빠른 음성 답변”을 세 장부로 나눈다. 행마다 성공의 뜻이 다르므로 점수를 합치기 전에 측정 시작점·끝점과 분모를 밝혀야 한다.

| 층 | 주된 결과 | 함께 기록할 지표 | 단독으로 보장하지 않는 것 |
| --- | --- | --- | --- |
| text serving | 현재 request에 대한 token 또는 text delta | queue-to-first-token, token 간 간격, p50·p95·p99, KV·batch 상태 | capture 시각, audio 재생, turn 품질 |
| 음성 표현 경로 | ASR text, 합성 audio 또는 공표된 native audio I/O | WER, 번역·내용 평가, MOS, 평가 input·output modality | 음향 특성의 완전 보존, 실제 대화 지연·중단 처리 |
| realtime runtime | 특정 session·turn의 media presentation | capture-to-first-presentation, cadence, jitter·late discard, A/V offset, barge-in·recovery | model의 비공개 내부 구조, 내용의 사실성 |

text serving의 첫 지표가 좋아도 turn detector가 늦게 경계를 확정하면 사용자는 늦게 답을 듣는다. ASR의 WER이 낮고 TTS의 MOS가 높아도 network jitter나 playout underflow가 크면 끊김이 생길 수 있다. 반대로 낮은 packet loss만으로 model이 적절한 답을 만들었다고 판단할 수도 없다.

### 같은 ‘latency’라는 말을 출발점과 도착점으로 번역한다

지연을 비교할 때는 숫자보다 먼저 이벤트를 적는다.

| 이름 | 가능한 시작점 | 가능한 끝점 | 다른 층의 지표로 바꾸면 생기는 오류 |
| --- | --- | --- | --- |
| 첫 token 지연 | server가 request를 받거나 queue에 넣은 때 | model이 첫 token을 만든 때 | 사용자가 첫 audio를 들은 시간이라고 부른다 |
| 전사 또는 turn 결정 지연 | 첫 audio frame 또는 silence window 시작 | partial transcript 또는 turn policy의 결정 | ASR output과 대화권 이전을 같은 event로 본다 |
| 첫 presentation 지연 | 공개한 capture·button·turn 기준점 | speaker·screen에서 처음 지각 가능한 output | network·codec·render·playout을 model latency로 숨긴다 |
| 복구 지연 | disconnect·cancel·barge-in이 감지된 때 | 새 session 또는 새 turn이 유효하다고 재검증된 때 | transport 연결만 복구된 것을 대화 복구로 부른다 |

각 경로의 단계는 겹쳐 실행될 수 있으므로 이 값을 보편적인 덧셈식으로 만들 수 없다. clock mapping, capture 기준, queue policy, codec, model streaming, renderer 중 무엇을 포함했는지를 trace에 남겨야 비교가 가능하다.

### 작은 event trace가 층 사이의 빈칸을 드러낸다

다음은 특정 framework의 schema가 아니라, 실험·운영 기록에 넣을 최소 질문이다.

1. 어떤 participant·track의 어느 media 범위가 input epoch에 들어왔는가?
2. VAD·partial ASR·사용자 입력 중 무엇이 turn policy에 쓰였고, 언제 turn이 확정됐는가?
3. 어느 model revision과 request 또는 turn이 어떤 output delta를 냈는가?
4. 그 delta는 어느 output epoch·buffer를 거쳐 언제 presentation됐는가?
5. barge-in 또는 cancel 뒤에 future generation, queued media, 이미 presentation된 결과는 각각 어떻게 처리됐는가?

이 다섯 질문이 있어야 text serving log와 media runtime log를 같은 사용자의 경험으로 연결할 수 있다. backpressure 역시 “queue가 길었다”는 관찰에서 끝나지 않고 throttle·stale media drop·quality 변경·cancel 중 무엇을 했는지와 함께 기록해야 한다. WHATWG Streams의 backpressure는 producer와 consumer capacity를 조절하는 추상화이지만, 어떤 media를 보존·폐기할지는 application 계약이다.

### 모델과 system의 책임을 다시 나눈다

| 문서 | 이 비교에서 맡는 질문 |
| --- | --- |
| [[멀티모달 대규모 언어 모델]] | model이 modality를 어떤 encoder·bridge·shared core·training 경계로 다루는가 |
| [[언어 모델 추론 서빙]] | text token의 prefill·decode·KV cache·batching과 tail을 어떻게 운용하는가 |
| [[음성을 텍스트로 옮기는 경계에서 무엇이 사라지는가 — 인식·합성·네이티브 오디오]] | ASR→text→TTS와 native audio가 어떤 표현·평가 경계를 갖는가 |
| [[실시간 멀티모달 상호작용]] | clock·frame·packet·buffer·turn·cancel·presentation·복구를 어떤 runtime 계약으로 다루는가 |
| 이 분석 | 위 장부가 한 사용자의 “답을 들었다·끼어들었다·다시 이어졌다”는 경험에서 어디서 이어지고, 어디서 대체되지 않는가 |

이 책임 분리는 한 model이 여러 역할을 수행할 수 없다는 뜻이 아니다. 공개된 정보가 부족한 경우에도 model architecture, serving 정책, media runtime, UX 평가의 증거 범위를 섞지 않게 하는 장치다.

## 검증과 한계

### 확인된 사실

- Orca와 vLLM은 text 생성 serving에서 자기회귀 iteration, scheduling, KV memory 관리가 응답 지연과 처리량의 조건임을 보여 준다.
- Whisper는 audio 특징에서 text token을, WaveNet은 조건화된 파형 표본을 생성하는 서로 다른 경로를 제시했다.
- GPT-4o의 공식 공표와 system card는 native audio를 포함한 학습·평가의 범위를 설명하지만, 모든 modality interface와 모든 배포 시점을 공개하지 않는다.
- RTP·RTCP RFC는 media timestamp, packet sequence, clock mapping과 보고 형식의 범위를 제공하며, VAD signal은 turn policy 자체가 아니다.
- Full-Duplex-Bench는 pause·backchannel·turn-taking·interruption을 나누어 평가하는 축의 한 예다. 이 benchmark 점수는 모든 device·network·사용자의 만족을 대변하지 않는다.

### 비교를 통한 해석

사용자가 경험하는 실시간 대화는 model이 token 또는 audio delta를 만든 사실보다 넓은 결과다. 그 결과는 표현 선택과 별개로 capture 기준, turn 결정, queue·playout, presentation, interrupt·recovery의 계약을 필요로 한다. text 중간 표현은 일부 음향 신호를 직접 조건에서 떼어 낼 수 있지만, 동시에 검색·감사·모듈별 오류 진단에 쓸 인터페이스가 되기도 한다. native audio가 그 trade-off를 다른 방식으로 만들 수 있어도, runtime 관측과 평가 장부를 대체하지는 않는다.

### 아직 입증되지 않은 계보와 적용 한계

이 비교는 ASR→text→TTS와 native audio model의 동일 조건 end-to-end 순위를 제공하지 않는다. native audio가 모든 억양·정서·접근성 요구를 더 잘 보존하거나 항상 더 빠르다는 결론도 제공하지 않는다. GPT-4o에 대해 공표된 audio response 수치를 microphone capture부터 사용자의 청취까지의 보편 지연으로 읽지 않는다.

또한 RTP, Web API, 특정 Realtime API event가 모든 product의 필수 protocol이라는 뜻도 아니다. model의 내부 tokenizer·codec·scheduler·cancel 순서를 공개 근거 없이 추정하지 않으며, audio output cancel을 이미 실행된 외부 action의 rollback으로 취급하지 않는다.
