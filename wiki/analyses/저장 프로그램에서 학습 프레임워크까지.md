# 저장 프로그램에서 학습 프레임워크까지

> [!note] 학습 안내
> **난이도:** 입문 → 중급<br>
> **선수 지식:** 없음 — instruction, compiler, library, 계산 그래프, 자동미분, kernel과 runtime을 한 내적 예에서 정의한다.<br>
> **읽고 나면:** 저장 프로그램이 곧 TensorFlow였다는 식의 직선 계보를 피하면서, Fortran·BLAS·역모드 자동미분·CUDA·cuDNN·TensorFlow가 각각 어떤 반복 작업을 감추고 어떤 계약을 남겼는지 설명할 수 있다.

## 1단계 — 먼저 잡을 핵심

### 하드웨어가 계산할 수 있다는 것과 연구자가 학습식을 실행할 수 있다는 것은 다르다

1945년 EDVAC 보고서는 산술 장치, 제어 장치, memory, input과 output을 구분하고 명령과 수치 자료를 다루는 전자식 계산 장치의 논리를 서술했다. 이것은 중요한 **프로그래밍 가능성**의 토대지만, 연구자가 `행렬을 곱하고 loss를 미분해 GPU 여러 개에서 실행하라`고 한 줄로 쓰게 해 주지는 않았다.

그 사이에는 서로 다른 반복 문제를 맡는 추상화가 쌓였다.

| 층 | 사람이 직접 하지 않게 된 일 | 여전히 사람이 책임질 계약 |
| --- | --- | --- |
| 저장 프로그램 | 배선을 다시 연결해 연산 순서를 바꾸기 | 올바른 instruction과 memory 배치 |
| Fortran compiler | 수식을 machine instruction으로 손번역하기 | 수식의 의미, 자료형, 배열 경계 |
| BLAS | 같은 vector·matrix loop를 응용마다 다시 쓰기 | operation, 길이, stride와 numerical meaning |
| 역모드 자동미분 | 합성 연산의 derivative를 매번 손으로 전개하기 | 미분할 scalar objective와 graph 의미 |
| CUDA·cuDNN | 모든 병렬 실행과 신경망 primitive를 처음부터 구현하기 | tensor layout, device, workspace, algorithm 선택 |
| TensorFlow | 장치 배치·graph 실행·gradient 연산을 응용 코드에 직접 엮기 | tensor shape, operation 의미, training objective와 결과 검증 |

핵심은 추상화가 아래층을 **없애지 않고 인터페이스 뒤로 숨긴다**는 것이다. 고수준 tensor 코드가 짧아도 실제 실행에는 compiler, library, kernel, memory와 device runtime이 남아 있다.

### 한 문장 결론

학습 프레임워크는 저장 프로그램의 자동 결과가 아니라, **프로그램 표현 → 번역 → 재사용 수치 연산 → gradient 생성 → 병렬 장치 실행 → graph runtime**의 계약이 오랜 기간 쌓인 소프트웨어 시스템이다.

## 2단계 — 작동 원리

### 같은 내적을 네 수준에서 읽기

$x=(2,3)$, $w=(4,5)$의 내적을 계산해 보자. 결과는 $2\cdot4+3\cdot5=23$이다.

#### 1. 고수준 loop

```text
s = 0
for i = 0, 1:
    s = s + x[i] * w[i]
```

Compiler는 변수, loop와 배열 접근을 machine instruction으로 번역한다. 이 표현은 계산 의미를 사람이 읽기 좋지만, 어느 vector instruction이나 memory access를 쓸지는 감춰져 있다.

#### 2. 재사용 library call

```text
s = dot(x, w)
```

BLAS의 dot product 계열은 “길이 $n$의 두 vector와 각 vector의 시작 위치·increment를 받아 scalar를 돌려준다”는 interface를 표준화했다. 호출자는 loop를 다시 구현하지 않아도 된다. 그러나 길이와 stride가 틀리거나 자료형을 혼동하면 library가 의도를 고쳐 주지 않는다.

#### 3. Tensor operator

```text
s = reduce_sum(x * w)
```

Framework는 `multiply`와 `reduce`를 tensor operation node로 나타낼 수 있다. Runtime은 각 operation을 CPU 또는 accelerator kernel에 배치하고, 준비된 입력이 생겼을 때 실행한다. 식은 짧아졌지만 shape와 device placement, memory transfer, numerical precision은 여전히 성능과 정확성을 바꾼다.

#### 4. 자동미분 graph

Loss를 단순히 $L=s=x^\top w$라고 두면 forward graph는 `x,w → multiply → sum → L`이다. Reverse mode는 출력의 미분값 $1$에서 시작해 graph를 거꾸로 따라간다.

$$
\frac{\partial L}{\partial w}=x=(2,3),
\qquad
\frac{\partial L}{\partial x}=w=(4,5)
$$

[[연쇄 법칙과 계산 그래프]]는 이 국소 derivative를 곱하고, 같은 값으로 들어오는 여러 경로의 기여를 더하는 수학을 맡는다. [[역전파]]는 이 원리를 neural network의 parameter gradient 계산에 사용한다. Framework의 automatic differentiation은 이 역방향 graph를 생성·실행하지만, 어떤 loss를 최소화해야 하는지 또는 그 loss가 실제 과업 품질을 대변하는지는 결정하지 않는다.

### 무엇을 감추고 무엇을 보존하는가

추상화는 네 계약을 구분해서 읽어야 한다.

1. **의미 계약:** `dot`, convolution, softmax와 loss가 어떤 수학 함수를 계산하는가
2. **Shape 계약:** 각 축이 batch·sequence·feature 중 무엇이며 입력과 출력 크기가 맞는가
3. **수치 계약:** 자료형·반올림·누적 순서가 허용 오차와 안정성을 만족하는가
4. **성능 계약:** 어느 device·kernel·layout·batch에서 latency, throughput, memory와 energy 목표를 만족하는가

Fortran compiler는 수식의 의미를 자동으로 검증하지 않았고, BLAS는 응용의 올바른 행렬을 골라 주지 않았다. TensorFlow도 잘못 정의한 objective를 올바른 연구 질문으로 바꾸지 않는다. 자동화가 늘수록 책임이 사라지는 것이 아니라 **책임이 interface 경계로 이동한다**.

## 3단계 — 기술과 근거

### 여섯 역사적 전환

#### 1. Instruction과 data를 memory로 다루기

EDVAC 보고서의 핵심은 현대 framework API가 아니라, central control이 memory의 명령과 수치 자료를 읽어 연산 순서를 바꿀 수 있는 machine organization이다. 프로그램 표현이 hardware 구성 변경과 분리될 수 있는 조건을 설명한다.

#### 2. Fortran이 수식과 machine code 사이를 번역하기

1957년 FORTRAN automatic coding system은 수학적 식, loop와 subroutine을 포함한 source program을 machine program으로 번역하고 diagnostic information을 제공했다. 중요한 변화는 processor가 새 산술을 얻었다는 것이 아니라, 사람이 **machine instruction보다 문제 식에 가까운 표기**로 프로그램을 만들 수 있게 된 것이다.

#### 3. BLAS가 수치 loop를 안정된 호출 경계로 만들기

1979년 BLAS 논문은 vector operation을 reusable subprogram interface로 정리했다. 여기서 library는 단순 편의 함수가 아니다. 응용과 machine-specific implementation 사이에 길이·increment·operation semantics라는 안정된 경계를 둔다. 훗날 backend가 달라져도 같은 상위 알고리즘이 primitive를 호출할 수 있는 패턴이다.

#### 4. Reverse mode가 합성 계산의 gradient를 재사용하기

Linnainmaa의 1970년 연구는 계산 과정의 국소 연산을 기록하고 역순으로 derivative를 누적하는 방법을 체계화했다. Neural network의 역전파만을 위해 발명된 것은 아니지만, scalar loss와 많은 parameter를 가진 학습에서는 한 번의 forward 계산 뒤 출력에서 입력 방향으로 gradient를 전파하는 핵심 원리가 된다.

#### 5. CUDA와 cuDNN이 accelerator 실행 경계를 나누기

CUDA는 GPU의 많은 thread를 block과 grid로 묶고 memory hierarchy를 다루는 병렬 프로그래밍 모델을 제공했다. cuDNN은 그 위에서 convolution·activation·pooling 같은 deep-learning primitive를 재사용 가능한 API로 제공했다. cuDNN 논문은 이를 BLAS가 dense linear algebra에 한 역할과 명시적으로 비교한다. 이 지점은 이 문서에서 확인되는 가장 분명한 **직접 영향**이다.

#### 6. TensorFlow가 tensor graph·device·gradient를 runtime으로 묶기

TensorFlow는 computation을 tensor가 operation 사이를 흐르는 dataflow graph로 나타내고, heterogeneous device와 distributed execution을 한 programming model 안에서 다뤘다. Symbolic differentiation은 주어진 graph에서 gradient operation을 구성한다. 그러나 graph abstraction은 backend kernel을 대체하지 않는다. TensorFlow 논문도 operation implementation이 kernel로 실행되는 층을 분리한다.

### 여섯 항목 측정 장부

| 항목 | 이 연결고리에서 기록할 것 |
| --- | --- |
| 작업 | Source program 번역, vector primitive 실행, scalar loss gradient 계산, tensor graph 학습을 구분한다. |
| 규모 | Source line, vector·matrix shape, graph node·parameter·device 수를 서로 다른 규모로 기록한다. |
| 결과 계약 | 같은 수학적 값, 허용 오차, 올바른 gradient, 목표 loss·task quality 가운데 무엇을 만족해야 하는지 밝힌다. |
| 시스템 경계 | Compiler, library kernel, 단일 device, distributed runtime 또는 end-to-end training 중 어디까지 재는지 적는다. |
| 고정 조건 | Algorithm, 자료형, layout, compiler·library version, hardware와 batch를 무엇까지 같게 뒀는지 적는다. |
| 지표 | Compile time, operation latency·throughput, memory, step time, time-to-quality를 섞지 않는다. |

FORTRAN, BLAS, cuDNN과 TensorFlow 논문은 시대·machine·workload가 다르다. 이 문서는 이들을 하나의 속도 순위로 바꾸지 않고, 각 층이 반복 가능한 실행에서 맡은 책임을 비교한다.

## 검증과 한계

### 인과를 네 종류로 감사한다

| 인과 표지 | 이 문서에서 허용하는 주장 |
| --- | --- |
| 직접 영향 | cuDNN 논문은 deep-learning primitive library를 BLAS가 dense linear algebra에 제공한 재사용 경계에 직접 비유한다. 이 명시적 설계 설명만 직접 영향으로 분류한다. |
| 가능 조건 | Compiler, 수치 library, reverse-mode AD와 GPU runtime은 현대 학습 framework가 실제 model을 반복 실행하는 조건을 제공했다. 존재했다는 사실만으로 TensorFlow 설계의 직접 원인이라고 하지는 않는다. |
| 병행 맥락 | Fortran의 자동 코딩과 TensorFlow의 graph programming은 서로 다른 시대에 “사람의 문제 표현과 machine 실행 사이를 번역한다”는 공통 문제를 다룬다. |
| 후대 유추 | 저장 프로그램 → compiler → library → framework라는 층별 사다리는 이 위키의 회고적 구조다. 하나의 조직이 합의한 roadmap이나 끊김 없는 단일 계보가 아니다. |

### 이 문서가 보장하지 않는 것

- EDVAC 보고서에서 TensorFlow로 직접 이어지는 문헌 계보를 주장하지 않는다.
- Fortran이 최초의 모든 compiler 개념을 단독으로 발명했다고 판정하지 않는다.
- BLAS API의 표준화와 특정 vendor implementation의 성능을 같은 기여로 합치지 않는다.
- 자동미분과 neural network 역전파의 역사 전체를 Linnainmaa 한 문헌으로 환원하지 않는다.
- 고수준 framework가 항상 hand-tuned kernel보다 빠르거나 더 정확하다고 가정하지 않는다.

CS_WIKI의 Fortran·compiler 설명은 추가 맥락을 찾는 독서 지도일 뿐 이 문서의 근거가 아니다. 모든 역사적 핵심 주장은 위 frontmatter의 LLM_Wiki evidence와 locator에 연결했다.

## 학습 확인

1. $x=(2,3)$, $w=(4,5)$의 내적을 loop, library call, tensor graph로 각각 쓸 때 감춰지는 구현과 남는 의미·shape 계약을 설명하라.
2. Automatic differentiation이 $\partial L/\partial w$를 만들어 줄 수 있어도 loss와 task quality가 올바르다는 것을 보장하지 못하는 이유는 무엇인가?
3. 새 framework가 “학습을 10배 빠르게 한다”고 주장한다. Compiler, primitive kernel, graph step, end-to-end time-to-quality 중 측정 경계를 정하고 여섯 항목 장부를 채워라.

시대순으로는 [[언어와 계산을 기계적 절차로 만들다]]에서 저장 프로그램의 의미를 확인하고, 이 문서 뒤에 [[행렬곱 가속은 딥러닝을 어떻게 현실화했나]]와 [[Transformer는 무엇을 병렬화했고 무엇을 남겼나]]를 읽는다.
