# 규모는 언제 연구 변수가 되었나

> [!note] 학습 안내
> **난이도:** 중급<br>
> **선수 지식:** [[concept.언어-모델-스케일링-법칙|언어 모델 스케일링 법칙]], [[concept.distributed-training-collectives|분산 학습과 집단 통신]]<br>
> **읽고 나면:** 2020년 scaling law가 model·data·compute를 어떻게 실험 변수로 만들었는지, Chinchilla가 같은 fixed-compute 질문을 어떻게 수정했는지, BLOOM·PaLM의 분산 실행이 추상 FLOP 예산을 실제 wall-clock과 memory로 바꾸는 조건을 설명할 수 있다.

## 1단계 — 먼저 잡을 핵심

### “더 크게”에서 “무엇을 얼마나 키울까”로

Model 규모는 신경망 초기부터 존재한 변수였다. 2020년 scaling law의 새로운 점을 “처음으로 큰 model을 만들었다”라고 쓰면 과장이다. 중요한 전환은 decoder-only Transformer의 평균 test loss를 model parameter $N$, 학습 token $D$, training compute $C$의 함수로 반복 측정하고, 고정된 compute에서 어느 조합에 예산을 배분할지 경험식으로 다룬 것이다.

Kaplan 등은 관측한 구간에서 다른 병목이 충분히 크다는 조건 아래 loss가 $N$, $D$, $C$와 매끄러운 power law 관계를 보인다고 보고했다. 이 결과는 parameter 수를 자랑하는 연표가 아니라 **규모를 통제하고 외삽하는 실험 방법**이었다. 그러나 직접 맞춘 목표는 평균 token cross-entropy다. 사실성, 안전성, 특정 추론 능력과 서비스 지연이 같은 곡선을 따른다는 뜻은 아니다.

### 추상 compute와 실현 가능한 학습은 다른 레일이다

Scaling law는 대략적인 FLOP budget 안에서 model과 data를 배분한다. 실제 run은 weight·activation·optimizer state가 장치 memory에 들어가야 하고, 여러 장치가 gradient와 parameter shard를 교환하며, 정해진 wall-clock 안에 끝나야 한다.

| 연구 변수 레일 | 시스템 실행 레일 | 연결할 때 남는 질문 |
| --- | --- | --- |
| $N$: model parameter | Weight·gradient·optimizer memory와 tensor/pipeline partition | Total parameter가 장치에 어떻게 나뉘는가? |
| $D$: 누적 학습 token | Input pipeline, data parallel batch와 저장·network | 고유 data와 반복 token을 어떻게 구분하는가? |
| $C$: training FLOPs | Device 처리량, utilization, collective와 wall-clock | 예상 FLOPs 중 실제로 얼마나 유효하게 실행됐는가? |
| $L$: 평균 token loss | Checkpoint·downstream 평가·서비스 품질 | 낮은 loss가 어떤 능력과 비용을 보장하지 않는가? |

Scaling law가 cluster 설계를 대신하지 않고, cluster가 compute-optimal 배분을 자동 결정하지도 않는다.

## 2단계 — 작동 원리

### Kaplan식 fixed-compute 배분

Dense decoder Transformer의 비embedding 학습량을 거칠게

$$
C\approx6NBS
$$

로 두면 $B$는 update당 token, $S$는 update 횟수이고 $D=BS$이므로 $C\approx6ND$로도 쓸 수 있다. 상수 6은 forward와 backward의 대표 연산을 세는 근사이며 context와 embedding, sparse 연산, communication과 hardware idle time을 완전히 담지 않는다.

Kaplan의 경험 fit은 compute가 커질 때

$$
N_{\mathrm{opt}}\propto C^{0.73},
\qquad
D_{\mathrm{opt}}\propto C^{0.27}
$$

인 배분을 제안했다. Model을 data보다 빠르게 늘리고 완전 수렴 전에 멈추는 방향이다. 이는 “Kaplan은 data를 고려하지 않았다”는 뜻과 반대다. Fixed compute에서 model–data 절충을 직접 분석했으며, 후속 연구가 그 지수를 다시 측정했다.

### Chinchilla가 같은 질문을 수정했다

Hoffmann 등은 70M 안팎부터 16B 초과 model, 약 5B부터 400–500B 수준의 token을 사용한 400개가 넘는 훈련 결과를 세 방법으로 분석했다. 세 방법은 대체로

$$
N_{\mathrm{opt}}\propto C^{0.5},
\qquad
D_{\mathrm{opt}}\propto C^{0.5}
$$

에 가까웠다. Compute가 늘 때 model과 token을 거의 같은 지수로 키우는 방향이다. “예산 절반을 parameter에 쓴다”는 회계 문장이 아니라 단위가 다른 두 규모의 power-law exponent가 비슷하다는 뜻이다.

70B Chinchilla는 1.4T token으로 학습돼 280B Gopher의 300B token과 같은 약 $5.76\times10^{23}$ FLOPs를 썼다. 더 작은 model이 더 많은 token을 처리해 여러 평가에서 강했다. Training compute를 줄인 비교가 아니라 같은 budget을 다르게 배분한 비교다.

### 분산 시스템이 추상 예산을 실행한다

Model을 수백 billion parameter로 키우면 한 장치에 weight·state가 들어가지 않는다. [[분산 학습과 집단 통신]]의 여러 축을 조합해 실행한다.

- Data parallel은 batch를 나누고 gradient를 동기화한다.
- Tensor parallel은 layer의 큰 행렬을 나눈다.
- Pipeline parallel은 layer 구간을 나눈다.
- ZeRO·FSDP는 optimizer·gradient·parameter의 중복 state를 shard한다.

BLOOM은 384개 A100에서 Megatron-DeepSpeed의 data·tensor·pipeline parallelism과 ZeRO를 결합했다. PaLM은 6,144개 TPU v4에서 Pod 내부 model parallel·FSDP와 Pod 사이 data parallel을 사용했고 pipeline parallel은 쓰지 않았다. 같은 parameter 규모에서도 software와 topology가 다르면 통신·memory·utilization 장부가 달라진다.

### Compute-optimal과 time-optimal은 다르다

두 구성이 같은 FLOPs를 사용해도 하나는 communication 때문에 더 오래 걸릴 수 있다. 반대로 더 많은 FLOPs를 수행해도 accelerator 이용률과 memory locality가 좋아 wall-clock이 짧을 수 있다. 실제 목적은 다음 중 무엇인지 밝혀야 한다.

- 정해진 FLOPs에서 가장 낮은 loss
- 정해진 날짜까지 가장 낮은 loss
- 정해진 비용·전력에서 목표 품질 도달
- 반복 inference까지 포함한 전체 수명주기 비용

Chinchilla는 주로 첫 질문을 다뤘다. LLaMA처럼 더 작은 model을 training-compute optimum보다 오래 학습해 반복 inference 비용을 낮추려는 선택은 목적 함수가 다르다.

## 3단계 — 기술과 근거

### Chinchilla–Gopher 측정 장부

| 항목 | 기록 |
| --- | --- |
| 작업 | Dense autoregressive language model 사전학습 |
| 규모 | Gopher 280B·300B token 대 Chinchilla 70B·1.4T token |
| 결과 계약 | 같은 계열 자료·설정의 pretraining loss와 논문 downstream 평가 |
| 시스템 경계 | 약 $5.76\times10^{23}$ training FLOPs의 model–data 배분 |
| 고정 조건 | 동일 FLOP budget을 중심으로 비교하되 optimizer·mixture 등 recipe 차이는 남음 |
| 지표 | loss frontier, MMLU 등 평가, parameter·token·FLOPs |

20 tokens/parameter는 Chinchilla 한 점과 일부 투영에서 유용한 근사다. Tokenizer·data mixture·model architecture와 높은 compute 외삽이 바뀌면 보편 상수가 아니다.

### BLOOM 실행 장부

| 항목 | 기록 |
| --- | --- |
| 작업 | 공개 접근 다국어 176B model 사전학습 |
| 규모 | 176,247,271,424 parameter, 366B 누적 token, A100 80GB 384개 |
| 결과 계약 | Causal LM objective, 공개 checkpoint와 논문 평가 |
| 시스템 경계 | Jean Zay 48-node cluster의 전체 run |
| 고정 조건 | Megatron-DeepSpeed 3D parallelism·ZeRO와 당시 software |
| 지표 | 약 3.5개월, 1,082,990 GPU-hours |

GPU-hour와 FLOPs는 같지 않다. GPU-hour에는 utilization이 낮은 시간도 들어가고, FLOPs 근사에는 communication·storage·중단 시간이 들어가지 않는다.

### PaLM 실행 장부

| 항목 | 기록 |
| --- | --- |
| 작업 | 540.35B dense PaLM 사전학습 |
| 규모 | 780B token, TPU v4 6,144개·host 1,536개 |
| 결과 계약 | Causal LM objective와 논문별 평가 protocol |
| 시스템 경계 | 두 TPU v4 Pod |
| 고정 조건 | Pod 내 12-way model parallel·256-way FSDP, Pod 간 data parallel |
| 지표 | 238.3k token/s, model FLOPs utilization 46.2% |

PaLM 수치를 BLOOM보다 “효율적”이라고 바로 결론 내릴 수 없다. Model·token·hardware·precision·quality·parallelism과 공개한 metric이 다르다.

### 일곱 능력층에서 본 전환

| 능력층 | 규모 연구가 바꾼 것 | 남은 경계 |
| --- | --- | --- |
| 계산 가능성 | 같은 LM objective를 더 크게 계산했다. | 새 종류의 계산 가능성은 아니다. |
| 알고리즘 복잡도 | $N,D,C$ 관계를 경험적으로 모델링했다. | FLOP 근사의 누락 항과 외삽 |
| 프로그래밍 가능성 | Megatron·DeepSpeed·Pathways로 분할 실행을 기술했다. | Framework·compiler·topology 종속 |
| 실현 성능 | 수백·수천 accelerator에서 training run을 완수했다. | Utilization·network·failure |
| 확장성 | Model·data·device 규모를 함께 늘렸다. | Strong/weak scaling과 global batch |
| 자원 효율 | 같은 FLOPs의 model–data 배분을 비교했다. | Wall-clock·energy·수명주기 비용 |
| 신뢰 가능한 결과 | Loss와 downstream 평가를 기록했다. | 사실성·안전성·서비스 SLO |

### 인과 관계를 고정한다

- **직접 영향:** Chinchilla는 Kaplan식 fixed-compute 문제와 결과를 명시적으로 재검토했다. BLOOM은 scaling-law 수정에 대응해 누적 token을 늘렸다고 기록했다.
- **가능 조건:** Megatron-DeepSpeed·ZeRO와 TPU Pod 병렬화는 BLOOM·PaLM의 실제 model을 memory와 시간 안에 실행한 조건이다.
- **병행 맥락:** 대규모 accelerator cluster의 발전과 scaling-law 연구는 서로 강화됐지만 hardware 증가가 특정 exponent를 만든 직접 원인이라고 쓰지 않는다.
- **후대 유추:** 현재의 비용·환경·접근성 논쟁을 2020년 loss fit의 직접 결론으로 소급하지 않는다.

### CS_WIKI와 함께 읽기

[CS_WIKI의 「컴퓨팅 능력이란 무엇인가」](https://yghnsim.github.io/CS_Wiki/concepts/%EC%BB%B4%ED%93%A8%ED%8C%85-%EB%8A%A5%EB%A0%A5%EC%9D%B4%EB%9E%80-%EB%AC%B4%EC%97%87%EC%9D%B8%EA%B0%80/)는 peak, 달성 성능, 확장성, 자원 효율과 신뢰 가능한 결과를 분리한다. 이 구분을 적용하면 parameter 수나 training FLOPs 하나로 “더 큰 컴퓨팅 능력”을 선언할 수 없다.

## 검증과 한계

Scaling law는 관측한 model family·data·tokenizer·optimizer·compute 범위에 조건화된 경험식이다. 높은 compute 구간의 외삽, data quality와 중복, sparse MoE의 active compute, 긴 context의 누락 항을 따로 검증해야 한다.

분산 실행 보고도 완전한 재현 recipe는 아니다. BLOOM은 공개 범위가 넓지만 동일 cluster·data·전문성이 필요하고, PaLM의 weight와 전체 training stack은 공개되지 않았다. 공개된 device 수나 utilization 한 값으로 총비용·전력·실패 복구를 복원할 수 없다.

이 본편은 compute를 연구 변수로 만든 전환에 집중한다. Memory wall·precision·MoE가 같은 FLOPs의 실제 시간을 바꾸는 과정은 후속 본편 **연산보다 데이터 이동이 비싸질 때**, 학습 뒤 반복 inference의 목적 함수는 **모델 능력에서 서비스 능력으로**가 맡는다.

## 학습 확인

1. Kaplan의 0.73/0.27과 Chinchilla의 약 0.5/0.5는 어떤 같은 질문에 대한 다른 경험적 답인가?
2. $C\approx6ND$가 6,144개 TPU의 wall-clock을 직접 예측하지 못하는 누락 항을 세 가지 쓰라.
3. 100B model 두 개가 같은 FLOPs로 학습됐지만 하나는 더 많은 token과 느린 network를 사용했다. Loss, FLOPs, communication, wall-clock, inference 비용을 분리한 측정 장부를 작성하라.

다음 본편 **연산보다 데이터 이동이 비싸질 때**에서는 FLOPs를 늘리는 것보다 memory traffic·precision·활성 expert를 바꾸는 편이 실제 효율을 더 크게 바꿀 수 있는 조건을 본다.
