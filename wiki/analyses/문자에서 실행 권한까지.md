# 문자에서 실행 권한까지

> [!note] 학습 안내
> **난이도:** 중급<br>
> **선수 지식:** [[concept.text-encoding-normalization|문자 인코딩과 정규화]], [[concept.구조화-출력|구조화 출력]]<br>
> **읽고 나면:** 유효한 UTF-8·JSON·schema·업무 값·인증·인가가 각각 다른 사실임을 설명하고, 외부 action 후보를 실행 전에 어떤 근거와 version으로 검사해야 하는지 구분할 수 있다.

## 1단계 — 먼저 잡을 핵심

### 같은 한 줄이 통과했다는 말은 여섯 가지 다른 뜻일 수 있다

다음 요청을 문서 삭제 기능의 **후보**라고 해 보자.

```json
{"operation":"delete_document","document_id":"D-17"}
```

이 한 줄이 화면에 보인다는 사실만으로는 아무것도 실행할 수 없다. “통과했다”는 말은 적어도 아래처럼 서로 다른 질문의 답일 수 있다.

| 관문 | 이 예에서 확인하는 것 | 통과해도 아직 모르는 것 |
| --- | --- | --- |
| 표현 | 선언한 byte encoding을 decode해 text로 읽을 수 있는가 | JSON 문법, 문서 존재, 요청 주체 |
| JSON parse | `{`, `}`, `:`, string이 JSON 문법에 맞는가 | 필요한 field, 실제 업무 의미 |
| schema | `operation`과 `document_id`가 허용된 이름·type·형태인가 | `D-17`이 실제 문서인지, 삭제해도 되는지 |
| 의미 검증 | 문서가 존재하고 현재 상태·업무 규칙에 맞는가 | 누가 요청했는지, 그 사람이 삭제할 수 있는지 |
| 인증 | 현재 요청 주체가 주장하는 계정·service인가 | 그 주체의 문서 삭제 권한 |
| 인가 | 이 주체가 이 문서에 이 행동을 지금 해도 되는가 | 실제 executor가 성공·commit·복구할 수 있는지 |

따라서 **형식이 맞는 action object는 실행 명령이 아니라 검증할 후보**다. UTF-8이나 JSON·schema가 만든 것은 다음 프로그램이 읽을 수 있는 표현이고, authorization이 만든 것은 현재 policy 아래 허용 또는 거절된 결론이다. 실제 상태 변화와 그 뒤의 성공·실패·복구는 다음 [[함수 호출과 도구 사용]] 보강 배치에서 다룰 별도 계약이다.

### 표현에서 권한으로 가는 지도

이 연결고리는 다음을 모든 제품의 고정된 실행 순서가 아니라, “어떤 통과가 무엇을 증명하는가”를 확인하는 **감사 순서**로 쓴다.

```text
선언된 byte encoding
  → decode 또는 reject
  → JSON text
  → parser가 만든 JSON value
  → schema validation
  → domain·현재 상태 semantic validation
  → authentication
  → authorization
  → authorized action proposal
  → [다음 배치: confirmation · execute · commit / failed / unknown]
```

배포 환경에 따라 authentication은 body parse보다 먼저 일어날 수 있고, 여러 관문이 하나의 service 안에서 함께 구현될 수도 있다. 이 그림의 목적은 시간 순서를 강제하는 것이 아니라, “UTF-8이면 안전하다”, “JSON이면 신뢰할 수 있다”, “로그인했으니 삭제할 수 있다”라는 서로 다른 비약을 끊는 데 있다.

## 2단계 — 작동 원리

### 1. text를 읽을 수 있어야 parser가 시작한다

[[문자 인코딩과 정규화]]가 맡는 앞단에서는 byte 열, 선언된 UTF-8 같은 decoding 규칙, Unicode text와 normalization 정책을 분리한다. RFC 8259는 닫힌 생태계 밖에서 교환하는 JSON text를 UTF-8로 보내도록 정하고, JSON parser는 JSON text를 다른 표현으로 바꾸는 component라고 설명한다. 하지만 유효한 UTF-8은 JSON 문법도, 사람 이름·문서 ID의 실제 의미도, 요청자의 권한도 증명하지 않는다.

보이는 문자열이 같아도 code point 열이나 normalization form이 다를 수 있다는 사실은 ID 비교와 lookup의 정책에도 영향을 준다. 그렇다고 이 문서가 어떤 normalization form을 강제하는 것은 아니다. 어떤 field를 원문 그대로 보존하고 어떤 field를 비교용으로 정규화할지, invalid byte·unpaired surrogate·길이 제한을 reject할지의 결정은 interface 계약으로 남겨야 한다.

### 2. JSON parse는 구문과 자료 구조를 확인한다

JSON parser가 성공하면 text를 object·array·string·number 같은 자료 구조로 읽을 수 있다는 뜻이다. parser는 input의 최대 길이·깊이·number 범위 같은 자원 제한을 둘 수도 있다. 이것은 “문자열을 code로 실행했다”가 아니라, **정해진 grammar로 serialized data를 읽었다**는 결과다.

특히 아래 object는 겉으로는 흔한 JSON처럼 보이지만 member name이 중복된다.

```json
{"operation":"read_document","operation":"delete_document","document_id":"D-17"}
```

RFC 8259는 object name이 고유할 것을 권고하며, 중복 name을 받은 software의 동작은 예측할 수 없을 수 있다고 설명한다. 어떤 parser는 마지막 값을 남기고, 어떤 parser는 error를 내거나 모든 pair를 보존할 수 있다. 따라서 parser 성공률만 기록하지 말고 **중복 key·크기·깊이·Unicode escape에 관한 parser policy와 version**도 남겨야 한다.

### 3. schema는 object의 모양을 확인한다

JSON Schema는 instance data의 구조에 제약을 둔다. 예를 들어 `operation`이 허용 enum 중 하나인지, `document_id`가 string인지, required field가 빠지지 않았는지를 검사할 수 있다. provider-native strict structured output은 model이 낸 text를 schema 형태에 맞추는 데 도움을 줄 수 있지만, 정상 완료·지원 schema·그 provider의 설정이라는 조건을 벗어나면 같은 보장을 일반화할 수 없다.

형식은 다음처럼 충분히 엄격할 수 있다.

```json
{
  "type": "object",
  "required": ["operation", "document_id"],
  "properties": {
    "operation": { "enum": ["read_document", "delete_document"] },
    "document_id": { "type": "string" }
  },
  "additionalProperties": false
}
```

그래도 `"document_id":"D-17"`이 존재하는지, 그것이 다른 사용자의 비공개 문서인지, 삭제 요청이 현재 보존 정책에 맞는지는 schema가 알 수 없다. JSON Schema 2020-12도 structural validation만으로 application이 값을 올바르게 활용하기에 충분하지 않을 수 있다고 명시한다.

### 4. 의미 검증은 현재 world state를 묻는다

semantic validation은 field의 type보다 **그 값이 지금 이 업무에서 가리키는 대상과 제약**을 확인한다. 예에서는 다음을 물을 수 있다.

- `D-17`이 실제로 존재하고 삭제 가능한 상태인가?
- 이 operation과 document type의 조합이 허용되는가?
- ID·날짜·금액·단위·상태 전이가 서로 모순되지 않는가?
- 조회 시점의 resource version과 policy가 뒤에서 사용할 version과 같은가?

이 단계는 database 조회, domain rule, 현재 resource snapshot처럼 JSON 밖의 근거를 쓴다. 그래서 schema pass와 semantic pass의 분모를 같다고 쓰지 않는다. 값이 structure에는 맞지만 domain rule에서 거절된 경우는 model의 token 오류, stale data, user request의 제약, consumer의 business policy 중 어디가 원인인지 따로 기록해야 한다.

### 5. 인증과 인가는 다른 질문이다

authentication은 요청을 보낸 claimant가 주장하는 주체인지 확인하는 과정이다. NIST SP 800-63-4의 일반 model에서 verifier는 claimant가 subscriber identity에 묶인 authenticator를 possession·control함을 확인하고 relying party에 긍정 결과를 전달한다. 이는 사람이 문서를 삭제할 수 있다는 허가가 아니라, **누가 요청한 것으로 다룰지**에 관한 근거다.

authorization은 그 주체가 특정 resource에 특정 action을 현재 context에서 할 수 있는지 결정한다. NIST SP 800-207의 policy engine·policy administrator·policy enforcement point는 policy decision과 enforcement를 분리해 생각하는 한 참조 model이다. 모든 application이 이 세 component를 그대로 구현해야 한다는 요구는 아니다. 이 문서의 audit record에서는 그 구분을 이용해 subject·resource·action·environment·policy version을 따로 남긴다.

사용자 confirmation은 authentication이나 authorization과 같은 말이 아니다. Policy가 위험도·법적 책임·조직 규칙에 따라 나중 confirmation을 요구할 수는 있다. 그러나 confirmation을 수집하고 어느 decision·resource version에 묶을지, stale confirmation을 어떻게 다룰지는 B8이 맡는다. 어느 경우에도 confirmation 화면 하나가 credential의 유효성, resource ownership, executor의 성공을 대신하지는 않는다.

## 3단계 — 기술과 근거

### 관문별 결과 계약을 한 줄씩 적는다

각 관문은 input, 성공 결과, 실패 또는 미확정 결과, 다음 관문에 남길 기록을 함께 가진다.

1. **Decode** — byte·encoding 선언·오류 정책을 받아 Unicode text를 만들거나 reject/replacement 결과를 낸다. encoding·Unicode/normalizer version과 raw 보존 정책을 남긴다.
2. **JSON parse** — text와 parser policy를 받아 JSON value/tree를 만들거나 syntax·duplicate key·depth·size 오류를 낸다. parser·library version과 error class를 남긴다.
3. **Schema** — JSON value와 schema version을 받아 정해진 structure인지 판정한다. required/type/enum 불일치라면 failing path와 schema ID·version을 남긴다.
4. **Semantic** — typed field·domain rule·resource snapshot을 받아 현재 업무 조건에 맞는 candidate인지 판정한다. unknown ID·stale state·rule 위반이면 rule·data snapshot·lookup time을 남긴다.
5. **Authentication** — claimant·credential/authenticator·session을 받아 식별된 principal 또는 session인지 판정한다. credential invalid·expired·unverified면 identity provider·assurance·session state를 남긴다.
6. **Authorization** — principal·resource·action·context·policy를 받아 allowed 또는 denied proposal을 낸다. policy deny·context change가 있으면 policy·scope·decision reason·time과 이후 confirmation 필요 여부를 남긴다.

이 표의 `성공`은 각 행의 질문에만 답한다. 예를 들어 schema success는 downstream object의 type safety에 도움이 되지만, authorization success는 executor가 network timeout 없이 request를 처리했다는 뜻이 아니다. 실행 request가 실제로 한 번만 commit됐는지, partial failure 뒤 어떻게 복구할지는 B8의 safe-effects 경계에서 다룬다.

### 이 연결고리의 일곱 칸 장부

| 항목 | 이 연결고리에서 기록할 내용 |
| --- | --- |
| 입력·대상 | byte/text 표현, JSON·schema action candidate, principal·resource·action·environment·policy context |
| 변환 경로 | decode/reject, parse, schema, semantic validation, authentication, authorization로 candidate를 분리; 이후 confirmation 요구 여부는 policy에 기록 |
| 시간·상태·자원 | encoding·parser·schema·policy version, credential/session expiry, resource snapshot과 결정 시각, size·depth·lookup budget |
| 결과 계약 | executor에 넘길 수 있는 allowed proposal 또는 명시된 deny; 실행·commit 결과는 아직 주장하지 않음 |
| 지표·평가 기준 | parse·schema·semantic pass와 reject reason, authentication failure, allow/deny 오류, 관문별 조건부 분모 |
| 실패·복구 경계 | decode·parse·schema·domain reject, credential expiry, policy deny·stale decision; execution·idempotency·compensation은 다음 배치 |
| 권한·책임·출처 추적 | request·principal·schema·policy·resource version, decision reason·time·actor를 민감 정보 최소화 원칙 아래 audit |

### 평가에서는 pass rate 하나를 성공률로 부르지 않는다

시스템이 다음 네 값을 함께 기록하면 failure 위치를 분리해 볼 수 있다.

1. **Parse rate:** 입력 text 중 parser가 JSON value로 읽은 비율이다.
2. **Schema pass rate:** parser가 성공한 값 중 structure contract를 통과한 비율이다.
3. **Semantic acceptance rate:** schema를 통과한 candidate 중 domain rule·현재 state 검사를 통과한 비율이다.
4. **Authorization decision quality:** label된 policy case에서 잘못 allow한 경우와 잘못 deny한 경우, 필요한 subject·resource·context를 빠뜨린 경우를 따로 센다.

각 분모를 적지 않으면 schema pass가 낮은 이유와 semantic reject가 많은 이유, policy가 의도적으로 deny한 정상 case를 하나의 “model 성공률”로 섞게 된다. 반대로 allow가 많이 나왔다고 좋은 시스템도 아니다. 권한이 없는 action을 allow한 한 건은 그 action의 위험도에 따라 평균 정확도와 다른 방식으로 보고해야 한다.

### 기존 문서와 나누는 책임

[[문자 인코딩과 정규화]]는 byte·Unicode·normalization·tokenizer의 표현 계약을 완결한다. [[구조화 출력]]은 JSON mode·strict schema·constrained decoding이 강화하는 형식 계약을 완결한다. [[함수 호출과 도구 사용]]은 model의 tool-call 제안, runtime의 검증·실행 protocol과 외부 결과 통합을 완결한다.

이 문서는 그 세 설명을 다시 쓰지 않는다. 그 사이에서 **앞 관문을 통과한 사실이 뒤 관문의 사실을 자동으로 만들지 않는다**는 trace를 만든다. 다음 B8은 allowed proposal이 executor에 들어간 뒤의 idempotency, partial failure, compensation, postcondition과 audit를 더 구체적으로 보강한다.

## 검증과 한계

### 확인된 사실과 비교 해석을 구분한다

- **확인된 사실:** RFC 8259는 JSON grammar·UTF-8 교환·parser의 text-to-representation 역할과 상호운용성 한계를 정한다. JSON Schema 2020-12는 structure constraint의 vocabulary이며 structural validation만으로 application value 활용이 충분하지 않을 수 있음을 적는다.
- **확인된 사실:** NIST SP 800-63-4는 authentication을 authenticator possession·control과 verifier의 확인으로 설명한다. NIST SP 800-207은 policy decision과 enforcement를 분리하는 zero-trust reference architecture를 제시한다.
- **비교를 통한 해석:** 이 표의 순서는 실제 network packet 순서가 아니라, model output을 external action 후보로 다룰 때 각 “통과”의 의미를 분리하는 감사 순서다.
- **아직 일반화하지 않는 것:** 어떤 JSON library, schema engine, identity provider, policy engine을 쓰면 모든 LLM tool system이 안전해진다는 증거는 여기 없다. 위험도·법적 의무·data retention·human approval의 적절한 설계는 domain별 별도 근거가 필요하다.

### 자주 생기는 혼동

- UTF-8 decode와 normalization은 text 표현을 정할 뿐 JSON parsing, account ownership, policy를 보장하지 않는다.
- Valid JSON은 parser가 읽을 수 있다는 뜻이지 duplicate key 처리나 field 의미가 모든 consumer에서 같다는 뜻이 아니다.
- Schema-valid object는 실제 ID·현재 state·업무 규칙을 확인하지 않았다면 action으로 쓰면 안 된다.
- Authentication success는 credential과 주체 연결에 관한 결과이지, resource·action·scope의 authorization이 아니다.
- Authorization decision은 현재 policy·resource·credential 상태에 묶인 판단이다. executor의 실제 성공, commit, rollback·compensation까지 보장하는 결과로 부르면 안 된다.
- JSON은 흔한 사례일 뿐 모든 tool interface의 필수 형식은 아니다. protobuf·form·RPC 같은 표현도 parse·structure·meaning·identity·policy를 구분해야 한다.

### 이 문서가 멈추는 곳

검사와 실행 사이에는 resource, policy, credential, network 상태가 바뀔 수 있다. 이 문서는 그 가능성을 version·snapshot·decision time으로 기록하라고 요구하지만, 재검사 시점, transaction, idempotency key, rollback, compensation, executor postcondition을 설계하지 않는다. 그 문제는 다음 safe-effects 배치의 범위다.
