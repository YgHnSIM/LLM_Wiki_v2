# 전력에서 서비스 결과 계약까지 무엇을 세어야 하나

> [!note] 학습 안내
> **난이도:** 중급<br>
> **선수 지식:** [[concept.llm-inference-energy-metrics|LLM 추론 에너지 지표]], [[concept.llm-inference-serving|언어 모델 추론 서빙]]<br>
> **읽고 나면:** J/token·J/request·J/good request가 왜 다른 질문인지, 품질·deadline·traffic·retry를 먼저 계약해야 서비스 에너지를 비교할 수 있는 이유를 설명할 수 있다.

## 1단계 — 먼저 잡을 핵심

### 적은 전력 사용은 곧 더 좋은 서비스가 아니다

한 요청을 처리할 때 쓴 J를 세는 일은 필요하다. 하지만 사용자가 받은 결과를 비교하려면 **무엇을 성공으로 볼지**도 함께 정해야 한다. 같은 문장을 같은 tokenizer로 생성했는지, 충분한 품질인지, 안전 정책을 통과했는지, 정한 시간 안에 도착했는지가 빠지면 “요청당 에너지”는 서비스 결과가 아니라 실행 일부의 비용이다.

이를 작은 회계 예로 보자. 같은 100개 입력과 같은 model·sampling·출력 길이 조건에서 A는 모든 attempt에 합계 10,000 J를 쓰고 90개만 품질·deadline을 통과했다. B는 합계 10,800 J를 쓰지만 100개가 통과했다. 단순 `J/request`는 A가 100 J, B가 108 J라서 A가 좋아 보인다. 그러나 실제로 유효한 결과 하나당 에너지는 다음과 같다.

$$
E_{\mathrm{good},A}=\frac{10{,}000}{90}\approx111.1\ \mathrm{J/good\ request},\qquad E_{\mathrm{good},B}=\frac{10{,}800}{100}=108\ \mathrm{J/good\ request}
$$

이 숫자는 어떤 표준 benchmark의 결과가 아니라, **같은 결과 계약 아래에서는 총 J가 더 큰 B가 유효 결과 하나당은 더 적을 수 있다**는 계산 예다. 실패·재시도·품질 저하를 숨기면 반대 결론도 쉽게 나온다.

### 먼저 고정할 다섯 가지

서비스 에너지 비교는 전력계부터 시작하지 않는다. 다음 다섯 가지를 먼저 문서에 적고, 그 다음에 J를 읽는다.

1. **출력 계약:** checkpoint·tokenizer·sampling과 품질·안전 기준이 같은가?
2. **시간 계약:** queue를 포함한 TTFT·종단 지연의 deadline은 무엇인가?
3. **수요 계약:** 입력·출력 길이, 도착률, burst, tenant priority와 동시성 분포는 같은가?
4. **시도 계약:** timeout·취소·거절·retry의 J와 결과를 어느 분자·분모에 넣는가?
5. **계측 계약:** GPU·node·service·facility 중 어디를, 어느 warmup·idle 구간과 함께 재는가?

이 중 하나라도 달라지면 수치가 잘못된 것은 아닐 수 있다. 다만 같은 질문의 답이라고 비교해서는 안 된다.

## 2단계 — 작동 원리

### 요청이 아니라 유효 결과를 분모로 쓰는 방법

한 운영 창 $W$에서 서비스 회계 예시를 다음처럼 쓸 수 있다.

$$
E_{\mathrm{good}}=\frac{\sum_{i\in A(W)}E_i}{\left|\left\{r\in R(W)\mid Q(r)\ge q_0\ \land\ L(r)\le \ell_0\ \land\ S(r)=1\right\}\right|}
$$

각 기호는 모두 수치 또는 명시적인 집합이다.

| 기호 | 자료형·범위 | 이 예에서의 역할 |
| --- | --- | --- |
| $W$ | 시간 구간 | 어떤 traffic·idle·warmup을 포함하는지 정한 관측 창 |
| $A(W)$ | attempt의 집합 | 이 창에서 시작했거나 끝난 attempt를 넣는 규칙 |
| $E_i$ | $E_i\ge0$인 스칼라 J | attempt $i$에 배정한 에너지; shared batch·idle 배분 규칙도 함께 밝힌다 |
| $R(W)$ | 사용자 request의 집합 | retry 전후를 하나의 사용자 요청으로 묶는 식별 규칙 |
| $Q(r),q_0$ | 품질 점수와 임계값 | 정답·사람 평가·task oracle 등으로 정한 최소 품질; 모든 task에 하나의 보편 점수는 없다 |
| $L(r),\ell_0$ | 초 단위 지연과 deadline | queue부터 마지막 유효 byte까지인지, 첫 token까지인지 정한다 |
| $S(r)$ | $0$ 또는 $1$ | 적용한 안전·형식·정책 검사를 통과했는지; 서비스에 그런 검사가 없다면 조건을 빼고 그 사실을 적는다 |

분자는 **최종 성공 attempt만** 세지 않는다. 사용자가 하나의 결과를 얻기 전에 timeout된 attempt가 실제로 쓴 J도 정한 규칙에 따라 포함한다. 반대로 다른 tenant의 무관한 작업, 실험 중 버린 warmup, 시설 냉각까지 넣었다면 그 범위도 독자가 재계산할 수 있게 밝혀야 한다.

### prefill·decode·queue가 같은 비율로 변하지 않는다

Prompt를 한 번 읽는 prefill, token을 하나씩 확정하는 decode, batch를 기다리는 queue는 길이와 부하에 다르게 반응한다. Orca의 iteration-level scheduling과 vLLM의 KV cache 관리는 이 차이 때문에 request-level batch와 연속적인 생성 상태를 따로 다룬다. 그러므로 짧은 prompt·낮은 부하에서 낮은 `J/token`을 보였다는 사실만으로 긴 context·burst traffic에서도 같은 `J/good request`가 나올 것이라 추론하지 않는다.

실무에서 비교표를 만들 때는 최소한 다음 세 줄을 나눠 기록한다.

| 구간 | 에너지에 영향을 주는 조건 | 결과 계약에 미치는 영향 |
| --- | --- | --- |
| queue·admission | replica 수, idle, priority, burst, 거절 정책 | deadline 전에 시작할 수 있는가 |
| prefill | input 길이, batch, memory bandwidth, prefix 공유 | TTFT와 긴 문맥 비용 |
| decode·후처리 | output 길이, KV cache, sampling, tool·safety·전송 | streaming cadence, 종단 지연, 취소·retry |

### 결과 계약은 평가 oracle을 숨기지 않는다

`good`이라는 단어는 스스로 측정값이 아니다. 번역이라면 참조 번역·사람 판정·안전 기준 중 무엇인지, 검색 답변이라면 근거 충실성·인용 가능성·형식 검증 중 무엇인지 적어야 한다. 같은 deadline도 “첫 token 2초”와 “완전한 응답 10초”는 다르다. 평가 oracle이 바뀌면 분모가 바뀌므로, 개선의 방향까지 달라질 수 있다.

## 3단계 — 기술과 근거

### 이 연결고리의 일곱 칸 장부

| 경계 | 이 분석에서 공개할 것 |
| --- | --- |
| 입력·대상 | model·tokenizer·request 길이·traffic과 성공으로 볼 사용자 요청 |
| 변환 경로 | admission·queue → prefill → decode → 후처리·전송 → 종료·재시도 |
| 시간·상태·자원 | 관측 창, warmup·idle, replica, batch, KV cache, GPU·host·network |
| 결과 계약 | 품질·안전·형식 기준과 TTFT·종단 deadline을 통과한 결과 |
| 지표·평가 기준 | W, J, J/token, J/request, J/good request, p50·p95·p99, 유효 처리량 |
| 실패·복구 경계 | timeout·취소·거절·OOM·retry·unknown outcome을 분자와 분모에 넣는 규칙 |
| 권한·책임·출처 추적 | 전력계·runtime·model·policy·oracle·traffic version과 배분·집계 책임자 |

이 표는 특정 서비스가 이 모든 값을 항상 측정해야 한다는 규칙이 아니다. 무엇을 주장하는지에 맞춰 빈칸을 숨기지 않도록 하는 비교 장부다.

### benchmark의 엄격함과 운영 회계의 차이

MLPerf Inference는 workload·scenario·하드웨어·소프트웨어를 정해 비교 가능한 제출을 만든다. 전력 제출에도 별도 조건이 있다. 이런 규율은 “모델명만 같으면 결과도 비교 가능하다”는 착각을 막는다. 그러나 MLPerf의 정한 workload가 모든 실제 고객의 품질 oracle·traffic burst·retry 정책을 대표한다고 결론 내릴 수는 없다.

TokenPowerBench는 LLM request의 prefill·decode와 GPU·node·system 경계를 나눠 관찰한다. 이는 계측을 세밀하게 하지만, multi-tenant idle 전력이나 사업자의 결과 계약을 하나의 유일한 분배 방식으로 결정하지는 않는다. 1세대 TPU의 data-center inference와 99백분위 제약, *The Tail at Scale*의 tail·여유 용량, energy-proportional computing의 부분 부하 문제는 모두 장치 밖의 조건이 결과 비용을 바꾼다는 맥락을 제공한다.

### 소비 문서에는 현재 선택만 남긴다

[[모델 능력에서 서비스 능력으로]]은 model 품질이 runtime·hardware·traffic·운영 정책과 함께 서비스 능력이 되는 큰 그림을 다룬다. 그 문서에서는 현재 비교의 결과 계약과 지표만 적고, J의 분자·분모·retry·idle 배분을 여기로 연결한다. 반대로 이 분석은 scheduler·KV cache 알고리즘을 완전하게 다시 설명하지 않고 [[언어 모델 추론 서빙]]의 owner 설명을 사용한다. 같은 설명을 세 문서에 복제하지 않기 위한 역할 분담이다.

## 검증과 한계

- **직접 영향:** MLPerf, TPU, Orca, vLLM과 TokenPowerBench는 각자의 hardware·software·workload·측정 경계에서 성능, 지연 또는 전력을 보고한다. 이 문서는 그 결과를 다른 traffic의 수치로 옮겨 쓰지 않는다.
- **가능 조건:** 전력계, runtime trace, request ID와 quality·deadline oracle이 있어야 유효 결과당 에너지를 재구성할 수 있다. 계측 가능성이 낮은 비용이나 더 좋은 사용자 경험을 자동 보장하지는 않는다.
- **병행 맥락:** energy-proportional computing과 tail-latency 연구는 LLM 이전 서비스 시스템의 부분 부하·여유 용량·분포 문제를 설명한다. 그것이 특정 LLM serving 구현의 직접 원인이라는 주장은 하지 않는다.
- **후대 유추:** `J/good request`는 분자·분모를 공개하는 교육용·운영 회계 예시다. 보편 표준, 유일한 지속가능성 지표, 또는 탄소 배출량의 대체값이 아니다.

탄소를 계산하려면 전력망의 지역·시간·계약, facility 경계, 필요하다면 장비 제조와 폐기의 lifecycle 자료가 더 필요하다. 품질도 task·언어·사용자 위험에 따라 달라진다. 이 분석은 그러한 정보를 모른 채 하나의 “친환경 LLM” 순위를 만들지 않는다.

## 학습 확인

1. 두 서비스의 `J/token`만 같고 input 길이·deadline·retry 규칙이 다르면 왜 `J/good request`를 바로 비교할 수 없는가?
2. timeout된 첫 attempt의 J를 분자에서 빼면 어떤 사용자 비용이 보이지 않게 되는가?
3. 번역 서비스의 `good`을 정의하려면 품질, 시간, 정책 중 무엇을 어떤 oracle로 적어야 하는가?

다음에는 [[모델 능력에서 서비스 능력으로]]에서 이 회계를 model·runtime·hardware·traffic의 공동 결과로 다시 읽고, [[LLM과 컴퓨팅 능력의 공진화]]에서 서비스 측정 경계가 컴퓨팅 능력의 역사와 어떻게 만나는지 확인한다.
