# 행렬곱 가속은 딥러닝을 어떻게 현실화했나

> [!note] 학습 안내
> **난이도:** 입문 → 중급<br>
> **선수 지식:** 없음 — batch, tensor, forward·backward, kernel, framework와 장치 memory를 작은 행렬 예에서 정의한다.<br>
> **읽고 나면:** 역전파와 CNN이 GPU 이전에도 존재했다는 사실을 보존하면서, CUDA·cuDNN·딥러닝 프레임워크가 큰 tensor 학습을 반복 가능한 실행 경로로 만든 과정을 설명하고 peak 연산량과 end-to-end 학습 시간을 구분할 수 있다.

## 1단계 — 먼저 잡을 핵심

### GPU 하나가 아니라 실행 스택이 바뀌었다

딥러닝은 GPU가 발명한 학습법이 아니다. [[018_역전파와 다층 신경망 학습]]과 [[021_합성곱 신경망과 특징 학습]]에서 보듯, 여러 층의 gradient를 계산하는 역전파와 손글씨를 인식하는 CNN은 현대 GPU 딥러닝 붐보다 앞서 실제로 작동했다.

달라진 것은 더 큰 data와 model을 감당하는 **실현 성능**, 같은 실험을 다시 만드는 **프로그래밍 가능성**, batch·장치를 키우는 **확장성**이었다. 이 변화에는 적어도 네 층이 함께 필요했다.

1. **계산 그래프:** convolution·행렬곱·activation·loss와 그 gradient를 정의한다.
2. **병렬 프로그래밍 모델:** CUDA가 많은 thread를 block·grid로 묶어 GPU에서 실행하게 한다.
3. **최적화 kernel library:** cuDNN이 convolution의 forward·backward 같은 반복 연산을 장치별 구현으로 제공한다.
4. **프레임워크:** tensor와 연산 그래프에서 gradient, device 배치와 실행 순서를 관리한다.

GPU의 많은 연산기가 있어도 model을 kernel로 내리는 software가 없으면 연구자가 매번 장치 코드를 다시 짜야 한다. 반대로 편리한 framework가 있어도 느린 kernel, 작은 memory와 잦은 data 이동을 없애지는 못한다.

### 두 발전 레일이 만난 지점

| 학습 모델 레일 | 컴퓨팅 능력 레일 | 만난 결과와 남은 제약 |
| --- | --- | --- |
| 역전파가 여러 층의 weight gradient를 계산 | CPU·vector 연산이 작은 network를 반복 실행 | 학습은 가능했지만 큰 image data·model은 오래 걸렸다. |
| CNN이 같은 filter를 image 여러 위치에 적용 | GPU가 많은 유사 연산을 높은 throughput으로 실행 | Dense·regular tensor work가 장치에 잘 맞았지만 memory 용량이 제한됐다. |
| AlexNet이 ReLU·dropout·augmentation과 큰 CNN을 결합 | 두 GTX 580과 맞춤 convolution 구현을 사용 | ImageNet 결과가 개선됐지만 5–6일과 3GB/device 제약이 남았다. |
| Framework가 model을 tensor graph로 표현 | CUDA·cuDNN이 device kernel과 memory 선택을 맡음 | 실험 작성은 쉬워졌지만 kernel launch·transfer·workspace가 실제 시간을 좌우했다. |

여기서 GPU는 **가능 조건**, AlexNet의 model·학습 기법은 **직접 구성 요소**, cuDNN과 framework는 **프로그래밍·실행 기반**이다. 어느 하나를 나머지 전체의 단일 원인으로 부르지 않는다.

### 가장 작은 구체적 예: 한 예제를 batch 행렬곱으로 바꾸기

회색조 $28\times28$ image 한 장을 길이 784의 vector로 펴고 256개 hidden feature를 만든다고 하자. 한 image $x\in\mathbb R^{1\times784}$와 weight $W\in\mathbb R^{784\times256}$의 출력은

$$
y=xW+b
$$

이고, 곱셈은 $784\cdot256=200{,}704$번 필요하다. Image 128장을 행으로 쌓으면 $X\in\mathbb R^{128\times784}$이고

$$
Y=XW+\mathbf 1b^\top,\qquad Y\in\mathbb R^{128\times256}
$$

가 된다. 이 한 행렬곱에는

$$
128\cdot784\cdot256=25{,}690{,}112
$$

번의 scalar 곱셈이 있다. 각 출력 원소는 많은 곱셈·덧셈을 요구하지만 서로 다른 행·열의 출력은 상당 부분 독립적이어서 많은 thread에 나누기 쉽다. 같은 $W$를 128개 image가 공유하므로 tile에 올린 weight·input 조각을 여러 출력 계산에 재사용할 여지도 생긴다.

Backward도 같은 종류의 큰 연산을 만든다. 위에서 온 gradient를 $G=\partial L/\partial Y\in\mathbb R^{128\times256}$라 하면

$$
\frac{\partial L}{\partial W}=X^\top G,\qquad
\frac{\partial L}{\partial X}=GW^\top
$$

이다. Forward 한 번과 이 두 backward 행렬곱만 세어도 약 $3\cdot25{,}690{,}112=77{,}070{,}336$번의 scalar 곱셈이다. Activation, bias, loss, data 읽기와 weight update는 이 수에 들어 있지 않다.

## 2단계 — 작동 원리

### 병목 1: 학습 그래프를 규칙적인 tensor 연산으로 묶는다

Neuron을 하나씩 해석하며 실행하면 작은 명령과 memory 접근이 많다. Batch dimension을 추가하고 convolution·dense layer를 tensor operator로 묶으면 동일한 instruction을 넓은 data에 반복할 수 있다.

Convolution도 본질적으로 입력의 여러 위치와 filter 사이의 내적을 반복한다. 구현은 직접 convolution, 행렬곱으로 변환하는 방식, FFT 계열 등 여러 algorithm을 선택할 수 있다. Model 식이 같아도 input shape, filter와 stride, workspace memory에 따라 빠른 구현이 달라진다.

### 병목 2: CUDA가 병렬 장치를 프로그램 가능한 대상으로 만든다

CUDA에서 **thread**는 작은 작업 단위, **block**은 shared memory와 synchronization을 함께 쓰는 thread 묶음, **grid**는 한 kernel launch가 만드는 block 집합이다. CPU가 kernel을 시작하면 GPU가 많은 thread를 실행한다.

행렬곱에서는 한 block이 출력 tile을 맡고, input·weight tile을 빠른 shared memory에 올린 뒤 재사용할 수 있다. 그러나 thread 수를 늘린다고 언제나 빨라지는 것은 아니다.

- 인접 thread가 흩어진 주소를 읽으면 memory transaction이 비효율적일 수 있다.
- Tile이 너무 크면 register·shared memory가 부족해 동시에 실행할 block 수가 줄어든다.
- 작은 연산을 자주 시작하면 kernel launch overhead가 실제 계산보다 커질 수 있다.
- Host와 device 사이에 tensor를 자주 복사하면 가속한 연산 시간을 transfer가 먹어 버릴 수 있다.

따라서 CUDA는 높은 throughput의 **표현 수단**이지 모든 program의 자동 가속 보장이 아니다.

### 병목 3: cuDNN이 반복되는 kernel 최적화를 library로 옮긴다

초기 GPU 연구 코드는 연구팀이 convolution과 gradient kernel을 직접 최적화하는 경우가 많았다. 새 GPU와 새 tensor shape가 나오면 같은 작업을 다시 해야 했다.

cuDNN은 BLAS가 선형대수 primitive를 재사용 가능하게 만든 것과 비슷하게, deep-learning primitive의 여러 구현을 library 경계 안에 두었다. Framework는 “이 shape의 convolution forward”나 “filter gradient”를 요청하고, library는 device·shape·workspace 조건에 맞는 algorithm을 고른다.

이 분리는 두 능력을 만든다.

- Model 연구자는 모든 CUDA 세부를 다시 구현하지 않고 network 구조를 바꿀 수 있다.
- Kernel 개발자는 같은 최적화를 여러 framework와 model이 쓰게 할 수 있다.

그렇다고 abstraction이 비용을 지우지는 않는다. Workspace가 부족하면 다른 algorithm을 써야 하고, 지원하지 않는 shape나 operation은 느린 fallback·새 kernel이 필요하다.

### 병목 4: 프레임워크가 수학 그래프와 장치 실행을 연결한다

TensorFlow의 2016년 system 설명을 예로 들면, graph의 vertex는 operation, edge를 흐르는 값은 tensor다. Matrix multiplication·convolution·ReLU 같은 primitive로 forward를 쓰고 각 primitive의 gradient rule을 조합해 backward graph를 만들 수 있다.

이 구조는 다음 관심사를 분리한다.

```text
모델 식과 loss
  ↓ tensor operation graph
자동미분으로 만든 gradient graph
  ↓ placement·partition
CPU/GPU별 kernel과 buffer 이동
  ↓ runtime
반복 step·checkpoint·평가
```

같은 model 정의가 여러 device를 겨냥할 수 있지만 성능이 자동으로 같아지지는 않는다. Placement, kernel 순서, buffer lifetime, host–device·device–device 통신과 input pipeline이 end-to-end step time을 결정한다.

### 병목 5: peak 연산량에서 실제 학습 완료 시간으로 이동한다

장치의 peak FLOP/s는 이상적인 연산을 초당 얼마나 수행할 수 있는지 나타낸다. 실제 학습 step은 개념적으로

$$
T_{\text{step}}
\approx
T_{\text{input}}+
T_{\text{kernel}}+
T_{\text{transfer}}+
T_{\text{sync}}+
T_{\text{update}}
$$

로 나눌 수 있다. 실제 system에서는 일부 항이 겹치므로 이 합은 정확한 물리 법칙이 아니라 병목을 빠뜨리지 않기 위한 장부다.

Model 하나의 peak 연산 이용률이 높아도 input이 늦거나 GPU 사이 synchronization이 길면 images/s는 낮다. 반대로 FLOP 수가 조금 늘어도 fused kernel과 data reuse가 좋아져 wall-clock은 줄 수 있다. 목표는 peak 수치가 아니라 같은 quality 계약에 도달하는 time-to-quality다.

## 3단계 — 기술과 근거

### GPU 이전에도 학습 CNN은 작동했다

LeCun 등의 1998년 논문은 gradient-based learning과 convolutional network를 우편·은행 문서 인식 시스템에 적용했다. 이는 역전파와 CNN의 계산 가능성이 2012년에 처음 생긴 것이 아님을 확인한다.

그러나 작은 문자 image를 처리한 당시 시스템의 성공이 곧 ImageNet 규모의 색상 image와 60 million parameter network를 같은 시간 안에 훈련할 수 있었다는 뜻은 아니다. Algorithm의 존재와 특정 규모에서의 실현 가능성을 구분해야 한다.

### AlexNet은 algorithm·data·GPU를 함께 쓴 사례다

2012년 AlexNet 논문은 1.2 million training images, 1,000 classes와 약 60 million parameters를 보고했다. Network를 두 NVIDIA GTX 580 3GB GPU에 나눠 약 90회 data를 통과했고, 훈련에는 5–6일이 걸렸다.

단일 GPU의 3GB memory에 network가 들어가지 않아 두 GPU에 kernel을 나눴고, 일부 layer에서만 GPU 사이 통신하도록 연결을 설계했다. 이 사례의 결론은 “GPU 두 대면 딥러닝이 된다”가 아니다.

- **Model:** 다섯 convolutional layer와 세 fully connected layer
- **Optimization:** mini-batch SGD, momentum, weight decay와 learning-rate schedule
- **학습 안정·일반화:** ReLU, data augmentation, dropout
- **실행:** 효율적인 GPU convolution과 두 GPU 분할
- **결과:** ILSVRC-2010 top-1 37.5%, top-5 17.0% test error

좋은 결과는 이 구성의 결합에 속한다. GPU는 큰 실험을 허용한 핵심 가능 조건이지만 accuracy의 단일 원인은 아니다.

### cuDNN은 최적화 비용의 소유권을 바꿨다

Chetlur 등의 2014년 cuDNN 보고서는 convolution·activation·pooling·normalization의 forward와 backward primitive를 GPU library로 제공했다. Caffe의 표준 model과 Tesla K40에서 기존 Caffe 구현 대비 전체 200 iteration 실행의 1.36배 speedup을 보고했다.

이 수치는 cuDNN의 모든 model·GPU에 대한 보장이 아니다. 해당 model, 초기 cuDNN release, Caffe integration과 device에서 얻은 결과다. 더 중요한 역사적 변화는 framework interface를 유지한 채 kernel 구현과 workspace 최적화를 교체할 수 있게 한 것이다.

### TensorFlow는 model graph를 이기종 실행 계획으로 만들었다

Abadi 등의 2016년 논문에서 TensorFlow는 계산과 mutable state를 하나의 dataflow graph로 표현하고, node를 CPU·GPU·TPU와 여러 machine에 배치했다. Primitive operator로 layer를 구성하면 framework가 gradient subgraph를 만들고 device별 subgraph로 나눌 수 있었다.

이는 Python 한 줄이 장치 비용을 없앤다는 뜻이 아니다. 논문도 operation placement에서 computation·memory·network 요구를 함께 균형 잡아야 한다고 설명한다. Framework의 기여는 연구자가 model 구조와 update rule을 조합하는 층과, runtime이 kernel·buffer·device를 관리하는 층 사이에 반복 가능한 interface를 만든 데 있다.

### 일곱 능력층으로 변화와 비변화를 분리한다

| 능력층 | 이 시기 바뀐 것 | 바뀌지 않거나 남은 것 |
| --- | --- | --- |
| 계산 가능성 | 역전파·CNN은 GPU 이전에도 계산 가능했다. | GPU가 새 학습 원리를 증명한 것은 아니다. |
| 알고리즘 복잡도 | Batch·convolution algorithm이 같은 계산을 다른 순서로 실행했다. | Model의 layer·tensor가 요구하는 산술·memory 하한은 남는다. |
| 프로그래밍 가능성 | CUDA, cuDNN과 framework가 device code 재사용·자동미분·배치를 지원했다. | 새 operator·shape는 구현과 검증이 필요하다. |
| 실현 성능 | 큰 tensor의 병렬 실행으로 실제 학습 시간이 감당 가능한 범위로 내려왔다. | Peak FLOP/s와 end-to-end time은 다르다. |
| 확장성 | Batch·model·device를 키우는 실행 경로가 생겼다. | Memory 용량과 device 간 통신이 곧 새 병목이 됐다. |
| 자원 효율 | Kernel 재사용과 data locality가 같은 work의 시간·memory를 줄였다. | Energy·비용은 보고 조건 없이는 추정할 수 없다. |
| 신뢰 가능한 결과 | Dataset·metric·checkpoint를 포함한 반복 pipeline이 자리 잡았다. | Accuracy가 다른 domain·서비스 품질을 보장하지 않는다. |

### CS_WIKI와 함께 읽기

[CS_WIKI의 「도메인 특화 가속기」](https://yghnsim.github.io/CS_Wiki/concepts/%EB%8F%84%EB%A9%94%EC%9D%B8-%ED%8A%B9%ED%99%94-%EA%B0%80%EC%86%8D%EA%B8%B0/)는 범용 processor와 특정 연산에 맞춘 가속기의 효율·유연성 교환을 설명한다. 이 문서는 그 관점을 GPU deep-learning stack에 적용하지만, 사실 근거는 위에 등록한 1차 자료에서 가져온다.

### 다음 병목: 더 큰 행렬에서 의존성·memory·통신으로

GPU와 framework는 큰 dense operation을 빠르게 실행했지만 model graph의 순차 의존까지 자동으로 없애지는 않았다. RNN은 이전 hidden state를 기다렸고, 여러 device로 나누면 synchronization과 통신이 필요했다. 또한 연산 처리량이 커질수록 HBM과 작은 on-chip memory 사이의 이동이 중요해졌다.

다음 본편 [[Transformer는 무엇을 병렬화했고 무엇을 남겼나]]는 recurrent state 의존을 줄여 더 많은 위치를 행렬곱으로 묶은 변화와, 자기회귀 생성의 순차성·attention memory라는 새 병목을 이어서 본다.

## 검증과 한계

AlexNet의 2012년 결과는 GPU만 바꾼 통제 실험이 아니다. Data 규모, architecture, ReLU, augmentation, dropout과 최적화가 함께 달랐다. 따라서 “GPU 때문에 error가 몇 % 줄었다”는 인과 효과를 이 논문만으로 분리할 수 없다.

CUDA 2008, AlexNet 2012, cuDNN 2014와 TensorFlow 2016은 하나의 조직이 미리 설계한 직선 roadmap도 아니다. 여기서는 각 자료가 확인하는 기능과 사용을 시간순으로 연결했으며, 직접 설계 영향을 입증하지 못한 연결은 가능 조건·병행 맥락으로 남겼다.

본편의 batch 행렬곱은 dense layer의 산술 구조만 보여 준다. 실제 convolution 구현, cache hit, warp divergence, mixed precision, distributed synchronization과 input decoding은 포함하지 않는다. Peak FLOP/s, kernel benchmark, 전체 training time과 task quality는 측정 경계가 달라 하나의 “몇 배 빠름”으로 합칠 수 없다.

## 학습 확인

1. $X\in\mathbb R^{128\times784}$와 $W\in\mathbb R^{784\times256}$의 forward·weight-gradient·input-gradient shape와 각 행렬곱의 scalar multiplication 수를 계산하라.
2. CUDA, cuDNN과 TensorFlow가 각각 맡은 문제를 thread 실행, optimized primitive와 graph·gradient 관리로 구분하라.
3. 새 accelerator가 “AI를 10배 가속했다”고 주장한다. 작업·규모·결과 계약·시스템 경계·고정 조건·지표를 채우고 peak, kernel, step, time-to-quality 가운데 어느 수치인지 판정하라.

다음에는 큰 tensor 연산에 잘 맞는 Transformer가 훈련에서 무엇을 병렬화했으며, 실제 token 생성에는 어떤 순차성을 남겼는지 확인한다.

### 횡단 연결

[[N-gram에서 LLM으로]]는 이 실행 스택이 가속한 workload가 단순히 더 큰 n-gram 표가 아니라, 연속 표현·공유 매개변수·조건부 sequence 생성을 학습하는 계산으로 이미 바뀌어 있었음을 설명한다.

또 다른 횡단 연결 [[저장 프로그램에서 학습 프레임워크까지]]은 CUDA·cuDNN·TensorFlow 앞에 compiler·BLAS·역모드 자동미분이라는 프로그래밍 추상화가 왜 필요했는지 하나의 내적 예로 복원한다.
