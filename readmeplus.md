# LLM Wiki v2 프로젝트 해설서

이 문서는 저장소를 빠르게 실행하는 방법을 알려 주는 README의 보충 자료다. README가 “무엇을 입력하면 실행되는가”를 설명한다면, 이 문서는 “왜 이런 구조를 선택했고 자료가 어떻게 공개 지식으로 바뀌는가”를 설명한다.

대상 독자는 개발자만이 아니다. AI와 언어 기술의 역사를 처음 접하는 사람, 문서를 읽고 편집하고 싶은 사람, 저장소의 자동 검증이 무엇을 보호하는지 알고 싶은 사람도 이 문서를 따라갈 수 있도록 작성했다.

---

## 1. 한 문장으로 보는 프로젝트

LLM Wiki v2는 초기 언어 모델, 기계 번역, AI 평가, 신경망 학습, 언어 구조, 대화형 AI의 역사를 한국어로 읽고 서로 연결하는 **근거 기반 지식베이스**다.

여기서 지식베이스란 문서를 많이 모아 둔 폴더가 아니라, 사실·해석·출처·관계를 다시 찾을 수 있도록 구조화한 지식 저장소를 뜻한다. 이 프로젝트는 다음 네 가지를 함께 지킨다.

| 목표 | 쉬운 뜻 | 프로젝트에서의 적용 |
| --- | --- | --- |
| 이해 | 독자가 배경부터 핵심 원리까지 따라갈 수 있어야 한다. | 모든 비메타 문서에 학습 안내와 단계별 설명을 둔다. |
| 정확성 | 사실, 해석, 후대의 평가를 섞지 않는다. | 외부 근거와 문헌 내 위치를 evidence로 기록한다. |
| 연결성 | 새 문서가 기존 지식과 어떤 질문을 공유하는지 보여 준다. | 링크, 관계, 관련 분석, 역링크를 제공한다. |
| 보존성 | 나중에 출처와 변경 경위를 다시 확인할 수 있어야 한다. | 원문 자료는 raw로 보존하고 해시와 로그를 남긴다. |

따라서 목표는 페이지 수를 늘리는 일이 아니다. 독자가 어떤 기술을 읽을 때 다음 질문에 답할 수 있게 하는 것이 목표다.

1. 이 용어나 기술은 일반적으로 어디에 쓰이는가?
2. 그 기술이 역사적으로나 기술적으로 중요한 이유는 무엇인가?
3. 이 프로젝트에서 그 기술을 설명해야 하는 이유는 무엇인가?
4. 반드시 그렇게 해야 하는 원리와, 당시 연구자가 선택한 설계는 무엇인가?

### 누가 어떻게 사용하는가

- **처음 배우는 독자**는 소스 문서의 학습 안내와 관련 항목을 따라가며 배경 개념부터 읽는다.
- **연구자나 집필자**는 evidence의 locator를 따라 원문에서 주장을 재확인하고, 분석 문서에서 자료 간 긴장을 찾는다.
- **편집자**는 schema, 태그, 관계, 로그를 사용해 문서가 서로 다른 규칙으로 작성되지 않도록 관리한다.
- **개발자**는 스키마 검증기와 사이트 생성기를 수정해 지식이 안전하게 공개되도록 한다.
- **팀의 새 참여자**는 raw와 wiki의 역할 차이, 검증 명령, 커밋 경계를 먼저 이해한 뒤 편집에 참여한다.

## 2. 전체 작동 흐름

한 편의 자료는 다음 경로를 지나 공개 페이지가 된다.

~~~text
외부 원문·1차 자료
        ↓
번역·해설 자료
        ↓
raw/에 불변 보존 + SHA-256 해시 등록
        ↓
evidence 레지스트리에 출처·locator 등록
        ↓
wiki/sources·concepts·entities·analyses 문서 작성
        ↓
frontmatter·링크·근거·raw 무결성 검사
        ↓
정적 사이트 생성·검색 색인·관계 그래프 생성
        ↓
GitHub Pages에 배포
~~~

이 흐름의 핵심은 “원문 보관”과 “공개 설명”을 분리하는 것이다. 원문 파일은 수집 당시 상태를 보존하는 자료이고, 위키 페이지는 그 자료를 읽고 검증한 뒤 독자에게 설명하는 편집 결과다.

### 정적 사이트란 무엇인가

**정적 사이트(static site)**는 방문자가 페이지를 열 때마다 서버가 데이터베이스를 조회하고 HTML을 조립하는 대신, 미리 완성한 HTML·CSS·JavaScript 파일을 제공하는 웹사이트다.

일반적인 용도와 의의:

- 문서 사이트, 블로그, 제품 안내서처럼 읽기 중심인 사이트에 널리 사용된다.
- 페이지 생성 결과가 파일로 남으므로 같은 입력에서 같은 결과를 재현하기 쉽다.
- 서버 데이터베이스와 실행 코드를 줄여 보안·운영 비용을 낮출 수 있다.

이 프로젝트에서 필요한 이유:

- 공개 지식의 기준을 Git 저장소의 Markdown과 레지스트리로 고정할 수 있다.
- 사이트를 만들 때 오류를 발견하면 배포 전에 빌드가 실패한다.
- 독자가 보는 결과와 저장소에 검토된 결과 사이의 차이를 줄인다.

정적 사이트 선택은 “동적인 기능이 필요 없어서”가 아니라, 이 프로젝트의 핵심이 문서 생성과 검증의 재현성에 있기 때문에 적합하다.

## 3. 프로젝트 목적에 맞춘 폴더 구조

~~~text
LLM_Wiki_v2/
├── raw/                         # 수정하지 않는 보존 자료
├── wiki/
│   ├── index.md                 # 전체 색인
│   ├── overview.md              # 범위와 진입점
│   ├── log.md                   # 편집·검증 기록
│   ├── sources/                 # 원문별 소스 노트
│   ├── concepts/                # 개념 설명
│   ├── entities/                # 인물·기관·작품
│   ├── analyses/                # 자료를 함께 읽은 분석
│   └── meta/                    # 스키마·태그·근거·경로 레지스트리
├── scripts/
│   ├── lib/                     # 공통 로더·링크·경로 모듈
│   ├── tests/                   # 회귀 테스트
│   ├── lint-wiki.mjs            # 위키 규칙 검사
│   ├── build-site.mjs           # 정적 사이트 생성
│   └── check-site.mjs           # 생성 산출물 검사
├── site/                        # 화면 스타일·브라우저 코드·폰트
├── dist/                        # 생성된 사이트 산출물
└── readmeplus.md                # 이 상세 해설서
~~~

### raw와 wiki를 나누는 이유

**raw artifact**는 수집 당시 받은 파일을 뜻한다. 이 프로젝트에서 raw는 “그 파일의 내용이 모두 사실”이라는 뜻이 아니라, “우리가 어떤 자료를 참고했는지 다시 확인할 수 있도록 원래 상태를 보존한다”는 뜻이다.

**wiki 문서**는 raw를 읽고 외부 1차 자료와 대조해 작성한 공개 설명이다. 따라서 raw의 오탈자나 설명 부족을 그대로 사실처럼 복사하지 않고, 위키 본문에서 검증 정정이나 원문 상태를 분리해 설명한다.

이 분리는 일반적인 디지털 보존에서도 중요하다. 원본을 수정하면 나중에 무엇이 수집 당시 내용이었고 무엇이 편집자의 수정인지 알 수 없기 때문이다. 여기서는 <code>raw/</code>의 변경을 해시 검사로 감지하고, 설명은 <code>wiki/</code>에서 갱신한다.

### 레지스트리란 무엇인가

**레지스트리(registry)**는 흩어진 정보를 목록과 규칙으로 정리한 관리 장부다. 예를 들어 다음 파일들이 레지스트리 역할을 한다.

- <code>evidence.yml</code>: 외부 문헌의 식별자, 제목, URL, DOI, 출처 상태
- <code>raw-artifacts.yml</code>: raw 파일의 역할, 출처 URL, 공식 번호, SHA-256
- <code>tags.yml</code>: 사용할 수 있는 태그와 태그의 의미
- <code>source-catalog.yml</code>: 공개 source/reference 페이지와 공식 번호의 단일 목록
- <code>red-links.yml</code>: 아직 작성하지 않았지만 의도적으로 허용한 링크
- <code>site-redirects.yml</code>: 옛 URL을 새 canonical URL로 연결하는 목록

레지스트리는 반복 입력을 줄이는 장치인 동시에, “이 값이 실제로 등록된 것인가?”를 자동 검사할 수 있게 하는 기준점이다.

## 4. 페이지 하나가 지키는 약속: schema v3

문서의 본문만 읽으면 제목이나 출처의 위치가 사람마다 달라질 수 있다. 그래서 각 페이지의 머리 부분에 기계가 읽는 메타데이터를 둔다.

### YAML frontmatter

**YAML frontmatter**는 Markdown 파일 맨 위에 <code>---</code>로 감싼 구조화된 정보다. YAML은 사람이 읽기 쉬운 설정·데이터 표현 형식이다.

일반적인 용도와 의의:

- 제목, 날짜, 유형, 태그 같은 문서 속성을 본문과 분리한다.
- 프로그램이 파일을 읽어 목록, 검색, 필터, 검증에 재사용할 수 있다.

이 프로젝트에서 필요한 이유:

- 394개 문서를 같은 방식으로 색인하고 검색해야 한다.
- 독자가 보는 본문과 기계가 사용하는 문서 상태를 분리해야 한다.
- schema v3 규칙을 통과한 문서만 공개 대상으로 삼을 수 있다.

페이지의 축약된 예시는 다음과 같다.

~~~yaml
---
schema_version: 3
id: concept.example
page_type: concept
title: 예시 개념
aliases: [다른 이름]
tags: [type/concept, domain/ai]
created: 2026-07-26
updated: 2026-07-26
editorial_status: active
review:
  evidence_coverage: verified
  content_mode: descriptive
artifacts:
  - raw/001_example.commentary.ko.md
evidence:
  - source_id: example-paper
    locator: section 2, p. 3
    relation: supports
relations:
  - target: concept.related
    kind: related
learning:
  difficulty:
    entry: introductory
    target: intermediate
  prerequisites: []
  assumed_knowledge: 기본적인 문장과 숫자 개념
  outcomes: [핵심 원리와 한계를 설명할 수 있다.]
  next:
    - target: concept.next
      reason: 더 정식인 표현으로 이동
---
~~~

### 주요 필드의 뜻과 필요성

| 필드 | 일반적인 용도 | 이 프로젝트에서 필요한 이유 |
| --- | --- | --- |
| <code>schema_version</code> | 데이터 구조의 버전을 표시한다. | 구조가 바뀌어도 어떤 규칙으로 작성됐는지 알 수 있다. |
| <code>id</code> | 파일명과 독립적인 영구 식별자다. | 제목이 바뀌어도 링크와 URL을 안정적으로 유지한다. |
| <code>page_type</code> | 문서의 역할을 구분한다. | source, concept, entity, analysis를 검색·검증·목록에서 다르게 다룬다. |
| <code>title</code>, <code>aliases</code> | 표시 제목과 검색용 다른 이름이다. | 번역명·원어·약어를 함께 찾을 수 있다. |
| <code>tags</code> | 주제와 구조를 분류한다. | 허용된 범위 안에서 필터와 탐색을 제공한다. |
| <code>created</code>, <code>updated</code> | 생성일과 갱신일이다. | 시간순 정렬과 편집 이력을 이해할 수 있다. |
| <code>editorial_status</code> | 초안·공개·보관 상태다. | 편집 수명주기와 사실 검토 상태를 섞지 않는다. |
| <code>review</code> | 근거 범위와 글의 성격을 표시한다. | verified 사실 설명과 partial 합성 분석을 구분한다. |
| <code>artifacts</code> | 참고한 저장소 파일 경로다. | 어떤 보존 자료를 읽었는지 추적한다. |
| <code>evidence</code> | 외부 문헌과 위치, 관계다. | 현재 문장의 근거를 사람이 다시 확인한다. |
| <code>relations</code> | 큐레이션한 방향성 관계다. | 단순 키워드 일치가 아닌 다음 읽을 길을 만든다. |
| <code>learning</code> | 난이도·선수 지식·학습 목표·다음 문서다. | 독자가 링크를 헤매지 않고 자립적으로 학습한다. |

### Schema와 JSON Schema

**Schema(스키마)**는 데이터가 어떤 모양이어야 하는지 정한 약속이다. **JSON Schema**는 그 약속을 컴퓨터가 검사할 수 있게 표현한 표준 형식이다.

일반적인 용도와 의의:

- API 요청, 설정 파일, 데이터베이스 레코드의 필수 필드와 자료형을 검증한다.
- 사람이 문서를 읽기 전에 누락·오타·잘못된 값을 빠르게 찾는다.

이 프로젝트에서 필요한 이유:

- 394개 문서를 사람의 기억에만 의존해 관리할 수 없다.
- <code>page_type</code>과 폴더, <code>type/*</code> 태그가 서로 어긋나면 목록과 URL이 틀어진다.
- 스키마 검사로 형식 오류를 초기에 발견하고, 내용의 정확성 검토에 집중할 수 있다.

스키마는 내용의 진실성을 자동 증명하지 않는다. “필드가 있고 값의 형식이 맞다”를 검사하며, 그 안의 주장이 맞는지는 evidence와 사람의 검토가 담당한다.

### editorial status와 review는 왜 분리하는가

- <code>editorial_status: active</code>는 독자가 읽을 수 있는 공개 상태라는 뜻이다.
- <code>review.evidence_coverage: verified</code>는 핵심 사실을 locator가 있는 근거로 확인했다는 뜻이다.
- <code>review.content_mode: descriptive</code>는 자료를 설명하는 글이다.
- <code>review.content_mode: synthesis</code>는 여러 자료를 비교해 해석을 제시하는 글이다.

공개되어 있다는 이유만으로 모든 문장이 완전히 검증됐다고 볼 수는 없다. 이 두 상태를 분리해야 편집 상태와 지식의 검증 수준을 정직하게 표현할 수 있다.

## 5. 본문은 학습 순서로 설계된다

이 위키의 문서는 사전처럼 정의 한 줄만 보여 주지 않는다. 독자가 숨은 선수 지식 없이 문제의 배경에서 기술적 세부로 올라갈 수 있도록 다음 순서를 따른다.

1. <code>1단계 — 먼저 잡을 핵심</code>
2. <code>2단계 — 작동 원리</code>
3. <code>3단계 — 기술과 근거</code>
4. <code>검증과 한계</code>
5. <code>학습 확인</code>
6. <code>출처</code>
7. <code>관련 항목</code>

H1 바로 뒤에는 학습 안내를 둔다. 학습 안내는 진입 난이도, 필요한 선수 지식, 읽고 나서 할 수 있는 일을 알려 준다.

### 전문 용어를 설명하는 네 가지 질문

전문 용어를 처음 쓸 때는 링크만 걸고 지나가지 않는다. 최소한 다음 네 층을 차례로 설명한다.

1. **일반적인 용도**: 이 용어는 보통 어떤 문제를 해결할 때 쓰이는가?
2. **의의**: 기존 방법과 비교해 무엇을 가능하게 했는가?
3. **프로젝트의 필요성**: 이 위키의 역사와 연결을 이해하려면 왜 필요한가?
4. **필연성과 선택**: 원리상 반드시 필요한 부분과 당시 연구자가 선택한 구현은 무엇인가?

예를 들어 Transformer를 설명한다면, “문장을 처리하는 신경망”이라고만 쓰지 않는다.

- 일반적으로는 순서가 있는 입력의 여러 위치가 서로 영향을 주도록 하는 모델 구조다.
- 의의는 긴 거리의 관계를 직접 비교하고 학습을 병렬화할 수 있게 한 데 있다.
- 이 프로젝트에서는 BERT, GPT, Transformer-XL, FlashAttention으로 이어지는 계보와 컴퓨팅 조건을 연결하는 공통 언어가 된다.
- 입력의 관계를 계산해야 한다는 문제는 필수이지만, self-attention의 점수 계산식, 위치 정보의 주입 방식, residual과 LayerNorm의 배치는 여러 설계 선택 중 하나다.

이 구분은 역사적 과장을 막는다. 어떤 후대 기술이 이전 기술에서 “직접 이어졌다”고 단정하기 전에, 실제 영향인지 공통 문제인지 수학적 유사성인지 분리해 쓸 수 있기 때문이다.

### 수식은 결과가 아니라 설명의 일부다

수식을 쓸 때는 기호를 나열하지 않는다. 계산 목적, 각 기호의 뜻과 자료형, 입력의 모양(shape), 항과 연산의 역할, 작은 숫자 예, 자연어 해석, 성립 가정, 실패 조건을 함께 설명한다.

이 방식의 일반적인 의의는 수학을 모르는 독자도 공식이 무엇을 보존하고 무엇을 버리는지 확인하게 하는 것이다. 이 프로젝트에서는 역사적 기술을 “이 식을 사용했다”에서 멈추지 않고, 왜 그 식이 해당 시대의 문제에 적합했는지 설명하기 위해 필요하다.

## 6. 정규 소스가 공개 지식이 되는 과정

정규 소스는 공식 책 목차 번호를 기준으로 관리한다. 외부 원문·번역·raw 파일명·공개 페이지의 <code>source.NNN</code>·관련 링크·커밋 메시지가 같은 세 자리 번호를 사용한다.

### 번호와 047 예외

- 공식 upstream 원문이 있는 장은 001–046, 048–110으로 처리한다.
- 047 Attention Mechanism은 알려진 upstream 결손이다.
- 047은 외부 번역본으로 가장하지 않고, 1차 문헌을 토대로 위키가 작성한 편집부 재구성으로 표시한다.
- 결손과 재구성 상태는 <code>wiki/meta/source-gaps.yml</code>에 기록한다.

### 단계별 처리

1. **원문 확인**: 외부 1차 자료와 번역 대상 파일을 확인한다.
2. **번역·해설 생성**: 원문과 commentary를 같은 공식 번호로 만든다.
3. **raw 보존**: <code>source:copy</code>가 검증된 쌍을 <code>raw/</code>에 복사하고 SHA-256을 등록한다.
4. **근거 등록**: 문헌 제목·URL·DOI와 재확인 가능한 locator를 <code>evidence.yml</code>에 추가한다.
5. **소스 노트 작성**: 요약, 검증 정정, 핵심 문장, 출처, 관련 항목을 작성한다.
6. **연결 문서 갱신**: 실제로 필요한 concept, entity, analysis만 보강한다.
7. **색인 동기화**: <code>sync:index</code>로 index, overview, log와 공개 목록을 맞춘다.
8. **준비 상태 검사**: <code>source:ready</code>로 테스트·lint·빌드·산출물을 확인한다.
9. **공개**: 범위를 검토한 뒤 정해진 커밋 경계로 main에 반영한다.

### locator란 무엇인가

**Locator**는 문헌에서 주장을 다시 찾을 수 있는 위치 정보다. 페이지, 절, 장, 표, 그림, 코드 기록 등이 될 수 있다.

일반적인 용도와 의의:

- 인용을 재현하고, 다른 사람이 원문을 빠르게 대조하게 한다.
- “출처가 있다”는 막연한 표시보다 검증 가능한 경로를 제공한다.

이 프로젝트에서 필요한 이유:

- raw 번역은 보존 자료이지 사실의 자동 증명이 아니다.
- 위키가 해석을 포함할수록 어떤 문장이 원문에 있고 어떤 문장이 편집자의 분석인지 구분해야 한다.

## 7. 정적 사이트는 어떻게 만들어지는가

사이트 생성기는 <code>scripts/build-site.mjs</code>를 중심으로 동작한다.

~~~text
Markdown 파일 읽기
    ↓
frontmatter 파싱 및 문서 유형 확인
    ↓
ID 기반 canonical 경로 계산
    ↓
Obsidian 링크를 실제 페이지 링크로 변환
    ↓
Markdown과 KaTeX 수식 렌더링
    ↓
허용 목록 기반 HTML sanitizer 적용
    ↓
상세 페이지·목록·검색·독자(reader) 생성
    ↓
검색 색인·관계 그래프·legacy redirect 생성
    ↓
임시 출력 디렉터리 검증 후 dist/로 교체
~~~

### Markdown

**Markdown**은 제목, 목록, 인용, 링크를 짧은 문자 규칙으로 표현하는 문서 형식이다.

- 일반적인 용도: GitHub, 문서 사이트, 블로그, 기술 문서 작성
- 의의: 사람이 읽기 쉽고 버전 관리와 변환이 쉽다.
- 프로젝트의 필요성: 위키 본문을 특정 편집 프로그램에 종속시키지 않고, 원문과 변경 이력을 텍스트로 보존한다.

### KaTeX

**KaTeX**는 LaTeX 수식을 브라우저에서 빠르게 표시하는 렌더러다. 수식을 이미지로 붙이지 않고 텍스트 기반으로 관리하므로 기호를 검색·검토하고 소스 변경을 추적하기 쉽다.

이 프로젝트에서 KaTeX는 역사적 논문과 신경망 설명에 등장하는 수식을 독자가 본문 흐름 안에서 읽게 하는 데 필요하다. 다만 수식 렌더링은 수식의 의미가 맞다는 것을 보증하지 않으므로, 기호와 가정은 문서 본문이 설명한다.

### Sanitizer

**Sanitizer**는 입력 HTML에서 허용되지 않은 태그, 속성, URL, 이벤트 코드를 제거하는 보안 처리다.

- 일반적인 용도: 사용자 입력이나 Markdown을 HTML로 바꿀 때 XSS 공격을 줄인다.
- 의의: “문서 파일을 그대로 웹 코드로 실행하지 않는다”는 경계를 만든다.
- 프로젝트의 필요성: 외부 자료와 작성자가 늘어날수록 링크·HTML·수식 입력이 웹 페이지의 안전성을 해치지 않도록 해야 한다.

### Canonical URL과 redirect

**Canonical URL**은 한 페이지를 대표하는 정식 주소다. 여기서는 파일명이나 제목이 아니라 영구 <code>id</code>를 바탕으로 만든다.

**Redirect**는 옛 주소로 들어온 방문자를 새 주소로 보내는 연결이다.

- 일반적인 용도: 사이트 개편이나 문서 제목 변경 뒤 기존 링크를 보존한다.
- 프로젝트의 필요성: schema v3에서 ID 기반 경로로 바꾸면서도 이미 공유된 469개 legacy 경로를 계속 읽을 수 있게 한다.

### 검색과 지식 그래프

사이트는 제목·별칭·본문·유형·검증 상태·태그를 이용해 검색한다. 별도의 서버 검색 데이터베이스 대신 빌드 시 검색 색인을 만든다.

**Knowledge graph(지식 그래프)**는 문서를 점(node)과 관계(edge)로 표현하는 구조다. 이 프로젝트에서는 문서 유형, <code>relations</code>, 본문 링크, 근거 연결을 시각적으로 탐색할 수 있게 한다.

그래프의 일반적인 의의는 “어떤 항목이 있는가”뿐 아니라 “어떤 항목이 어떻게 연결됐는가”를 보여 주는 것이다. 이 프로젝트에서는 역사적 계보를 자동으로 확정하기보다, 편집자가 큐레이션한 방향성 관계를 다음 질문으로 이동하는 탐색 장치로 사용한다.

## 8. 검증 파이프라인을 읽는 법

### Lint

**Lint**는 프로그램을 실행하지 않아도 규칙 위반을 찾아 주는 정적 검사다. 정적이라는 말은 실제 웹 요청을 보내거나 서비스를 띄우지 않고 파일을 분석한다는 뜻이다.

이 프로젝트의 lint는 다음을 확인한다.

- frontmatter가 JSON Schema와 맞는가
- 폴더, <code>page_type</code>, <code>type/*</code> 태그가 일치하는가
- ID가 중복되지 않는가
- 제목과 H1이 같은가
- evidence ID와 locator가 실제로 등록됐는가
- raw 경로가 존재하고 SHA-256이 보존 당시 값과 같은가
- 링크와 관련 항목이 존재하는가
- 색인과 source catalog가 실제 문서 수와 맞는가
- verified 문서에 해결되지 않은 경고가 남아 있지 않은가

### 회귀 테스트와 브라우저 테스트

**회귀 테스트(regression test)**는 이미 고친 기능이 새 변경으로 다시 깨지지 않았는지 확인하는 테스트다. Node.js 내장 테스트 러너로 문서 파싱, URL, 링크, 레지스트리, 사이트 출력 계약을 검사한다.

**브라우저 테스트**는 실제 Chromium에서 페이지를 열고 검색·필터·메뉴·반응형 레이아웃이 동작하는지 확인한다. HTML 파일이 생성됐다는 사실만으로 사용자가 버튼을 누를 수 있다는 보장은 없기 때문에 별도 검사가 필요하다.

### 주요 명령

| 명령 | 역할 | 언제 필요한가 |
| --- | --- | --- |
| <code>npm run raw:check</code> | raw 해시와 보존 상태를 확인한다. | raw를 참조하거나 전체 검증할 때 |
| <code>npm run translation:normalize:check</code> | 외부 번역 산출물의 형식 계약을 확인한다. | 번역 흐름을 마무리할 때 |
| <code>npm run lint:wiki</code> | 위키 구조·링크·근거·레지스트리를 검사한다. | 문서 변경 후 항상 |
| <code>npm test</code> | Node 회귀 테스트를 실행한다. | 스크립트·스키마·사이트 로직 변경 후 |
| <code>npm run build:site</code> | 정적 사이트를 생성한다. | 공개 화면 변경을 확인할 때 |
| <code>npm run check:site</code> | 생성된 HTML과 로컬 참조를 검사한다. | 빌드 산출물 검증 시 |
| <code>npm run test:browser</code> | Chromium에서 사용자 흐름을 검사한다. | 화면·검색·반응형 변경 후 |
| <code>npm run verify</code> | 로컬 전체 검증을 실행한다. | 공개 전 최종 확인 |
| <code>npm run verify:ci</code> | 외부 번역 디렉터리에 의존하지 않는 CI 검증이다. | GitHub Actions에서 실행 |

현재 저장소의 기준 규모는 다음과 같다.

- 위키 Markdown 394개
- source 110개, concept 204개, entity 29개, analysis 45개, meta 6개
- evidence 516개
- 불변 raw artifact 220개
- 생성 HTML 1,090개
- legacy redirect 469개
- 검색 색인 항목 393개
- 해결된 위키 링크 9,565개
- Node 회귀 테스트 152건, Playwright 브라우저 테스트 16건

이 수치는 문서 품질 그 자체가 아니다. 다만 구조가 커질수록 사람이 눈으로만 확인하기 어렵다는 사실을 보여 주며, 자동 검증이 필요한 이유를 설명한다.

### CI란 무엇인가

**CI(Continuous Integration, 지속적 통합)**는 변경 사항이 저장소에 들어올 때 자동으로 테스트와 빌드를 실행하는 방식이다.

- 일반적인 용도: 여러 사람이 자주 변경하는 소프트웨어의 통합 오류를 빠르게 발견한다.
- 의의: “내 컴퓨터에서는 됐다”를 공동 검증 결과로 바꾼다.
- 프로젝트의 필요성: 문서 하나의 링크·스키마·raw 해시 변경이 전체 사이트와 색인에 영향을 줄 수 있다.

GitHub Actions는 <code>main</code>에 push되거나 Pull Request가 만들어질 때 Node 22 환경에서 <code>verify:ci</code>를 실행하고, 통과한 <code>dist/</code>를 GitHub Pages에 배포한다.

## 9. Git과 GitHub Pages 배포

**Git**은 파일의 변경 이력을 저장하는 버전 관리 시스템이다. 파일을 직접 덮어쓰는 대신, 누가 언제 무엇을 왜 바꿨는지 커밋 단위로 남긴다.

이 프로젝트의 커밋 접두사는 변경 목적을 읽기 쉽게 한다.

- <code>ingest: number_title</code>: 정규 소스 공개 처리
- <code>reference: short_title</code>: 참고 자료 보강
- <code>content: short_title</code>: 분석·개념·본문 개선
- <code>fix: short_title</code>: 오류 수정
- <code>schema: short_title</code>: 스키마·레지스트리 계약 변경
- <code>lint: short_title</code>: 검사 규칙 변경
- <code>site: short_title</code>: 화면·사이트 생성 변경
- <code>docs: short_title</code>: 설명서·운영 문서 변경

**GitHub Pages**는 저장소의 정적 파일을 웹 주소로 제공하는 호스팅 서비스다. 이 프로젝트와 잘 맞는 이유는 사이트가 <code>dist/</code>의 파일로 완성되며 별도 애플리케이션 서버가 필요하지 않기 때문이다.

배포는 다음과 같다.

1. 변경을 커밋하고 <code>main</code>에 push한다.
2. GitHub Actions가 검증·빌드를 실행한다.
3. 검증이 통과하면 <code>dist/</code>를 Pages artifact로 업로드한다.
4. GitHub Pages가 공개 URL에서 새 파일을 제공한다.

검증이 실패하면 배포하지 않는 것이 안전하다. 문서 사이트도 깨진 링크, 잘못된 근거, 위험한 HTML이 공개되면 지식의 신뢰성과 독자의 안전이 함께 손상되기 때문이다.

## 10. 비개발자를 위한 프로젝트 학습 순서

### 첫 번째 시간: 목적과 범위

<code>README.md</code>의 요약과 이 문서의 1–3장을 읽는다. <code>raw/</code>는 보존 자료이고 <code>wiki/</code>는 편집된 공개 지식이라는 차이를 먼저 익힌다.

### 두 번째 시간: 문서 한 편 읽기

<code>wiki/concepts/Transformer.md</code> 또는 관심 있는 source 문서를 연다. H1 아래 학습 안내를 읽고, 1단계부터 출처까지 순서대로 따라간다.

### 세 번째 시간: 근거와 메타데이터

문서 상단 frontmatter에서 <code>id</code>, <code>page_type</code>, <code>review</code>, <code>artifacts</code>, <code>evidence</code>, <code>relations</code>, <code>learning</code>을 찾는다. 본문 출처 절에서 locator가 어떤 문장을 뒷받침하는지 확인한다.

### 네 번째 시간: 사이트 생성

<code>scripts/build-site.mjs</code>를 전체적으로 외우기보다 “읽기 → 링크 변환 → 안전한 HTML → 페이지와 색인 생성 → 산출물 검사”라는 흐름만 먼저 이해한다.

### 다섯 번째 시간: 작은 변경

새 문서를 만들기 전에 오탈자 하나, 관련 링크 하나, 설명 문장 하나를 수정하고 다음 순서로 확인한다.

~~~powershell
npm run lint:wiki
npm test
npm run build:site
npm run check:site
~~~

검사가 왜 실패했는지 이해할 수 있을 때 새 source나 concept을 추가한다. 명령을 무조건 통과시키는 것보다 실패 이유를 지식 품질 문제와 연결하는 것이 중요하다.

## 11. 기술 용어 사전: 왜 이 프로젝트에 필요한가

### Markdown

- **뜻**: 문서 구조를 간단한 문자 표기로 적는 형식
- **일반적인 용도와 의의**: 읽기 쉽고 Git diff로 변경을 비교하기 좋다.
- **프로젝트의 필요성**: 위키 본문을 오래 보존하고, 사이트·검색·검증으로 여러 번 재사용한다.

### YAML frontmatter

- **뜻**: Markdown 앞부분의 구조화된 문서 속성
- **일반적인 용도와 의의**: 내용과 메타데이터를 분리해 자동 처리한다.
- **프로젝트의 필요성**: 수백 개 문서를 유형·날짜·검토 상태·학습 경로로 일관되게 다룬다.

### JSON Schema

- **뜻**: JSON 형태의 데이터가 지켜야 할 구조와 값의 범위를 설명하는 표준
- **일반적인 용도와 의의**: 데이터 계약을 실행 가능한 검사 규칙으로 만든다.
- **프로젝트의 필요성**: 문서 형식 오류를 사이트 생성 전에 발견한다.

### Evidence와 locator

- **뜻**: evidence는 주장을 뒷받침하는 문헌 기록이고 locator는 그 문헌 안의 위치다.
- **일반적인 용도와 의의**: 인용·감사·재현성을 확보한다.
- **프로젝트의 필요성**: raw 번역과 편집자의 설명을 사실의 직접 근거와 혼동하지 않는다.

### Artifact와 SHA-256

- **뜻**: artifact는 보존할 파일이고, SHA-256은 파일 내용을 요약한 고정 길이 해시다.
- **일반적인 용도와 의의**: 파일이 바뀌었는지 확인하는 무결성 검사에 사용된다.
- **프로젝트의 필요성**: raw가 조용히 덮어써지지 않았는지 감지한다.
- **주의**: 해시가 같다는 것은 파일이 그대로라는 뜻이지, 그 파일의 주장까지 참이라는 뜻은 아니다.

### Static site generator

- **뜻**: Markdown과 데이터로 완성된 HTML 사이트를 만드는 프로그램
- **일반적인 용도와 의의**: 문서 사이트를 재현 가능하게 빌드한다.
- **프로젝트의 필요성**: 검증된 저장소 상태를 그대로 공개 페이지로 변환한다.

### Lint

- **뜻**: 실행 전에 파일의 규칙 위반을 찾는 정적 검사
- **일반적인 용도와 의의**: 오타·누락·형식 불일치를 값싼 비용으로 발견한다.
- **프로젝트의 필요성**: 페이지 수가 늘어날수록 사람이 기억할 수 없는 계약을 자동화한다.

### CI

- **뜻**: 변경이 들어올 때 자동으로 검사·빌드하는 지속적 통합
- **일반적인 용도와 의의**: 여러 변경이 결합될 때 생기는 문제를 빠르게 찾는다.
- **프로젝트의 필요성**: 문서, 레지스트리, 사이트, 배포가 함께 맞는지 공동 기준으로 확인한다.

### Sanitizer

- **뜻**: 위험한 HTML과 URL을 제거해 안전한 출력만 남기는 처리
- **일반적인 용도와 의의**: 외부 입력이 실행 코드가 되는 것을 막는다.
- **프로젝트의 필요성**: Markdown을 공개 HTML로 바꾸는 경계에서 독자와 사이트를 보호한다.

### Knowledge graph와 community

- **뜻**: 문서를 점과 관계로 표현한 그래프, community는 서로 조밀하게 연결된 주제 묶음이다.
- **일반적인 용도와 의의**: 키워드 목록을 넘어 지식의 구조와 탐색 경로를 보여 준다.
- **프로젝트의 필요성**: 인물·개념·소스·분석이 어떤 질문을 공유하는지 시각적으로 살핀다.
- **주의**: 그래프의 연결이 역사적 인과를 자동으로 증명하지는 않는다. 관계의 의미는 문서와 evidence를 함께 읽어 판단한다.

## 12. 안전한 확장 방법

### 새 concept 추가

1. 기존 문서에 이미 같은 개념이 있는지 검색한다.
2. 파일을 적절한 폴더에 만들고 유일한 <code>id</code>를 정한다.
3. H1, 학습 안내, 단계별 H2, 출처, 관련 항목을 작성한다.
4. 실제로 사용한 raw와 evidence만 등록한다.
5. 허용 태그와 링크를 확인한다.
6. index와 overview를 동기화하고 lint·테스트·빌드를 실행한다.

개념을 추가하는 목적은 명사를 하나 더 만드는 것이 아니다. 독자가 기존 문서의 설명을 반복하지 않고 다음 질문으로 이동할 수 있을 때만 새 페이지를 만든다.

### evidence 변경

locator를 고치거나 새 evidence를 추가하면 어떤 주장 범위가 바뀌었는지 살핀다. 필요한 경우 <code>evidence-scope-baseline.yml</code>에 해당 범위와 변경 사유를 남긴다. 출처 ID만 추가하고 본문이 실제로 무엇을 주장하는지 확인하지 않는 방식은 피한다.

### schema 변경

스키마를 바꾸는 일은 필드 하나를 고치는 작업이 아니다.

1. <code>page.schema.json</code>과 관련 레지스트리 스키마를 함께 수정한다.
2. 기존 문서를 의미를 잃지 않게 마이그레이션한다.
3. lint, 회귀 테스트, 사이트 빌드, 산출물 검사를 보강한다.
4. README, AGENTS, 운영 문서와 로그를 갱신한다.
5. canonical URL이나 검색·그래프 계약에 영향을 주는지 확인한다.

스키마 변경은 문서 작성자의 편의를 위한 선택이 아니라, 전체 지식베이스의 공용 인터페이스를 바꾸는 일이다. 따라서 변경 범위와 호환성 검토가 필요하다.

### raw는 수정하지 않는다

raw에 오류가 있으면 raw를 덮어쓰지 않고, 위키 본문에서 원문 상태와 검증 정정을 설명한다. 정말 다른 수집 자료라면 새 artifact로 등록하고 기존 자료와 역할을 구분한다.

## 13. 자주 묻는 질문

### 왜 모든 링크를 양방향으로 만들지 않나?

링크는 독자가 다음 질문으로 이동하도록 큐레이션한 방향성 관계다. 모든 링크를 자동으로 되돌리면 의미 없는 연결이 늘어난다. 반대 방향 탐색은 사이트의 역링크로 제공한다.

### 왜 raw와 evidence를 따로 두나?

raw는 어떤 파일을 보존했는지 말하고, evidence는 현재 주장에 어떤 문헌의 어느 위치가 관계되는지 말한다. 파일의 존재와 주장 검증은 서로 다른 질문이다.

### verified인데 해석이 포함될 수 있나?

verified는 핵심 사실이 확인됐다는 뜻이지, 글 전체가 해석이 없다는 뜻은 아니다. 여러 자료를 비교한 해석은 <code>content_mode: synthesis</code>와 <code>evidence_coverage: partial</code>처럼 별도로 표현한다.

### 왜 lint를 빌드보다 먼저 실행하나?

사이트가 만들어졌다는 사실은 내용이 올바르다는 뜻이 아니다. 잘못된 ID, 빠진 근거, 깨진 raw 해시를 먼저 막아야 잘못된 지식을 예쁜 화면으로 배포하지 않는다.

### 기술의 필연성은 무엇을 뜻하나?

문제의 요구로부터 반드시 필요한 원리와, 가능한 여러 구현 중 연구자가 고른 설계를 구분하는 말이다. 이 구분이 있어야 후대의 성공을 과거 기술의 유일한 결과처럼 과장하지 않는다.

### 어디서 시작하면 좋은가?

<code>README.md</code>로 실행 명령을 확인한 뒤, 이 문서 1–5장과 관심 있는 concept 또는 source 문서 한 편을 읽는다. 이해가 막힌 용어는 관련 항목으로 이동하되, 링크가 현재 문서의 정의를 대신한다고 생각하지 않는다.

## 14. 핵심 요약

- <code>raw/</code>는 수집 당시 상태를 보존하고, <code>wiki/</code>는 검증·편집된 공개 지식이다.
- frontmatter와 JSON Schema는 수백 개 문서가 같은 약속을 지키게 한다.
- evidence와 locator는 “출처가 있다”를 “어디서 다시 확인할 수 있다”로 바꾼다.
- 학습 구조는 배경, 최소 예, 원리, 기술 근거, 한계, 다음 질문의 순서를 따른다.
- 정적 사이트 생성기는 검증된 Markdown을 검색·그래프·HTML로 재현 가능하게 변환한다.
- lint, 테스트, CI, 브라우저 검사는 지식의 형식·안전성·사용자 경험을 공개 전에 확인한다.
- Git과 GitHub Pages는 변경 이력과 공개 배포를 연결한다.
- 이 프로젝트의 성공 기준은 페이지 수가 아니라, 독자가 근거를 따라가며 기술의 일반적 용도와 역사적 의미를 이해하고 다음 질문으로 이동할 수 있는가이다.
