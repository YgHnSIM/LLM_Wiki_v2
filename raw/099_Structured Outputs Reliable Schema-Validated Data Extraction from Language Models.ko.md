# 구조화된 출력: 언어 모델에서 스키마로 검증되는 신뢰할 수 있는 데이터 추출

원본 출처: https://mbrenndoerfer.com/writing/structured-outputs-schema-validated-data-extraction-language-models

---



2024년 언어 모델에 도입된 구조화된 출력을 종합적으로 안내한다. 구조화된 출력이 신뢰할 수 있는 데이터 추출을 가능하게 하고, 취약한 텍스트 파싱을 없애며, 언어 모델을 프로덕션 환경에 적합하게 만드는 방식을 알아본다. 스키마 명세, 형식 제약, 검증 보장, 실제 응용, 한계, AI 애플리케이션 개발에 미친 변혁적 영향을 이해한다.

## 2024년: 구조화된 출력

2024년 언어 모델에 [구조화된 출력](/writing/constrained-decoding-structured-llm-output) 모드가 도입된 것은 개발자가 대규모 언어 모델에서 구조화된 데이터를 신뢰성 있게 추출하는 방식을 근본적으로 바꿨다. 프로덕션 애플리케이션을 제약해 온 신뢰하기 어려운 텍스트 파싱에서 벗어날 수 있게 됐기 때문이다. 2023년의 [함수 호출](/writing/function-calling-tool-use-practical-ai-agents)은 외부 함수를 호출할 때 모델이 구조화된 출력을 생성하게 했지만, 모델 응답에서 임의의 구조화된 정보를 추출하는 더 넓은 과제는 여전히 큰 장벽이었다. 애플리케이션 개발자는 개체를 추출하고, 사용자 의도를 파악하고, 콘텐츠를 분류하며, 자연어를 프로그램에서 사용할 수 있는 형식으로 바꿔야 했다. 그러나 언어 모델은 일관되지 않은 텍스트를 출력했기 때문에 복잡한 파싱 로직이 필요했다. 2024년에 개발된 전용 구조화 출력 기능은 이 근본적 한계를 다루면서, 모델이 JSON·XML 또는 그 밖의 스키마로 검증되는 구조처럼 지정된 형식의 출력을 생성하도록 제약할 수 있게 했다.

OpenAI가 2023년 말에 도입하고 2024년 내내 개선한 [JSON 모드](/writing/constrained-decoding-structured-llm-output), 다른 제공자의 유사 기능, [LangChain](/writing/building-intelligent-agents-langchain-langgraph-part-1-core-concepts)의 Pydantic 구조화 출력은 언어 모델 역량의 중요한 진화를 나타냈다. 이 기능을 사용하면 개발자는 특정 스키마를 따르는 출력을 요청할 수 있고, 출력이 유효한 JSON이거나 제공된 스키마와 일치한다는 보장을 받을 수 있었다. 이 발전은 API 통합과 데이터 파이프라인부터 에이전트 시스템과 자동화 워크플로까지, 신뢰할 수 있는 구조화 데이터 추출이 필요한 프로덕션 애플리케이션을 개발자가 구축하던 중요한 시점에 등장했다.

구조화된 출력은 더 많은 애플리케이션에서 언어 모델을 진정으로 프로덕션에 사용할 수 있게 했다는 점에서도 의미가 컸다. 모델은 품질 높은 텍스트를 생성할 수 있었지만, 형식의 불일치와 자연어 출력을 파싱해야 한다는 요구는 실제 애플리케이션을 만드는 개발자에게 상당한 마찰을 일으켰다. 구조화된 출력은 이 마찰을 크게 줄여, 예측 가능하고 파싱 가능한 데이터 형식을 요구하는 소프트웨어 시스템에 언어 모델을 신뢰성 있게 통합할 수 있게 했다. 이 발전은 [함수 호출](/writing/function-calling-tool-use-practical-ai-agents)을 보완하면서 도구 사용을 넘어서는 구조화 데이터 추출의 일반적 문제를 다뤘다.

AI 산업이 실험적 애플리케이션에서 프로덕션 배포로 이동하던 시점이라는 점에서도 구조화된 출력은 특히 중요했다. 개발자는 언어 모델이 더 큰 시스템 안의 구성 요소로 작동하기를 원했고, 그런 통합·테스트·유지보수에는 신뢰할 수 있는 데이터 형식이 필수였다. 구조화된 출력을 보장할 수 있게 되면서 언어 모델은 이러한 프로덕션 환경에 적합해졌고, 신뢰할 수 있는 구조화 데이터 추출에 의존하는 새로운 부류의 애플리케이션이 가능해졌다.

## 문제

구조화된 출력이 등장하기 전, 개발자는 언어 모델 응답에서 구조화된 정보를 추출할 때 근본적인 어려움에 부딪혔다. 모델이 생성한 자연어 텍스트에는 원하는 정보가 들어 있을 수 있었지만 응답마다 형식·표현·구조가 달랐다. 모델은 한 응답에서는 “사용자의 이메일은 [john@example.com](mailto:john@example.com)입니다”라고 하고, 다른 응답에서는 “이메일: [john@example.com](mailto:john@example.com)”이라고 하며, 또 다른 응답에서는 “자세한 내용은 [john@example.com](mailto:john@example.com)으로 문의하세요”라고 할 수 있었다. 사람은 어떤 형식에서도 이메일 주소를 쉽게 추출할 수 있지만 프로그램에는 일관되고 예측 가능한, 신뢰성 있게 파싱할 수 있는 형식이 필요했다.

모델 출력의 변동성은 개발자에게 몇 가지 실질적인 문제를 만들었다. 첫째, 자연어에서 구조화된 데이터를 추출하려면 다양한 형식을 처리할 수 있는 복잡한 [정규 표현식](/writing/regular-expressions-pattern-matching-nlp-python)이나 자연어 처리 로직을 작성해야 했다. 이 파싱 로직은 취약해서 모델의 출력 형식이 조금만 달라져도 실패하기 쉬웠다. 표현이나 문장 부호의 작은 변화가 파서를 망가뜨리고 애플리케이션 실패를 일으킬 수 있었다. 개발자는 모델이 정보를 표현할 수 있는 여러 방식에 대응하기 위해 광범위한 [오류 처리](/writing/plan-and-execute-ai-agents) 코드를 작성해야 했다.

둘째, 출력 형식에 관한 보장이 없으면 모델 응답을 검증하거나 신뢰할 수 있는 API를 제공하기 어려웠다. 애플리케이션이 사용자에게 구조화된 데이터를 반환하겠다고 약속하더라도 언어 모델이 예상 형식의 출력을 만들 것이라고 보장할 수 없었다. 이 때문에 중요한 기능을 모델 출력에 의존하는 서비스를 구축하는 일에는 위험이 따랐다. 애플리케이션은 대체 로직과 수동 검토 단계를 포함해야 했고, 그 결과 복잡성이 커지고 자동화 가능성은 줄었다.

셋째, 출력 형식이 일관되지 않으면 여러 작업을 안정적으로 연결해 실행하기 어려웠다. 워크플로의 한 단계가 다음 단계를 위해 파싱해야 하는 비구조화 텍스트를 생성할 경우, 파싱 실패가 전체 워크플로를 중단시킬 수 있었다. 개발자는 광범위한 오류 처리와 재시도 로직을 만들어야 했고 워크플로는 복잡하고 취약해졌다. 신뢰할 수 있는 구조화된 출력의 부재는 언어 모델이 자동화 시스템의 안정적인 구성 요소로 쓰이는 것을 막았다.

넷째, 특정 데이터 스키마나 검증이 필요한 애플리케이션에서는 구조화된 출력을 보장하지 못한다는 점이 큰 문제였다. 애플리케이션에 특정 JSON Schema, XML 형식 또는 데이터베이스 스키마와 일치하는 데이터가 필요해도, 언어 모델이 검증을 통과하는 출력을 만들 것이라고 기대할 수 없었다. 애플리케이션은 비구조화 텍스트를 필요한 형식으로 변환하려는 후처리 단계를 포함해야 했고 성공률은 일정하지 않았다.

이 문제는 단순한 데이터 추출을 넘어 더 복잡한 사용 사례로 이어졌다. 여러 개체를 추출하거나, 콘텐츠를 범주로 분류하거나, 사용자 의도를 파악하거나, 특정 스키마에 따라 정보를 구조화해야 하는 애플리케이션은 모두 같은 근본 문제에 직면했다. 언어 모델은 구조화된 데이터가 아니라 텍스트를 생성했다. 개발자는 애플리케이션마다 맞춤형 파싱 로직을 만들어야 했고, 이는 개발 시간을 늘리고 잠재적인 실패 지점을 추가했다.

이전에 사용한 구조화 데이터 추출 접근법에도 한계가 있었다. 일부 개발자는 모델에 “데이터를 JSON으로 반환하라”고 요청하거나 원하는 형식의 예를 제공하는 등 특정 형식을 요구하는 프롬프트 엔지니어링을 사용했다. 이런 기법은 일관성을 높일 수 있었지만 보장을 제공하지는 않았다. 모델은 여전히 요청한 형식을 벗어나거나, 유효하지 않은 JSON을 생성하거나, 파서를 망가뜨리는 추가 텍스트를 포함할 수 있었다. 다른 접근법은 후처리로 모델 출력을 파싱했지만, 이 역시 취약했고 자연어 생성의 모든 변동성을 처리할 수 없었다.

2023년에 개발된 [함수 호출](/writing/function-calling-tool-use-practical-ai-agents)은 함수 호출에 한정된 구조화 출력을 다뤘지만, 모델 응답에서 구조화된 데이터를 추출하는 더 넓은 문제는 남아 있었다. 함수 호출 이외의 목적으로 구조화된 데이터가 필요한 애플리케이션은 여전히 신뢰하기 어려운 텍스트 파싱에 의존해야 했다. 개발자가 언어 모델로 더 정교한 애플리케이션을 만들면서 구조화된 출력에 관한 더 일반적인 해법의 필요성이 점점 분명해졌다.

## 해결책

[구조화된 출력](/writing/constrained-decoding-structured-llm-output) 모드는 개발자가 언어 모델을 특정 형식의 출력만 생성하도록 제약하고, 그 출력이 유효하며 스키마를 따른다는 보장을 제공함으로써 해법을 제시했다. 이 해법에는 스키마 명세, 형식 제약, 검증 보장, 기존 개발 워크플로와의 통합이라는 몇 가지 핵심 구성 요소가 있었다.

구조화된 출력의 핵심 메커니즘은 언어 모델의 추론 과정을 확장해 형식 제약을 강제하는 방식이었다. 개발자가 JSON Schema, Pydantic 모델, XML DTD 같은 원하는 출력 스키마를 지정하면 모델은 생성 중에 그 스키마와 일치하는 출력만 만들도록 제약된다. 이 제약은 토큰 수준에서 강제되어 모델이 유효하지 않은 형식을 생성하지 못하게 했다. 모델은 계속 언어 이해 능력으로 정보를 추출하고 구조화하지만, 지정된 형식의 제약 안에서 이를 수행한다.

OpenAI의 JSON 모드 구현을 사용하면 개발자는 모델이 유효한 JSON 출력을 생성하도록 요청할 수 있었다. 모델은 JSON 문법 규칙을 따르는 응답을 생성해 표준 JSON 파서가 신뢰성 있게 처리할 수 있는 JSON을 만들었다. [JSON 모드](/writing/constrained-decoding-structured-llm-output)는 특정 스키마를 강제하지는 않았지만 유효한 JSON 문법을 보장했고, 이는 비구조화 텍스트보다 크게 개선된 점이었다. 개발자는 표준 검증 라이브러리를 사용해 그 JSON 구조가 예상 스키마와 일치하는지 검증할 수 있었다.

[LangChain](/writing/building-intelligent-agents-langchain-langgraph-part-1-core-concepts)의 Pydantic 구조화 출력처럼 더 정교한 구현에서는 개발자가 Pydantic 모델로 정확한 스키마를 지정할 수 있었다. 모델은 필드 유형, 제약, 중첩 구조를 포함해 Pydantic 모델의 구조와 일치하는 출력만 생성하도록 제약된다. 이는 형식 보장과 스키마 검증을 한 단계에서 함께 제공해 출력이 예상 데이터 구조와 정확히 일치하도록 했다. 시스템은 출력을 스키마에 따라 검증하고 검증 오류를 적절히 처리할 수 있었다.

기술 구현에는 몇 가지 구성 요소가 관여했다. 첫째, 스키마를 모델의 생성 과정에서 강제할 수 있는 제약으로 변환했다. JSON 모드에서는 생성되는 토큰이 JSON 문법 규칙에 맞도록 보장하는 것을 뜻했다. 스키마 검증 출력에서는 제약이 더 정교해져 생성된 값이 필드 유형과 제약을 따르도록 했다. 둘째, 모델의 어휘와 생성 과정을 조정해 유효한 형식 구조를 유지하는 토큰을 선호하게 하면서도, 모델이 언어 이해를 사용해 정보를 적절히 추출하고 구조화할 수 있게 했다.

시스템에는 모델이 의도한 출력이 지정된 형식에 자연스럽게 맞지 않을 때를 처리하는 메커니즘도 포함됐다. 일부 구현에서 모델은 스키마와 일치하는 유효한 출력을 생성할 수 없음을 알릴 수 있어 애플리케이션이 예외 상황을 적절히 처리하게 했다. 검증 로직은 형식 오류를 포착하고 피드백을 제공할 수 있었지만, 목표는 유효하지 않은 출력이 생성된 뒤 잡아내는 것이 아니라 생성 시점에 막는 데 있었다.

기존 개발 워크플로와의 통합은 구조화된 출력의 핵심 요소였다. 이 해법은 개발자가 API 검증과 데이터 모델링에 이미 사용하던 JSON Schema 같은 표준 스키마 언어와 함께 작동했다. 또한 많은 개발자가 데이터 검증에 사용하던 Python의 Pydantic 같은 인기 프레임워크와도 통합됐다. 개발자가 새로운 도구를 배우거나 기존 개발 방식을 크게 바꾸지 않고 구조화된 출력을 사용할 수 있게 한 것이다.

[구조화된 출력](/writing/constrained-decoding-structured-llm-output) 접근법은 단순한 데이터 추출을 넘어 여러 사용 사례를 지원했다. 모델은 복잡한 중첩 구조, 객체 배열, 선택적 필드, 스키마 명세에 따른 조건부 구조를 생성할 수 있었다. 이런 유연성 덕분에 구조화된 출력은 단순한 [개체 추출](/writing/named-entity-recognition-ner-tutorial)부터 복잡한 데이터 변환 작업까지 광범위한 애플리케이션을 처리할 수 있었다. 모델은 언어 이해 능력으로 자연어 입력을 구조화된 스키마에 지능적으로 대응시킬 수 있었다.

[오류 처리](/writing/plan-and-execute-ai-agents)와 검증은 구조화 출력 시스템에 내장됐다. 모델이 형식 제약을 위반하는 출력을 생성하려 하면 시스템은 이 오류를 포착해 생성을 재시도하거나 구조화된 오류 응답을 반환할 수 있었다. 이 방식은 파싱이 실패할 때까지 형식 오류를 알아차리지 못할 수 있는 후처리보다 구조화된 출력을 더 신뢰성 있게 만들었다. 애플리케이션은 예기치 않은 파싱 실패를 처리하는 대신 검증 오류를 프로그램 방식으로 처리할 수 있었다.

## 응용과 영향

구조화된 출력은 비구조화 텍스트 출력으로는 구축하기 어렵거나 실용적이지 않았던 광범위한 애플리케이션을 가능하게 했다. 즉각적인 응용 분야 중 하나는 [API 통합](/writing/using-a-language-model-in-code)과 데이터 파이프라인 구축이었다. 이제 언어 모델은 자연어 입력에서 구조화된 데이터를 추출해 대화형 텍스트나 비구조화 문서를 API와 데이터베이스가 기대하는 형식으로 변환하는 지능형 파서 역할을 할 수 있었다. 광범위한 맞춤형 파싱 로직 없이 기존 시스템에 자연어 인터페이스를 제공할 수 있게 된 것이다.

[개체 추출](/writing/named-entity-recognition-ner-tutorial) 애플리케이션도 구조화된 출력으로 달라졌다. 복잡한 개체명 인식 파이프라인을 구축하거나 취약한 텍스트 파싱에 의존하는 대신, 개발자는 [구조화된 출력](/writing/constrained-decoding-structured-llm-output) 스키마와 언어 모델을 사용해 개체를 신뢰성 있게 추출할 수 있었다. 모델은 텍스트에서 사람 이름, 조직, 장소, 날짜와 그 밖의 개체를 추출해 애플리케이션이 바로 사용할 수 있는 구조화된 형식으로 반환할 수 있었다. 이 방식은 맞춤형 모델을 훈련해야 하는 전통적 접근법보다 개체 추출을 더 쉽게 이용하고 유연하게 적용할 수 있게 했다.

콘텐츠 분류와 태깅 애플리케이션도 상당한 이점을 얻었다. 모델은 텍스트를 미리 정한 범주로 분류하고 관련 태그나 키워드를 추출하며, 분류 결과를 스키마에 따라 구조화할 수 있었다. 이는 자동 [콘텐츠 모더레이션](/writing/content-safety-and-moderation-ai-agents), 문서 라우팅, 구조화된 출력을 사용하는 감성 분석과 그 밖의 많은 분류 작업을 가능하게 했다. 구조화된 형식 덕분에 분류 결과를 후속 시스템과 워크플로에 쉽게 통합할 수 있었다.

대화형 인터페이스의 의도 파악은 구조화된 출력으로 훨씬 더 신뢰성 있게 됐다. 자연어로 표현한 사용자 요청을 매개변수와 함께 구조화된 의도로 파싱할 수 있어 애플리케이션은 요청을 적절히 전달하고 동작 매개변수를 신뢰성 있게 추출할 수 있었다. 이는 사용자 의도를 이해해 프로그램 동작으로 변환해야 하는 챗봇, 음성 비서, 명령 인터페이스를 구축할 때 특히 유용했다. 구조화된 형식은 애플리케이션 로직이 의도 파악 결과를 신뢰성 있게 처리하도록 보장했다.

데이터 변환과 [정규화](/writing/normalization-feature-scaling-min-max-machine-learning-guide) 애플리케이션은 구조화된 출력을 활용해 비구조화 정보를 표준 형식으로 변환했다. 모델은 자연어 설명에서 날짜, 주소, 전화번호와 그 밖의 구조화 데이터를 파싱하면서 형식을 정규화하고 구성 요소를 신뢰성 있게 추출할 수 있었다. 이를 통해 언어 이해를 사용해 형식 변동을 지능적으로 처리하는 자동 [데이터 정리](/writing/data-quality-outliers-measurement-error-missing-data)·정규화 파이프라인을 만들 수 있었다.

에이전트 시스템과의 통합은 특히 중요한 응용 분야였다. 에이전트 프레임워크는 구조화된 출력을 사용해 에이전트 결정, 상태 갱신, 중간 결과가 예측 가능한 형식을 따르게 할 수 있었다. 개발자는 자연어 에이전트 출력을 파싱하는 대신 구조화된 상태와 의사결정 로그를 살펴볼 수 있어 에이전트 시스템의 신뢰성과 디버깅 가능성이 높아졌다. 구조화된 출력은 [다중 에이전트](/writing/agents-working-together-multi-agent-systems-collaboration) 워크플로에서 다른 시스템이나 에이전트가 신뢰성 있게 소비할 수 있는 형식으로 결과를 생성하게 했다.

양식 채우기와 데이터 입력 자동화도 중요한 응용 영역이었다. 언어 모델은 자연어 설명이나 비구조화 문서에서 정보를 추출해 양식에 구조화된 데이터를 채울 수 있었다. 송장, 계약서, 신청서와 그 밖의 문서에서 구조화된 정보를 뽑아야 하는 처리를 자동화할 수 있게 된 것이다. [구조화된 출력](/writing/constrained-decoding-structured-llm-output) 형식은 추출된 데이터가 양식 스키마와 정확히 일치하도록 보장했다.

구조화된 출력은 프로덕션 소프트웨어 개발에 언어 모델을 더 적합하게 만들었다. 이제 개발자는 언어 모델을 전통적인 소프트웨어 라이브러리처럼 신뢰할 수 있고 검증된 출력을 내는 구성 요소로 다룰 수 있었다. 따라서 출력이 예상 형식을 따른다는 확신을 가지고 언어 모델을 프로덕션 시스템에 통합할 수 있었다. 오류가 발생하기 쉬운 파싱 로직의 필요가 줄어 애플리케이션의 유지보수성과 신뢰성도 높아졌다.

구조화된 출력은 신뢰할 수 있는 데이터 추출에 의존하는 새로운 유형의 AI 애플리케이션 개발에도 영향을 미쳤다. 검색 엔진은 구조화된 출력을 사용해 웹 페이지에서 정보를 추출하고 구조화할 수 있었다. 전자상거래 애플리케이션은 설명에서 제품 세부 정보를 추출할 수 있었다. 연구 도구는 학술 논문의 정보를 구조화할 수 있었다. 구조화된 출력의 [신뢰성](/writing/monitoring-reliability-ai-agents) 덕분에 이런 애플리케이션은 데이터 처리 능력을 신뢰하면서 구축할 수 있었다.

구조화된 출력의 발전은 [언어 모델 API](/writing/using-a-language-model-in-code) 설계와 [표준화](/writing/standardization-normalizing-features-fair-comparison-machine-learning-math-formulas-python-scikit-learn)에도 영향을 미쳤다. 스키마를 명시하고 검증된 출력을 받는 패턴은 현대 언어 모델 API의 표준 기능이 됐고, 여러 제공자가 [구조화된 출력](/writing/constrained-decoding-structured-llm-output) 기능을 제공했다. 구조화 출력 인터페이스가 플랫폼 전반에서 일관되면서 개발자는 여러 언어 모델 제공자와 함께 작동하는 이식성 높은 애플리케이션을 더 쉽게 구축할 수 있었다.

## 한계

구조화된 출력에는 상당한 이점이 있지만, 응용 범위를 제한하고 향후 발전이 필요한 영역을 보여 주는 몇 가지 중요한 한계도 있었다. 한 가지 근본적 한계는 [구조화된 출력](/writing/constrained-decoding-structured-llm-output) 제약 때문에 미리 정의한 스키마에 깔끔하게 들어맞지 않는 미묘하거나 복잡한 정보를 모델이 표현하는 능력이 줄어들 수 있다는 점이었다. 스키마를 따라야 하므로 단순화가 강제되거나 비구조화 텍스트라면 가치 있었을 세부 사항이 빠질 수 있었다. 매우 유연하거나 창의적인 출력이 필요한 애플리케이션에는 구조화된 출력이 지나치게 제약적일 수 있었다.

구조화된 출력의 품질은 모델에 제공하는 스키마 명세의 품질에 크게 의존했다. 스키마가 지나치게 엄격하면 모델은 자연어를 요구한 구조에 대응시키기 어려울 수 있었다. 스키마가 지나치게 느슨하면 출력의 유용성이 떨어질 수 있었다. 개발자는 효과적인 구조화 출력 명세를 만들기 위해 스키마 설계와 데이터 모델링 전문성을 갖춰야 했고, 이는 개발 과정의 복잡성을 더했다.

구조화된 출력을 사용해도 검증과 [오류 처리](/writing/plan-and-execute-ai-agents)는 여전히 중요했다. 형식 제약은 파싱 오류 가능성을 줄였지만 모델은 스키마에 따르면 기술적으로 유효하면서도 의미상 틀리거나 불완전한 출력을 생성할 수 있었다. 애플리케이션에는 구조화된 출력이 형식 요구사항만이 아니라 예상 정보와 비즈니스 규칙도 충족하는지 확인하는 검증 로직이 여전히 필요했다.

[구조화된 출력](/writing/constrained-decoding-structured-llm-output) 제약을 강제하는 계산 오버헤드는 성능과 비용에 영향을 줄 수 있었다. 구조화된 출력을 생성하려면 자유 형식 텍스트보다 더 많은 토큰이나 더 복잡한 생성 과정이 필요할 수 있어 지연 시간과 [API 비용](/writing/managing-reducing-ai-agent-costs-optimization-strategies)이 늘어날 가능성이 있었다. 애플리케이션마다 이 오버헤드와 구조화된 출력의 이점을 저울질해야 했다. 일부 단순한 사용 사례에서는 추가 복잡성과 비용이 정당화되지 않을 수 있었다.

구조화된 출력은 예외 상황과 모호한 입력을 처리하는 데에도 한계가 있었다. 입력 텍스트가 불명확하거나 여러 방식으로 해석될 수 있을 때 구조화된 출력은 모호성을 줄이는 선택을 해야 할 수 있었고, 그 과정에서 미묘한 의미를 잃을 가능성이 있었다. 여러 해석이 모두 타당한 상황에서도 구조화된 형식은 하나의 해석을 강제할 수 있었다. 애플리케이션은 구조화된 출력이 정보를 원하지 않는 방식으로 단순화하거나 모호성을 해소하는 경우를 처리해야 했다.

기존 시스템에 구조화된 출력을 통합할 때 서로 다른 스키마 형식 사이의 변환이나 매핑이 필요하기도 했다. JSON Schema를 사용하는 애플리케이션이 XML, Pydantic 또는 다른 스키마 형식을 쓰는 시스템과 함께 작동해야 할 수 있었다. 변환은 흔히 간단했지만 통합 워크플로에 복잡성과 잠재적인 실패 지점을 추가했다.

구조화된 출력은 개발자가 원하는 출력 스키마를 미리 명확하게 정의할 수 있을 때 가장 잘 작동한다는 한계도 있었다. 탐색적 애플리케이션이나 출력 구조를 사전에 알 수 없는 사용 사례에서는 스키마를 지정해야 한다는 요구가 장벽이 될 수 있었다. 출력 구조를 동적으로 발견하거나 조정해야 하는 애플리케이션에는 구조화된 출력이 비구조화 생성 방식보다 덜 적합했다.

자연어를 구조화된 스키마에 대응시키는 모델의 능력도 학습과 추론 역량의 제약을 받았다. 복잡하거나 새로운 스키마는 모델이 이해하고 정확하게 생성하기 어려울 수 있었다. 조건부 필드, 복잡한 검증 규칙, 도메인 특화 제약 같은 스키마 기능은 모델이 처리하기 어려울 수 있었다. 이 때문에 구조화된 출력과 함께 신뢰성 있게 사용할 수 있는 스키마의 정교함에는 한계가 있었다.

구조화된 출력은 언어 모델의 [신뢰성](/writing/monitoring-reliability-ai-agents)과 관련된 모든 문제를 해결하지도 않았다. 형식 일관성을 높였지만 구조화된 형식 안에서도 나타날 수 있는 환각, 사실 오류 또는 추론 오류는 다루지 않았다. 애플리케이션은 형식뿐 아니라 구조화된 출력의 내용과 정확성도 계속 검증해야 했다.

## 유산과 전망

구조화된 출력은 언어 모델을 프로덕션 소프트웨어 시스템에 통합하는 근본적인 패턴을 확립했고, 이 패턴은 현대 AI 애플리케이션 개발의 필수 요소가 됐다. 출력 형식을 보장하고 스키마에 따라 검증하는 능력은 언어 모델을 더 큰 시스템의 신뢰할 수 있는 구성 요소로 사용하기에 적합하게 만들었고, 개발자가 AI 기반 애플리케이션을 설계하고 배포하는 방식에 영향을 미쳤다. 이 패턴은 업계 전반에 채택돼 [구조화된 출력](/writing/constrained-decoding-structured-llm-output) 기능이 언어 모델 API와 프레임워크의 표준 기능으로 자리 잡았다.

구조화된 출력의 도입은 프로덕션 환경에 언어 모델을 배포하는 방식의 중요한 진화를 나타냈다. 모델은 예측하기 어려운 텍스트 생성기가 아니라, 적절한 제약을 받으면 검증된 구조화 데이터를 생성하는 구성 요소로 인식되기 시작했다. 이 변화는 API 통합과 데이터 파이프라인부터 에이전트 시스템과 자동화 워크플로까지, 신뢰할 수 있는 구조화 데이터 추출에 의존하는 새로운 부류의 애플리케이션을 가능하게 했다.

현대 AI 애플리케이션 프레임워크는 구조화 출력 패턴을 광범위하게 활용해 신뢰할 수 있는 데이터 추출과 변환의 기반 역량으로 삼는다. [LangChain](/writing/building-intelligent-agents-langchain-langgraph-part-1-core-concepts) 같은 프레임워크는 인기 스키마 언어와 검증 프레임워크를 통합한 구조화 출력 추상화를 제공해, 개발자가 프롬프트 엔지니어링이나 형식 명세의 깊은 전문 지식 없이도 구조화된 출력을 이용할 수 있게 한다. 이 패턴은 이제 프로덕션 AI 애플리케이션의 기본 요구사항으로 여겨질 만큼 근본적인 요소가 됐다.

구조화된 출력의 발전은 언어 모델의 역량과 학습에 관한 연구 방향에도 영향을 미쳤다. 연구자들은 형식 제약을 더 잘 강제하는 방법, 더 나은 스키마 이해, 더 정교한 검증 메커니즘을 탐구했다. 이 패턴은 [코드 생성](/writing/codex-ai-assisted-code-generation-transformation-software-development)·과학 데이터 추출·문서 처리 같은 영역에서 구조화된 출력을 만드는 멀티모달 모델과 특수 모델에 관한 연구에도 영향을 주었다.

앞으로도 구조화된 출력은 스키마 명세 언어의 개선, 더 나은 제약 강제 메커니즘, 더 정교한 검증 역량과 함께 계속 발전할 것이다. 이 패턴은 기존 시스템을 위한 자연어 인터페이스부터 자동 데이터 처리 파이프라인까지, 신뢰할 수 있는 구조화 데이터 추출에 의존하는 차세대 AI 애플리케이션을 가능하게 한다. 언어 모델의 역량과 프레임워크의 정교함이 커져도 구조화된 출력은 AI 애플리케이션을 프로덕션에 적합하고 신뢰할 수 있게 만드는 데 필수적인 요소로 남는다.

구조화된 출력의 유산은 AI 시스템의 [신뢰성](/writing/monitoring-reliability-ai-agents)과 검증을 바라보는 방식으로도 이어진다. 정확하고 완전한 구조화 출력을 보장하는 과제는 더 나은 검증 메커니즘, 스키마 설계 관행, AI 애플리케이션을 위한 [오류 처리](/writing/plan-and-execute-ai-agents) 전략에 관한 연구를 촉진했다. 이런 발전은 구조화된 출력뿐 아니라 신뢰할 수 있는 AI를 프로덕션에 배포하는 더 넓은 분야에도 영향을 미친다.

구조화된 출력은 언어 모델을 프로덕션 소프트웨어 개발에 실용적으로 사용할 수 있게 한 중요한 이정표다. 적절한 명세가 주어지면 모델을 제약해 신뢰할 수 있고 검증된 출력을 만들 수 있음을 보여 주었다. 이 발전은 새로운 부류의 애플리케이션을 열었고, 오늘날에도 개발자가 AI 기반 시스템을 구축하는 방식을 형성하는 패턴을 확립했다. AI 애플리케이션이 더 널리 퍼지고 중요한 시스템에 통합될수록 [구조화된 출력](/writing/constrained-decoding-structured-llm-output) 패턴은 진정으로 유용한 AI 애플리케이션을 가능하게 하는 신뢰할 수 있는 데이터 추출과 변환의 토대로 남는다.
