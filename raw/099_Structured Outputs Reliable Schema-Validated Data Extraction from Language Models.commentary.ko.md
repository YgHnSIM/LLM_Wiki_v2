# 구조화 출력의 스키마 보장과 의미 정확성 경계 해설

## 1. 한눈에 보기

- 핵심 주제: 언어 모델의 자유 형식 응답을 유효한 JSON 또는 지원되는 JSON Schema에 맞는 데이터로 제한하는 API 흐름
- 등장 배경: 2023년 함수 호출과 JSON mode가 형식 안정성을 높였지만 특정 스키마 준수까지 보장하지 못했고, 2024년 OpenAI가 `strict: true` Structured Outputs를 공개한 시기
- 가장 중요한 아이디어: **JSON 구문 유효성**, **스키마 준수**, **필드 값의 의미·사실 정확성**, **업무 규칙과 권한**은 서로 다른 보장이다.
- 이후 LLM/NLP에 남긴 영향: 취약한 자연어 파싱을 줄이고 API·데이터 파이프라인·에이전트 상태를 명시적 계약으로 연결했지만, 검증과 오류 처리를 없애지는 않았다.

> 이 문서는 `099_Structured Outputs Reliable Schema-Validated Data Extraction from Language Models.md`의 번역문을 이해하기 위한 해설입니다. 원문의 넓은 산업 평가를 그대로 반복하기보다 2023–2024년 공식 기능의 연표, 제약 디코딩이 보장하는 범위, 형식이 맞아도 내용이 틀릴 수 있는 경계를 정리합니다.

## 2. 핵심 요약

구조화 출력의 역사는 한 번의 발명보다 보장 범위가 단계적으로 넓어진 과정으로 읽어야 한다. OpenAI의 2023년 6월 Function Calling은 모델이 함수 이름과 JSON 인수를 제안하는 인터페이스를 제공했다. 같은 해 11월 JSON mode는 응답을 문법적으로 유효한 JSON 객체로 만드는 기능을 별도로 도입했지만, 원하는 필드·자료형·필수 조건을 갖춘 특정 스키마까지 자동으로 보장하지는 않았다. 2024년 8월 Structured Outputs는 호환 모델과 지원되는 JSON Schema에서 `strict: true`를 사용해 구조 일치를 강화했다.

OpenAI가 공개한 구현 설명에서 JSON Schema는 문맥자유문법(CFG)으로 변환되고, 생성 시점마다 현재 접두사 다음에 올 수 없는 토큰의 확률을 0으로 만드는 동적 제약이 적용된다. 이는 닫히지 않은 중괄호나 허용되지 않은 필드처럼 형식상 불가능한 경로를 차단한다. 그러나 허용된 문자열 자리에 틀린 사람 이름을 쓰거나, 존재하지 않는 계정 번호를 넣거나, 입력에 없는 사실을 채우는 것은 여전히 가능하다. 따라서 구조화 출력은 **출력 계약의 구조**를 강화하지 **내용의 진실성**을 자동 보증하지 않는다.

- 무엇을 다루는가: JSON mode, 엄격한 스키마 준수, Pydantic·Zod 같은 SDK 표현, 데이터 추출과 워크플로 통합
- 어떤 문제를 해결하려 했는가: 응답 표현이 조금만 달라져도 깨지는 정규식·문자열 파싱과 재시도 로직
- 어떤 방식이 새로웠는가: 프롬프트로 형식을 부탁하는 대신 생성 가능한 토큰 자체를 스키마 규칙으로 제한한 점
- 결과적으로 무엇을 바꾸었는가: 모델 출력 뒤의 파서 계약을 명시적으로 만들었지만 semantic validation·권한·실행·grounding은 별도 계층으로 남겼다.

## 3. 역사적 배경

초기 언어 모델 API에서 개발자는 “JSON으로 답하라”는 지시와 few-shot 예시를 사용했다. 잘 작동하는 경우도 많았지만 Markdown code fence, 설명 문장, 잘못 닫힌 괄호, 필드명 변형이 섞이면 파서가 깨졌다. JSON을 추출하는 정규식, 부분 복구, 재프롬프트는 응답 형식의 변동을 애플리케이션 코드가 떠안는 방식이었다. 이 장의 원 웹글은 2025년 9월 17일 공개된 회고적 설명이며, 장 제목의 2024년은 글의 발행 연도가 아니라 중심 사건의 연도다.

연표는 세 층으로 구분해야 한다.

- **2023년 6월 13일:** OpenAI Function Calling이 함수 설명과 JSON Schema 형태의 매개변수, 모델의 함수 이름·인수 제안을 공개했다. 모델이 실제 함수를 실행한 것이 아니라 애플리케이션이 파싱·검증·실행했다.
- **2023년 11월 6일:** DevDay 발표가 JSON mode를 공개했다. 문법적으로 유효한 JSON을 보장했지만 특정 스키마 일치는 보장하지 않았다.
- **2024년 8월 6일:** Structured Outputs가 `strict: true`와 지원되는 JSON Schema를 이용한 엄격한 구조 일치를 공개했다. 공식 발표의 복잡한 스키마 내부 평가에서는 `gpt-4-0613`이 40% 미만, `gpt-4o-2024-08-06` strict 조건이 100%로 보고됐다.

이 100%는 특정 schema-conformance 평가 결과다. 모든 값의 사실성, 모든 제공자, XML DTD, 임의의 검증 규칙, 외부 API의 성공률을 뜻하지 않는다. 원문이 JSON mode의 등장, 2024년 strict schema, LangChain의 Pydantic 표현을 하나의 동일한 제약 메커니즘처럼 묶는 대목은 구현 층위를 나눠 읽어야 한다.

## 4. 핵심 개념 해설

### 네 개의 보장 층

| 층 | 묻는 질문 | 대표 수단 | 남는 실패 |
| --- | --- | --- | --- |
| 구문 유효성 | 표준 JSON parser가 읽을 수 있는가? | JSON mode·parser | 필드 누락·잘못된 자료형 |
| 스키마 준수 | required·type·enum·중첩 구조를 만족하는가? | `strict: true`·JSON Schema·validator | 틀린 값·누락된 근거 |
| 의미 검증 | 입력과 현실에 맞는 값인가? | 업무 규칙·database lookup·cross-field check | 권한·외부 실행 실패 |
| 시스템 검증 | 허용된 주체가 안전하게 처리할 수 있는가? | 인증·인가·승인·transaction | 모델의 후속 설명 오류 |

예를 들어 `{ "currency": "USD", "amount": 1000000 }`은 스키마가 요구한 문자열과 숫자 자료형에 완벽히 맞을 수 있다. 그러나 사용자가 10달러를 요청했다면 의미상 틀린 값이다. 형식과 의미를 같은 “정확성”으로 부르면 실제 실패 위치를 찾을 수 없다.

### 제약 디코딩

자기회귀 모델은 각 단계에서 다음 토큰의 확률분포를 만든다. 제약 디코딩은 지금까지 생성한 접두사와 문법 상태를 바탕으로 허용되지 않은 토큰을 마스킹한 뒤 남은 후보에서 다음 토큰을 고른다.

$$
p'(t_i \mid t_{<i}, x) \propto p_\theta(t_i \mid t_{<i}, x)\,\mathbf{1}[t_i \in A(t_{<i}, G)],
$$

여기서 $G$는 스키마에서 만든 문법이고 $A$는 현재 상태에서 허용되는 토큰 집합이다. 이 식은 형식적으로 불가능한 토큰을 막지만, 허용된 후보 가운데 의미가 맞는 것을 자동으로 골라 주지는 않는다. OpenAI 발표는 `gpt-4o-2024-08-06`이 모델 학습만으로 복잡한 스키마 평가에서 93%를 기록했고 제약 디코딩을 결합해 100%에 도달했다고 설명했다. 두 수치 모두 내용 정확도가 아니라 해당 schema-conformance 평가다.

### Pydantic은 어느 층인가

Pydantic 모델은 Python에서 스키마를 표현하고 결과를 자료형으로 변환·검증하는 편리한 계층이다. Provider-native Structured Outputs를 사용하는 경우 SDK가 Pydantic 정의를 지원되는 JSON Schema로 바꾸고 API의 제약 디코딩을 이용할 수 있다. 반대로 프레임워크가 모델 응답을 받은 뒤 Pydantic으로 검증하고 재시도하는 경로도 있다. “Pydantic을 썼다”는 사실만으로 생성 중 토큰 수준 제약이 적용됐다고 단정할 수 없다.

## 5. 원문의 논리 구조

원문은 먼저 2024년 구조화 출력이 자연어 파싱에서 스키마 기반 통합으로의 전환이었다고 평가한다. 이어 같은 이메일을 여러 문장 형식으로 표현하는 예를 들어 사람이 읽을 수 있는 텍스트와 프로그램이 안정적으로 파싱할 수 있는 데이터의 차이를 보여 준다.

해결책 절은 스키마 명세, 생성 제약, 검증, 개발 프레임워크 통합을 하나의 흐름으로 설명한다. JSON mode는 구문 유효성, 더 엄격한 구조화 출력은 스키마 일치를 맡고, Pydantic 같은 도구가 애플리케이션의 자료형과 연결된다는 구조다.

응용 절은 API 통합, 개체 추출, 분류, 의도 파악, 정규화, 에이전트 상태, 양식 채우기를 열거한다. 마지막 두 절은 지나치게 엄격하거나 느슨한 스키마, 모호한 입력, 계산 비용, 사전 스키마가 어려운 탐색 작업, 의미 오류를 한계로 들고 구조화 출력이 프로덕션 AI의 기본 패턴으로 남았다고 평가한다.

논리의 강점은 개발 문제를 입력–생성–파싱–검증–후속 시스템이라는 전체 경로에서 본다는 점이다. 다만 모든 제공자·프레임워크·스키마 형식이 같은 생성 제약을 사용한다는 듯한 일반화와 “검증된 출력”을 내용까지 검증된 것으로 읽힐 수 있는 표현은 공식 구현 범위에 맞게 좁혀야 한다.

## 6. 왜 중요한가

구조화 출력은 모델 성능 수치보다 **소프트웨어 경계의 명시성**을 바꿨다는 점에서 중요하다. 이전에는 자연어 응답과 파서 사이의 암묵적 약속에 의존했지만, 이제 required field·enum·배열·중첩 객체를 기계 판독 가능한 계약으로 선언할 수 있다. 계약이 명시되면 versioning, fixture test, 관측 지표와 실패 분류도 구체화된다.

그러나 “파싱이 사라졌다”기보다 **취약한 임의 텍스트 파싱이 줄었다**고 말하는 편이 정확하다. JSON decoding, schema validation, semantic validation, business rule과 error path 처리는 여전히 남는다. Refusal이나 token limit로 정상 완료되지 않은 응답도 성공 데이터와 분리해야 한다.

데이터 추출에서는 precision·recall과 근거 위치가 스키마 통과율보다 중요할 수 있다. 모든 필드가 존재해도 원문에 없는 값을 채우면 extraction은 실패다. 따라서 nullable·`unknown`·근거 span·confidence가 필요한지 스키마 설계 단계에서 결정해야 모델이 모호함을 억지로 한 값에 압축하지 않는다.

## 7. 현대 LLM과의 연결

현대 API는 구조화 출력을 일반 응답 형식과 함수 호출 인수 양쪽에 적용한다. 두 경우 모두 스키마를 사용할 수 있지만 목적은 다르다. 일반 구조화 출력은 분류·추출·변환 결과를 애플리케이션 데이터로 돌려주고, 함수 호출은 어떤 외부 동작을 어떤 인수로 제안하는지 표현한다. 함수 호출 뒤에는 권한·부작용·재시도·도구 결과의 신뢰 경계가 추가된다.

에이전트 시스템에서는 계획 단계, 도구 선택, 상태 전이, 중간 관찰을 서로 다른 스키마로 나눌 수 있다. 이는 로그와 재현성을 개선하지만 스키마에 맞는 잘못된 계획도 가능하다. 모델이 만든 객체를 곧바로 실행하지 말고 schema 이후 semantic·authorization·execution 관문을 둬야 한다.

문맥자유문법과의 연결도 중요하다. OpenAI가 공개한 구현은 JSON Schema를 CFG로 바꿔 재귀적인 중첩 구조를 다룬다. 이 설명은 특정 제품 구현의 근거이지, 1950년대 형식언어 연구가 현대 Structured Outputs로 직접 이어진 단일 계보를 입증하지는 않는다. 공통점은 허용되는 문자열 집합을 문법으로 정의하고 파싱·생성 가능성을 계산한다는 데 있다.

## 8. 한계와 비판적 관점

- **지원되는 스키마 부분집합:** `strict: true`는 임의의 JSON Schema 기능 전체가 아니라 API가 지원하는 부분집합과 호환 모델에서 작동한다.
- **안전 거부:** 모델이 안전상 거부하면 스키마 객체 대신 별도의 `refusal` 경로를 반환할 수 있다. 거부를 잘못된 JSON으로 취급하지 말고 별도 상태로 다룬다.
- **불완전 종료:** 최대 출력 토큰이나 stop 조건으로 응답이 중단되면 정상 스키마 결과를 보장할 수 없다.
- **병렬 함수 호출:** 2024년 발표는 strict schema 준수가 필요할 때 parallel function calls와의 제한을 명시했다.
- **의미 오류:** Schema-valid output도 사실과 다르거나 입력의 중요한 정보를 빠뜨릴 수 있다.
- **첫 스키마 지연:** 새 스키마를 처음 사용할 때 문법 전처리와 캐시 때문에 추가 지연이 생길 수 있다.
- **프라이버시와 보존:** 외부 API에 스키마와 입력을 보내는 문제, 스키마 캐시 조건, 민감 필드 기록은 별도 검토가 필요하다.

원문의 “XML DTD도 같은 방식으로 제약된다”, “여러 제공자에 걸쳐 인터페이스가 일관돼 이식성이 확보됐다”, “프로덕션 준비가 됐다”는 넓은 평가는 이 자료만으로 일반화할 수 없다. OpenAI의 공식 발표가 직접 보장하는 것은 해당 API·모델·지원 schema와 정상 완료 경로의 구조 일치다. LangChain 같은 프레임워크는 provider-native 기능, tool calling, 사후 파싱·검증을 모두 추상화할 수 있으므로 실제 전략을 확인해야 한다.

계산 비용도 단순히 “더 많은 토큰을 쓴다”고 일반화하기 어렵다. 제약 디코딩에는 문법 전처리와 매 단계 마스킹 비용이 있지만 불필요한 설명 문장과 실패 재시도를 줄일 수도 있다. 실제 latency·token·retry·validation 비용은 같은 스키마와 같은 과제로 측정해야 한다.

## 9. 용어 정리

- **JSON mode:** 응답이 문법적으로 유효한 JSON 객체가 되도록 하는 모드. 특정 필드 구조까지 자동 보장하지 않는다.
- **Structured Outputs:** 지원되는 JSON Schema에 출력을 맞추도록 제약하는 API 기능을 가리키는 명칭. 제공자별 의미와 지원 범위를 확인해야 한다.
- **JSON Schema:** JSON 자료의 자료형, required field, enum, 배열과 객체 구조 등을 선언하는 스키마 언어다.
- **제약 디코딩(constrained decoding):** 생성 중 현재 문법 상태에서 허용되지 않은 토큰을 후보에서 제거하는 디코딩 방식이다.
- **문맥자유문법(CFG):** 허용되는 문자열 구조를 재귀적 생성 규칙으로 나타내는 형식 문법이다.
- **구문 유효성(syntactic validity):** parser가 입력을 문법적으로 읽을 수 있다는 뜻이다.
- **스키마 준수(schema conformity):** 출력의 필드·자료형·중첩 구조가 선언한 스키마와 맞는다는 뜻이다.
- **의미 검증(semantic validation):** 값이 입력·현실·업무 규칙과 맞는지 확인하는 별도 단계다.
- **Pydantic:** Python 자료형 모델과 검증을 제공하는 라이브러리다. 생성 중 제약과 사후 검증 중 어느 경로를 쓰는지 구분해야 한다.
- **Refusal:** 모델이 안전 정책 등의 이유로 요청한 구조화 결과 대신 거부 상태를 반환하는 경로다.

## 12. 짧은 결론

구조화 출력의 핵심 성취는 언어 모델의 응답과 소프트웨어 사이에 기계 판독 가능한 형식 계약을 둔 것이다. 2023년 함수 호출과 JSON mode를 거쳐 2024년 strict schema가 구조 일치의 보장 범위를 넓혔지만, 그 계약은 허용되는 **모양**을 제한한다. 올바른 **내용**, 충분한 **근거**, 허용된 **권한**, 안전한 **실행**은 여전히 애플리케이션이 별도로 검증해야 한다.

따라서 구조화 출력을 프로덕션 신뢰성의 완성으로 보지 않고, 구문→스키마→의미→권한→실행으로 이어지는 직렬 관문의 한 단계로 읽는 것이 가장 정확하다. 이 구분을 지킬 때 구조화 출력은 취약한 파싱을 줄이면서도 잘못된 확신을 늘리지 않는 실용적 인터페이스가 된다.
