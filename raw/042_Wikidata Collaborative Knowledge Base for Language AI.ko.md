# Wikidata: 언어 AI를 위한 협업형 지식 베이스

출처: https://mbrenndoerfer.com/writing/wikidata-collaborative-knowledge-base-language-ai

2012년 출범한 협업형 다언어 지식 베이스 Wikidata를 종합적으로 살펴본다. Wikidata가 구조화된 지식 표현을 어떻게 바꾸었고, 언어 모델의 grounding을 어떻게 지원했으며, 사실 기반 AI 시스템의 중요한 인프라가 되었는지를 설명한다.

## 2012년: Wikidata — 기계가 마침내 사실을 바로잡았을 때

2012년 10월 Wikimedia Foundation은 겉보기에는 지루해 보이는 또 하나의 데이터베이스를 출범시켰다. 데이터베이스는 1960년대부터 존재했고 Wikipedia도 인간 지식을 10년 넘게 정리하고 있었다. 또 다른 정보 모음이 무엇을 바꿀 수 있었을까?

원문은 Wikidata가 기계를 위해 지식을 조직하는 방식을 근본적으로 바꿨다고 평가한다. 2012년 인터넷에는 텍스트가 넘쳤지만 구조는 부족했다. 언어 AI는 단어 패턴을 찾는 데 능숙해지고 있었지만 단순한 사실 질문에도 안정적으로 답하기 어려웠다. “프랑스의 수도는 어디인가?”에 답하려면 수많은 웹 문서를 검색하고, 모호한 자연어를 분석하고, 정보를 추출하고, 출처의 신뢰성을 판단해야 했다.

통계 기계 번역과 신경망은 텍스트 패턴을 배울 수 있었지만 `Paris`가 `France` 근처에 자주 등장한다는 통계와 Paris가 France의 수도라는 명시적 사실은 달랐다. Wikidata는 Wikipedia의 공동 편집 모델을 구조 데이터에 적용해, 문장에서 정보를 매번 추출하는 대신 기계가 조회할 수 있는 관계로 사실을 저장하려 했다.

원문은 이를 “사실을 텍스트가 아니라 데이터로 저장한다”는 전환으로 요약한다. 이 구조는 이후 언어 AI가 외부 사실과 연결되는 기반이 되었다.

## 문제: 안다는 것과 이해한다는 것이 같지 않을 때

2012년의 컴퓨터가 Wikipedia 전체에 접근할 수 있어도 자연어 문장에서 답을 찾으려면 여러 단계를 거쳐야 했다.

1. 문장의 통사 구조를 분석한다.
2. `Paris`와 `France`가 개체임을 식별한다.
3. `capital`이 두 개체 사이의 관계임을 알아낸다.
4. 관계를 정확히 추출한다.
5. 정보의 출처와 신뢰성을 확인한다.

### 지식 표현 문제

Wikidata 이전에도 지식 베이스는 있었다. WordNet은 동의어·반의어·상하위어처럼 단어와 어휘 의미의 관계를 정리했지만 Paris가 France의 수도라는 개별 현실 사실을 중심에 두지는 않았다.

DBpedia는 Wikipedia infobox에서 구조 데이터를 추출했다. 원문은 언어판·문서별 infobox 형식 차이와 누락 때문에 추출이 불안정할 수 있었다고 설명한다.

### 다언어 문제

Paris에 관한 정보는 영어·프랑스어·독일어 등 여러 Wikipedia 언어판에 따로 존재했다. 공통 식별자가 없으면 응용 프로그램은 언어판별 표제를 별개 대상으로 취급하고 같은 개체를 다시 연결해야 한다. 언어판마다 인구 수치와 갱신 시점이 달라질 수도 있었다.

### 유지 관리 문제

Paris 인구처럼 여러 문서와 언어판에 반복되는 사실이 바뀌면 각 위치를 수동으로 갱신해야 했다. Paris 문서, France 문서, 유럽 수도 목록, 프랑스 도시 목록 등 수많은 위치에 같은 값이 나타날 수 있어 불일치가 생겼다.

### AI 정확성 문제

텍스트 패턴만으로 답하는 시스템은 그럴듯하지만 틀린 사실을 만들 수 있다. France와 함께 자주 등장하는 다른 도시를 수도라고 답하거나, 도시 인구와 광역권 인구를 혼동할 수 있다. 구조 지식은 이런 주장을 조회·검증할 외부 기준을 제공할 수 있다.

문서를 매번 처리하고 정보를 추출·검증하는 계산 비용도 컸다. 중앙의 구조 지식 베이스는 색인·캐시·직접 질의로 반복되는 사실 조회를 빠르게 만들 수 있었다. 분야는 구조화·질의 가능·다언어·협업 유지가 가능한 표현을 필요로 했다.

## 해법: 텍스트가 아니라 데이터로 저장한 사실

Wikidata는 자연어 문장 대신 구조 데이터로 사실을 저장했다. 원문은 다음과 같은 형식을 예로 든다.

```text
개체: Paris
속성: capital of
값: France
```

### 항목·속성·값

**항목**(item)은 사람·장소·개념·사건처럼 식별할 대상을 나타낸다. 항목에는 언어와 무관한 Q 식별자가 붙는다.

- Paris → Q90
- France → Q142
- Douglas Adams → Q42
- cat → Q146

**속성**(property)은 특성이나 관계를 나타내며 P 식별자를 가진다.

- capital → P36
- date of birth → P569
- population → P1082
- author → P50

**값**(value)은 날짜, 수, 문자열, 다른 항목 등 실제 데이터를 담는다.

### 사실과 triple

원문은 항목·속성·값을 주어–속성–목적어 triple로 설명하고 “Paris는 France의 수도다”를 `(Q90, P36, Q142)`로 제시한다. 같은 항목에 인구·면적·시장·설립 시점·국가·도시 유형 등 여러 속성을 연결하면 개체 관계망, 즉 지식 그래프가 만들어진다.

### triple이 중요한 이유

하나의 구조화된 명제는 독립적으로 확인·갱신·삭제할 수 있다. Paris 인구가 바뀌면 관련 값만 수정하고 다른 사실은 유지할 수 있다. 관계를 여러 단계 따라가면 다음처럼 복합 질문을 만들 수 있다.

```text
city → population → 1 million 초과
city → capital of → country
country → located in → Europe
```

원문은 구조 지식이 자연어의 동음이의성을 줄인다고 설명한다. `bank`라는 문자열 대신 금융기관 항목과 강둑 항목의 서로 다른 식별자를 사용하면 응용 프로그램이 대상을 명시적으로 구분할 수 있다.

### 함께 지식 만들기

Wikidata는 Wikipedia의 공개 협업 모델을 구조 데이터에 적용했다. 사용자는 새 항목·속성을 추가하고, 출처와 함께 값을 입력하며, 오류를 고치고, 바뀐 정보를 갱신하고, 다른 기여를 검토할 수 있었다. 소수 전문가만으로는 유지하기 어려운 규모를 공동체 기여로 확장한다는 접근이었다.

### 공동체 품질 관리

원문은 네 가지 장치를 강조한다.

- **출처 참조**: 명제에 근거 출처를 붙여 추적·검증할 수 있다.
- **한정자(qualifier)**: 직업의 시작·종료 시점처럼 값이 성립하는 문맥을 기록한다.
- **변경 이력**: 모든 편집을 기록해 검토·되돌리기가 가능하다.
- **공동체 합의**: 논쟁적 표현과 모델링 방식을 토론으로 조정한다.

### 언어 장벽 넘기

Q146이라는 항목은 언어와 무관하고, 그 항목에 여러 언어의 label·description·alias를 붙일 수 있다.

- 영어: cat
- 프랑스어: chat
- 독일어: Katze
- 스페인어: gato
- 일본어: 猫
- 아랍어: قط

응용 프로그램은 공통 식별자로 지식을 조회한 뒤 사용자 언어의 label을 표시할 수 있다. 같은 개체의 사실을 언어별로 중복 저장하는 문제를 줄이는 방식이다.

### Wikipedia 통합

Wikidata 항목은 여러 Wikimedia 언어판 문서의 sitelink를 모으고, Wikipedia template·infobox가 선택적으로 Wikidata 값을 사용할 수 있게 했다. 원문은 한 값을 갱신하면 이를 사용하는 여러 언어판에 변화가 반영되어 중복 유지 비용이 줄어든다고 설명한다.

### 지식 그래프 질의

Wikidata Query Service는 SPARQL로 관계를 질의한다. 예를 들어 19세기에 태어나 Nobel Prize를 받은 여성 과학자를 찾는 질의는 인간·성별·직업·출생일·수상 관계와 연도 필터를 조합한다.

```sparql
SELECT ?scientist ?scientistLabel WHERE {
  ?scientist wdt:P31 wd:Q5 .
  ?scientist wdt:P21 wd:Q6581072 .
  ?scientist wdt:P106 wd:Q901 .
  ?scientist wdt:P569 ?birthDate .
  ?scientist wdt:P166 wd:Q7191 .
  FILTER(YEAR(?birthDate) >= 1800 && YEAR(?birthDate) < 1900)
}
```

SPARQL은 표의 행·열뿐 아니라 개체 사이의 관계 경로를 따라간다. 인구 100만 이상인 유럽 국가 수도나, Oscar 수상 감독의 영화에 출연한 배우 같은 조건을 여러 관계로 결합할 수 있다.

### 열린 접근

원문은 연구자가 데이터 dump를 내려받고, 응용 프로그램이 API와 live query를 사용하며, 개발자·학생이 제한 없이 활용할 수 있다는 공개 접근의 의미를 강조한다. 개방 데이터는 라이선스 협상 없이 연구·응용을 시도하고 개선을 다시 공동체에 돌려줄 수 있게 했다.

## Wikidata가 언어 AI를 바꾼 방식

### 질의응답

질의응답 시스템은 텍스트에서 답 후보를 추출하는 것과 함께 Wikidata의 구조 관계를 직접 조회할 수 있다. “The Hitchhiker's Guide to the Galaxy의 저자의 배우자는 누구인가?” 같은 질문은 작품 → 저자 → 배우자 관계를 따라 Douglas Adams와 Jane Belson을 찾는 다중 단계 질의로 표현할 수 있다.

### 개체 중의성 해소

`Paris`는 France의 수도, Texas의 도시, Paris Hilton, 그리스 신화 인물 등 여러 대상을 가리킨다. 개체명 인식·개체 연결 시스템은 Wikidata의 식별자·속성·관계·문맥을 이용해 어느 항목인지 구분할 수 있다. 다언어 label은 한 언어의 언급을 공통 Q 식별자에 연결하고 다른 언어 label로 표시하는 데 도움이 된다.

### 전문 지식 그래프

연구자는 Wikidata의 일반 지식을 바탕으로 의학·법률·과학 같은 전문 자료를 연결할 수 있다. 공통 항목과 속성은 서로 다른 데이터 원천을 맞추는 기준이 된다.

### 기계 번역

원문은 번역 시스템이 원문 속 개체를 Wikidata 항목에 연결해 언어별 이름을 일관되게 고르고, `bank`의 금융기관과 강둑처럼 의미가 다른 대상을 구분할 수 있다고 설명한다.

### 검색 엔진·가상 비서·추천

원문은 검색 엔진의 구조 답변 상자, Siri·Alexa·Google Assistant 같은 가상 비서의 사실 질문, 의미 관계 기반 추천에서 Wikidata가 쓰였다고 서술한다. 항목의 감독·장르·수상·인물 관계를 이용하면 단순 공동 조회 패턴 외의 추천 신호를 만들 수 있다는 설명이다.

### 연구 자료

완전한 변경 이력과 광범위한 영역은 공동 지식 구축, 논쟁 해결, 시간에 따른 사실 변화와 영역별 지식 표현을 연구하는 자료가 될 수 있다.

## Wikidata가 해결하지 못한 것

### 품질 관리

누구나 편집할 수 있어 오류·훼손·편향이 들어갈 수 있다. 공동체가 검토하고 되돌리더라도 잘못된 값이 일정 시간 남을 수 있으므로 응용 프로그램은 값을 무조건 신뢰해서는 안 된다.

### ‘중립적 사실’ 문제

영토·국가 지위·정치 사건·문화적 주장처럼 사실 표현 자체가 논쟁적인 영역에서는 하나의 값으로 합의하기 어렵다. Taiwan의 지위를 예로 들듯 서로 양립하기 어려운 관점이 존재할 수 있다.

### 범위의 공백

잘 알려진 역사 인물·지리·과학 개념은 풍부하지만 작은 지역·덜 알려진 인물·새 사건·전문 영역은 불완전할 수 있다. 기여자의 관심과 언어·지역 분포가 coverage에 반영된다.

### 모호하고 맥락적인 지식

생년월일·인구·화학식처럼 명시적인 값은 구조화하기 쉽지만 “영향력이 컸다”, “논쟁적이다”, “걸작으로 평가된다” 같은 질적 판단은 누구의 어떤 기준인지 함께 표현해야 한다. 단순 속성–값은 이런 맥락을 잃을 수 있다.

### 언어 label 불균형

식별자는 언어 중립적이어도 모든 항목에 모든 언어의 label·description이 있는 것은 아니다. 공동체 규모와 관심에 따라 다언어 coverage가 달라져, 잘 알려지지 않은 항목은 목표 언어 label이 없을 수 있다.

### 계산 과제

항목과 명제가 늘면서 전체 그래프의 복잡한 join·filter 질의는 상당한 계산 자원을 요구한다. 실시간 응용은 live SPARQL 대신 부분 집합·사전 계산 색인·cache를 사용할 수 있다.

### 움직이는 대상

항목·속성은 병합·삭제·재구성될 수 있다. 특정 식별자와 property 경로에 의존한 응용은 모델 변경을 추적하고 코드를 유지해야 한다.

## 지속적인 영향

원문은 Wikidata가 구조 지식 베이스를 언어 AI의 중요한 인프라로 만들었다고 평가한다. 2024년에는 1억 개가 넘는 항목을 가진 대규모 자원으로 성장했으며, 개방 협업이 서술형 문서뿐 아니라 구조 데이터에도 적용될 수 있음을 보였다.

### 언어 모델의 사실 grounding

대규모 언어 모델은 유창하지만 그럴듯한 오답을 만들 수 있다. 원문은 Australia의 수도를 Sydney라고 하거나 Einstein의 Nobel Prize 이유를 상대성이론이라고 하는 사례를 든다. Wikidata 같은 외부 자료는 주장을 조회하고 출처를 확인할 수 있는 구조적 기준을 제공한다.

### 검색 증강 생성

원문은 RAG 시스템이 질문에서 개체·관계를 식별하고 SPARQL로 Wikidata를 조회한 뒤, 얻은 사실을 언어 모델 응답에 제공하는 흐름을 제시한다.

1. 사용자가 질문한다.
2. 시스템이 개체와 관계를 분석한다.
3. Wikidata 질의를 구성한다.
4. 구조 사실을 돌려받는다.
5. 사실을 생성 모델의 문맥에 넣는다.
6. 언어 모델이 자연어 답을 만든다.

언어 모델의 문장 생성 능력과 지식 베이스의 구조 사실 저장 능력을 결합해 사실 오류를 줄이려는 접근이다.

### 언어 AI 밖의 영향

원문은 항목–속성–값 모델이 semantic web, graph database, information architecture, 기업 지식 베이스에 영향을 주었다고 설명한다. 언어 독립 식별자와 다언어 label의 결합도 다언어 지식 시스템의 참고 사례가 되었다.

### 개방 접근의 유산

연구자는 별도 라이선스 협상 없이 dump를 내려받고 분석·응용을 만들 수 있었다. 공개 협업과 재사용은 폐쇄 지식 베이스에서 어려웠을 실험과 도구 개발을 촉진했다.

### 미래의 혼합 시스템

현대 언어 AI는 여러 방식으로 신경 언어 모델과 구조 지식을 결합한다.

- 추론 중 Wikidata 조회로 사실 확인·검색
- 지식 관계를 훈련 자료로 사용
- 지식 그래프 질의·추론 전용 시스템
- 신경 언어 처리와 기호 지식 추론을 결합한 혼합 구조

원문은 언어 AI의 미래가 텍스트 학습만이 아니라 구조 지식 원천과의 통합을 포함한다고 결론짓는다. 2012년의 또 하나의 데이터베이스처럼 보였던 Wikidata는 “기계가 사용할 사실을 어떻게 저장할 것인가”라는 문제에 데이터라는 답을 제시했다.
