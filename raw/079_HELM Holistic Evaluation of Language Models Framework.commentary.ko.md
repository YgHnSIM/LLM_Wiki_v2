# HELM과 언어 모델의 총체적 평가 해설

## 1. 한눈에 보기

- 핵심 주제: HELM(Holistic Evaluation of Language Models)이 언어 모델을 여러 시나리오와 여러 평가 차원에서 일관되게 비교하려 한 방법
- 등장 배경: 거대 언어 모델이 빠르게 늘었지만 모델마다 사용한 과제, 프롬프트, 지표와 보고 방식이 달라 결과를 직접 비교하기 어려웠던 2022년의 평가 환경
- 가장 중요한 아이디어: 하나의 정확도나 종합 순위 대신 **시나리오–적응 방법–메트릭**을 명시하고, 성능과 위험 및 비용을 같은 평가 체계 안에서 함께 관찰한다.
- 이후 LLM/NLP에 남긴 영향: 평가를 모델의 부수적인 성능표가 아니라 재현성·투명성·배포 판단을 좌우하는 독립적인 연구 문제로 부각했다.

> 이 문서는 `078_HELM Holistic Evaluation of Language Models Framework.md`의 번역문을 이해하기 위한 해설입니다. 원문을 반복하기보다 HELM의 평가 설계, 역사적 의미, 현대적 확장과 측정상의 한계를 정리합니다.

## 2. 핵심 요약

HELM은 Stanford Center for Research on Foundation Models(CRFM)을 중심으로 2022년에 제안된 언어 모델 평가 체계다. 당시 모델 보고서는 각기 다른 과제와 지표를 골라 제시하는 경우가 많아, 표에 적힌 숫자가 실제 모델 차이인지 평가 조건 차이인지 분리하기 어려웠다. HELM은 평가할 사용 사례인 **시나리오**, 모델을 과제에 적용하는 **적응 방법**, 결과를 판단하는 **메트릭**을 구조적으로 명시했다. 초기 공개판은 30개 언어 모델을 42개 시나리오에서 실행하고, 16개 핵심 시나리오에는 가능한 범위에서 정확성·보정·강건성·공정성·편향·독성·효율성의 일곱 메트릭을 함께 적용했다. 이 설계는 모델마다 강점과 약점의 모양이 다르며 모든 차원에서 일관되게 우세한 단일 모델을 기대하기 어렵다는 점을 드러낸다. 또한 프롬프트와 원시 생성 결과까지 공개해 점수의 출처를 추적하고 다른 연구자가 분석을 다시 수행할 수 있게 했다. 다만 ‘총체적’이라는 이름은 모든 언어·사용자·위험을 빠짐없이 측정했다는 선언이 아니라, 평가 범위와 측정 축을 명시적으로 넓히고 계속 갱신하겠다는 방법론적 목표로 읽어야 한다.

- 무엇을 다루는가: 범용 언어 모델을 여러 사용 사례와 여러 품질·위험 메트릭으로 평가하는 공통 기반
- 어떤 문제를 해결하려 했는가: 선택적인 벤치마크 보고, 서로 다른 프롬프트와 지표, 불투명한 상용 모델 결과 때문에 생긴 비교 불가능성
- 어떤 방식이 새로웠는가: 시나리오·적응·메트릭을 분리하고, 같은 실행 규칙과 보고 형식 아래 모델의 성능·위험·비용을 함께 공개했다.
- 결과적으로 무엇을 바꾸었는가: “어느 모델의 평균 점수가 가장 높은가?”에서 “어떤 조건에서 어떤 능력과 위험의 절충이 나타나는가?”로 평가 질문의 중심을 옮겼다.

## 3. 역사적 배경

HELM 이전에도 표준화된 평가는 존재했다. [[059_GLUE and SuperGLUE Standardized Evaluation for Language Understanding]] 같은 벤치마크는 여러 자연어 이해 과제를 하나의 묶음으로 제공해 모델 비교를 크게 개선했다. 그러나 GLUE 계열은 주로 정답이 있는 자연어 이해 과제의 성능을 집계했으며, 범용 생성 모델의 프롬프트 민감성, 확률 보정, 사회적 편향, 독성, 추론 비용까지 한꺼번에 설명하도록 설계된 체계는 아니었다.

GPT-3 이후에는 하나의 사전 학습 모델이 zero-shot 또는 few-shot 프롬프트만으로 매우 다른 과제를 수행하기 시작했다. 이 변화로 모델 가중치뿐 아니라 지시문 형식, 예시 개수, 답 후보 제시 방식, 디코딩 설정 같은 **적응 조건**이 성능을 크게 좌우하게 되었다. 서로 다른 연구팀이 서로 다른 설정으로 일부 과제만 보고하면 공정한 비교가 더 어려워졌다. 상용 API 모델의 훈련 데이터와 구조가 공개되지 않는 문제도 모델 투명성의 격차를 키웠다.

또 하나의 배경은 정확도 중심 평가의 한계다. 배포되는 모델은 정답을 많이 맞히는 것만으로 충분하지 않다. 입력 표현이 조금 바뀌어도 결과가 유지되는지, 특정 집단에서 성능이 급락하지 않는지, 해로운 텍스트를 생성하는지, 자신 없는 답에도 과도한 확신을 보이는지, 실행 비용을 감당할 수 있는지를 함께 알아야 한다. HELM은 이런 항목을 서로 대체 가능한 하나의 점수로 압축하기보다, 여러 축의 결과를 병렬로 보여 주려 했다.

- 이전 접근법: 개별 데이터셋 순위표, 과제 묶음의 평균 점수, 각 모델 개발자가 선택한 소수 벤치마크
- 당시의 한계: 평가 과제와 프롬프트가 일치하지 않아 모델 간 비교가 불완전했고, 성능 외의 위험·비용 정보가 드물었다.
- 이 주제가 필요했던 이유: 범용 모델의 능력과 배포 위험은 한 과제의 정확도로 환원되지 않으므로 비교 가능한 다차원 평가 규약이 필요했다.

## 4. 핵심 개념 해설

### 4.1 ‘총체적 평가’는 완전한 평가가 아니다

HELM의 holistic은 모든 중요한 현상을 이미 측정했다는 뜻이 아니다. 핵심은 평가의 **범위(coverage)**, **다중 메트릭(multi-metric measurement)**, **표준화**(standardization)를 동시에 개선하는 데 있다. 어떤 시나리오와 모델을 포함했는지 표로 드러내고, 한 시나리오에서 가능한 여러 메트릭을 함께 계산하며, 모델 사이의 실행 조건을 최대한 일관되게 맞추는 방식이다.

이렇게 보면 총체성은 완료된 상태가 아니라 평가 설계의 원칙이다. 새 모델과 새로운 위험이 등장하면 시나리오와 메트릭도 바뀌어야 한다. 실제 HELM도 고정된 시험지 한 장보다 버전과 실행 결과가 누적되는 ‘살아 있는 벤치마크(living benchmark)’에 가깝다.

### 4.2 시나리오–적응–메트릭

HELM의 평가 실행은 세 질문으로 풀어 읽을 수 있다.

1. **시나리오(scenario): 무엇을 하게 할 것인가?** 질문 답변, 요약, 정보 검색, 감정 분류처럼 모델이 마주할 사용 사례와 데이터 조건을 정한다.
2. **적응(adaptation): 범용 모델을 그 시나리오에 어떻게 적용할 것인가?** zero-shot인지 few-shot인지, 문맥 예시를 어떻게 배열하는지, 선택지를 한 번에 제시하는지 따로 제시하는지 등을 정한다.
3. **메트릭(metric): 결과의 어떤 속성을 어떻게 잴 것인가?** 정확도뿐 아니라 보정, 강건성, 공정성, 편향, 독성, 효율성을 적절한 측정법으로 계산한다.

같은 모델과 데이터셋이라도 적응 방법이 달라지면 점수가 달라진다. 따라서 프롬프트는 단순한 문구가 아니라 평가 조건의 일부다. HELM이 이 층을 분리해 기록한 것은 나중에 결과를 재현하거나 실패 원인을 분석할 때 특히 중요하다.

### 4.3 일곱 평가 메트릭과 절충 관계

초기 HELM이 강조한 일곱 축은 다음처럼 구분할 수 있다.

- **정확성(accuracy):** 과제가 요구한 정답 또는 품질 기준을 얼마나 충족하는가
- **보정(calibration):** 모델이 표시한 확신과 실제 정답률이 얼마나 잘 대응하는가
- **강건성(robustness):** 의미를 크게 바꾸지 않는 입력 변화나 분포 변화에서 성능이 얼마나 유지되는가
- **공정성(fairness):** 관련 집단 사이에서 성능 격차가 어떻게 나타나는가
- **편향(bias):** 생성이나 연관 점수에 사회적 고정관념과 집단별 불균형이 어떻게 드러나는가
- **독성(toxicity):** 유해하거나 공격적인 표현을 생성할 위험이 어느 정도인가
- **효율성(efficiency):** 추론 시간과 계산 자원 같은 실용 비용이 어느 정도인가

공정성과 편향은 비슷해 보이지만 같은 질문은 아니다. 공정성 메트릭은 집단별 과제 수행 격차에 초점을 맞출 수 있고, 편향 메트릭은 모델 출력의 사회적 연관이나 고정관념을 살핀다. 또한 한 축이 좋아진다고 다른 축도 자동으로 좋아지지 않는다. 더 큰 모델이 정확도에서는 앞서도 효율성에서 불리할 수 있고, 한 종류의 안전 조정이 특정 과제의 유용성을 낮출 수도 있다. HELM의 다중 메트릭 표는 바로 이런 절충을 보존한다.

### 4.4 표준화와 투명성

표준화는 모든 모델을 똑같이 취급한다는 단순한 뜻이 아니다. 동일한 시나리오, 적응 규칙, 표본 수, 디코딩 조건과 메트릭을 적용해 **평가 절차에서 생기는 차이**를 줄이는 일이다. 모델 API가 허용하는 기능이 다르거나 학습 정보가 비공개인 경우에는 완전한 동등성이 불가능하므로, 무엇이 같고 무엇이 다른지 기록하는 투명성이 함께 필요하다.

HELM은 최종 표뿐 아니라 프롬프트와 모델 응답 같은 원시 산출물을 공개하는 방향을 택했다. 이로써 연구자는 집계 점수가 이상할 때 개별 사례로 내려가 원인을 살피고, 새로운 메트릭을 나중에 다시 적용할 수 있다. 공개 코드는 평가를 재실행하는 데 도움을 주지만, 원격 API의 버전 변경이나 접근 중단까지 없애 주지는 않는다.

## 5. 원문의 논리 구조

원문은 대략 다음 흐름으로 전개됩니다.

1. 2022년 언어 모델의 규모와 능력이 빠르게 늘었지만 이를 포괄적으로 비교할 공통 평가 체계가 부족했다고 문제를 제기한다.
2. 정확도 하나만으로는 강건성·편향·안전·효율성의 문제를 발견할 수 없다는 가상 사례를 든다.
3. HELM이 여러 과제와 여러 메트릭을 표준화된 절차로 결합한 해결책이라고 설명한다.
4. 정확성, 강건성, 편향, 독성·안전, 효율성 평가가 각각 무엇을 포착하려는지 개괄한다.
5. 공개 코드와 데이터가 연구·개발·배포 판단 및 후속 평가 프레임워크에 미친 영향을 서술한다.
6. 측정하기 어려운 이해와 장기 안전, 누락될 수 있는 편향, 현실의 예외, 계산 비용과 차원 간 절충을 한계로 든다.

이 흐름은 HELM의 동기를 이해하는 데 유용하지만, 원문에 열거된 ‘적대적 공격’, ‘도메인 적응’, ‘인구통계적 동등성 검사’ 같은 표현을 HELM의 모든 시나리오에서 동일하게 시행한 구체적 구현 목록으로 읽어서는 안 된다. 실제 메트릭과 절차는 시나리오에 따라 달라지며, 일곱 메트릭도 모든 시나리오에서 항상 계산 가능한 것은 아니었다. 원문은 연구의 역사적 의의를 설명하는 2차 개설문이고, 세부 구현을 확인할 때는 HELM의 버전별 명세와 실행 결과를 함께 봐야 한다.

## 6. 왜 중요한가

HELM은 먼저 **비교 가능성의 조건**을 연구 대상으로 만들었다. 모델 A가 모델 B보다 점수가 높다는 문장은 두 모델이 같은 과제, 같은 적응 방법, 같은 메트릭으로 측정됐을 때에만 강한 의미를 갖는다. HELM은 이 조건을 숨은 부속 설정이 아니라 평가 결과와 함께 기록해야 할 핵심 정보로 취급했다.

둘째, 능력과 위험을 같은 화면에 놓았다. 정확도만 높은 모델을 자동으로 ‘좋은 모델’이라 부르지 않고, 보정·강건성·공정성·편향·독성·효율성을 따로 보게 했다. 이는 안전성과 사회적 영향이 성능 개발이 끝난 뒤 확인하는 부가 항목이 아니라 모델 선택에 동시에 반영해야 할 변수임을 보여 준다.

셋째, 평가 결과의 **감사 가능성**(auditability)을 높였다. 원시 프롬프트와 응답을 공개하면 집계 점수 아래에서 모델이 실제로 무엇을 했는지 확인할 수 있다. 잘못된 정답 키, 취약한 자동 메트릭, 특이한 프롬프트 효과가 발견되었을 때 평가 자체를 비판하고 수정할 근거도 생긴다.

특히 중요한 점:

- 선택적으로 유리한 벤치마크만 보고하는 관행을 줄이고, 모델별 평가 공백을 눈에 보이게 만들었다.
- 단일 순위보다 메트릭 사이의 절충 관계를 보존해 연구와 배포 목적에 맞는 판단을 돕는다.
- 평가 코드와 원시 출력을 공개함으로써 벤치마크를 재사용·확장·감사할 수 있는 연구 기반을 제공했다.

## 7. 현대 LLM과의 연결

- **Instruction tuning과 RLHF:** [[076_InstructGPT and RLHF Aligning Language Models with Human Preferences]] 이후 모델의 목표는 다음 토큰 예측 정확도만이 아니라 지시 이행, 유용성, 무해성까지 넓어졌다. 따라서 조정 전후 모델을 같은 과제에서 비교하고, 능력 향상과 안전성 및 집단별 성능의 변화를 함께 보는 HELM식 다차원 장부가 필요하다.
- **프롬프트와 추론 방식:** [[079_Chain-of-Thought Prompting Unlocking Latent Reasoning in Language Models]]처럼 프롬프트가 모델의 관측 성능을 크게 바꾸는 기법은 adaptation을 명시해야 하는 이유를 잘 보여 준다. Chain-of-thought 사용 여부, 예시의 수와 순서, 답안 추출 규칙이 다르면 같은 모델의 점수도 같은 실험으로 볼 수 없다.
- **지속 평가(continuous evaluation):** 모델 API와 데이터 분포가 변하면 한 번 만든 순위표는 빠르게 낡는다. 현대 평가 파이프라인은 모델 버전, 프롬프트, 데이터셋과 메트릭 버전을 고정하고, 변경 때마다 회귀 평가를 다시 실행하는 방향으로 발전했다. 이는 HELM의 구조화된 실행·공개 원칙을 운영 단계로 확장한 것이다.
- **LLM-as-a-judge:** 생성 결과를 다른 언어 모델이 채점하는 방식은 확장성이 높지만, 평가 모델의 편향·위치 선호·길이 선호와 자기 계열 모델 선호가 새 측정 오차가 될 수 있다. HELM의 교훈에 따르면 judge 모델과 프롬프트, 척도, 인간 평가와의 일치도도 adaptation과 metric 명세의 일부가 되어야 한다.
- **RAG와 에이전트:** 검색 증강 생성과 도구 사용 시스템은 기본 모델만 평가해서는 충분하지 않다. 검색 성공률, 근거 충실성, 도구 호출 정확도, 지연 시간, 누적 비용과 연속 행동의 안전성처럼 시스템 수준 시나리오가 추가되어야 한다. HELM은 이런 확장을 위한 틀을 제공하지만 원래의 정적 언어 모델 평가가 현대 시스템 전체를 곧바로 포괄하는 것은 아니다.

## 8. 한계와 비판적 관점

- 기술적 한계: 30개 모델과 42개 시나리오도 당시의 전체 모델·언어·도메인을 대표하지 않는다. API 제한, 서로 다른 토큰화와 생성 인터페이스, 비공개 학습 정보는 완전한 조건 통제를 어렵게 한다.
- 이론적 한계: 정확성·편향·독성 같은 개념은 관찰 가능한 하나의 자연량이 아니다. 데이터셋과 주석 기준, 임계값을 어떻게 정하느냐에 따라 측정 대상 자체가 달라지는 구성 타당도(construct validity) 문제가 남는다.
- 실용적 한계: 많은 모델을 많은 시나리오와 메트릭 조합에서 실행하면 계산비와 API 비용이 크다. 자원이 적은 연구자는 전체 평가를 반복하기 어렵고, 상용 API가 갱신되면 과거 결과를 정확히 재현하기도 어렵다.
- 오늘날 관점에서 다시 봐야 할 점: 초기 HELM은 2022년의 모델과 위험 지형을 반영한다. 장문 맥락, 다국어·다문화 사용, 멀티모달 입력, 코드 실행, 검색·도구 사용, 대화의 장기 상태와 고도화된 사이버·생물학 위험은 별도 시나리오와 시스템 평가가 필요하다.

추가로 다음 사항을 구분해야 한다.

1. **측정된 강건성과 현실의 강건성:** 정해진 교란이나 분포 변화에서 통과했다고 예측하지 못한 모든 현실 입력에 강하다는 뜻은 아니다.
2. **집단 평균과 개인 피해:** 집단별 평균 격차가 작아도 교차 집단이나 특정 개인에게 반복되는 실패가 남을 수 있다.
3. **독성 탐지와 안전 전체:** 유해 단어의 빈도를 낮추는 것만으로 허위 정보, 조작, 개인정보 유출, 위험한 행동 조언까지 해결되지는 않는다.
4. **표준화와 실제 사용:** 동일 조건은 모델 비교에 유리하지만 실제 제품의 사용자, 도메인, 프롬프트와 운영 정책을 모두 재현하지 못한다.
5. **벤치마크 오염과 포화:** 공개 데이터가 학습 자료에 포함되거나 모델들이 반복 최적화되면 점수 상승이 새로운 일반화 능력을 뜻하지 않을 수 있다.
6. **차원의 집계:** 여러 메트릭을 하나의 평균으로 다시 합치면 HELM이 보존하려 한 절충과 가치 판단이 사라진다. 어떤 위험을 얼마나 중시할지는 배포 맥락에서 별도로 정해야 한다.

원문의 “포괄적 평가가 모델을 공정하고 안전하게 보장한다”는 식의 표현도 신중히 읽어야 한다. 평가는 문제를 발견하고 비교할 증거를 제공하지만, 모델의 공정성이나 안전성을 스스로 만들어 내거나 보증하지 않는다. 또한 자동 메트릭과 인간 평가의 결합은 중요하지만 어느 메트릭을 어느 시나리오에 적용했는지 버전별로 확인해야 하며, 모든 차원이 자동·인간 평가를 동일한 비율로 사용한 것은 아니다.

## 9. 용어 정리

| 용어 | 설명 |
|---|---|
| HELM | Holistic Evaluation of Language Models. 언어 모델을 여러 시나리오와 메트릭으로 비교하고 결과의 투명성을 높이려는 평가 프레임워크 |
| 시나리오(scenario) | 모델이 무엇을 해야 하는지를 나타내는 사용 사례와 데이터 조건 |
| 적응(adaptation) | 범용 언어 모델을 특정 시나리오에 적용하는 프롬프트, 문맥 예시, 답안 형식 등의 절차 |
| 실행(run) | 특정 모델·시나리오·적응 설정과 메트릭을 결합해 수행한 하나의 평가 단위 |
| 메트릭(metric) | 모델 출력의 정확성, 위험 또는 비용 같은 속성을 수치화하는 규칙 |
| 다중 메트릭 평가 | 하나의 성능 수치로 환원하지 않고 여러 평가 축의 결과를 함께 기록하는 방식 |
| 보정(calibration) | 모델의 예측 확신과 실제 정답 빈도가 일치하는 정도 |
| 강건성(robustness) | 입력 표현이나 분포가 변할 때 성능이 얼마나 안정적으로 유지되는지를 나타내는 성질 |
| 공정성(fairness) | 관련 집단 사이의 성능이나 결과 격차를 특정 규범과 메트릭으로 살피는 평가 축 |
| 편향(bias) | 출력이나 내부 연관에서 사회적 고정관념 또는 집단별 불균형이 나타나는 현상 |
| 효율성(efficiency) | 모델 실행에 필요한 시간, 계산량, 메모리나 비용과 관련된 평가 축 |
| 살아 있는 벤치마크 | 모델·시나리오·메트릭과 결과를 버전별로 계속 갱신하는 평가 체계 |
| 구성 타당도 | 사용한 지표가 ‘안전’, ‘편향’, ‘이해’처럼 평가하려는 추상 개념을 실제로 얼마나 잘 나타내는지에 관한 문제 |

## 11. 읽고 생각해볼 질문

1. 두 모델의 정확도 점수를 공정하게 비교하려면 시나리오·적응·메트릭 중 어떤 조건을 같게 하거나 공개해야 하는가?
2. 정확도가 높은데 보정과 강건성이 낮은 모델은 어떤 사용 환경에서 위험할 수 있는가?
3. 공정성과 편향을 서로 다른 평가 축으로 유지해야 하는 이유는 무엇인가?
4. 여러 메트릭을 하나의 평균 점수로 합칠 때 어떤 정보와 가치 판단이 숨겨지는가?
5. Chain-of-thought나 LLM-as-a-judge를 사용하는 현대 평가에서 새로 기록해야 할 adaptation 조건은 무엇인가?
6. RAG 또는 도구 사용 에이전트를 평가한다면 초기 HELM의 시나리오와 메트릭에 어떤 시스템 수준 항목을 추가해야 하는가?
7. 공개 벤치마크가 학습 데이터에 포함된 뒤에도 그 점수가 일반화 능력을 보여 준다고 말하려면 어떤 추가 검증이 필요한가?

## 12. 짧은 결론

HELM의 역사적 의미는 언어 모델 평가 항목을 단순히 많이 모았다는 데 있지 않다. 무엇을 평가하는지, 모델을 그 과제에 어떻게 적용하는지, 결과의 어떤 성질을 재는지를 분리하고 같은 절차로 여러 모델을 실행함으로써 비교 가능성과 투명성을 평가의 핵심 조건으로 만들었다. 정확성·보정·강건성·공정성·편향·독성·효율성을 나란히 본 설계는 모델의 능력, 위험과 비용이 서로 다른 축이며 단일 순위로는 충분하지 않다는 점을 분명히 했다.

동시에 HELM은 안전 인증서가 아니라 측정 프레임워크다. 포함된 시나리오와 메트릭 밖의 실패를 보장할 수 없고, 사회적 개념을 수치화하는 과정에는 규범적 선택이 들어가며, 모델과 현실 사용 환경은 계속 변한다. 따라서 HELM의 가장 오래가는 교훈은 특정 점수표가 아니라 **평가 조건을 명시하고, 여러 축의 절충을 보존하며, 원시 결과를 감사 가능하게 공개하고, 새 위험에 맞춰 평가를 계속 갱신하라**는 원칙이다.
