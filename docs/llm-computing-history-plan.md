# LLM과 컴퓨팅 능력의 공진화 — 실행 계획

이 문서는 LLM_Wiki의 언어 모델 발전사와 CS_WIKI의 컴퓨팅 능력 발전사를 한 독서 경로로 연결하는 편집 규격이다. 변하는 구현 상태와 다음 행동은 `docs/llm-computing-history.yml`이 맡는다.

## 1. 목표

독자가 “컴퓨터가 빨라져서 LLM이 생겼다”는 한 줄 설명을 넘어, 다음 반복 구조로 기술 변화를 비교할 수 있게 한다.

> 기존 병목 → 모델·시스템의 대응 → 새로 가능해진 능력 → 보장되지 않은 것 → 다음 병목

공개 결과물은 메타 허브 하나, 본편 analysis 아홉 편, 횡단 연결고리 analysis 세 편, 종합 analysis 하나다. LLM_Wiki가 정본이며 CS_WIKI는 컴퓨팅 역사 맥락과 1차 자료를 찾는 독서 지도다. CS_WIKI의 설명은 그 자체로 LLM_Wiki의 외부 근거를 대신하지 않는다.

## 2. 능력과 역사 층위

모든 본편은 컴퓨팅 능력을 다음 일곱 층으로 나누어 읽는다.

1. **계산 가능성** — 문제를 유한한 기계적 절차로 표현할 수 있는가?
2. **알고리즘 복잡도** — 입력 규모가 커질 때 필요한 시간·공간이 어떻게 자라는가?
3. **프로그래밍 가능성** — 범용 장치를 반복 가능한 프로그램과 도구로 사용할 수 있는가?
4. **실현 성능** — 특정 장치·소프트웨어에서 실제 작업을 얼마나 빨리 끝내는가?
5. **확장성** — 문제·데이터·장치를 늘릴 때 유효한 처리 능력이 함께 늘어나는가?
6. **자원 효율** — 같은 품질을 시간·메모리·전력·비용을 덜 써서 얻는가?
7. **신뢰 가능한 결과** — 수치·품질·지연·가용성 계약을 만족하는 결과를 반복해서 내는가?

역사 자료는 `theory`, `machine`, `architecture`, `software`, `system`, `service`, `measurement` 가운데 어느 층을 주로 설명하는지 본문에서 밝힌다. 이 표지는 인과 관계가 아니라 설명 대상의 층위다.

## 3. 성능 주장의 측정 장부

각 본편은 대표 수치나 비교를 다음 여섯 항목으로 기록한다.

| 항목 | 기록할 내용 |
| --- | --- |
| 작업 | 학습, 평가, prefill, decode, 검색 등 무엇을 했는가 |
| 규모 | model, data, sequence, batch, device 수는 얼마인가 |
| 결과 계약 | loss, accuracy, 같은 수학적 출력, 허용 오차, 지연 목표 등 무엇을 만족해야 하는가 |
| 시스템 경계 | 단일 연산, accelerator, host, cluster, end-to-end service 중 어디까지 재는가 |
| 고정 조건 | hardware, precision, software, parallelism, 품질 중 무엇을 같게 두었는가 |
| 지표 | FLOPs, byte, throughput, latency, time-to-quality, energy, 비용 중 무엇을 보고했는가 |

본문에서는 이 장부를 세로형 표나 짧은 정의 목록으로 배치해 390px 화면에서도 읽을 수 있게 한다. 매개변수 수, FLOPs, 처리량, 지연, 품질을 서로의 대리값으로 자동 치환하지 않는다.

## 4. 인과 표현 규칙

기술 사이 연결은 다음 네 종류 가운데 하나로 한정한다.

- **직접 영향** — 저자 기록, 설계 문서나 논문이 앞선 기술을 실제 설계 근거로 명시한다.
- **가능 조건** — 해당 장치·소프트웨어·데이터가 실제 실행에 쓰였지만 설계 아이디어의 직접 원인이라는 증거는 없다.
- **병행 맥락** — 같은 시기에 존재했거나 같은 병목을 다뤘지만 직접 연결은 확인되지 않았다.
- **후대 유추** — 현재의 분석을 위해 비교한 것이며 당시 행위자의 설명이 아니다.

“무어의 법칙이 LLM을 낳았다”, “GPU가 Transformer를 만들었다”처럼 여러 층을 하나의 원인으로 합치는 문장을 쓰지 않는다. 직접 영향으로 분류한 관계에는 이를 확인할 수 있는 locator가 있어야 한다.

## 5. 본편 읽기 순서

1. **기계 이전의 계산은 어떻게 능력이 되었나** — 인간 계산자·수학표·알고리즘·검산
2. **언어와 계산을 기계적 절차로 만들다** — 불 대수·튜링·섀넌·저장 프로그램
3. **학습 규칙이 있어도 왜 규모화되지 못했나** — 초기 기계번역·퍼셉트론·ADALINE
4. **확률적 언어 모델은 어떤 계산 인프라를 요구했나** — 말뭉치·N-gram·HMM·CPU 군집
5. **행렬곱 가속은 딥러닝을 어떻게 현실화했나** — GPU·CUDA·프레임워크
6. **Transformer는 무엇을 병렬화했고 무엇을 남겼나** — 가속기 친화성·생성 순차성
7. **규모는 언제 연구 변수가 되었나** — 스케일링 법칙·Chinchilla·분산 학습
8. **연산보다 데이터 이동이 비싸질 때** — memory wall·혼합 정밀도·FlashAttention·MoE
9. **모델 능력에서 서비스 능력으로** — 양자화·KV cache·지연·에너지·가용성

종합편 `LLM 능력은 모델의 속성인가 시스템의 속성인가`는 각 이정표를 일곱 능력층에 배치하고, 독자가 서로 다른 두 시대를 같은 측정 장부로 비교하게 한다.

### 횡단 연결고리

본편의 시간 순서는 유지하되, 다음 세 문서는 여러 시대를 가로질러 “중간 단계가 왜 필요했는가”를 설명한다.

1. **N-gram에서 LLM으로** — 희소한 빈도표가 학습된 연속 표현과 조건부 생성으로 바뀐 작업 전환
2. **저장 프로그램에서 학습 프레임워크까지** — 명령 저장, 컴파일러, 수치 라이브러리, 자동미분, 가속기 런타임이 쌓인 프로그래밍 추상화
3. **집적도 증가에서 가속기까지 무엇이 더 필요했나** — 집적도, 전력, 메모리, 병렬 프로그래밍, 도메인 특화가 실제 성능으로 이어지는 조건

연결고리는 새 본편이 아니다. 각 문서는 최소 두 본편의 `batch` ID를 `connects`로 지정하고, 해당 본편들 사이에서 생략된 변환 과정을 여섯 항목 측정 장부와 네 종류 인과 구분으로 설명한다.

## 6. 문서별 공통 골격

본편과 종합편은 프로젝트의 고정 H2 순서를 지킨다.

1. `1단계 — 먼저 잡을 핵심`: 당시 문제, 핵심 결론, 두 발전 레일
2. `2단계 — 작동 원리`: 기존 병목부터 다음 병목까지의 변화
3. `3단계 — 기술과 근거`: 측정 장부, 구체적 구성, 역사 자료와 locator
4. `검증과 한계`: 인과 분류, 비교할 수 없는 수치, 빠진 조건
5. `학습 확인`: 본문 질문 2–3개와 새 사례에 적용하는 전이 과제
6. `출처`
7. 마지막 `관련 항목`

링크가 정의를 대신하지 않는다. 각 편은 필요한 용어를 짧게 다시 정의하고, 반복해서 필요한 완전한 설명은 다음 owner concept가 맡는다.

- 가속기와 행렬 계산
- 메모리 계층과 데이터 이동
- 분산 학습과 집단 통신
- 수치 형식·혼합 정밀도·양자화
- 언어 모델 추론 서빙

## 7. 근거 보강 범위

기존 LLM 소스와 분석을 우선 재사용한다. 빠진 컴퓨팅 역사 주장은 다음 1차 자료군을 LLM_Wiki evidence 레지스트리에 등록하고 필요할 때 `reference` 페이지로 보존한다.

- 저장 프로그램·EDSAC·Fortran과 자동 프로그래밍
- Moore·Dennard scaling·memory wall·Roofline
- GPU·CUDA·cuDNN과 심층 학습 실행
- AllReduce·DistBelief·Megatron-LM·ZeRO·Pathways
- TPU·mixed precision·MLPerf
- PagedAttention·continuous batching·speculative decoding·tail latency

새 concept나 reference는 두 편 이상에서 재사용되거나, 현재 문서 안의 짧은 정의로는 숨은 선수 지식을 제거할 수 없을 때만 만든다.

## 8. 구현과 커밋 경계

읽기 순서와 구현 순서는 다르다. 기존 근거가 가장 풍부한 Transformer 편을 형식 표본으로 만든 뒤 `6 → 7 → 8 → 9 → 1 → 2 → 3 → 4 → 5` 순서로 진행한다. 마지막 배치에서 허브·종합편·이전/다음 탐색을 완성한다.

각 배치는 다음 순서로 끝낸다.

1. 원장의 `current_batch`, `stage`, `next_action`, blockers를 현재 상태로 갱신한다.
2. 필요한 owner concept를 소비 문서보다 먼저 완성한다.
3. 본편과 실제 사용한 근거만 연결한다.
4. `index.md`, `overview.md`, `log.md`를 동기화한다.
5. `npm run history:check`, `npm run sync:index`, `npm run verify`를 통과시킨다.
6. 관련 파일만 `content:` 커밋으로 `main`에 커밋하고 `origin/main`에 푸시한다.

내부 계획·검사기만 바꾸는 첫 배치는 `docs:` 커밋을 사용한다. `raw/`, CS_WIKI와 기존 첨부·사용자 변경은 수정하거나 staging하지 않는다.

### 원장 schema v2의 연결고리 계약

`docs/llm-computing-history.yml`의 `bridges`는 필수 배열이다. 각 항목은 다음 필드를 가진다.

| 필드 | 규칙 |
| --- | --- |
| `id` | 연결고리 안에서 유일한 영구 식별자 |
| `title` | 공개 analysis의 제목·H1과 같은 값 |
| `path` | 저장소 안의 안전한 상대 경로 |
| `page_id` | 공개 analysis frontmatter의 영구 ID |
| `stage` | `planned`, `in_progress`, `complete`, `deferred` 중 하나 |
| `connects` | 서로 다른 기존 본편 batch ID를 최소 두 개 지정 |
| `capability_layers` | 일곱 능력층 허용 어휘 가운데 하나 이상 |

완료된 연결고리는 파일이 존재해야 하며, 본편과 같은 H2 순서·여섯 항목 측정 장부·네 종류 인과 표지를 포함해야 한다. status 출력은 배치·본편·연결고리·owner의 진행률을 각각 표시한다.

## 9. 완료 정의

- 허브 1개, 본편 9개, 연결고리 3개, 종합편 1개가 공개돼 시간 순서와 횡단 질문으로 연결된다.
- 다섯 owner concept가 필요한 설명을 맡고 소비 문서는 현재 맥락만 국소 설명한다.
- 모든 본편에 일곱 능력층, 여섯 항목 측정 장부, 네 종류 인과 구분이 적용된다.
- 근거 공백과 원장 blocker가 없다.
- 데스크톱과 390px 화면에서 연표·표·수식이 깨지지 않는다.
- `npm run history:check`와 `npm run verify`가 통과하고 원격 `main`에 반영된다.
